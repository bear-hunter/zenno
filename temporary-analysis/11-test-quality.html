Executive summary

Bottom line: Zenno has a substantial and unusually thoughtful unit/widget suite around the canvas engine, persistence round-trips, timers, and schema migration. The highest remaining risk is not low test volume; it is that several real platform and destructive boundaries are replaced by fakes or are not exercised at all.

The four highest-value additions are: a Galaxy Tab S9 FE/S Pen release verification path; real import/PDF boundary tests; direct Drift tests for goal/revision/reflection mutations; and isolated filesystem tests for deletion/cleanup. Those cover the places where a passing VM widget suite can still coexist with lost media, incorrect study records, or pen interactions that break flow.

Method & scope

This pass read the repository instructions, repository inventory, production/test line distribution, public repository APIs, persistence and migration code, input handling, import/export boundaries, focus timing, app/router bootstrap, and the corresponding tests. Tracked files and relevant untracked plans/reviews were inventoried; unrelated material was not treated as executable evidence.

  • Evidence type: static source/test inspection only. A test's presence proves intent and assertions, not that it currently passes.
  • Explicit limitation: the delegated task forbids running tests, builds, coverage, the app, or device checks. Runtime status therefore remains not verified.
  • Severity: expected consequence if the gap permits a regression, weighted toward note data integrity and uninterrupted thinking flow.
  • Confidence: confidence that the verification gap exists, not confidence that production code currently contains the predicted failure.

Evidence-backed findings

High

No checked-in end-to-end Android/S Pen verification path

ConfidenceHigh
Flow impactVery high
Data impactMedium

Evidence: the repository has no integration_test/, androidTest/, test_driver/, Patrol, or Maestro suite. The README identifies the Galaxy Tab S9 FE and S Pen as the real target and says a real S Pen is required for final pressure, hover, palm rejection, and latency verification (README.md:3-5, README.md:108-110). The widget suite synthesizes stylus events extensively, for example test/canvas_view_input_test.dart:67-81, but synthetic Flutter events cannot establish Samsung/Android event fidelity, palm rejection, hover behavior, renderer latency, storage permissions, or process lifecycle behavior.

Root-cause reasoning: the test architecture stops at the Flutter VM/widget boundary while the app's primary UX depends on hardware- and OS-specific input. A regression can therefore pass hundreds of tests yet still interrupt handwriting on the actual tablet.

Analysis-only recommendation: define a small release gate on the target tablet: cold open an existing DB, draw pressure-varying ink, rest a palm while writing, hover, use the side button, background/restore, import media, close/reopen, and confirm persisted geometry. Automate only stable portions; preserve a short named manual protocol for latency and feel.

High

The real image/PDF import and PDFium boundary is replaced by fakes

ConfidenceHigh
Flow impactHigh
Data impactHigh

Evidence: CanvasImporter owns the data-critical copy from a picker/cache path into app documents, image decoding, and PDF probing (lib/canvas/io/canvas_import.dart:61-68, 87-132, 146-164). Analysis-only recommendation: split picker selection from file staging and inject a documents-directory/filesystem boundary. Test cancel, missing path, same-name repeated imports, copy failure cleanup, corrupt image/PDF, multipage probe order, scale-bucket clamps, concurrent document reuse, and dispose-during-open. Add one Android integration fixture for a real image and PDF.

Actual destructive filesystem cleanup has no isolated tests

ConfidenceHigh
Flow impactMedium
Data impactVery high

Evidence: native cleanup resolves allowed roots, follows file symlinks, deletes selected files, and scans the media/thumbnail roots for unreferenced files (lib/features/library/data/library_file_cleanup_io.dart:5-26, 29-59). High

Editor exit integrity is only partially verified

ConfidenceMedium-high
Flow impactHigh
Data impactVery high

Evidence: the controller tracks failed writes and retries by syncing current state (lib/canvas/canvas_controller.dart:1059-1117), with good controller tests for dismiss/retry (test/canvas_repository_test.dart:870-927). The page separately flushes, checks hasUnsavedWrites, and asks whether to stay or leave (lib/canvas/canvas_editor_page.dart:258-290), while disposal uses an unawaited flush (208-214). Existing editor tests cover title/back, stale routes, arrival viewports, and selection behavior, but not a real failed canvas write followed by Stay, Retry, or Leave. The linked-navigation regression closes an editor only on the successful path (test/canvas_editor_navigation_test.dart:20-128), so it does not prove a failed write blocks unwinding to an existing canvas.

A second unsaved layer exists before the controller sees content: text-note typing is held in a dialog-local TextEditingController and becomes an undoable/persisted element only after Save (lib/canvas/canvas_editor_page.dart:349-395; lib/canvas/canvas_controller.dart:3703-3747). Static search found controller-level TextElement tests but no page test that opens New/Edit note, cancels, presses Back, saves blank/nonblank content, or encounters persistence failure. A route/app loss while that dialog is open therefore has no specified draft behavior.

Root-cause reasoning: lower-layer failure state is covered and toolbar banner rendering is covered, but the navigation boundary where the user can abandon failed structural writes is not. Pre-commit typed text sits outside even that failure queue, so it needs an explicit product-level draft/dirty-exit contract before a test can protect it.

Analysis-only recommendation: add widget regressions with a controllable failing repository: back waits for in-flight write; Stay retains route and state; retry success permits close; Leave is explicit; repeated back cannot open duplicate dialogs; disposal after an external route removal still drains or records failure. For typed notes, test new/edit Save, Cancel, Back, blank-edit deletion, locked-layer behavior, and save failure. If long-form text must survive process loss, persist a separate non-destructive draft and test restore/clear semantics; do not silently overwrite the last committed note with a partial draft.

ConfidenceHigh

Data impactHigh

Evidence: repositories expose live streams for boards, reflections, focus history/details, distractions, rituals, library canvases/folders/titles, settings, and attachments. Medium–high

Partial-corruption recovery behavior is inconsistent and unverified

ConfidenceHigh
Flow impactHigh
Data impactVery high if corruption occurs

Evidence: canvas reconstruction intentionally skips a base element whose subtype row is missing rather than failing the whole read (lib/canvas/persistence/canvas_repository.dart:77-82, 195-319), which makes the surviving base record invisible to the editor. By contrast, malformed ink bytes propagate from InkCodec.decodePoints during load (lib/canvas/persistence/canvas_repository.dart:224-230); the editor catches a failed load and offers only Back or Retry behind the generic “Could not load this canvas” state (lib/canvas/canvas_editor_page.dart:132-150, 502-530). Reflection template schemas and stored answer maps call jsonDecode directly (lib/features/goal_cycle/domain/reflection_template_schema.dart:94-105, 130-140). No test constructs a partially missing subtype row, bad persisted ink payload, malformed reflection JSON, or a recovery where valid sibling records remain usable.

Root-cause reasoning: low-level format validation is well tested, but the repositories and screens have no explicit record-level corruption policy. Depending on the field, corruption may silently omit note content or reject the entire canvas/reflection stream. A generic retry cannot succeed until the stored record changes, so it does not itself provide recovery.

Analysis-only recommendation: define and test a non-destructive recovery contract before changing behavior: retain every stored row, identify the corrupt record, keep valid sibling content accessible where safe, offer export/diagnostic recovery, and never auto-delete. Add database fixtures for missing detail rows, bad ink headers, malformed shape/control-point JSON, malformed reflection schemas/answers, and successful retry after an explicit repair. Also lock down the intended fallback for malformed palette, stylus-mapping, and pen-profile settings—the current settings suite only exercises invalid tool-wheel position JSON (test/settings_repository_test.dart:145-173). Assert both user-visible warning state and preservation of untouched records.

ConfidenceHigh
Flow impactHigh
Data impactVery high if durability regresses

Evidence: production constructs ZennoDatabase() over openZennoConnection(), whose native implementation is driftDatabase(name: 'zenno') (lib/core/database/database.dart:48-53; lib/core/database/connection_native.dart:1-4), and the keep-alive provider closes it when its container is disposed (lib/core/providers/database_provider.dart:6-14). Medium–high

No repeatable performance budget protects flow on realistically large notes

ConfidenceHigh
Flow impactVery high
Data impactLow directly

Evidence: the canvas deliberately uses a spatial index plus bounded tile/path caches (lib/canvas/canvas_controller.dart:157-158, 268-314; lib/canvas/render/elements_painter.dart:45-55, 227-255). Medium

Missing-record mutations have inconsistent, mostly untested success semantics

ConfidenceHigh
Flow impactHigh
Data impactMedium

Evidence: LibraryRepository.moveCanvasToFolder checks that exactly one row changed and throws when the canvas is gone (lib/features/library/data/library_repository.dart:142-156), with a direct regression (test/library_repository_test.dart:64-69). In contrast, library rename/archive/touch/thumbnail updates return after an unchecked update (lib/features/library/data/library_repository.dart:173-185, 254-268); goal/revision card and column updates commonly ignore affected rows (lib/features/goal_cycle/data/goal_repository.dart:198-230, 331-348; lib/features/revision/data/revision_repository.dart:168-200, 293-300); and reflection entry/template updates can also report completion after zero rows (lib/features/goal_cycle/data/reflection_repository.dart:177-193, 302-325). No test defines the missing-record result for these user-facing mutations.

Root-cause reasoning: repository methods erase Drift's affected-row result behind Future<void>. A stale page or concurrent delete can therefore finish its save animation and navigate away even though nothing was persisted. Deletes may intentionally be idempotent; edits that tell the user “saved” usually need a different contract.

Analysis-only recommendation: classify every public mutation as idempotent no-op or must-affect-one-row. Add a shared not-found error for the latter and table-driven missing-record tests across canvas/library, goal, revision, reflection, focus, ritual, settings, and attachments. At the widget boundary, verify a stale edit remains open with an actionable message rather than showing success. Preserve harmless no-op deletion only where explicitly intentional.

Low–medium

Persistence ordering across clock/time-zone changes has no explicit contract test

ConfidenceHigh for the gap
Flow impactMedium
Data impactLow

Evidence: Drift is configured to store dates as sortable ISO-8601 text (lib/core/database/database.dart:58-62). Canvas and library repositories stamp rows with local DateTime.now() in many write paths (lib/canvas/persistence/canvas_repository.dart:347-570; lib/features/library/data/library_repository.dart:84-176), while goal, revision, reflection, attachment, seed, and focus-clock paths generally call toUtc(). Root-cause reasoning: most tables are internally consistent during ordinary use, and the current target timezone has no DST, so this is not evidence of a present high-severity defect. However, uninjectable repository clocks make travel/timezone or manual-clock-change behavior hard to specify, and ISO text ordering is easiest to reason about when persisted instants are normalized.

Analysis-only recommendation: inject a small UTC clock into repositories that create/order durable timestamps, persist instants consistently in UTC, and localize only for display. Add order tests across a backward clock adjustment and mixed legacy local/UTC fixtures, plus calendar-date tests for target dates so date-only values do not shift a day when converted. Keep the existing fake-clock timer suite unchanged.

Evidence: canvas_elements.canvas_id and layer_id are separate foreign keys; the schema does not require the layer to belong to the same canvas (lib/core/database/tables/canvas_tables.dart:137-164). The repository accepts canvasId and an element's layerId independently. Its rollback test rejects a nonexistent layer (test/canvas_repository_test.dart:804-837), but no case supplies an existing layer owned by another canvas. Similarly, board_cards stores both column_id and denormalized board_id with independent foreign keys (lib/core/database/tables/board_tables.dart:40-61); goal/revision moveCard changes only columnId and position (lib/features/goal_cycle/data/goal_repository.dart:198-212; lib/features/revision/data/revision_repository.dart:168-182). The two repository tests exercise dense column reorder and goal save rollback only (test/kanban_repository_test.dart:11-94).

Root-cause reasoning: both models encode ownership twice for useful queries, but neither the database nor repository tests enforce agreement. Normal UI lists likely pass only same-owner IDs, so this does not prove a current user-path defect. A future drag/drop, import, repair, or stale-state path can nevertheless create a structurally valid row that appears under the wrong canvas/board or loses feature-specific detail semantics.

Analysis-only recommendation: add negative repository tests using an existing wrong-owner layer/column. Choose an explicit invariant: reject cross-owner moves atomically, or update every denormalized owner field and feature-detail row as one supported transfer. Prefer database-enforceable composite keys where practical; otherwise centralize validation in the repository and verify rollback leaves both owners unchanged.
