3Claims narrowed or rejected

Primary risk concentration: the canvas is robust against ordinary operations, but the hostile boundaries are asymmetric. One malformed ink record can make an otherwise recoverable note unreadable; imported and reopened images are decoded at original size before memory limits apply; and large notes pay quadratic hydration cost, total-document scans during viewport work, plus unbounded history retention. Export adds a separate peak-memory path whose 32-megapixel output can itself require hundreds of MiB across intermediate buffers. These failures interrupt thought flow and can turn a recoverable save into an inaccessible or crash-prone one.

Highest-leverage defensive principle: validate and isolate at persistence boundaries. Clamp persisted numbers, quarantine malformed child records instead of failing their parent, and impose explicit resource ceilings before allocation. This protects note accessibility without complicating the visible UI.

Scope constraint: findings are based on source, schema, tests, and relevant untracked review/plan material read statically. Per instruction, no build, test, app run, package install, Git mutation, or external service operation was performed.

Detailed findings

AF-01One malformed ink BLOB blocks the entire canvas

High · High confidence
Adversarial sequence
A canvas contains many valid elements and one truncated, unknown-version, or misaligned ink payload. Opening the canvas reconstructs elements sequentially; the invalid child throws and aborts the parent load.
Evidence
lib/canvas/persistence/canvas_repository.dart:83-192 bulk-loads child records; :213-230 calls InkCodec.decodePoints without per-record isolation. lib/canvas/persistence/ink_codec.dart:76-123 deliberately throws FormatException for invalid payloads. The page catches only the whole load.
Root cause
The repository tolerates a missing detail row but not a malformed detail payload. Corruption containment exists at the relationship boundary, not at the codec boundary.
Flow / integrity
The valid note data remains in storage, but all of it becomes inaccessible through the editor. Retry deterministically fails on the same child, so the recovery UI cannot recover.
Recommendation
Decode each persisted element inside a narrow guard, report/quarantine the failing element ID, and load the remaining elements. Preserve the raw row for later repair; do not silently delete it. Add a corruption fixture proving valid siblings still open.

AF-02Image import and reopening decode at original size before the raster budget can help

High · High confidence
Adversarial sequence
Select a very large image or a compact decompression-bomb-style image, or reopen/pan onto a previously saved giant image. Zenno requests a full-resolution frame before the controller can account for it; two image jobs may decode concurrently.
Evidence
lib/canvas/io/canvas_import.dart:87-107 uses readAsBytes then instantiateImageCodec(bytes) without target dimensions. The reopen path lib/canvas/canvas_controller.dart:4262-4317 calls ImageDescriptor.instantiateCodec() without a target at :4299-4313. The controller permits two image jobs (:467-470) and charges the 96 MiB raster budget only after decode at :4289-4293.
Root cause
The resource limit accounts for decoded images after allocation; it is not an admission-control limit. Encoded file size also does not bound decoded RGBA size.
Flow / integrity
A single file can exhaust memory and kill the process while a note is open. Recent in-memory work is at risk even though the imported file itself has not yet been committed as an element.
Recommendation
Probe dimensions first, reject or explicitly confirm pathological pixel counts, and request a target-sized decode appropriate to the initial element/display. Enforce a pre-decode pixel ceiling in addition to the post-decode LRU budget.

AF-03Large-canvas hydration performs quadratic list scans

High · High confidence
Adversarial sequence
Open a canvas containing thousands of strokes/elements. For every loaded element, insertion scans the growing list for a duplicate and then scans it again for the z-order insertion point.
Evidence
lib/canvas/canvas_controller.dart:791-807 implements the two linear scans in addElementToStore; :876-899 calls it for every sorted element during load.
Root cause
A mutation-safe, idempotent insertion primitive is reused for bulk hydration even though the repository already returns a sorted, finite snapshot.
Flow / integrity
Open time grows approximately with N², so a legitimate long-form handwritten note can appear hung exactly when the user needs to resume thinking.
Recommendation
Add a bulk-hydration path: validate IDs once with a set, assign the sorted list once, and build the spatial index in a single pass. Keep ordinary command insertion unchanged.

AF-04Undo/redo history retains unbounded full element snapshots

High · High confidence
Adversarial sequence
Keep one canvas open through a long drawing session, repeatedly transform a large selection, partially erase dense strokes, or import a huge PDF. Each command remains reachable for the controller lifetime.
Evidence
lib/canvas/canvas_controller.dart:283-287 owns unbounded lists; :1128-1134 appends every command with no count/byte cap. lib/canvas/engine/canvas_commands.dart:35-42 states that commands carry full reversal data; move/transform/replace commands retain both before and after lists at :136-177, :190-235, and :244-289.
Root cause
Correctness-oriented immutable snapshots have no retention policy. Clearing redo does not bound a monotonically growing undo stack.
Flow / integrity
Memory rises with session history rather than current document size. A process death can lose recent unsaved thought and makes long, productive sessions less reliable.
Recommendation
Introduce a measured history budget (estimated bytes, not only command count), evict oldest commands, and surface no new UI unless the user reaches the boundary. Treat a single oversized command explicitly.

AF-05Zero or negative focus targets can trap the UI isolate in an infinite loop

High · High confidence
Adversarial sequence
Restore a running Pomodoro/session whose persisted work or break target is zero (or negative), then process a tick whose elapsed time completes the phase. The transition loop subtracts a nonpositive duration without reducing its overrun.
Evidence
lib/features/focus/domain/timer_engine.dart:439-460 loops while advancing phases and subtracts nextTarget. Positivity is protected only by constructor assertions at :186-188 and :206-208, which do not execute in release. lib/features/focus/application/active_session_controller.dart:504-548 trusts restored persisted minute/second values.
Root cause
A release-critical invariant is expressed as a debug-only assertion and not revalidated at the persistence boundary.
Flow / integrity
The next timer tick can synchronously hang the UI isolate. The active session is then hard to pause or end and may require process restart.
Recommendation
Validate targets in production constructors and normalize corrupt persisted state during restore. Add a loop-progress guard so transition logic cannot nonterminate even if future callers violate the invariant.

AF-06Persisted canvas geometry bypasses numeric safety and can nonterminate

High · High confidence
Adversarial sequence
A stored viewport has a tiny positive/zero/nonfinite scale, or an element has an extreme finite coordinate/rotation. The editor accepts the values. Transform inversion can fail; grid iteration can become effectively unbounded; inserting a distant element repeatedly doubles and rebuilds the quadtree; rotating an element whose angle is so large that subtracting 2π no longer changes the double traps the normalization loop.
Evidence
lib/canvas/persistence/canvas_repository.dart:199-318 reconstructs raw bounds/rotations and :829-840 reconstructs raw viewport reals. lib/canvas/canvas_controller.dart:876-905 assigns them. lib/canvas/model/viewport_state.dart:11-26 has no validation. lib/canvas/engine/canvas_transform.dart:80-86 assumes invertibility, while clamps exist only in gesture producers. lib/canvas/engine/spatial_index.dart:59-73 doubles until containment and :295-342 re-inserts the previous tree on every growth. lib/canvas/canvas_controller.dart:3376-3391 feeds stored element rotation into the subtraction loop at :3448-3456.
Root cause
Numeric invariants are enforced by ordinary UI producers, not by persisted-state consumers; loop bodies also assume each arithmetic step makes progress.
Flow / integrity
A single hostile numeric row can make canvas load or a later transform hang, render blank, throw during inversion, or propagate nonfinite coordinates. Reset View does not repair element geometry and is unavailable during a load hang.
Recommendation
Sanitize every persisted geometry value before model/index construction: finite bounded coordinates/sizes/rotations, finite positive scale clamped to transform limits, and safe defaults with diagnostics. Normalize angles with a constant-time modulo/remainder operation plus finite checks. Put a hard iteration/progress guard around index expansion.

AF-07Export's pixel cap still permits multiple enormous frame buffers plus source rasters

High · High confidence
Adversarial sequence
Export a near-cap canvas, especially as JPEG, with several high-resolution images or PDF page rasters. A 32-megapixel output alone is roughly 128 MiB as RGBA; JPEG conversion then materializes another raw RGBA payload while prepared source images remain owned.
Evidence
lib/canvas/io/canvas_export.dart:127-180 allows 32 × 1024 × 1024 output pixels, then :214-245 allocates the full ui.Image. JPEG conversion at :425-444 obtains raw RGBA and copies it with Uint8List.fromList; the worker constructs another image representation at :23-47. Source preparation at :315-390 retains owned decoded images, and :393-406 uses untargeted source decode.
Root cause
The output cap constrains dimensions, not peak live bytes. Output image, raw byte copies, encoder representation, encoded output, and all source rasters have overlapping lifetimes.
Flow / integrity
Export can terminate the app or fail after a long wait; this risks in-progress work and makes sharing a large study canvas unreliable.
Recommendation
Define the limit in measured peak bytes, lower dimensions to a device-safe ceiling, avoid redundant full-frame copies, decode sources to output-needed resolution, and process/dispose sources in bounded batches. Stress later with a near-cap JPEG plus multiple rasters on the target tablet.

AF-08Viewport culling is followed by total-document scans on the frame path

High · High confidence
Adversarial sequence
Pan or zoom a very large canvas whose viewport contains only a few elements. The spatial index correctly returns a small ID set, but rendering and media scheduling still iterate or rebuild maps from every visible-layer element on viewport-triggered work.
Evidence
lib/canvas/render/elements_painter.dart:383-456 queries the index then loops the complete supplied element list; the tile-cache route builds two full maps every paint at :491-499. lib/canvas/canvas_controller.dart:328-335 supplies all layer-visible elements, not viewport-visible ones. Raster scheduling repeats the pattern at :4079-4137. lib/canvas/render/canvas_view.dart:1425-1451 schedules this as the viewport changes.
Root cause
The index returns IDs but the ordered list has no persistent ID map/order index, so culling results are joined back through O(N) scans. The source comment claiming render cost is bounded by on-screen content (elements_painter.dart:16-37) does not match the implementation.
Flow / integrity
Per-frame and post-frame work scales with total note size. On a dense long-lived handwriting canvas, the fundamental pan/zoom interaction can miss frames or become unusable despite almost no content being visible.
Recommendation
Maintain ID→element and ID→paint-order maps with the list/index, retrieve only queried IDs, then sort the small visible set by stable paint order. Do not rebuild total-document maps inside paint. Verify with a large off-screen corpus benchmark later.

AF-09Malformed reflection JSON poisons aggregate streams

Medium · High confidence
Adversarial sequence
One stored reflection template or entry contains syntactically invalid JSON. Watching templates or a card's reflection history maps every row eagerly; one exception fails the complete stream.
Evidence
lib/features/goal_cycle/domain/reflection_template_schema.dart:94-105 and :130-140 call jsonDecode without catching syntax errors, despite comments describing malformed input as tolerable. lib/features/goal_cycle/data/reflection_repository.dart:112-120 and :244-266 map whole result sets.
Root cause
Field-level tolerance is implemented only after successful JSON parsing; syntactic corruption escapes before fallback logic runs.
Flow / integrity
One bad record can hide all templates or all reflections for a card. The data is not deleted, but learning history becomes unavailable.
Recommendation
Catch JSON/shape errors per row, preserve raw data, return an explicit degraded representation, and surface which record needs repair while continuing to show valid siblings.

AF-10Rapid settings edits can overwrite a just-completed edit

Medium · Medium–high confidence
Adversarial sequence
Change two stylus mappings or pen-profile controls faster than the watched settings model round-trips from SQLite. The second callback constructs a whole object from its captured, stale model and writes it after the first.
Evidence
lib/features/settings/presentation/pages/settings_page.dart:125-179 rebuilds complete stylus mappings from the captured model. Pen controls do the same with profile.copyWith at :364-420. lib/features/settings/data/settings_repository.dart:223-234 persists complete JSON values.
Root cause
Independent controls issue whole-value writes from render snapshots; updates are neither serialized against the latest repository value nor reduced locally.
Flow / integrity
The first preference appears to change and then silently reverts. For stylus buttons, the mismatch breaks muscle memory during note taking.
Recommendation
Serialize/reduce settings updates through one controller holding the optimistic current value, or provide atomic field-level repository mutations. Test two updates issued before the provider emits.

AF-11Rapid Kanban drops can calculate from stale column snapshots

Medium · Medium confidence
Adversarial sequence
Drop a card, then begin/drop another before the stream publishes the first ordering. The second target computes its midpoint from the old card list. If position gaps are small, the first update commits before a separate renormalization reads and rewrites a snapshot; a failure reports an error after the card has actually moved, while an overlapping move can be overwritten by stale normalization.
Evidence
lib/shared/kanban/kanban_column_view.dart:68-110 computes from the rendered column; the drop callback at :654-657 is not awaited or UI-gated. Revision and goal repositories update first at lib/features/revision/data/revision_repository.dart:168-182 and lib/features/goal_cycle/data/goal_cycle_repository.dart:198-212. Their renormalizers read outside the later transaction and rewrite the snapshot at revision_repository.dart:351-402 and goal_cycle_repository.dart:399-450.
Root cause
Ordering is derived from rendered snapshots, and the move plus normalization is not one atomic mutation over current database state. There is no mutation queue, version check, or transaction spanning both phases.
Flow / integrity
Cards can land in surprising order or share positions and reorder after refresh. Card contents remain intact.
Recommendation
Queue board mutations, or calculate target order and any normalization transactionally from current DB state with a board revision. Disable subsequent drops only for the short commit window if simpler.

AF-12Denormalized card ownership can diverge from its column

Medium · High confidence
Adversarial sequence
Partial-state recovery creates a second board of the same type. The watcher merges columns from both boards into one rendered board, making an ordinary drag capable of moving a card into a column owned by the duplicate board while its boardId remains the original. The card renders through the destination column but is cascade-owned by the source board.
Evidence
lib/core/database/tables/board_tables.dart stores both columnId and boardId foreign keys with no cross-table equality constraint or uniqueness on board type. Watchers choose rows.first as the board but accumulate all matching columns in lib/features/revision/data/revision_repository.dart:65-142 and lib/features/goal_cycle/data/goal_cycle_repository.dart:70-169. Move methods at revision_repository.dart:168-180 and goal_cycle_repository.dart:198-210 update only column/position and do not validate board equality.
Root cause
Ownership is denormalized for query convenience, but the two sources of truth are maintained by caller convention only.
Flow / integrity
Deleting or repairing board A can unexpectedly delete a card that appears under board B. Normal healthy state constrains drops to one board, but AF-13's duplicate-board recovery path makes the invariant break UI-reachable.
Recommendation
Validate destination ownership inside the repository transaction and either reject cross-board moves or update boardId atomically. Add a database trigger or remove the redundant ownership column if practical.

AF-13Seed recovery is unsafe when the database is nonempty but marked unseeded

Medium · Medium–high confidence
Adversarial sequence
The settings row/seed flag is missing or false while user data already exists (partial restore, corruption, or legacy state). Startup reruns initial seeding against live rows.
Evidence
lib/core/database/seed/seed_data.dart:30-44 gates on the settings flag then uses insertOrReplace for settings; :140-145 replaces built-in templates, and :148-179 always creates new boards/columns. Reflection entries reference templates with restrictive deletion semantics in lib/core/database/tables/reflection_tables.dart:31-36. Board type is not unique, and the revision/goal watchers merge all same-type rows as described in AF-12.
Root cause
A bootstrap marker is treated as proof that the entire database is empty. SQLite replace semantics can delete/reinsert parent rows, conflicting with references, while settings replacement can reset preferences and unconditional board creation can duplicate logical singletons.
Flow / integrity
The transaction may fail and prevent opening the database, reset preferences, or create duplicate boards whose columns are merged into one UI and can corrupt card ownership. Normal first-run seeding is atomic; this concerns recovery/partial states.
Recommendation
Make seeding row-wise idempotent with conflict-update only for fields owned by the seed, never replace user-owned settings, and derive/reconcile missing built-ins without assuming emptiness.

AF-14The schema can cascade-delete focus history when a canvas is deleted

Medium · High confidence
Adversarial sequence
A canvas is deleted through any path that omits the library repository's protective unlink step. The foreign key deletes linked focus-session history rather than clearing the optional link.
Evidence
lib/core/database/tables/focus_tables.dart:74-78 declares linkedCanvasId with cascade delete. lib/features/library/data/library_repository.dart:190-199 explicitly nulls these links before deleting a canvas, confirming that cascade loss is undesirable and currently mitigated only in that code path.
Root cause
Database-level behavior contradicts application-level ownership: a focus session optionally references a canvas but is not logically owned by it.
Flow / integrity
An alternate deletion path, migration, or direct cleanup can erase study-history records. The current primary UI path is safe.
Recommendation
Change the foreign key to SET NULL and keep the explicit unlink as defense in depth. Add a migration test that canvas deletion preserves session history.

AF-15PDF import has no page-count or total-work ceiling

Medium · High confidence
Adversarial sequence
Import a valid but extremely long PDF. Zenno probes every page, creates one canvas element per page, records the entire add as one undoable operation, and persists the batch.
Evidence
lib/canvas/io/canvas_import.dart:115-131 collects page metadata; lib/canvas/pdf/pdf_raster_service.dart:121-132 returns information for every page; lib/canvas/canvas_controller.dart:3961-4015 constructs/imports the complete element list in one operation.
Root cause
Raster concurrency is bounded, but document cardinality, element allocation, layout extent, undo retention, and persistence batch size are not.
Flow / integrity
A hostile or merely book-length document can freeze import, create an enormous canvas transaction/history entry, and destabilize the editor.
Recommendation
Set a clear total-page/pixel/work budget before copying/committing, offer range selection for long documents, and import in recoverable bounded chunks if whole-book import is required.

AF-16Unserialized orphan cleanup can delete a freshly staged import or thumbnail

Medium · Medium–high confidence
Adversarial sequence
Repository construction starts cleanup and snapshots all database-referenced paths. Before cleanup lists the owned directory, an image/PDF import copies its file (or thumbnail capture writes its PNG) but has not yet committed the path. Cleanup sees the new file absent from its stale reference set and deletes it; the later DB write succeeds with a path that no longer exists.
Evidence
lib/features/library/application/library_providers.dart:17-23 starts cleanup unawaited. The generated provider is auto-dispose (lib/features/library/application/library_providers.g.dart:27-36), so this is not guaranteed to be a once-per-process startup action. lib/features/library/data/library_repository.dart:31-44 snapshots references before delegating; lib/features/library/data/library_file_cleanup_io.dart:29-47 deletes every later-listed unreferenced file. Import copies before controller commit at lib/canvas/io/canvas_import.dart:151-164; thumbnail capture writes before path update at lib/canvas/canvas_editor_page.dart:217-237.
Root cause
File creation and database ownership publication are a two-step protocol with no lock, temporary-file state, age grace, or cleanup serialization. Cleanup assumes no live writer, but provider lifecycle does not enforce that assumption.
Flow / integrity
The in-memory raster can hide the deletion until the canvas is reopened, when the image becomes a placeholder/missing attachment. This is a timing window, not an inevitable import failure.
Recommendation
Run cleanup from an explicit once-per-launch coordinator only after startup recovery, serialize it with media/thumbnail writers, and ignore files younger than a conservative grace interval. Prefer a staged-file protocol where ownership is published atomically before a file becomes cleanup-eligible.

AF-17Focus-history hydration issues two sequential child queries per session

Medium · High confidence
Adversarial sequence
Accumulate a long study history and open/refresh History. Every parent emission loads distractions and ritual checks for each session with separate awaited queries.
Evidence
lib/features/focus/data/focus_repository.dart:367-399 loads all sessions, then performs two sequential child reads inside the per-session loop. The comment assumes the feed is small rather than imposing pagination or using set-based joins.
Root cause
Aggregate hydration uses an N+1 pattern (specifically 2N+1 queries) and eagerly reconstructs the entire history.
Flow / integrity
History becomes progressively slower over months/years of use, penalizing the very accumulation of learning evidence the feature is meant to support. Data remains intact.
Recommendation
Page the parent history and fetch both child tables in set-based IN queries for the page, then group in memory. Keep stream invalidation scoped so one session update does not rehydrate the entire archive.

AF-18The PDF document pool is unbounded across distinct source files

Medium · High confidence
Adversarial sequence
Open a canvas containing pages from many distinct imported PDF files and visit enough pages to trigger rasterization. One native document object is cached for each source path and none is evicted while the editor controller lives.
Evidence
lib/canvas/pdf/pdf_raster_service.dart:57-60 describes the pool as capped, but the implementation is an unrestricted Map<String, PdfDocument> at :84-86. :108-113 inserts on every new path; only whole-service disposal closes documents at :228-247.
Root cause
The service correctly shares one handle among pages of the same file, but conflates eventual disposal with a pool-size cap. There is no maximum, least-recently-used eviction, or idle close for distinct files.
Flow / integrity
A long editor session over a collage of many PDFs can accumulate native memory and file handles until later page loads fail or the process becomes unstable. Stored notes remain intact, but their referenced pages can degrade into placeholders.
Recommendation
Bound open documents by count and measured/native cost, close least-recently-used handles that have no active raster job, and make acquire/release semantics explicit. Preserve the current per-path sharing.

AF-19Generic export failures escape the dialog's error boundary

Medium · High confidence
Adversarial sequence
Export when storage is full/unwritable, path resolution fails, the renderer rejects hostile geometry, or a large allocation fails. Progress closes in finally, but the dialog handles only the service's bespoke exception type; the async invocation is not awaited by its menu action.
Evidence
lib/canvas/widgets/canvas_toolbar.dart:1959-2025 catches only CanvasExportException. The action starts the dialog without awaiting it at :711-724. lib/canvas/io/canvas_export.dart:130-163 performs path/directory/file operations that can throw platform or filesystem exceptions, while rendering/encoding has additional generic error paths.
Root cause
The UI assumes every export-layer failure is normalized to one domain exception, but the service wraps only selected validation conditions and lets infrastructure/runtime exceptions cross the boundary.
Flow / integrity
The export fails without a useful user-visible reason or retry guidance and may surface as an unhandled asynchronous error. The note itself is not intentionally mutated, but the interruption is especially disruptive after a costly export attempt.
Recommendation
Normalize expected service failures or catch Object at the final UI boundary, log the raw error, and show a concise failure/retry message. Await or deliberately attach error handling to the menu-started future.

Claims challenged or deliberately narrowed

  • “Rapid focus buttons can double-complete a session” — not promoted. The active page serializes actions through an _action future and disables controls (lib/features/focus/presentation/pages/focus_active_page.dart:119-137). A periodic checkpoint may overlap under a very slow database, but the ordinary double-tap claim is not supported.
  • “Navigation can open duplicate canvas controllers” — not promoted. lib/canvas/presentation/canvas_editor_navigation.dart:7-103 tracks in-flight IDs and reuses registered routes. Existing tests explicitly exercise rapid/stale navigation paths.
  • “Duplicate attachment insert loses a canvas” — not promoted. insertOrIgnore can return a newly generated ID for an ignored duplicate (lib/shared/canvas_attachments/card_canvas_attachment_repository.dart:115-135), but the current UI ignores that returned attachment ID and the existing attachment remains intact. This is an API-contract defect, not supported note loss.

Coverage, method, and limits

Repository inspected: 237 tracked files; 137 handwritten Dart source files plus tests, generated migration fixtures, assets/configuration, and relevant untracked plans/reviews. Existing unrelated untracked files were preserved and not attributed to this analysis.

Areas read in depth: database schema/connection/migrations/seed path; canvas controller, commands, persistence, codecs, import/export and export UI boundary, PDF document/raster scheduling, render/tile cache, geometry/spatial index, editor/navigation; library file cleanup and deletion; focus engine/controller/repository/history/UI gating; goal/revision Kanban repositories and shared drag/drop layer; attachment transaction paths; reflection schemas/repository/editors; settings repository and UI; relevant tests and prior reviews.

Static coverage gaps observed: codec unit tests prove malformed ink throws, but the repository/page path is not shown isolating a corrupt child; transform tests exercise small positive scales, not invalid persisted scales; timer tests cover elapsed-time flooring, not nonpositive restored phase targets; no matching tests were found for syntactically invalid reflection JSON, two settings writes before provider refresh, PDF document-pool eviction, or resource ceilings/near-cap allocation behavior for huge image/PDF imports and exports.

What this report does not claim: static source establishes reachable logic and missing guards, not device-specific timing, actual memory thresholds, or measured frame times. Performance severity uses algorithmic/resource evidence and should later be calibrated on the target tablet with synthetic data—outside this analysis-only task.
