Executive view

Most important outcome: committed canvas elements have a sound write-through/retry architecture, but the act of typing still has fragile edges. Canvas note drafts, reflections, focus-review notes, and card notes remain memory-only until an explicit Save. The canvas text-note renderer can also hide substantial saved content, and clearing a note then pressing a button labelled “Save” deletes the element.

The highest-value direction is not a broad visual redesign. It is a small durable-draft layer plus honest text-note geometry: preserve incomplete thought text through lifecycle interruption, never disguise deletion as saving, and guarantee that saved text is visible or visibly marked as overflowing.

Evidence boundary: findings are based on source, tests, tracked plans/reviews, and relevant untracked planning material. No behavior was executed. “Confirmed” means the code path is direct and deterministic; device/IME behavior is marked with lower confidence where static analysis cannot prove runtime details.

A05-01 — Canvas text exists only in a modal controller until explicit Save

HIGH

The text editor creates a route-local TextEditingController, and the canvas model is changed only after the dialog returns. Cancel, default barrier/Back dismissal, process termination, or route teardown before Save leaves no durable draft to recover.

Evidence
lib/canvas/canvas_editor_page.dart:350–361 applies the edit only after _showTextNoteDialog resolves; :364–395 owns the entire draft in a temporary controller and exposes only Cancel/Save. The showDialog call does not disable Flutter’s default barrier dismissal and adds no dirty PopScope, so ordinary outside-tap/Back cancellation returns null through the same loss path. A repository-wide search found no AppLifecycleListener, WidgetsBindingObserver, restoration mixin, or restorable text controller for this editor.
Root cause
The text tool was implemented as a minimal modal transaction, while canvas autosave starts only at the element-command boundary. Draft state sits above that boundary and is therefore invisible to persistence.
Flow impact
A thought can be several paragraphs long. Loss does not require rare Android process reclamation: an outside tap or Back while writing can discard it too. This breaks trust in the notebook even though already-committed strokes remain safe.
Confidence
High for both the absence of a durable draft path and the unguarded ordinary-dismissal path; actual accidental-dismissal frequency was not measured.
Recommendation
Persist a separate per-canvas text draft after a short debounce, keyed by canvas and edited element/new-placement token. Restore it on reopen; clear it only after the final element transaction succeeds. Also guard dirty dialog dismissal or make the first outside tap explicitly confirm discard. Do not autosave partial text over the last committed note unless that product behavior is explicitly chosen.

A05-02 — Saved note text can be silently clipped below the fixed note rectangle

HIGH

The dialog permits up to ten visible input lines and unlimited total text, but every new note starts in a fixed 320×180 rectangle. The painter lays out unlimited lines and then clips to the inner rectangle without an overflow marker.

Evidence
lib/canvas/canvas_editor_page.dart:370–382 uses a 5–10-line field; lib/canvas/model/canvas_element.dart:837–855 fixes the default rectangle at 320×180; lib/canvas/render/elements_painter.dart:845–880 lays out all lines, calls clipRect(inner), and paints with no ellipsis, fade, count, or expansion. At 100% with the default 22-unit font and 1.25 line height, the usable height fits roughly six lines, fewer than the dialog shows.
Root cause
Text content length and visual geometry are independent. Editing changes only text; neither placement height nor a visible overflow state is recomputed.
Flow impact
Saved learning content appears missing on the canvas. Reopening the editor reveals it, but the spatial overview—the main benefit of a thinking canvas—becomes misleading.
Confidence
High; clipping is explicit and deterministic.
Recommendation
Measure text before commit and grow the note height with a sane minimum/maximum, or render a conspicuous continuation indicator and offer “fit to content.” Add coverage for ten-line and very long unbroken text at multiple zoom levels.

A05-03 — “Save” silently becomes “Delete” when an existing note is empty

HIGH

Clearing an existing note and pressing Save removes the whole element. The command is undoable, but the dialog neither labels the action as deletion nor confirms it.

Evidence
lib/canvas/canvas_editor_page.dart:389–391 labels the action “Save.” lib/canvas/canvas_controller.dart:3733–3738 routes an empty body to removeElements. The older review reaches the same conclusion at reviews/02-canvas.md:17–19; current source shows it remains applicable.
Root cause
Empty-value normalization is coupled to element deletion inside a generic update method, so the UI cannot represent the semantic change honestly.
Data impact
Accidental deletion is plausible during normal rewriting. Global Undo can recover it, but only while the route and in-memory history survive, and no contextual Undo feedback points to that recovery.
Confidence
High.
Recommendation
Keep Save non-destructive. Offer an explicit Delete action with confirmation or immediate Undo feedback. If blank notes are invalid, disable Save for empty input and explain why.

A05-04 — Non-canvas learning drafts share the same lifecycle-loss gap

HIGH

Reflection answers, goal/revision notes, reflection-template text, focus-review notes, and focus-setup goal text are local UI/provider drafts until an explicit final action. Normal back navigation is often guarded, but process death and route reconstruction have no restore path.

Evidence
lib/features/goal_cycle/presentation/pages/reflection_editor_page.dart:61–75,92–111,135–187 keeps answers in a local map and writes only on Save; lib/features/goal_cycle/presentation/widgets/reflection_form.dart:64–87 merely emits an in-memory map per keystroke. The template editor retains its name, description, and each prompt in controllers until _save at template_editor_page.dart:33–75,146–187,230–270. lib/features/focus/presentation/pages/focus_review_page.dart:30–41,161–187,232–255 persists the session note only on “Save & finish.” Goal and revision sheets likewise use local controllers plus explicit Save at goal_card_detail_sheet.dart:45–135 and revision_card_detail_sheet.dart:43–153.
Root cause
Unsaved-change prompts were used as the safety boundary. They cover deliberate navigation but not OS lifecycle loss, and every feature reimplements its own ephemeral draft.
Learning impact
Reflections and session reviews are exactly the moments where a user externalizes understanding. Losing them is more damaging than losing ordinary form input.
Confidence
High for architecture; medium for interruption frequency.
Recommendation
Introduce one narrow local draft service with typed keys and versioned payloads. Debounce writes, restore visibly, and clear only after the corresponding repository write succeeds. Prioritize reflection answers and focus-review notes before short metadata fields.

A05-05 — Existing notes require switching into Text mode to edit

MEDIUM

A Pan-tool tap can follow a link but has no path for opening a text note. Only a Text-tool tap emits the editor callback, so reading and revising a thought requires a tool-mode detour.

Evidence
lib/canvas/render/canvas_view.dart:447–500 maps Pan to pan/link-follow and Text to edit; :1065–1080 dispatches those two tap outcomes separately; :1285–1293 performs text hit-testing only from the text-edit gesture.
Root cause
Editing is modeled as a placement-tool behavior rather than a content affordance.
Flow impact
The tool becomes visible at the exact moment the user is trying to stay with the idea. This is repeated friction for iterative notes.
Confidence
High.
Recommendation
Keep single-tap Pan behavior predictable, but allow double-tap or a selected-note “Edit” affordance to open text without permanently changing tools. Verify that link following remains unambiguous.

A05-06 — New-note readability changes drastically with the current zoom

MEDIUM

The new note rectangle is divided by viewport scale so it always occupies about 320×180 screen pixels at insertion, but the default font remains 22 world units. Consequently the text’s initial screen size is 22 × zoom.

Evidence
lib/canvas/canvas_controller.dart:3703–3728 uses a fixed default font size; :3768–3775 divides only note width/height by viewport.scale. The painter uses the stored world font directly at lib/canvas/render/elements_painter.dart:865–876.
Root cause
Insertion geometry follows screen-space semantics while typography follows canvas-space semantics.
Impact
At 400%, the initial 22-unit text is about 88 screen pixels inside the same 320-pixel-wide box; at 25%, it is about 5.5 pixels. This amplifies clipping at high zoom and illegibility at low zoom.
Confidence
Medium: the math is certain, but the intended design semantics are not documented clearly enough to call the choice categorically wrong.
Recommendation
Choose one explicit model. For screen-consistent insertion, divide the initial font size by scale along with the rectangle. For world-consistent typography, stop making the rectangle screen-constant. Capture the chosen invariant in tests.

A05-07 — Desktop keyboard coverage is partial and platform-specific

MEDIUM

The canvas offers useful shortcuts, but Undo/Redo and transforms are Control-only, there is no Meta equivalent, and selection deletion is Delete-only. Tool letters are unmodified and not surfaced in the in-app gesture guide.

Evidence
lib/canvas/canvas_editor_page.dart:550–623 defines Control+Z/Shift+Control+Z, Delete, Escape, Control+arrows/brackets/minus/equal, and plain V/P/E/L/S/T/K. lib/canvas/widgets/canvas_toolbar.dart:749–806 documents touch/stylus gestures but not keyboard mappings. test/canvas_editor_page_test.dart:53–72,147–188 checks title suppression and Escape, not platform variants.
Root cause
Shortcuts were added as direct bindings rather than a platform-aware command map with a discoverable help surface.
Flow impact
External-keyboard and web users cannot rely on native muscle memory; keyboard-only operation is incomplete.
Confidence
High for missing bindings; medium for user impact because the primary target is Android tablet.
Recommendation
Add Meta equivalents on Apple platforms, Backspace as a selection-delete alias where safe, and a compact keyboard section in the existing guide. Keep shortcuts disabled whenever any editor field owns focus.

A05-08 — The dispose fallback cannot guarantee final persistence or surface failure

MEDIUM

The normal close path is careful, but generic widget disposal launches flush() without awaiting it and disposes the controller only afterward. There is no lifecycle flush before background/termination.

Evidence
lib/canvas/canvas_editor_page.dart:208–214 uses unawaited(controller.flush().whenComplete(controller.dispose)). The user-driven close path correctly awaits title save and controller flush at :258–305. Element writes are immediate and tracked at lib/canvas/canvas_controller.dart:926–979,1099–1117, limiting but not eliminating the exposure.
Root cause
Flutter dispose cannot be async, and no earlier lifecycle checkpoint exists.
Data impact
Committed element writes usually begin immediately, so risk is lower than for drafts; pending viewport state or slow/failing writes can still be lost during abrupt teardown with no chance to show the retry affordance.
Confidence
High for the lifecycle gap; medium for occurrence.
Recommendation
Flush at app inactive/paused and route-deactivation checkpoints while keeping explicit close as the authoritative guard. Do not claim termination durability without a persisted pending-write journal.

A05-09 — Tapping the canvas to finish title editing can also start a canvas gesture

MEDIUM

Title editing disables keyboard shortcuts, but it does not suspend the canvas pointer listener. The field saves on an outside pointer event; that same outside stylus or primary-mouse event can reach the canvas and begin the active tool.

Evidence
lib/canvas/canvas_editor_page.dart:550–648 empties only CallbackShortcuts while leaving CanvasView mounted; :795–821 saves on onTapOutside. lib/canvas/render/canvas_view.dart:296–365 routes a stylus/primary-mouse down to the active tool. The default active tool is Pen (canvas_controller.dart:344–345), and a one-point stroke is committed at :1224–1258,1302–1328.
Root cause
Focus-mode isolation was implemented for keyboard callbacks, not pointer input. Tap-region outside notifications do not express “consume this pointer before the canvas uses it.”
Impact
A user dismissing the title editor with the stylus can leave an unintended dot or start another tool action, breaking flow and adding cleanup work.
Confidence
Medium-high from event routing; device hit-testing should still be confirmed manually because runtime execution was prohibited.
Recommendation
While title editing is active, absorb canvas tool pointers (but keep the title interactive), or provide an explicit Done affordance and consume the first outside tap solely as “finish title.” Add a stylus/mouse widget test for no element creation on outside-save.

A05-10 — Focus Review always frames Back as discarding “unsaved changes”

LOW

The review page does not track whether energy or note fields changed; Back is always blocked and opens the generic discard-changes dialog, even on a fresh untouched review.

Evidence
lib/features/focus/presentation/pages/focus_review_page.dart:30–56 has no dirty flag and sets canPop: _allowPop; :258–283 invokes the shared prompt. The prompt unconditionally says “You have unsaved changes” at lib/core/widgets/app_dialog.dart:26–61. Discard safely preserves the completed session row but omits review answers via focus_repository.dart:268–274.
Impact
Copy is inaccurate and makes a clean exit feel dangerous. The extra confirmation may also discourage returning to the review later.
Confidence
High.
Recommendation
Track review dirtiness and use review-specific copy: “Finish without a review?” when untouched, “Discard this review draft?” when edited.

A05-11 — Removing a reflection-template prompt immediately destroys its draft text

MEDIUM

Each removable prompt has a close-icon action that deletes the row immediately. Its question and hint controllers are disposed in the same state update, with no confirmation and no prompt-level undo.

Evidence
lib/features/goal_cycle/presentation/pages/template_editor_page.dart:150–154 removes the prompt and disposes its controllers synchronously. The callback is wired directly at :385–403, and the icon is labelled only by the tooltip “Remove prompt” at :545–568. test/goal_reflection_safety_test.dart:141–180 verifies dirty-route and duplicate-save protection, but repository-wide test search found no prompt-removal recovery coverage.
Root cause
Prompt removal is treated as ordinary list-state mutation even though a row can contain substantial learning-framework text. The editor’s route-level discard guard cannot undo just this action.
Data impact
Before Save, the persisted template remains intact, so the user can Back → discard every other unsaved edit to reload it. If the deletion is missed and the template is saved, the prompt is intentionally persisted as removed. Neither path provides low-cost recovery for an accidental tap.
Confidence
High for immediate destruction and missing local recovery; medium for accidental-trigger frequency.
Recommendation
Use an immediate “Prompt removed · Undo” action that retains the draft object until the undo window closes. This is less interruptive than a confirmation dialog and preserves the rest of the editing flow.

A05-12 — Canvas note content is absent from semantic and keyboard traversal

MEDIUM

Canvas elements, including typed notes, are rendered as pixels by CustomPaint. No semantics builder exposes their text, bounds, selection state, or edit action, and keyboard commands only operate after pointer-driven selection.

Evidence
lib/canvas/render/canvas_view.dart:1455–1552 builds pointer listeners and four paint layers; committed elements are the ElementsPainter layer at :1492–1510. lib/canvas/render/elements_painter.dart:293–330,839–887 paints note text directly and defines no semanticsBuilder. A repository-wide canvas search found no CustomPainterSemantics or canvas-content semantics tests, although toolbar actions deliberately add semantics at lib/canvas/widgets/canvas_toolbar.dart:549–565,2768–2795.
Root cause
The interaction model treats the canvas as a pointer surface and accessibility semantics as a control-layer concern, leaving document content outside Flutter’s semantic tree.
Flow impact
A keyboard-only or screen-reader workflow cannot discover, read, select, or invoke editing on an existing note. The useful shortcuts in A05-07 do not close that entry-point gap.
Confidence
High for missing code paths; runtime traversal was not executed under the analysis-only constraint.
Recommendation
Add viewport-scoped semantic nodes for visible text notes, with concise labels and select/edit actions mapped to the same controller commands. Define a deterministic traversal order (for example z-order then position) and test it with Flutter semantics APIs.

A05-13 — One-shot create dialogs lose authored content when the following write fails

MEDIUM

Distraction, quick-card, and ritual-item dialogs all close with a value before persistence is attempted. A failed write then shows a generic “try again” message after the editor and its controllers have gone, without retaining an actionable retry payload.

Evidence
lib/features/focus/presentation/widgets/distraction_sheet.dart:31–37,45–57 pops a one-shot capture; focus_active_page.dart:465–483 writes after dismissal and offers only a failure Snackbar. Quick-card title/notes follow the same sequence at lib/shared/kanban/kanban_column_view.dart:460–488,822–927. Post-review ritual labels do so at lib/features/focus/presentation/pages/focus_review_page.dart:197–229,285–297. Happy-path quick-card coverage exists at test/kanban_board_view_test.dart:69–87, but repository-wide searches found no failure/payload-recovery cases for these creators.
Root cause
The UI closes optimistically, while callers route failures through value-agnostic Snackbar helpers. That pattern is adequate for idempotent button actions, not original user-authored input.
Learning impact
A failed distraction forces the user to reconstruct a thought during focus; a failed goal/revision card loses planning text; a failed ritual item loses the intended process improvement. Each message says “try again” without making retry possible.
Confidence
High for the failure path; medium for database-failure frequency.
Recommendation
Use one small payload-aware create helper: retain the submitted value until success, then on failure offer Retry and Edit (prefilled) actions. Clear it only after confirmed persistence or explicit dismissal; keep longer-lived editor pages in place as they already do.

A05-14 — Undo history grows without a bound for the full canvas-editor session

MEDIUM

Every structural canvas mutation appends a reversible command, and no count- or memory-based eviction exists. Deleted, replaced, transformed, and cleared content remains referenced for Undo until the editor route is destroyed.

Evidence
lib/canvas/canvas_controller.dart:283–287 declares unbounded list stacks; :1123–1167 only appends, moves the last command, or clears redo after a fork. Repository-wide search found no undo-stack trim or maximum. Commands retain element snapshots at lib/canvas/engine/canvas_commands.dart:35–42,63–101,136–153,190–208,244–261; ClearCommand snapshots every current element at :292–320. Raster images are intentionally stripped from snapshots at :5–10, which reduces—but does not remove—the exposure.
Root cause
Correct reversibility was prioritized without a retention policy. A session-scoped stack is safe only if session edit volume is implicitly bounded, which an infinite thinking canvas is not.
Flow/data impact
Long drawing sessions can retain old stroke point lists and prior element states after they disappear from the current canvas. Rising memory pressure can cause jank or process eviction; that would compound the durable-draft gaps above. Static analysis cannot quantify the device threshold.
Confidence
High for unbounded growth; medium for perceptible impact because element snapshots share some immutable data and no profiling was permitted.
Recommendation
Set an explicit history budget, preferably estimated bytes plus a conservative command-count fallback. Evict oldest commands atomically, expose no promise of unlimited Undo, and add controller tests proving retention stays bounded across many strokes, transforms, erases, and clears.

A05-16 — Multi-field learning editors provide no deliberate focus progression

MEDIUM

After selecting a reflection framework, no answer field receives focus. Across reflections, template authoring, and goal/revision detail forms, single-line fields also omit Next actions and explicit focus handoff, so soft-keyboard entry repeatedly falls back to tapping each field.

Evidence
lib/features/goal_cycle/presentation/pages/reflection_editor_page.dart:165–187 swaps in the form after framework selection. Its fields at lib/features/goal_cycle/presentation/widgets/reflection_form.dart:130–150 define neither autofocus, textInputAction, nor submitted-focus behavior. The same omissions recur in template identity/prompt fields at template_editor_page.dart:343–367,572–593, goal fields at goal_card_detail_sheet.dart:288–320, and revision fields at revision_card_detail_sheet.dart:338–360. The quick-card title goes further and submits the whole title/notes dialog on its first field’s action at lib/shared/kanban/kanban_column_view.dart:875–898. Repository-wide focus searches found no feature-level FocusNode or nextFocus in these areas.
Root cause
Each field is implemented independently, with focus left to Flutter defaults rather than treating multi-step thinking forms as a keyboard flow.
Flow impact
Reflection is interrupted immediately after choosing a framework by an extra precision tap. On longer custom templates and goal forms, the keyboard’s Done action does not communicate or perform the natural move to the next short field. In quick-card creation it can close and save before the optional Notes field is visited.
Confidence
High for missing focus policy; medium for impact because hardware Tab traversal may still follow widget order and runtime keyboard behavior was not executed.
Recommendation
After a new reflection framework is committed, focus its first prompt once. Set TextInputAction.next and nextFocus() on short intermediate fields; keep Enter as newline for true multiline answers and Done for the final short field. Add widget tests for initial focus and keyboard progression without stealing focus during template selection.

A05-17 — An empty inline canvas title silently snaps back with no validation cue

LOW

Clearing the inline title and pressing Done or tapping outside exits editing, restores the prior title, and reports success to the page. No error text or message explains that a title is required.

Evidence
lib/canvas/canvas_editor_page.dart:753–762 groups an empty normalized title with an unchanged title, resets the controller, leaves editing, and returns true. The field at :795–822 has no validation/error state. Existing canvas-editor tests exercise title save on system Back at test/canvas_editor_page_test.dart:31–50, but repository-wide search found no empty-title test.
Root cause
Invalid input and a no-op are collapsed into the same early-return branch.
Flow impact
The snap-back looks like ignored input or a transient persistence failure, prompting repeated attempts and breaking confidence in the inline editor. Existing data stays safe.
Confidence
High.
Recommendation
Keep the field open and show a concise inline “Title is required” error. Treat an unchanged nonempty title as the only silent no-op.

A05-18 — Untouched energy defaults are persisted as if the user self-rated

MEDIUM

Both Focus Setup and Focus Review start with energy 3 selected. A user can start and later save a review without touching either control, causing two neutral ratings to enter learning statistics as answered observations.

Evidence
lib/features/focus/application/focus_setup_controller.dart:28–41,99–111,123–145 seeds preEnergy: 3 and always builds a non-null config; session creation persists it at active_session_controller.dart:131–164. Review initializes _postEnergy = 3 and always submits it at lib/features/focus/presentation/pages/focus_review_page.dart:30–32,73–78,232–255. FocusSessions.postEnergy is nullable but preEnergy is not at lib/core/database/tables/focus_tables.dart:39–50. Statistics average every pre value and every non-null post value at lib/features/focus/domain/focus_stats.dart:69–100.
Root cause
The UI’s visual neutral default is also the domain value; there is no separate unanswered state or evidence that the selector was touched.
Data impact
Energy trends can be biased toward 3 and appear more complete than the underlying user observations. That weakens the app’s feedback loop about when learning sessions work best.
Confidence
High for persisted behavior; medium that this violates intended product semantics because a preselected neutral default may be deliberate.
Recommendation
Represent unanswered separately. For low friction, allow Skip/Not rated and keep statistics nullable; if ratings are required, present an unselected state and enable Start/Save only after an explicit tap. Do not infer intent merely from a rendered default.
