Method and boundaries

Read-only boundary honored. No source, configuration, dependency, test, Git, branch, remote, PR, or external-service state was changed. No build, test, install, app run, or destructive command was performed. This HTML is the only file created.

The pass inspected tracked implementation and tests plus relevant untracked instructions, plans, and historical review material. Historical reviews were treated as leads only: several of their former high-severity claims are contradicted by current guards/error handling and were not repeated.

Evidence was cross-checked across schema, repository, provider lifecycle, controller, UI caller, and tests where available. Severity is consequence-weighted; confidence distinguishes a directly demonstrated code path from a conditional architectural hazard.

Executive assessment

Zenno has a thoughtful local-first core: database writes for compound records are usually transactional, the canvas exposes failed writes instead of pretending success, focus timing is wall-clock based, destructive UI actions are commonly confirmed, and every historical schema version has a current-schema migration check. The most consequential risks remain at recovery boundaries: a partial canvas load can later authorize deletion, there is no product-controlled restorable backup, and a failed multi-step schema upgrade can leave a partially migrated database that repeats from its old version on the next launch.

Top order of operations: make partial canvas loads explicit and non-destructive; add a real, media-inclusive backup/restore contract; make schema upgrades failure-atomic and test reopening after injected failure; then serialize owned-file garbage collection and align destructive UI with recoverable domain semantics.

Medium Confidence: high

Database foreign keys encode destructive ownership for relationships the product treats as non-owning

Impact
A future alternate deletion path, migration, repair script, or regression can turn deleting a folder into deleting every canvas in it, and turn deleting a canvas into deleting linked focus history. The consequence is high, but the current supported repository paths avoid it.
Flow / integrity
Data integrity: a serious latent invariant mismatch, not a demonstrated current UI-path deletion bug. Flow: recovery would be impossible without a backup.
Root cause
The schema models “grouping/linking” as ownership with ON DELETE CASCADE, while repositories compensate procedurally by nulling references first. The invariant is therefore not enforced at the strongest layer.
Recommendation
Use SET NULL for canvases.folder_id and focus_sessions.linked_canvas_id, migrate with explicit preservation checks, and add database-level tests that direct parent deletion preserves children/history. Review the ritual snapshot FK for the same semantic mismatch.
  • lib/core/database/tables/canvas_tables.dart:29-33 — Canvases.folderId references folders with KeyAction.cascade.
  • lib/features/library/data/library_repository.dart:158-170 — the repository promises folder deletion will preserve canvases and must manually null every folderId before deletion.
  • lib/core/database/tables/focus_tables.dart:74-78 — FocusSessions.linkedCanvasId also cascades.
  • lib/features/library/data/library_repository.dart:187-199 — canvas deletion explicitly detaches focus sessions first to avoid the schema cascade.
  • lib/core/database/tables/focus_tables.dart:91-95 vs. :85-99 — ritual rows snapshot labels for history, yet deleting the source item cascades the snapshot row.
  • lib/features/focus/data/ritual_repository.dart:107-115 — the supported ritual removal path soft-retires the source row, so that cascade is also latent rather than presently exercised.
  • Generated schema history from v1 through v13 retains the folder and linked-canvas cascades; this is longstanding schema intent, not a newly introduced migration defect.
Medium Confidence: high

Owned-file garbage collection can race imports, thumbnail writes, provider recreation, and undo-only media

Impact
An image/PDF can remain as an element in SQLite while its app-owned source file has been deleted, producing a permanent placeholder and breaking export. A deleted media element retained only in the in-memory undo stack can lose the file needed to undo.
Flow / integrity
Data integrity: high consequence for imported media, with a bounded concurrency window. Flow: images/PDF pages can disappear after apparently successful placement or undo.
Root cause
Cleanup snapshots all DB references, then asynchronously deletes every other file in shared directories. File creation and DB reference insertion are separate operations, there is no cleanup/import lock or grace period, and cleanup is launched fire-and-forget from an auto-disposed provider rather than from a single controlled startup coordinator.
Recommendation
Make cleanup single-flight and lifecycle-owned; use an age/grace threshold; stage imports outside the collectible directory or create the DB intent before moving the file atomically; protect paths reachable from active undo histories; and re-check each candidate against the DB immediately before deletion.
  • lib/features/library/application/library_providers.dart:16-24 — provider construction immediately launches cleanup with unawaited.
  • lib/features/library/application/library_providers.g.dart:27-36 — that provider is generated with isAutoDispose: true, despite being documented as a singleton.
  • lib/features/library/data/library_repository.dart:31-45 — references are collected as a point-in-time set before file traversal.
  • lib/features/library/data/library_file_cleanup_io.dart:29-47 — every regular file absent from that snapshot is deleted, with no age, active-editor, transaction, or second-reference check.
  • lib/canvas/io/canvas_import.dart:96-107,125-132,151-164 — media is copied first and only later returned for element creation.
  • lib/canvas/canvas_controller.dart:3897-3918,3967-4013 — the DB reference is created after decode/probe and controller placement, leaving a collectible interval.
  • lib/canvas/canvas_editor_page.dart:217-237 — thumbnail file write likewise precedes DB path update.
  • lib/config/router/app_router.dart:21-38 — the indexed shell starts on and retains the Library branch, so normal app lifetime probably keeps the provider alive. This narrows the claim: repeated provider reconstruction is possible from its auto-dispose contract but is not required for the one startup race.
  • No cleanup, grace-period, or concurrent import/cleanup test was found in the test corpus.
High Confidence: high

Lossy canvas loading becomes destructive when save recovery reconciles from memory

Impact
A parent element row with a missing detail row is silently hidden. If any later write fails and the user retries, snapshot reconciliation classifies that hidden row as stale and permanently deletes it. A repairable inconsistency becomes irreversible loss without warning.
Flow / integrity
Data integrity: high under partial corruption plus a save failure. Flow: user sees an incomplete canvas but is not told it loaded partially.
Root cause
The read API returns only reconstructed elements, with no completeness/corruption metadata. The recovery API assumes the in-memory list is authoritative and deletes every durable ID not present in it.
Recommendation
Return a load result containing valid elements plus quarantined row IDs/errors. Block destructive full-state sync after any lossy load; never delete unknown durable rows during recovery; provide an integrity/repair path and preserve raw rows for export or diagnosis.
  • lib/canvas/persistence/canvas_repository.dart:77-83,177-192 — missing-detail elements are deliberately skipped.
  • lib/canvas/persistence/canvas_repository.dart:199-217,232-318 — reconstruction returns null for each absent detail type.
  • lib/canvas/canvas_controller.dart:862-923 — the controller accepts the reduced list as its full state and exposes no partial-load status.
  • lib/canvas/canvas_controller.dart:1059-1090 — retry abandons individual failed writes and performs full current-state sync.
  • lib/canvas/persistence/canvas_repository.dart:572-591 — full sync deletes every stored element ID not present in memory.
  • No test matching “missing detail,” “partial load,” or “corrupt detail + retry” was found in test/canvas_repository_test.dart.
High Confidence: high

There is no user-accessible, restorable, media-inclusive backup path

Impact
Device loss, app-data clearing, database corruption, or an accidental permanent delete has no product-controlled recovery path. Visual PNG/JPG/SVG exports preserve appearance, not editable note structure or cross-canvas relationships.
Flow / integrity
Data integrity: systemic recoverability gap. Flow: the user cannot move the knowledge base safely to another installation.
Root cause
A document codec exists only as isolated library/test code and embeds absolute image/PDF paths rather than media bytes. The UI exposes only visual exports to an internal directory and no restore/import workflow uses the codec.
Recommendation
Design a versioned, atomic archive containing database snapshot/manifest plus deduplicated media and checksums. Add validate-before-import, non-destructive restore, and explicit backup status. Do not present the current JSON codec as portable until media is bundled and ID/link remapping is defined.
  • lib/canvas/widgets/canvas_toolbar.dart:1959-2025 — user export is limited to rendered image/SVG files.
  • lib/canvas/io/zenno_document.dart:29-84 — a JSON codec exists, but repository search found use only in test/zenno_document_test.dart.
  • lib/canvas/io/zenno_document.dart:191-205,274-292 — image/PDF entries serialize and restore sourceFilePath strings, not the media itself.
  • lib/features/library/presentation/widgets/canvas_card.dart:171-203 — deletion is explicitly permanent; there is no restore surface.
  • android/app/src/main/AndroidManifest.xml:2-32 has no explicit backup/extraction rules. Android's platform default may provide backup on some devices/accounts, but the repository contains no app-owned, verifiable restore contract or test, so it cannot be treated as reliable Zenno recovery.
Medium Confidence: high

One malformed structured payload can block an entire canvas or reflection collection

Impact
A single corrupt or forward-incompatible ink stroke makes every otherwise valid note on that canvas inaccessible. The same failure boundary exists in reflections: one malformed template JSON can fail the full template stream, and one malformed saved entry can hide the full reflection list for its goal card.
Flow / integrity
Data integrity: data remains stored but becomes unavailable through its normal collection view. Flow: the user loses access to unrelated valid work because decoding is all-or-nothing.
Root cause
Collection mappers decode each stored payload inline without a per-record corruption boundary. Shape/settings decoders use defensive defaults, but ink and reflection JSON syntax errors escape and terminate the enclosing load/stream.
Recommendation
Decode each record behind a typed corruption boundary, retain raw failing rows, expose valid records with a precise partial-load warning, and offer export/repair. Do not silently skip without recording the failure or let a single record terminate its collection.
  • lib/canvas/persistence/ink_codec.dart:78-99,128-157 — malformed version/length/values throw FormatException.
  • lib/canvas/persistence/canvas_repository.dart:177-190,213-230 — decoding occurs inside the full reconstruction loop with no per-row catch.
  • lib/canvas/canvas_editor_page.dart:132-144,502-530 — the resulting error becomes a whole-canvas generic load failure.
  • lib/features/goal_cycle/domain/reflection_template_schema.dart:94-108,124-136 — both schema and answer helpers call jsonDecode outside a syntax-error fallback.
  • lib/features/goal_cycle/data/reflection_repository.dart:112-139,245-266 — template and entry streams map every row through those decoders; one throw terminates the entire list emission.
Medium Confidence: high

Focus controls mutate the timer before persistence, so a reported failure can leave UI and durable runtime disagreeing

Impact
If pause/resume/phase-change persistence fails, the screen already shows the changed timer even though the snackbar says the operation failed. A process death before a later checkpoint can restore the prior durable phase and count time differently. A failed finish stops the ticker and changes the engine before the session row is closed.
Flow / integrity
Data integrity: conditional runtime/history divergence during storage failure. Flow: the visible state contradicts the failure message and the retry action may now be the opposite action.
Root cause
Controller methods mutate TimerEngine and emit state first, then await the database. On error they neither roll back the engine nor retain a visible pending-sync state. The periodic checkpoint can heal ordinary transitions after up to 15 seconds, but not a stopped ticker after failed finish; it also lacks a single-flight guard, so a write slower than one second can overlap later checkpoints.
Recommendation
Choose and enforce one failure contract: either persist the intended transition transactionally before committing UI state, or keep the optimistic state with an explicit unsynced flag and durable retry loop. Make checkpoint persistence single-flight. For finish, retain a retriable closing state without pretending the session is still normally active.
  • lib/features/focus/application/active_session_controller.dart:192-220 — pause, resume, end-stretch, and skip-break all mutate/emit before await _persistRuntime().
  • lib/features/focus/application/active_session_controller.dart:264-303 — stop finishes/abandons the engine and stops the ticker before awaiting finishSession.
  • lib/features/focus/presentation/pages/focus_active_page.dart:119-167 — errors produce “Could not…” feedback but do not restore the prior controller state.
  • lib/features/focus/application/active_session_controller.dart:354-370 — continued ticker checkpoints can eventually repair transition state, which bounds but does not eliminate the failure window.
  • lib/features/focus/application/active_session_controller.dart:344-370 — Timer.periodic invokes async _onTick without awaiting or guarding a checkpoint already in flight.

Recoverability primitives exist for canvases, but destructive knowledge workflows bypass them

Impact
A confirmed mistake permanently removes a canvas and its elements/media, an entire goal plus its reflections, an individual reflection, a revision card, or a Kanban column and all its cards. There is no trash window, undo, or restore for these knowledge artifacts.
Flow / integrity
Data integrity: intentional but unnecessarily irreversible. Flow: confirmation is the only defense.

isArchived and archiveCanvas exist, while the UI routes its only canvas removal action directly to deleteCanvas. Other knowledge objects are modeled solely with cascade-backed hard deletion. Confirmation is treated as the recovery strategy rather than the last gate before final purge.

Medium Confidence: high

Android export produces a private file but provides no usable handoff to the user

Impact
The export operation can render successfully yet leave the result only inside Zenno's app-private documents directory. The UI reports a raw internal path but offers no system save picker, share sheet, open action, or gallery/media-store publication. Repeated exports also accumulate with no management or cleanup surface.
Flow / integrity
Data integrity: original notes are safe, but large unmanaged exports can consume private storage. Flow: a user-visible “Exported” success is not an end-to-end successful export if the result cannot be retrieved normally.
Root cause
The renderer and file writer are complete, but the delivery half of export is absent. getApplicationDocumentsDirectory() is used as the final destination rather than staging for a platform handoff.
Recommendation
After rendering, invoke Android's document-creation picker or share sheet and treat successful handoff as completion. If a private staging file is necessary, purge it after handoff or expose an export manager. Keep export rendering separate from delivery so failures are accurately reported.
  • lib/canvas/io/canvas_export.dart:127-162 — every export is written under getApplicationDocumentsDirectory()/canvas_exports.
  • lib/canvas/widgets/canvas_toolbar.dart:1999-2022 — success only shows the raw result.filePath in a snackbar.
  • Repository search found no share/open/save-file/MediaStore integration and no other reference to canvas_exports; there is consequently no retrieval or cleanup path in current code.

Text-heavy thinking workflows guard navigation but keep drafts only in memory

Impact
Switching away and later losing the Android process can discard an in-progress reflection, template, goal/revision note, focus setup goal, or focus review note. Back-button guards prevent an intentional navigation mistake, but they do not protect against process death—the resilience case most relevant to a tablet used alongside reading material.
Flow / integrity
Data integrity: already-saved records remain safe; unsaved thinking can be lost. Flow: losing prose while researching interrupts the learning process and makes users afraid to leave the app.

Draft state lives in widget TextEditingControllers or an auto-disposed/in-memory Riverpod controller and is written only on explicit Save/Start/Finish. Dirty-state PopScope logic is consistently implemented, but there is no draft table, restoration state, or debounced autosave contract.
Recommendation
Add lightweight local draft persistence for the highest-value prose first (reflections and focus review), keyed by destination record/session with schema/version and explicit clearing after successful save/discard. Restore drafts visibly; never overwrite the last committed record with partial text.

  • lib/features/goal_cycle/presentation/pages/template_editor_page.dart:40-75,210-268,297-300 — the entire template draft is controller state with explicit Save and a PopScope guard.
  • lib/features/goal_cycle/presentation/widgets/goal_card_detail_sheet.dart:45-92,107-134,261-265 and lib/features/revision/presentation/widgets/revision_card_detail_sheet.dart:43-98,128-152,311-315 — note fields are memory-only until explicit save.

High Confidence: high

A failure mid-schema-upgrade can leave a partially migrated database that fails again on every launch

Impact
If storage exhaustion, I/O failure, or an unexpected schema edge interrupts an upgrade after some DDL succeeds, the database can retain those changes while still advertising the old version. The next launch repeats the same upgrade and can fail on an already-created table, index, or column, leaving all notes inaccessible until a repair or restore. This is a credible failure mode, not evidence that it has occurred.
Flow / integrity
Data integrity: rows are not proven deleted, but the entire knowledge base can become durably unavailable during an app update. A user-facing recovery path does not exist. Flow: Zenno may stop opening at all.
Root cause
Zenno's upgrade hook performs many individually awaited DDL/DML statements without an explicit encompassing transaction and without idempotent guards. In the locked Drift 2.31 runtime, the migration hook is called directly and user_version is advanced only after the hook and beforeOpen complete; no transaction wrapper is added around the hook.
Recommendation
Make each version transition failure-atomic, using an explicitly supported transaction strategy for the target executors or a tested idempotent/resumable migration design. Before migrating valuable local-only data, create and validate a recoverable snapshot. Add fault-injection tests that fail after each material migration statement, close, reopen, and prove either complete rollback or successful resume with preserved rows.
  • lib/core/database/database.dart:64-152 — onUpgrade runs the v2–v13 column/table/index creation and v8 layer backfill as a long sequence with no explicit transaction.
  • lib/core/database/database.dart:115-134 — v8 alone creates a table and two indexes, adds a column, inserts default layers, and backfills elements; interruption after any successful prefix creates a non-idempotent partial state.
  • pubspec.yaml:36 and pubspec.lock:284-300 — production and development are locked to Drift 2.31.0.
  • drift 2.31.0 runtime: db_base.dart:118-138; engines.dart:495-527 — local dependency source confirms direct onUpgrade/beforeOpen invocation and version advancement only after success, with no enclosing transaction in that path.
  • test/database_test.dart:391-455,551-566 — successful v7→v8 backfill and exact v1–v12→v13 results are well covered, but repository search found no injected migration failure, rollback, or reopen-after-partial-upgrade test.

Verified strengths worth preserving

  • Canvas failed writes remain visible and retryable: CanvasController retains unsaved state even after banner dismissal and reconciles the latest snapshot rather than replaying stale closures (lib/canvas/canvas_controller.dart:1059-1117).
  • Editor exit is guarded: normal back flushes pending writes and asks before leaving when unsaved writes remain (lib/canvas/canvas_editor_page.dart:243-309,481-485).
  • Focus timing uses wall time: elapsed time survives ticker stalls/backgrounding and checkpoints runtime every 15 seconds (lib/features/focus/domain/timer_engine.dart:136-163,268-305; active_session_controller.dart:354-404).
  • Reflection history snapshots template name/schema: later template edits do not rewrite old reflections (lib/core/database/tables/reflection_tables.dart:23-47).
  • Compound writes are commonly transactional: canvas generic/detail rows, focus start plus ritual snapshot, cards plus detail rows, and folder-preserving deletion use transactions.
  • Current UI has corrected many historical review complaints: PopScope/dirty guards, async busy states, confirmations, and friendly failure messages now exist across canvas, focus, goal/reflection, revision, library, and Kanban surfaces.
  • Canvas transient input is deliberately reversible: pointer cancel/dispose paths cancel strokes, erases, lassos, shapes and transforms rather than committing partial gestures (lib/canvas/render/canvas_view.dart:246-263,742-795,1000-1157).
  • Migration verification is unusually concrete: every stored schema v1 through v12 is migrated and compared to the exact v13 schema (test/database_test.dart:551-566).

Next-pass challenges

Iteration 4 will continue trying to falsify the remaining claims before expanding them. Priority checks:

  1. Read every ignored affected-row count and cross-table write outside transactions; distinguish harmless idempotence from stale-ID success feedback or orphan risk.
  2. Trace database-open seeding on abnormal but reachable flags, and separate transactional fresh-install behavior from repair/reopen traps.
  3. Quantify all-element work during viewport movement, selection, tile-cache rebuild, raster scheduling, and hit-testing; only promote it if the scale-dependent interruption is structurally credible.
  4. Audit DateTime persistence/ordering across time-zone changes, Android lifecycle restoration, low-storage behavior, and app-private file ownership.
  5. Challenge the trash recommendation against attachments, canvas links, focus references, media cleanup, and board ordering so the recommendation does not introduce hidden dangling state.
  6. Continue mapping tests to each risk and remove or demote any claim supported only by absent tests rather than an implementation path.
