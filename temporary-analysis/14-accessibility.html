Executive summary

6high severity

The dominant issue is architectural: Zenno’s primary note surface is four painted layers driven by raw pointer events, with no semantic representation of the notes on that surface. Screen-reader users cannot inspect typed notes, links, images, PDFs, shapes, selection, or viewport state, while keyboard users cannot traverse or select canvas objects. Keyboard shortcuts help only after a pointer-created selection and therefore do not close the access gap. Painted typed notes also bypass the system text scaler and silently clip vertical overflow.

The next most consequential gaps are interaction equivalence. Kanban columns and within-column card order remain drag-only; the radial tool wheel exposes some screen-reader actions but its gesture-based actions are not in the physical-keyboard focus model; viewport pan/zoom has no keyboard command path; and both Android and the installed web app restrict orientation, in opposite directions. Several custom controls—including the keyboard-focusable canvas settings fallback—communicate selection or checked state visually without exposing it semantically. Reflection/focus prompts also use nearby visual labels without programmatically naming their fields, while page and section headings are plain text across the app.

Data integrity: iteration 6 found one direct inclusive-input risk: keyboard edits can remain enabled during asynchronous saves, after which an older snapshot is treated as final and the newer draft can be discarded. Separately, failed canvas writes are retained for retry and guarded on exit, but the failure is not announced when it first occurs. Other findings primarily create indirect wrong-target or unverifiable-edit risk. Recommendations below are analysis only and prioritize preserving every newer draft.

Current findings

High A14-001 — The infinite canvas has no accessible object model

Confidence
High
Flow impact
Core note content cannot be read, navigated, selected, opened, or edited without pointer/visual access.
Data-integrity impact
No direct corruption; high wrong-target and unverifiable-edit risk for partial-access users.
Evidence. lib/canvas/render/canvas_view.dart:1455-1551 builds a raw Listener around four CustomPaint layers. Repository-wide searches found no semanticsBuilder in the canvas painters. The model explicitly includes typed text, links, images and PDFs (lib/canvas/model/canvas_element.dart:16-37), but none are emitted as semantic nodes. It also has no authorable description field for an image (path, intrinsic size and raster only at lib/canvas/model/canvas_element.dart:363-399; persistence fields at lib/core/database/tables/canvas_tables.dart:214-233) or PDF page (path, page number and page size at .../canvas_element.dart:501-547; filename/page metadata only at .../canvas_tables.dart:190-211). Links do carry a human label (.../canvas_element.dart:735-762), showing that accessible identity already fits one element type. lib/canvas/canvas_editor_page.dart:550-623 adds tool and transform shortcuts, yet every object-transform shortcut requires an already-selected object and there is no next/previous/select/open object command.

Root cause. Rendering, hit testing, and commands are modeled only in world/pointer coordinates; accessibility was not made a parallel consumer of the element/spatial-index model.

Analysis-only recommendation. Build a stable semantic object layer from visible canvas elements, with meaningful roles/labels/actions for text notes and links, persisted user-authored descriptions for images/PDF pages, selection state, and ordered keyboard traversal. Add keyboard commands to move focus among objects, select the focused object, follow/edit it, and pan/zoom without a pointer. Expose PDF filename/page and any extracted text separately from an optional author description; never present OCR as authorial meaning. Keep ink/shapes summarized unless the user supplies a description, and never infer note meaning from geometry.

High A14-002 — Column order and same-column card order are drag-only

Confidence
High
Flow impact
Keyboard and screen-reader users cannot fully organize revision or goal boards.
Data-integrity impact
No deletion; users can be left with an order they cannot repair independently.
Evidence. The column handle is a LongPressDraggable with a button label but no invokable reorder action (lib/shared/kanban/kanban_column_view.dart:279-299). Cards are wrapped in another LongPressDraggable (.../kanban_column_view.dart:492-535). The accessible card move menu is a good partial alternative, but targets explicitly exclude the current column (.../kanban_column_view.dart:235-244) and the menu only moves to another column’s tail (.../kanban_column_view.dart:604-629). Column drop slots are pointer DragTargets (lib/shared/kanban/kanban_board_view.dart:208-237).

Root cause. Drag/drop is the sole command surface for ordering, while the fallback menu models only cross-column placement.

Analysis-only recommendation. Add explicit “Move before/after/to start/to end” actions for both columns and cards, including within the current column. Reuse the same normalized positioning commands as drag/drop, announce the new position, and retain drag as the fast pointer path.

High A14-003 — Core radial-wheel actions are outside physical-keyboard focus traversal

Confidence
High
Flow impact
Keyboard-only users cannot traverse the wheel’s page/context/property actions even though the canvas editor itself advertises keyboard shortcuts.
Data-integrity impact
None direct; missing access to selection and tool properties can force imprecise work.
Evidence. Main wheel actions are 40×40 positioned GestureDetectors wrapped in Semantics(onTap: ...) (lib/canvas/widgets/canvas_toolbar.dart:2733-2856), and property actions are 34×34 GestureDetectors (.../canvas_toolbar.dart:2857-2909). Unlike InkWell, these controls have no Focus/Actions/FocusableActionDetector. The unmodified-letter shortcuts cover seven base tools only (lib/canvas/canvas_editor_page.dart:609-622), not wheel pages, selection actions, property changes, color choices, or wheel movement.

Root cause. Screen-reader semantics were added as an overlay, but the same actions were not exposed through Flutter’s keyboard focus/action system.

Analysis-only recommendation. Make each semantic wheel action a real focusable action with Enter/Space activation, visible focus, directional navigation appropriate to radial layout, and increase/decrease actions for numeric properties. Publish a discoverable shortcut reference and avoid unmodified-letter shortcuts when a text-entry descendant can retain focus.

High A14-004 — Installed app orientation is restricted, inconsistently by platform

Confidence
High
Flow impact
Users who mount or hold a device in one orientation cannot use the app in that orientation.
Data-integrity impact
None.
Evidence. Android forces android:screenOrientation="userLandscape" in android/app/src/main/AndroidManifest.xml:13. The web app manifest independently requests "orientation": "portrait-primary" in web/manifest.json:9. The opposite restrictions also demonstrate that neither orientation is universally essential to the product.

Root cause. Platform manifests encode product-layout preferences as hard device-orientation requirements.

Analysis-only recommendation. Permit sensor/user orientation on both platforms. Let the responsive shell adapt navigation and toolbar placement; if a particular canvas workflow genuinely needs more width, offer a non-blocking suggestion rather than locking the whole app.

High A14-016 — The infinite-canvas viewport cannot be explored with the keyboard

Confidence
High
Flow impact
Keyboard-only users cannot pan to off-screen notes or incrementally zoom the workspace, independently blocking discovery even if canvas objects later gain semantics.
Data-integrity impact
No direct mutation; users cannot verify content outside the current viewport and may work in the wrong spatial context.
Evidence. Canvas panning is implemented only from touch/stylus/mouse movement (lib/canvas/render/canvas_view.dart:550-559, 719-730); zoom is driven by pointer scroll (.../canvas_view.dart:1302-1313) or two-touch pinch (.../canvas_view.dart:1361-1410). The editor shortcut map uses Ctrl+Arrow and Ctrl+Minus/Equal to transform the current selection, not the viewport, and contains no viewport navigation commands (lib/canvas/canvas_editor_page.dart:550-623). Zoom in/out, fit content and reset view exist inside the non-keyboard-focusable wheel identified in A14-003 (lib/canvas/widgets/canvas_toolbar.dart:1179-1221, 1354-1378); the visible HUD provides only a button that resets zoom to 100% (.../canvas_toolbar.dart:429-456).

Root cause. Viewport navigation is modeled as a pointer gesture, while keyboard shortcuts were designed only for tools and already-selected objects.

Analysis-only recommendation. Add non-conflicting keyboard commands for viewport pan, zoom in/out, fit content and reset view; keep selection transforms separately modified. Anchor zoom to the focused object or viewport center, announce the resulting zoom/region at useful boundaries, and document the commands in a keyboard-accessible help surface.

High A14-022 — Keyboard edits made during asynchronous save can be discarded as “saved”

Confidence
High
Flow impact
Fast keyboard users can continue editing while a save is in flight; the screen then closes or marks the newer draft clean even though only the earlier snapshot was persisted.
Data-integrity impact
High: the last keystrokes in goals, revision notes, reflections, templates, or focus reviews can be lost without a warning.
Evidence. Goal saving snapshots three controllers, sets _saving, awaits persistence, and unconditionally pops on success (lib/features/goal_cycle/presentation/widgets/goal_card_detail_sheet.dart:107-134). Its busy guard is only AbsorbPointer around still-enabled TextFields (.../goal_card_detail_sheet.dart:261-320). Flutter documents and implements AbsorbPointer as pointer hit-test blocking, not keyboard focus/input blocking (packages/flutter/lib/src/widgets/basic.dart:7831-7846; packages/flutter/lib/src/rendering/proxy_box.dart:3974-4050). Template and reflection editors repeat the snapshot/await/pop pattern behind AbsorbPointer (lib/features/goal_cycle/presentation/pages/template_editor_page.dart:230-269, 297-329; lib/features/goal_cycle/presentation/pages/reflection_editor_page.dart:92-120, 135-159). Revision editing has no input absorber: after awaiting the captured title/notes, it sets persisted values and _textDirty = false even if controllers changed during the await (lib/features/revision/presentation/widgets/revision_card_detail_sheet.dart:128-151, 305-360). Focus review captures energy/note, leaves both controls enabled, awaits, then pops to the first route (lib/features/focus/presentation/pages/focus_review_page.dart:70-78, 150-187, 232-255).

Root cause. Async save treats the draft captured at start as the final UI state, and pointer absorption is mistaken for a complete interaction lock; keyboard focus/editing remains a separate path.

Analysis-only recommendation. Prefer a revision-token approach over a blanket lock: capture a draft revision with the save, and on completion pop/mark clean only if the current draft still matches; otherwise keep the newer draft open and dirty. During operations that truly must freeze input, set fields readOnly/enabled: false and prevent focus traversal as well as pointer hits. Preserve newer text in memory and never discard it merely because an older write succeeded.

Medium A14-005 — Checklist state is visual only

Confidence
High
Flow impact
A screen-reader user cannot tell which pre-focus ritual items are checked.
Data-integrity impact
The persisted ritual snapshot can contain a state the user could not verify.
Evidence. lib/features/focus/presentation/widgets/ritual_checklist.dart:133-190 uses an InkWell and swaps between checked/unchecked Icons. It does not provide Semantics(checked: ...), a checkbox role, or an explicit toggled value. The icon has no semantic label, so the row exposes an activation action and label but not state.

Root cause. A checkbox was visually reimplemented instead of using CheckboxListTile or equivalent toggle semantics.

Analysis-only recommendation. Prefer a native checkbox control, or expose checked state, toggle role/action, enabled state, and a single merged label on the entire 48dp row.

Medium A14-006 — Timer-mode and mastery choices do not announce selection

Confidence
High
Flow impact
Screen-reader users can activate options but cannot reliably confirm the active mode/mastery value.
Data-integrity impact
Wrong study mode or mastery classification can be saved.
Evidence. Timer mode is an InkWell whose selection is represented only by color, border and check icon (lib/features/focus/presentation/widgets/timer_type_picker.dart:68-123). Mastery choices do the same (lib/features/revision/presentation/widgets/revision_card_detail_sheet.dart:463-516). Neither uses selected, radio/check semantics, or an in-group value. In contrast, EnergyRatingSelector correctly exposes exactly one selected pip at lib/features/focus/presentation/widgets/energy_rating_selector.dart:99-129.

Root cause. Custom selectable cards/chips do not share a semantic selection primitive.

Analysis-only recommendation. Add a reusable selectable-control wrapper with button/radio role, label, selected state, group context, and keyboard activation; use it for mode and mastery choices.

Medium A14-007 — Flowmodoro ratio can announce a different percentage from the displayed value

Confidence
High
Flow impact
A screen-reader user may choose the wrong earned-break ratio.
Data-integrity impact
The saved session configuration can differ from the perceived choice.
Evidence. Setup displays percent = flowBreakRatio * 100, but its slider has no semanticFormatterCallback or semantic value wrapper (lib/features/focus/presentation/pages/focus_setup_page.dart:330-357). Flutter 3.41.6 reports the normalized slider position as a percentage when no formatter exists (packages/flutter/lib/src/material/slider.dart:1929-1943 in the installed SDK). For example, value 0.20 on range 0.05–0.50 is visually “20%” but normalizes to roughly “33%”. Settings avoids this by wrapping sliders with the domain value at lib/features/settings/presentation/pages/settings_page.dart:677-687.

Root cause. The visual value is a domain percentage, while default slider semantics describe relative position within a non-zero-based range.

Analysis-only recommendation. Supply a semantic formatter that returns the domain value (for example “20 percent break ratio”) and meaningful increased/decreased values.

Medium A14-008 — The live timer exposes two unlabeled progress bars

Confidence
High
Flow impact
Screen-reader traversal encounters an unexplained 100% ring plus a second percentage before the timer figure.
Data-integrity impact
None.
Evidence. The timer stack contains one determinate CircularProgressIndicator(value: 1) and another determinate indicator for phase progress, neither with semanticsLabel (lib/features/focus/presentation/widgets/timer_display.dart:63-91). Flutter emits each determinate indicator as a progress-bar semantic node with a default numeric value (packages/flutter/lib/src/material/progress_indicator.dart:146-160 in the installed SDK). The time and “work remaining” text are separate at .../timer_display.dart:92-120.

Root cause. A decorative track is implemented as a semantic progress widget, and the meaningful arc lacks a purpose label.

Analysis-only recommendation. Exclude the decorative 100% track from semantics. Give the meaningful timer one coherent semantic node containing phase, formatted time, paused/running state and progress; announce phase transitions deliberately rather than making every one-second repaint a live announcement.

Medium A14-009 — Repeated overflow controls lack item context

Confidence
Medium-high
Flow impact
Control-list and swipe navigation yields multiple indistinguishable “options/actions” buttons.
Data-integrity impact
Raises wrong-item rename/delete/retire risk, although destructive dialogs reduce the worst outcomes.
Evidence. Repeated rows/cards use generic tooltips: “Canvas options” (lib/features/library/presentation/widgets/canvas_card.dart:274-280), “Folder options” (lib/features/library/presentation/pages/library_page.dart:697-700), “Column actions” (lib/shared/kanban/kanban_column_view.dart:341-344), “Edit ritual item” (lib/features/focus/presentation/widgets/ritual_checklist.dart:161-164), “Reflection actions” (lib/features/goal_cycle/presentation/widgets/reflection_entry_tile.dart:120-134), and “Template actions” (lib/features/goal_cycle/presentation/widgets/template_tile.dart:122-134). Attached-canvas rows repeat both “Open canvas” and “Canvas actions” without the attachment label (lib/shared/canvas_attachments/card_canvas_attachments_section.dart:119-151). The card move menu demonstrates the clearer pattern with Move ${card.title} at .../kanban_column_view.dart:615-629.

Root cause. Menu components receive callbacks but not the owning item’s accessible name.

Analysis-only recommendation. Include the item label in each tooltip/semantic label (for example “Options for Anatomy notes”) and make confirmation text equally specific.

Medium A14-010 — Canvas cards deliberately hide recency metadata from assistive technology

Confidence
High
Flow impact
A screen-reader user cannot use “Edited …” information to resume the right canvas.
Data-integrity impact
None; discovery and recall are impaired.
Evidence. lib/features/library/presentation/widgets/canvas_card.dart:228-273 wraps the entire open surface in Semantics(label: 'Open canvas …', excludeSemantics: true). This suppresses the title and the visible Edited ${relativeTime(...)} at lines 252-266, replacing both with only the open-action label.

Medium A14-013 — Visible prompt labels are not programmatically associated with their fields

Confidence
High
Flow impact
Direct form-control navigation can land on an unnamed answer, study-goal, session-note, framework, canvas-title, note-body, or column-name field.
Data-integrity impact
Answers, titles, and organization labels can be entered under the wrong context and then saved.
Evidence. Reflection prompts render Text(prompt.label) as a sibling before a TextField whose decoration contains only an optional hint (lib/features/goal_cycle/presentation/widgets/reflection_form.dart:122-150). The framework picker repeats that pattern (lib/features/goal_cycle/presentation/pages/reflection_editor_page.dart:317-348). Focus setup’s “What are you studying?” field (lib/features/focus/presentation/pages/focus_setup_page.dart:94-104) and review’s “Session note” field (lib/features/focus/presentation/pages/focus_review_page.dart:160-171) likewise use nearby headings plus placeholder text rather than labelText or an explicit semantic relationship. Re-audit found the inline canvas-title editor has no label or hint at all (lib/canvas/canvas_editor_page.dart:795-823); the text-note body relies on a placeholder and dialog title (.../canvas_editor_page.dart:364-382); and the shared column-name dialog similarly has only an optional hint plus a separate dialog title (lib/shared/kanban/kanban_column_view.dart:731-803).

Root cause. Visual grouping is treated as sufficient labeling; Flutter does not infer an accessible-name relationship from a preceding sibling Text.

Analysis-only recommendation. Put the prompt/question into InputDecoration.labelText or provide one merged semantic field node whose label is the prompt and whose hint remains secondary. Preserve visible editorial labels if desired, but suppress duplicate announcements and test direct control navigation with populated fields.

Medium A14-014 — Visual page and section headings are not exposed as headings

Confidence
High
Flow impact
Screen-reader users cannot jump among major areas of long settings, setup, review, and detail pages.
Data-integrity impact
None; navigation and comprehension cost increase.
Evidence. A repository-wide search found no Semantics(header: true) or SemanticsRole.header. The shared top bar renders eyebrow/title/subtitle as plain Text widgets (lib/core/widgets/aurora.dart:89-135), and settings panel titles are also plain text (lib/features/settings/presentation/pages/settings_page.dart:303-358). Many long forms use private _SectionTitle widgets that return only Text, for example lib/features/focus/presentation/pages/focus_setup_page.dart:426-435.

Root cause. Typography encodes document hierarchy visually, but the same hierarchy is absent from the semantic tree.

Analysis-only recommendation. Add semantic heading roles to page titles and meaningful section titles through the shared top-bar/section-title components. Avoid marking every styled label as a heading; preserve a shallow, useful outline.

Medium A14-015 — Color swatches do not expose selection state or consistent color identity

Confidence
High
Flow impact
Screen-reader and color-vision users cannot reliably confirm the current ink/paper color.
Data-integrity impact
Notes can be created in an unintended or low-contrast color, though existing content is not deleted.
Evidence. The compact palette identifies swatches only by hex tooltip and renders selection as a border/check icon (lib/canvas/widgets/canvas_toolbar.dart:3128-3199). The larger swatch control has a selected parameter used only for border styling (.../canvas_toolbar.dart:3397-3438). Palette slots announce only “Palette color N,” omitting the color value and selected state (.../canvas_toolbar.dart:4147-4188). Paper preset swatches again expose hex only and put the selected check solely in the visual child (.../canvas_toolbar.dart:4594-4639).

Root cause. Tooltips were used as the only non-visual identity, while selection stayed entirely decorative.

Analysis-only recommendation. Give each swatch a stable human-friendly name plus hex value, expose selected, group the choices, and announce ink versus paper/background purpose. Keep the checkmark and border for sighted users; add a contrast preview/warning for typed text without blocking expressive drawing colors.

Medium A14-017 — Fixed status colors fail text contrast in supported default-theme contexts

Confidence
High for the default palettes and cited widgets
Flow impact
Low-vision users can miss whether a focus session is completed, abandoned, in progress, under review, or in a break phase.
Data-integrity impact
None direct; diminished status perception can lead users to resume or review the wrong session.
Evidence. The three fixed status colors are green #718D68, yellow #C49B49, and red #B85F50 (lib/config/theme/app_colors.dart:64-66). Recent-session status text is 12px labelSmall in one of those colors directly on the page surface (lib/features/focus/presentation/pages/focus_home_page.dart:494-540; size defined at lib/config/theme/app_text_styles.dart:108-113). Exact sRGB calculations against the default light paper #F7F3EA yield 3.32:1 green, 2.33:1 yellow and 3.96:1 red, all below 4.5:1 for normal text. History chips put the same 12px text over a 16%-tinted fill (lib/features/focus/presentation/pages/focus_history_page.dart:319-345), reducing the light-theme ratios further to approximately 2.83:1, 2.06:1 and 3.27:1. The shared phase pill similarly places 13px accent text over a 9%-tinted fill (lib/core/widgets/aurora.dart:232-269); the green break chip chosen at lib/features/focus/presentation/widgets/timer_display.dart:28-36, 164-176 is approximately 3.04:1 in the default light theme. In the default dark theme, red is also below 4.5:1 in these contexts (4.29:1 direct; approximately 3.66:1 on the 16% fill).

Root cause. One immutable semantic palette is used as foreground text across light/dark surfaces, and translucent same-hue fills reduce rather than guarantee foreground separation.

Analysis-only recommendation. Define theme-aware on-status text colors (or use normal onSurface text with color confined to a redundant icon/border), and test the final composited foreground/background pairs rather than raw swatches. Keep the written status labels so meaning never depends on color alone.

Medium A14-018 — Keyboard-focusable canvas settings still hide their selected state

Confidence
High
Flow impact
A keyboard or screen-reader user can reach the linear tool-settings controls but cannot confirm the current pen, eraser, selection, shape, pressure, or paper mode.
Data-integrity impact
Notes can be drawn, erased, or selected with an unintended mode; undo limits but does not eliminate disruption.
Evidence. The shared _HudButton accepts selected but applies it only to foreground/background colors; it creates an IconButton without isSelected and without an enclosing selected/toggled semantic node (lib/canvas/widgets/canvas_toolbar.dart:3283-3327). This primitive represents pressure, the mutually exclusive eraser modes, pen kinds, selection modes and shape kinds in the linear settings surface (.../canvas_toolbar.dart:1531-1621, 1635-1673, 1725-1748). Flutter’s own IconButton.isSelected path would emit Semantics(selected: ...) (packages/flutter/lib/src/material/icon_button.dart:939-953 in Flutter 3.41.6), but Zenno does not pass it. Paper-kind buttons similarly use selected only for color, border and weight on an InkWell (.../canvas_toolbar.dart:4460-4524).

Root cause. The full-controls fallback reused visual selection styling without routing state into the native toggle/selection semantics already available in Flutter.

Analysis-only recommendation. Pass isSelected for toggle icon buttons or wrap each group in explicit radio/selected semantics. Distinguish momentary actions from mutually exclusive modes, announce group purpose, and update paper-kind buttons the same way. Keep the existing changing action labels for pressure/lock toggles as useful redundancy.

Medium A14-020 — Typed notes on the canvas ignore the system text scaler and clip overflow

Confidence
High
Flow impact
Low-vision users who enlarge system text receive no enlargement for the actual typed notes in the thinking workspace.
Data-integrity impact
None direct; note content can be visually inaccessible or clipped without indication.
Evidence. Typed notes are painted directly with TextPainter using only the persisted element.fontSize; no MediaQuery.textScalerOf value is passed (lib/canvas/render/elements_painter.dart:839-880). Flutter 3.41.6 therefore resolves the unspecified scaler to a linear factor of 1.0 (packages/flutter/lib/src/painting/text_painter.dart:596-625). The painter lays out unlimited lines, then clips them to the fixed note rectangle without an ellipsis or overflow signal (elements_painter.dart:864-880). Fresh notes always start with font size 22 and a 320×180 screen-derived placement rectangle (lib/canvas/canvas_controller.dart:481-482, 3703-3729, 3768-3775).

Root cause. Canvas text is treated as zoomable drawing geometry rather than readable text that also participates in the user’s accessibility text-size preference.

Analysis-only recommendation. Apply the current nonlinear TextScaler when rendering typed notes and define a deterministic layout policy: reflow/expand the note, offer an explicit accessible reading view, or clearly expose overflow. Preserve author-set world size separately so accessibility scaling does not silently mutate persisted geometry. Coordinate this with A14-016 so keyboard users can also zoom and frame the focused note.

Medium A14-021 — A failed canvas autosave appears visually but is not announced

Confidence
High
Flow impact
A screen-reader user can continue thinking under the assumption that notes are safely persisted and may not discover the retry action until leaving.
Data-integrity impact
High potential, mitigated by a blocking leave confirmation: failed writes remain queued, but the user lacks timely awareness while staying in the editor.
Evidence. A persistence failure is caught, stored and surfaced only by notifyListeners() (lib/canvas/canvas_controller.dart:1099-1116). The toolbar responds by inserting a “Canvas not saved” icon button (lib/canvas/widgets/canvas_toolbar.dart:420-427, 654-662); repository-wide searches found no liveRegion, SemanticsService.announce, or focus move for that transition. Import errors use a SnackBar instead (lib/canvas/canvas_editor_page.dart:492-500), and Flutter’s SnackBar is explicitly a semantic live region (packages/flutter/lib/src/material/snack_bar.dart:828-833). The exit path does correctly flush and show a blocking “Canvas not saved” dialog before allowing departure (lib/canvas/canvas_editor_page.dart:258-289), so this finding is about timely in-editor status rather than an absent last-resort guard.

Root cause. The persistence state transition is represented as a passive HUD decoration; visual tree insertion is assumed to notify users.

Analysis-only recommendation. Announce the transition into save failure exactly once with a concise live status and expose the retry button persistently. Announce retry success/failure, but do not announce routine autosaves or each failed operation repeatedly. Keep the existing leave guard and queued-write recovery behavior intact.

Low A14-011 — Several canvas controls fall below the project’s own 48dp target

Confidence
High
Flow impact
Motor and low-vision users face small, dense controls in the app’s most frequent workspace.
Data-integrity impact
Mis-taps can select the wrong tool/color; undo reduces but does not remove disruption.
Evidence. The project defines AppSpacing.touchTarget = 48 at lib/config/theme/app_spacing.dart:33-35. The wheel instead uses 40dp action overlays and 34dp property controls (lib/canvas/widgets/canvas_toolbar.dart:2708-2709, 2756-2768, 2857-2870), 34dp side buttons (.../canvas_toolbar.dart:3089-3125), a 32dp palette whose items may be 28dp wide (.../canvas_toolbar.dart:3128-3199), 30–42dp palette swatches (.../canvas_toolbar.dart:4147-4218), and 34dp paper swatches (.../canvas_toolbar.dart:4594-4639). Visible wheel labels are explicitly 6.2–7px and property values 6.5px (.../canvas_toolbar.dart:2709, 2814-2845, 2894-2902).

Root cause. The radial/docked geometry is optimized for density and stylus precision, overriding the global target token.

Analysis-only recommendation. Preserve visual density if desired, but enlarge semantic/hit regions to at least 48dp without overlap, support text scaling without clipping, and provide a linear “full controls” mode with full-size controls. Stylus optimization should not remove touch accessibility.

Low A14-012 — Automated accessibility coverage is concentrated on one card flag

Confidence
High
Flow impact
Regressions in the core canvas and custom control states are unlikely to be caught automatically.
Data-integrity impact
Indirect quality risk only.
Evidence. Repository-wide test search found one explicit semantics assertion: test/kanban_board_view_test.dart:110-133 verifies only that a card node has the button flag. There are no semantics-tree assertions for CanvasView, the radial wheel, ritual checks, timer mode, mastery choices, timer display, or route orientation. Existing canvas shortcut tests validate bindings, not keyboard focus reachability.

Root cause. Widget tests emphasize visible copy and callback behavior rather than accessible names, roles, values, actions, focus order and guideline checks.

Analysis-only recommendation. Add focused semantics-tree and keyboard-navigation tests for every custom control, plus tap-target and text-scaling checks. Treat the canvas semantic object model as an acceptance criterion, not a test-only patch.

Low A14-019 — Custom canvas modal surfaces omit dialog roles and closed-loop focus containment

Confidence
High for route configuration; runtime focus destination is platform/tree dependent
Flow impact
Screen-reader users receive weaker context when settings open, and Tab/Shift+Tab are allowed to climb out of the modal’s local focus scope instead of cycling predictably.
Data-integrity impact
None direct.
Evidence. Tool settings, paper settings and the stylus quick wheel use showGeneralDialog (lib/canvas/widgets/canvas_toolbar.dart:1461-1522, 1883-1924, 2056-2136). Their returned surfaces are SafeArea/_FloatingSurface/_Cluster/Stack, not Dialog widgets or explicit dialog/menu semantic roles. In Flutter 3.41.6, showGeneralDialog creates a RawDialogRoute without a traversal-edge override (packages/flutter/lib/src/widgets/routes.dart:2746-2772), so the Navigator default is TraversalEdgeBehavior.parentScope (packages/flutter/lib/src/widgets/navigator.dart:1251-1258). In contrast, showDialog explicitly defaults to closedLoop (packages/flutter/lib/src/material/dialog.dart:1484-1527). The framework does provide a route-scoped dismiss action for dismissible modal routes, so this is not a claim that Escape is absent (packages/flutter/lib/src/widgets/routes.dart:975-990, 1199-1203).

Root cause. Visually positioned popovers were implemented as raw modal routes without reintroducing the dialog semantics and focus policy supplied by Material dialog routes.

Analysis-only recommendation. Use an aligned Dialog/DialogRoute for settings panels, with a semantic title, initial focus and closed-loop traversal; model the quick wheel as a focusable menu if that better matches its behavior. Preserve Escape/barrier dismissal and restore focus to the invoking control after close.

Verified strengths and corrected prior assumptions

Core default text contrast is strong. Static WCAG contrast calculations for defined palette pairs found: dark onSurface/surface 16.20:1, dark muted/container-low 7.82:1, dark primary/surface 7.49:1, light ink/paper 13.62:1, light muted/paper 5.05:1, and light primary/paper 5.79:1. A14-017 is narrowly about fixed status-color text and does not contradict the theme-role pairs.
Native Material controls are used extensively. App navigation, dialogs, text fields, standard buttons, segmented buttons, switches, sliders, menus and date picking generally inherit keyboard and screen-reader behavior. The global theme sets padded tap targets and 48dp minimum sizes at lib/config/theme/app_theme.dart:129-138, 224-303.
Several old review issues have been fixed. Energy rating now marks only the exact selected pip (energy_rating_selector.dart:47-52, 99-129); settings steppers include the setting name in tooltips (settings_page.dart:591-617); the kanban card move menu provides a keyboard/screen-reader-friendly cross-column alternative; the column drag handle now has a label/tooltip; distraction capture no longer autofocuses the optional note field.
Template prompt reordering has framework semantics. Although its drag handle is custom, ReorderableListView wraps items with move-to-start/up/down/end semantic actions in Flutter 3.41.6. This pass therefore does not repeat the stale claim that prompt order is screen-reader drag-only. A future pass will still assess direct physical-keyboard discoverability.
Dismissible modal routes retain Escape support. Flutter’s modal scope maps DismissIntent to maybePop whenever the route barrier is dismissible. A14-019 is therefore limited to semantic role and focus containment, not keyboard dismissal.
Canvas links already retain author-facing labels. LinkElement persists a short human-readable label alongside its destination, so a future canvas semantic layer can expose link identity without inventing it. Image/PDF elements need an equivalent optional description field.
SnackBar feedback is announced by the framework. Flutter wraps SnackBars in a semantic live region, so Zenno’s many save/error/import completion SnackBars have a built-in announcement path. A14-021 is limited to the canvas persistence failure that bypasses SnackBar/live-region feedback; the editor also retains failed writes and blocks an unacknowledged exit.
