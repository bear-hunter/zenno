The review traced the app root, the full go_router table, every imperative Navigator entry point, every PopScope, stateful screen initialization/disposal, focus runtime restoration, canvas flushing, database lifetime, Android launch configuration, web/PWA launch configuration, and the relevant navigation/lifecycle tests. Severity reflects likely impact on Zenno's thinking flow and data integrity. Confidence separates a definite code property from a user-visible outcome that depends on an OS or timing condition. Recommendations are analysis-only.

Executive summary

The in-memory navigation design is pleasant during an uninterrupted session: five independent branches preserve their stacks, the canvas is full-bleed on the root navigator, and the focus timer is wall-clock based. The weak boundary is interruption and initialization concurrency. A swipe-down gesture can bypass the dirty guards inside editable bottom sheets, app/process restoration is not configured, focus recovery is lazy and can become permanently poisoned after one startup read failure, the canvas has no lifecycle checkpoint before Android may suspend or kill it, and fire-and-forget repository activation cleanup can race a media import into deleting the newly attached file.

6 Mediumprocess restoration, focus ownership, wakelock sync, route payload/error handling, canvas ID ownership
3 Lowpre-first-frame failure, PWA orientation, and ineffective tab reset

Priority order

  1. Disable drag-to-dismiss on editable goal/revision sheets and route all dismiss attempts through their existing guarded close path.
  2. Serialize orphan cleanup with media imports, or revalidate every candidate against current database references immediately before deletion.
  3. Make focus transitions durable before exposing them as successful, especially Finish/End early, and add a retryable shutdown checkpoint.
  4. Add one app-owned lifecycle/checkpoint boundary for canvas writes and one eager, recoverable bootstrap for active focus restoration.
  5. Decide the intended restoration contract: at minimum restore the selected branch/current durable screen and preserve text drafts that represent unfinished thinking.
  6. Give each canvas ID a distinct route/widget ownership key and define guarded behavior for any in-place canvas location replacement.

HighN15-01 — Drag-to-dismiss bypasses dirty guards in editable bottom sheets

Confidence: 99% after cross-checking the installed Flutter 3.41.6 bottom-sheet and navigation implementation.

  • Goal details use showModalBottomSheet with showDragHandle: true and leave enableDrag at its default true: lib/features/goal_cycle/presentation/widgets/goal_card_detail_sheet.dart:22-31.
  • Revision details use the same dismissible configuration: lib/features/revision/presentation/widgets/revision_card_detail_sheet.dart:20-29.
  • Both sheet bodies attempt to protect dirty/busy state with PopScope: goal_card_detail_sheet.dart:261-265 and revision_card_detail_sheet.dart:305-315.
  • In the installed Flutter implementation, scrim dismissal uses Navigator.maybePop (which consults PopScope), but a completed downward sheet drag calls Navigator.pop directly. Direct pop does not consult Route.popDisposition; the callback arrives with didPop == true, after the route has already closed.

Impact. After typing a goal title/summary/status note or revision title/notes, the user can swipe the sheet down and lose the draft without the intended “Discard changes?” prompt. The failure is especially plausible because both sheets visibly advertise dragging with a handle. Persisted records remain intact, but original thought text is discarded.

Root cause. PopScope protects back and maybePop requests; it cannot retroactively veto a direct programmatic Navigator.pop. The modal route owns the drag gesture outside the guarded sheet body.

Analysis-only recommendation. Set enableDrag: false for editable sheets. Keep scrim/back dismissal, which can reach PopScope, or set isDismissible: false too and provide an explicit close button that invokes the same guard. If drag is a hard requirement, own the sheet route/drag callback and ask the draft owner before popping. Add tests for dirty scrim, system back, and downward drag as three separate paths.

HighN15-02 — Canvas persistence has route-exit flushing but no app-lifecycle checkpoint

Confidence: 92% that the gap exists; 72% that a given interruption loses a committed mark because the write-through window is normally short.

  • The editor waits for _controller.flush() on its controlled back path before popping: lib/canvas/canvas_editor_page.dart:258-305.
  • On widget disposal it starts, but cannot await, flush().whenComplete(dispose): lib/canvas/canvas_editor_page.dart:207-215.
  • Structural writes are asynchronous and tracked; viewport writes are delayed by 400 ms: lib/canvas/canvas_controller.dart:222-252, 931-943, 1036-1057, and 1099-1117.
  • lib/canvas/canvas_controller.dart:4514-4517 explicitly says callers that skip flush can lose the final viewport.
  • A repository-wide search found no AppLifecycleListener, WidgetsBindingObserver, or didChangeAppLifecycleState in production source.

Impact. Home-button/background transitions followed by process reclamation can occur without the guarded back path. A recent viewport is definitely exposed to the debounce window; recently committed elements may still have an in-flight SQLite write. An in-progress live stroke is not a committed element until pointer-up (lib/canvas/canvas_controller.dart:1226-1336). This is the highest data-integrity risk in this lens even though normal local writes are fast.

Root cause. Save durability is owned by the editor route, but Android can suspend/terminate the app without closing that route. Widget dispose is a teardown notification, not an awaitable shutdown barrier.

Analysis-only recommendation. Give the editor (or an app-level canvas session owner) a lifecycle observer and checkpoint on inactive/paused. Coalesce concurrent flushes, commit or explicitly cancel the active gesture according to a documented policy, and keep the existing guarded route close. Verify with a fake lifecycle transition and delayed repository writes; do not rely on dispose for durability.

HighN15-03 — One focus-restoration read failure permanently poisons starting a session for that app lifetime

Confidence: 98%.

  • lib/features/focus/application/active_session_controller.dart:116-117 stores a single Future.microtask(_restoreAtStartup) in _restoreFuture.
  • active_session_controller.dart:449-454 uses try/finally but no catch; it changes restoring state to “none” even when the database read throws, then leaves the future completed with that error.
  • Every start awaits that same future before doing anything: active_session_controller.dart:131-138.
  • focus_home_page.dart:50-59 will render “Start a focus session” after state becomes none, while focus_setup_page.dart:184-203 can only report a generic start failure; it cannot repair or replace the poisoned restore future.

Impact. A transient database-open/lock/migration/read error can make the UI advertise that a new session can start, but every attempt fails until the provider container/app is recreated. If a persisted session exists, the user also cannot safely replace it. This is a recoverability dead-end at exactly the moment lifecycle restoration is needed.

Root cause. Restoration outcome and restoration completion are conflated. The controller suppresses the visible restoring state in finally but preserves the error in the gating future, with no error state or retry transition.

Analysis-only recommendation. Model restoration as restoring / restored / failed(error). Catch the read error, expose a retry action, and replace the gate only when a new restoration attempt starts. A start request should either await a successful restore or show the restoration error; it should never present a usable start card backed by a permanently failed gate.

MediumN15-04 — Process recreation restores data records, not navigation context or unfinished text

Confidence: 99%.

  • lib/app.dart:35-42 creates MaterialApp.router without a restorationScopeId.
  • lib/config/router/app_router.dart:25-81 supplies no router, shell, or branch restoration scope IDs and always declares Library as the initial location.
  • A full production search found no RestorationMixin, RestorableProperty, restorationId, or restorable route push.
  • Important drafts live only in widget/controller memory: focus setup (focus_setup_controller.dart:122-208), review note (focus_review_page.dart:30-41), reflection answers (reflection_editor_page.dart:56-83), and template prompt controllers (template_editor_page.dart:33-75).

Impact. After Android process death or web reload, Zenno returns to Library rather than the last branch/screen. Unsaved review notes, reflection answers, template drafts, setup choices, search text, collapsed folders, branch back stacks, and modal ownership are gone. Persisted canvas/board rows remain safe, but the user's place in a thought process is not restored.

Root cause. StatefulShellRoute preserves state only in memory unless restoration is wired; most feature screens are anonymous imperative MaterialPageRoutes and therefore have no durable identity or serializable arguments.

Analysis-only recommendation. Define a narrow restoration contract before broad refactoring: selected branch, current durable screen and ID, canvas ID/viewport, active focus/review destination, and drafts that contain original user text. Give durable screens named/declarative routes and serializable arguments; use restoration IDs or explicit draft persistence for text. Do not attempt to serialize transient dialogs or in-flight destructive operations.

MediumN15-05 — Active focus restoration and ownership are lazy, despite being app-wide state

Confidence: 97%.

  • The initial route is Library: lib/config/router/app_router.dart:25-28.
  • All shell branches use the default lazy loading policy; none is marked for preload: app_router.dart:29-73.
  • activeSessionControllerProvider is watched only by Focus Home, Active, and Review screens; the root app and shell never read it. Relevant root/shell evidence: lib/app.dart:27-42 and lib/core/widgets/app_scaffold.dart:11-115.
  • The provider begins restoration only inside its build: active_session_controller.dart:94-117.
  • The controller documentation says a “global shell pill” renders its state (active_session_controller.dart:23-24), but no such shell consumer exists.

Impact. After restarting into Library, a persisted running session is not restored, checkpointed, or given its configured wakelock until the user first opens Focus. The wall-clock timer can catch up later, so elapsed time is not inherently corrupted, but active work is invisible and app-wide lifecycle behavior is delayed. While working in Library/Revision/Goals/Settings, there is also no shell-level timer/status affordance.

Root cause. An app-scoped session is technically keepAlive after creation, but screen-scoped consumers are the only creation trigger and the shell does not own the advertised global presentation.

Analysis-only recommendation. Eagerly initialize restoration from a small app bootstrap owner after the database is ready, and expose recoverable failure state. If the product intends cross-feature focus, add the documented lightweight shell pill/return action; otherwise remove the global claim and explicitly define Focus as tab-owned.

MediumN15-06 — Changing “keep screen on” during an active session does not update the live wakelock

Confidence: 96%.

  • Settings writes the preference reactively: lib/features/settings/presentation/pages/settings_page.dart:187-240.
  • The active controller reads settings only when a session starts or restores through _syncWakelockWithSettings: active_session_controller.dart:175-184, 436-445, and 477-484.
  • No listener watches appSettingsProvider or settings changes from the active-session owner.

Impact. Because branch switching during a session is supported, the user can open Settings and toggle this option. The control persists, but the current session continues with the old wakelock state until it ends/restarts. That can allow the tablet to sleep unexpectedly or keep it awake contrary to the new choice.

Root cause. Settings owns persistence and Focus owns the platform resource, but there is no live coordination channel between them.

Analysis-only recommendation. Have the app-scoped active-session owner listen to just keepScreenOnInFocus while a session exists and reconcile the wakelock on changes. Serialize toggles and keep the existing best-effort error handling so rapid setting changes cannot finish out of order.

MediumN15-07 — Linked-canvas arrival state is carried in an ephemeral route object

Confidence: 88%.

  • lib/canvas/canvas_editor_navigation.dart:89-103 pushes only /canvas/<id> in the URL and puts ViewportState in extra.
  • lib/canvas/canvas_editor_page.dart:311-319 reads the viewport only from that runtime object.
  • The GoRouter has no extraCodec or restoration configuration: lib/config/router/app_router.dart:25-81.

Impact. Normal in-process link following works, and applying the viewport later schedules persistence. However, immediate reload/process recreation/browser history restoration cannot reconstruct which pinned viewport the link intended from the route alone. The canvas may open at its last persisted camera instead of the linked thought location.

Root cause. Durable identity (canvas ID) is in the route; durable navigation intent (target camera) is an unserialized object.

Analysis-only recommendation. Encode a bookmark/link identifier or compact validated viewport parameters in serializable route state, then resolve against the repository after load. Prefer an ID over raw floating-point URL fields if links already have stable identity. Keep the existing “arrival wins after hydration” ordering.

MediumN15-08 — Unknown or stale locations have no Zenno-owned recovery route

Confidence: 95%.

  • The router defines five shell roots and one canvas route only: lib/config/router/app_router.dart:25-81.
  • There is no errorBuilder, errorPageBuilder, onException, redirect, or catch-all route.
  • A stale canvas ID is thoughtfully handled inside the editor (lib/canvas/canvas_editor_page.dart:502-536), but an unrecognized URL never reaches that recovery UI.

Impact. A malformed/stale web URL or future route rename falls through to framework-owned error presentation rather than a quiet Zenno screen with “Return to Library.” This is primarily a flow/recoverability issue, not a data-integrity issue.

Root cause. Route success paths are centralized, but route failure ownership is left to go_router.

Analysis-only recommendation. Add one minimal router error page that logs technical detail only in diagnostics and gives the user a safe Library action. Avoid automatic redirects that would hide a route bug or discard a recoverable stack.

LowN15-09 — Uncaught platform setup calls can prevent the first Flutter frame

Confidence: 90% for the control flow; 55% for practical occurrence on the Android target.

  • lib/main.dart:7-15 awaits immersive mode and preferred orientation before runApp, with no fallback or error boundary.
  • Database opening is lazy after runApp, so its failures can at least render provider error states; these two platform futures cannot.

Impact. An unsupported or failing platform-channel call can leave only the native launch surface and no actionable recovery UI. The configured Android target should normally support both calls, so severity is low.

Root cause. Non-essential window policy is a hard prerequisite for constructing the app.

Analysis-only recommendation. Keep orientation-before-first-frame if it prevents visible rotation, but catch/report platform setup failures and still call runApp. Treat immersive mode as best-effort. If orientation failure is considered fatal, show a native/Flutter error surface instead of hanging startup.

LowN15-10 — Installed web app declares portrait while Zenno initializes as landscape-only

Confidence: 99% that configuration conflicts; runtime enforcement varies by browser.

  • web/manifest.json:4-10 declares "orientation": "portrait-primary".
  • lib/main.dart:10-14 requests only landscapeLeft and landscapeRight.
  • The Android manifest is internally consistent with landscape at android/app/src/main/AndroidManifest.xml:7-16; the conflict is web/PWA-only, and README identifies Android as the real runtime target (README.md:3-5).

HighN15-11 — Failed focus transition writes leave memory and durable runtime describing different sessions

Confidence: 98% for divergence after a failed write; restart impact depends on interruption before a later successful retry.

  • Pause, resume, end-stretch, and skip-break mutate the engine and emit the new UI state before awaiting persistence: lib/features/focus/application/active_session_controller.dart:192-220.
  • Finish/abandon mutates the engine, stops the ticker, and emits the terminal snapshot before finishSession succeeds: active_session_controller.dart:264-303.
  • On write failure, the active page catches the exception and shows “Could not …” but does not restore the preceding engine state: lib/features/focus/presentation/pages/focus_active_page.dart:69-92, 119-167, 169-220.
  • The provider's shutdown callback stops the ticker and disables wakelock but does not checkpoint or retry runtime: active_session_controller.dart:103-117.
  • The existing failed-pause test expects the UI to have already switched from Pause to Resume while persistence is still pending/failing: test/focus_flow_safety_test.dart:70-109.

Impact. A failed Pause can leave memory paused while SQLite says running; a failed Resume can do the reverse. Most importantly, failed Finish/End early leaves the in-memory engine terminal with its ticker stopped while the row is still inProgress. If Zenno is then backgrounded/killed before a successful retry, restart reconstructs the stale durable state—potentially counting the entire downtime as focus or freezing time that was actually worked. The history can therefore misstate learning effort.

Root cause. Engine state is updated optimistically, but there is no rollback snapshot, durable “transition pending” state, or lifecycle flush. Error copy says the action failed while the visible state often shows that it succeeded.

Analysis-only recommendation. For these local SQLite transitions, prefer a simple durable-first boundary: compute the next runtime/final tally, persist it, then publish the new controller state. If optimistic UI is retained, snapshot and roll back the engine on failure and expose an explicit unsynced/retry state that blocks unsafe exit. Finish/abandon must not stop the only retry mechanism until the row close succeeds. Add delayed/failing repository tests followed by provider disposal and restoration.

HighN15-12 — Fire-and-forget repository cleanup can delete a newly imported canvas attachment

Confidence: 98% that the race is possible; occurrence requires an overlap between repository activation's enumeration and a user's file import.

  • Creating libraryRepositoryProvider launches cleanupOrphanedFiles() without awaiting it, then immediately returns the interactive repository: lib/features/library/application/library_providers.dart:16-24.
  • Despite its “singleton” comment, generated metadata marks this provider isAutoDispose: true, so cleanup is tied to provider activation and can run again after a period without listeners: lib/features/library/application/library_providers.g.dart:11-36.
  • Cleanup reads image, PDF, and thumbnail references once, then passes that frozen set to filesystem cleanup: lib/features/library/data/library_repository.dart:28-45.
  • The filesystem pass later enumerates every file under canvas_media and thumbnails and directly deletes anything absent from that old set; it performs no current database check before deletion: lib/features/library/data/library_file_cleanup_io.dart:29-59.
  • Image/PDF import copies the selected file directly into canvas_media before returning it to the controller: lib/canvas/io/canvas_import.dart:87-107, 115-132, 146-164.
  • Only after decoding/probing and placement does the controller enqueue the database upsert; that write is explicitly asynchronous: lib/canvas/canvas_controller.dart:945-961, 982-1017, 3891-3918, 3961-4015. Image/PDF reference rows are written inside the later element transaction at lib/canvas/persistence/canvas_repository.dart:338-376, 401-435.

Impact. If cleanup snapshots references, then an import creates its app-owned file before cleanup reaches that directory, cleanup can delete the file whether the subsequent element transaction is still pending or has already committed. The canvas can visibly accept an image/PDF and persist a row whose source path no longer exists. That is attachment data loss and a broken note after reload; an image may remain deceptively visible from its in-memory raster until the editor closes.

Root cause. The comment calls cleanup “safe to call at startup” because undo history is empty, but provider activation is not an exclusive phase: the cleanup future is detached and the UI becomes interactive. The reference snapshot, filesystem scan, file creation, and reference insertion have no shared serialization or atomic protocol. Auto-disposal also means “startup” is not a one-time invariant enforced by the provider.

Analysis-only recommendation. Use one repository-level media coordinator. The smallest safe design is to await orphan cleanup before allowing media import and, for defense in depth, re-query current references immediately before each deletion. A stronger design stages imports outside the owned live directory, commits the reference, then atomically promotes the file while cleanup ignores staged names. Add a deterministic test that pauses cleanup after its snapshot, completes an import/reference write, resumes cleanup, and asserts the file survives.

LowN15-13 — Reselecting the current tab requests a reset that imperative child routes do not perform

Confidence: 99% for the route reconciliation behavior in the locked go_router 17.2.3 / Flutter 3.41.6 versions.

  • The shell passes initialLocation: true precisely when the user selects the already-current branch: lib/core/widgets/app_scaffold.dart:44-48.
  • The five branch route tables contain only their root pages: lib/config/router/app_router.dart:29-74. Focus history/setup/active/review and Goal templates/reflections are instead pushed with raw Navigator.push(MaterialPageRoute); representative call sites are lib/features/focus/presentation/pages/focus_home_page.dart:62-118 and lib/features/goal_cycle/presentation/pages/templates_page.dart:40-126.
  • The repository locks go_router 17.2.3: pubspec.lock:419-426. Its goBranch(initialLocation: true) calls go for the same branch root. Flutter reuses the unchanged keyed root page and reattaches its associated pageless routes; only removing/replacing the owning page forces those pageless routes out.
  • No application-shell test exercises reselecting a branch while an imperative child screen or modal is present; the only shell test builds root placeholder pages: test/quiet_desk_design_test.dart:180-205.

Impact. Tapping Focus while already on Focus Setup/Active/Review, or Goals while inside Templates/Reflection, does not return to the tab root despite the explicit reset flag. This is a minor navigation predictability issue. The current behavior has an important safety benefit: it does not silently remove dirty drafts or bypass Active session abandonment rules.

Root cause. go_router can reset only the route matches it owns. Zenno's deeper branch screens live exclusively in the child Navigator's imperative history and are intentionally preserved when their owning declarative root page is reused.

Analysis-only recommendation. Decide the product contract explicitly. If reselect should preserve the current thinking context, pass initialLocation: false and remove the misleading reset intent. If reselect should return home, add a branch-level, asynchronous guarded-unwind coordinator that allows each dirty/busy owner to approve leaving; do not convert to an unconditional declarative reset. Cover clean, dirty, saving, and active-session stacks in an AppScaffold navigation test.

MediumN15-14 — An in-place /canvas/:id route update can reuse the editor state across different notes

Confidence: 99% for state reuse under go/route replacement; current in-app canvas entry points use unique-keyed push, which substantially limits present-day reachability.

  • The canvas route builds CanvasEditorPage without a widget key derived from id: lib/config/router/app_router.dart:75-80.
  • The locked go_router version is 17.2.3 (pubspec.lock:419-426). Dependency inspection shows normal route matches key pages by the matched path pattern, so both /canvas/a and /canvas/b use /canvas/:id; only imperative push wraps the match in a fresh unique key.
  • CanvasEditorPage constructs a late final controller once with the then-current ID: lib/canvas/canvas_editor_page.dart:98-129. The outer editor state has no didUpdateWidget handling for a changed canvasId.
  • After widget reuse, build-time ownership reads the new ID for the title (canvas_editor_page.dart:475-480, 649-654), inline rename writes widget.canvasId (702-768), and thumbnail generation writes widget.canvasId (217-236), while structural edits still flow through the old controller/repository ID.
  • Current internal navigation consistently funnels through openCanvasEditor, which calls context.push: lib/canvas/canvas_editor_navigation.dart:14-23, 58-103. Existing tests cover push/reuse stacks but not router.go or route-information replacement between two IDs: test/canvas_editor_navigation_test.dart:20-128.

Impact. If a same-route location update occurs, the screen can say canvas B and rename or thumbnail B while drawing, deleting, importing, and viewport writes still mutate canvas A. That violates note ownership and can place thinking in the wrong document. It is not reached by the current internal link/card actions, but it is a dangerous invariant for future redirects, restoration, browser route changes, or deep-link handling.

Root cause. Route identity is based on the path template while state identity is document-specific. The widget reads the live parameter in some paths, but the controller snapshots it once, creating split ownership when Flutter legitimately reuses the state.

Analysis-only recommendation. Make document identity explicit at the page/widget boundary with a key containing canvasId, and keep all supported internal transitions on the guarded openCanvasEditor path. Because declarative page replacement can bypass PopScope, also define how the old controller is flushed before allowing any go/replace-style canvas switch. A focused router test should load A, replace the location with B, edit, and prove that only B changes while A flushes cleanly.

Controls already protecting flow

  • Full-bleed canvas ownership is explicit. A root navigator key keeps /canvas/:id above the shell (lib/config/router/app_router.dart:13-17, 75-80).
  • Duplicate live canvas editors are actively coordinated. The static registry closes only current editors through their guarded path and reuses an existing route (lib/canvas/canvas_editor_navigation.dart:27-123); focused coverage exists in test/canvas_editor_navigation_test.dart:20-128.
  • Stale canvas routes do not recreate deleted notes. Existence is checked before hydration (lib/canvas/canvas_controller.dart:869-874) and a user-facing missing state is rendered.
  • Focus timing is wall-clock based. Background ticker throttling does not itself create drift, and phase overrun can traverse multiple Pomodoro boundaries (lib/features/focus/domain/timer_engine.dart:268-305, 433-460).
  • Focus setup waits for startup restoration. This prevents a fast start from orphaning an older persisted session when restoration succeeds (active_session_controller.dart:131-138), with evidence in test/active_session_controller_test.dart:140-199.
  • Dirty-screen back guards are broadly present. Ordinary Android back and modal-scrim maybePop paths are guarded; the remaining confirmed bypass is bottom-sheet drag dismissal.
