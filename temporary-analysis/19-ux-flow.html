Zenno repository analysis · analysis only

The canvas captures thought quickly. The rest of the system does not yet return it as quickly.

Zenno’s strongest path is “Library → New canvas → draw.” The editor also takes unsaved work seriously. The largest end-to-end weakness appears later, when a growing body of notes must be found, related, revisited, or converted into revision and goal work. Search stops at canvas and folder names, link activation is both tool- and input-device-dependent, and study artifacts live in separate boards and nested sheets. The interface therefore asks the user to remember where a thought was stored—the very memory burden a thinking tool should remove.

Critical findings supported
Core diagnosis. The information architecture is container-first while the learning workflow is idea-first. Canvas titles, folders, Kanban lanes, attached canvases, bookmarks, and canvas links each work locally, but there is no cross-surface retrieval layer. This is manageable with a small collection and increasingly costly as knowledge accumulates.

Method and scope

Static, read-only source analysis. No app, build, test, installation, dependency, Git-state, branch, remote, PR, or external-service action was run or changed. Conclusions distinguish behavior directly encoded in source from likely user impact inferred from interaction structure. Existing review documents were treated as historical context only; resolved claims were not carried forward.

Inspected tracked application code plus relevant repository documentation and untracked planning/review material. Primary code paths covered:

  • routing and responsive shell
  • Library, folders, cards, search and sorting
  • canvas editor, gestures, toolbar and persistence
  • text, image, PDF, links, bookmarks and navigation
  • Focus setup, active session, distractions and review
  • Revision and Goal Kanban flows
  • goal reflections and reusable templates
  • shared canvas attachments and pickers
  • settings and persisted interaction preferences
  • schemas/repositories supporting these journeys

Severity: High means likely to undermine a core learning journey or create serious recoverability risk; Medium means recurring friction or misleading state; Low means bounded polish/scaling friction. Confidence: High means directly visible in active code; Medium means behavior is supported but experiential impact is inferred without running the app.

Detailed findings

F1 · Retrieval searches containers, not knowledge

HighHigh confidence

Root cause. The Library computes search results from the already-loaded canvas list and folder names. It never queries canvas element text or any study records. Goal reflections are reachable only inside a goal detail sheet; Revision and Goal are horizontal boards without search or filter controls.

Flow impact. A learner who remembers an idea, phrase, reflection, or linked concept—but not its canvas title or folder—cannot retrieve it. Collection growth converts organization into a memory test and encourages overlong titles or duplicated canvases.

Data integrity. No stored data is corrupted, but practically undiscoverable knowledge behaves like lost knowledge.

Analysis-only recommendation. Define a single retrieval contract before implementing UI: which content is indexed, how results are grouped, and how a result navigates to an exact canvas element, goal/reflection, revision card, or focus record. Start with canvas title + text-note content + goal/revision/reflection text; expose scope and result type rather than silently searching only some stores.

Evidence
  • lib/features/library/presentation/pages/library_page.dart:328–365 filters only lowercased canvas titles and folder names.
  • lib/core/database/tables/canvas_tables.dart:275–290 stores typed canvas-note text separately, but Library does not read it.
  • lib/features/goal_cycle/presentation/widgets/goal_card_detail_sheet.dart:333–369 exposes reflections only inside one goal sheet.
  • lib/features/revision/presentation/pages/revision_board_page.dart:82–91 and lib/features/goal_cycle/presentation/pages/goal_board_page.dart:70–80 provide board/card actions but no search surface.

F2 · Permanent canvas deletion bypasses an already-present archive model

HighHigh confidence

Root cause. The visible card action confirms and then permanently deletes a canvas, its elements, and owned files. The repository already supports isArchived and archiveCanvas, and the main query hides archived canvases, but no active UI route calls archive or restores archived content.

Flow impact. Cleanup requires a high-stakes decision. Fear of deleting useful thought can produce clutter; one mistaken confirmation can destroy notes and media with no recovery path. The warning mentions content “on” the canvas but not cross-feature consequences: card attachments vanish and incoming links remain as visually normal but dangling references.

Data integrity. The confirmation is clear and focus-history links are detached safely, but the impact is irreversible after confirmation. Under Zenno’s “data integrity is absolute” rule, the missing recovery state is a high-priority gap.

Analysis-only recommendation. Make archive the ordinary removal action, add an Archived/Trash view with restore, and reserve permanent deletion for a secondary action with explicit retention semantics. Before permanent deletion, summarize attached study cards and incoming links that will be removed or broken. Decide whether owned files remain while archived before implementation.

Evidence
  • lib/features/library/presentation/widgets/canvas_card.dart:171–203 labels the operation permanent and calls deleteCanvas.
  • lib/features/library/data/library_repository.dart:47–70 hides archived canvases from the normal Library.
  • lib/features/library/data/library_repository.dart:180–185 implements archive, while repository-wide call-site search found no UI use.
  • lib/features/library/data/library_repository.dart:187–205 cascades database deletion and removes orphaned owned files.
  • lib/core/database/tables/board_tables.dart:89–116 cascades card attachment rows when a canvas is deleted.
  • lib/core/database/tables/canvas_tables.dart:249–252 intentionally preserves incoming links as soft, potentially dangling references.

F3 · Canvas links behave like tool operations, not universal reading affordances

HighHigh confidence

Root cause. A link opens only when Pan is active and the pointer follows the tool-gesture path. All touch pointers are routed to viewport/long-press-lasso handling and return before tool gestures are created; only stylus and mouse reach link hit-testing. The authoring dialog creates only whole-canvas targets even though the persistent model supports exact destination viewports. Its target control is an unsearchable dropdown and failed option loads are rendered as “No other canvases.” No active edit/retarget flow was found.

Flow impact. The natural reading gesture on a tablet—a finger tap—cannot open a visible connection. A stylus/mouse tap can draw, erase, select, or follow depending on the current tool. That is a combined input-device and mode error at the boundary between writing and reading. Large libraries also turn link creation into dropdown scanning, while a mistaken label or target appears to require deleting and recreating the link.

Data integrity. Links themselves persist safely. The risk is navigation ambiguity and false “empty library” feedback on load failure, not note corruption.

Analysis-only recommendation. Exploit the existing input separation: let a stationary single-finger tap on a link open it while finger drag continues to pan, independent of the active stylus tool. Define a movement threshold and test it against pinch and long-press lasso so navigation does not steal viewport gestures. Reuse a searchable canvas picker, distinguish error/empty/loading states, expose edit/retarget, and either ship region links or remove dormant region promises until their authoring journey is designed.

Evidence
  • lib/canvas/model/canvas_element.dart:638–734 defines exact destination viewport support and documents Pan-only tapping.
  • lib/canvas/canvas_editor_page.dart:403–420 follows a link only when the Pan tool callback is reached.
  • lib/canvas/render/canvas_view.dart:97–104, 296–328 routes touch pointers to viewport/long-press handling and returns before tool gestures are created.
  • lib/canvas/render/canvas_view.dart:337–365 routes only stylus and mouse through the active tool, where Pan can hit-test links.
  • lib/canvas/widgets/link_target_dialog.dart:91–112 always constructs LinkTarget(targetCanvasId: ...) without a viewport.
  • lib/canvas/widgets/link_target_dialog.dart:155–193 collapses absent/error data to an empty list and uses a dropdown without search.
  • Repository-wide source search found no active link update/retarget call site; only creation, persistence, navigation, import/export, and tests.

F4 · The persistent tool wheel is the loudest object on the thinking surface

MediumHigh confidence

Root cause. The editor always overlays a multi-page radial wheel, a 34-pixel side-action strip, and a palette. At normal widths the wheel alone is 187.2–211.2 logical pixels; the cluster also carries top-corner navigation, zoom, orientation, bookmarks, and save state. The wheel can move and its position persists, but there is no active collapse/hide state in the rendered control path. Meanwhile, the only in-editor explanation of pen long-press, two-finger undo and three-finger redo is itself an action inside the More → View wheel page.

Flow impact. The control that should disappear after tool selection remains a large focal object and occludes content. Nested tool/context/more/insert/appearance/view pages replace spatially stable, quiet access with mode memory, while the most space-efficient gestures require knowing where their hidden guide lives.

Data integrity. None. This is sustained attention and usable-canvas-area cost.

Analysis-only recommendation. Validate with the target tablet before redesign. Prefer a compact resting state that shows active tool/color and expands at the pointer or on stylus command, while keeping undo/save status independently visible. Preserve the movable position as an accessibility escape hatch.

Evidence
  • lib/canvas/widgets/canvas_toolbar.dart:16 applies a 1.2 wheel scale.
  • lib/canvas/widgets/canvas_toolbar.dart:176–264 maintains seven radial pages with context-dependent center behavior.
  • lib/canvas/widgets/canvas_toolbar.dart:314–388 computes a minimum 120-pixel wheel and preferred 187.2/211.2-pixel wheel plus palette/side controls.
  • lib/canvas/canvas_editor_page.dart:643–673 overlays the toolbar across the full canvas.
  • lib/canvas/widgets/canvas_toolbar.dart:749–807, 1199–1223 places the multi-touch/stylus guide inside the View wheel actions.
  • test/canvas_toolbar_test.dart:95–130 explicitly requires the wheel/palette to remain visible after drawing and confirms a 211.2-pixel tablet wheel. This test was read, not run.

F5 · Typed-note capture leaves the spatial context for a modal editor

MediumHigh confidence

Root cause. Tapping with the Text tool opens an AlertDialog containing a conventional text field; saving commits the text back at the tapped world point. Existing notes use the same modal. Saving an empty edit removes the element.

Flow impact. A thought that belongs at a specific visual location is composed in a detached dialog, hiding nearby strokes and references. The empty-save deletion behavior is not communicated in the dialog, so clearing text can unexpectedly become a delete gesture.

Data integrity. Empty removal is undoable through the canvas command stack, but its semantics are implicit.

Analysis-only recommendation. Prefer an in-place editor anchored to the note bounds, keeping surrounding content visible. If modal editing remains, state the empty-save behavior or disallow empty Save and offer an explicit Delete action.

Evidence
  • lib/canvas/canvas_editor_page.dart:349–395 opens a dialog for both create and edit.
  • lib/canvas/canvas_controller.dart:3703–3731 places a non-empty text element at the selected canvas point.
  • lib/canvas/canvas_controller.dart:3733–3747 interprets an empty edit as removeElements.

F6 · Focus setup repeats defaults before every session

MediumMedium confidence

Root cause. Starting a session presents a long scrolling form: ritual, study goal, energy, timer type, timer-specific values, target length, and working canvas. Settings already persist the timing and length defaults, yet the setup page gives each configuration block equal visual weight.

Flow impact. The user must configure focus before focusing. Repeated choices create activation energy precisely where the desired behavior is to begin work, and make the optional canvas link feel like another form field rather than the workspace.

Data integrity. None. Runtime persistence is strong once a session begins.

Analysis-only recommendation. Treat persisted defaults as a one-tap “Start” preset. Keep goal/canvas near the primary action, summarize timing in one compact row, and reveal ritual/timing customization progressively. Preserve explicit setup as an advanced path rather than removing it.

Evidence
  • lib/features/focus/presentation/pages/focus_setup_page.dart:68–159 renders every setup section before the Start button.
  • lib/features/settings/presentation/pages/settings_page.dart:187–243 already stores Focus rhythm and session-length defaults.
  • lib/features/focus/presentation/pages/focus_setup_page.dart:224–290 adds or creates a linked canvas as another dialog flow.

F7 · Break- and pause-time distractions are indistinguishable from work interruptions

MediumHigh confidence

Root cause. The Distraction action remains available regardless of whether the timer is working, paused, or on break. The saved row records wall-clock seconds into the session, kind, note and timestamp, but not timer phase/status or accumulated focus time. Later aggregates count every record as a session distraction.

Flow impact. Capturing remains fast, and “minutes into the session” is accurately encoded. But future “when do I drift?” analysis cannot tell a focus interruption from something intentionally noticed during a break or pause. Counts and attention-pattern conclusions can therefore mix meaningfully different events.

Data integrity. Records are structurally and temporally valid; the missing contextual dimension makes the analytic meaning ambiguous rather than the elapsed value incorrect.

Analysis-only recommendation. Decide whether break/pause capture is valuable. If yes, persist phase/status plus both session-wall and accumulated-focus elapsed values at capture; if no, disable or relabel the action outside work phases. Keep “into the session” for the current wall-clock field.

Evidence
  • lib/features/focus/presentation/pages/focus_active_page.dart:414–472 exposes Distraction without receiving or gating on timer phase/status.
  • lib/features/focus/application/active_session_controller.dart:222–249 saves wall time since session start; its focus-time comment is inconsistent with the implementation.
  • lib/core/database/tables/focus_tables.dart:105–116 stores timestamp, kind, note and seconds into session, but no phase/status/focus elapsed.
  • lib/features/focus/presentation/pages/focus_review_page.dart:392–403 accurately labels the field “into the session.”
  • lib/features/focus/application/focus_stats_provider.dart:32–52 counts all captured distractions without phase distinction.

F8 · Revision completion and next scheduling are separate mental transactions

LowHigh confidence

Intentional tradeoff. “Mark revised” only stamps time and increments a count, then closes the detail sheet. Revision lanes are explicitly manual; moving a card to its next interval is a separate board action. Repository planning documents confirm this is deliberate and explicitly prohibit automatic movement.

Flow impact. The most natural moment to schedule the next encounter is immediately after review, but the workflow ends before that decision. The user must remember which card was just reviewed and move it separately, creating stale scheduling state.

Data integrity. History remains correct, but board position can stop representing intended next review.

Analysis-only recommendation. Preserve manual scheduling unless the product decision is reopened. Validate whether users actually forget the follow-up movement. If so, prefer a non-automatic cue—keep the sheet open, briefly highlight the reviewed card, or offer an optional “Move next” action—rather than silently advancing it.

Evidence
  • lib/features/revision/presentation/widgets/revision_card_detail_sheet.dart:173–197 marks and immediately closes.
  • lib/features/revision/data/revision_repository.dart:258–276 changes only last-revised time and revision count.
  • lib/features/revision/presentation/pages/revision_board_page.dart:82–91 supplies a manual Kanban surface.
  • plan/revisionUIUX.md:4, 56 explicitly requires manual buckets and says Mark revised must not move a card.

F9 · Creating a study card is a modal followed by another editor

MediumHigh confidence

Root cause. The shared Kanban column first asks for title and optional notes in a “New card” dialog. Both Revision and Goals then open the newly created card’s full detail sheet immediately.

Flow impact. “Add topic” and “Add goal” feel like two consecutive forms, with the first fields repeated in the second. Quick capture is impossible without entering—and then dismissing—the heavier editor.

Data integrity. The card is persisted before the detail sheet opens, so dismissing the second stage does not lose the title/notes.

Analysis-only recommendation. Choose one capture contract: either create a minimal card inline and stop, with detail opened only on demand; or open the full editor first and persist once. The inline/minimal path best preserves rapid capture.

Evidence
  • lib/shared/kanban/kanban_column_view.dart:460–487 saves a draft and invokes onCardAdded.
  • lib/shared/kanban/kanban_column_view.dart:822–909 defines the initial title/notes dialog.
  • lib/features/revision/presentation/pages/revision_board_page.dart:88–90 opens detail for new topics.
  • lib/features/goal_cycle/presentation/pages/goal_board_page.dart:77–79 does the same for new goals.

F10 · Shared canvas pickers do not scale with the Library

MediumHigh confidence

Root cause. The attachment/Focus picker renders every canvas in a 280-pixel list without search, folder grouping, current-folder context, or already-attached filtering. Its recency label prints the raw DateTime. The link dialog independently implements a second, less capable dropdown picker.

Flow impact. Connecting a goal, revision topic, or focus session becomes a scanning task as the Library grows. Multiple selection patterns teach different behavior for the same “choose a canvas” job.

Data integrity. Existing duplicate attachment insertion is ignored in persistence, but the picker still permits selecting an attached canvas and provides no “already attached” feedback.

Analysis-only recommendation. Consolidate on one searchable, folder-aware canvas chooser with recent results, relative timestamps, exclusions/selected state, distinct error/empty/loading states, and create-new. Reuse it for links, focus and card attachments.

Evidence
  • lib/shared/canvas_attachments/canvas_picker_dialog.dart:64–114 combines create-new and an unfiltered list.
  • lib/shared/canvas_attachments/canvas_picker_dialog.dart:125–157 caps the list at 280 pixels and prints raw lastOpenedAt.
  • lib/shared/canvas_attachments/card_canvas_attachments_section.dart:70–98 attaches without excluding current attachments.
  • lib/shared/canvas_attachments/card_canvas_attachment_repository.dart:115–135 ignores duplicate inserts yet returns a newly generated ID, so the UI has no duplicate signal.
  • lib/canvas/widgets/link_target_dialog.dart:155–193 separately uses an unsearchable dropdown.

F11 · Missing or corrupt canvas media is visually indistinguishable from pending media

MediumHigh confidence

Root cause. Image decode and PDF rasterization failures are caught and discarded. The element remains in its placeholder state with no error marker, retry action, file location, or repair path.

Flow impact. A learner revisiting a visually anchored note cannot tell whether a document is loading, missing, unsupported, or corrupt. Silent failure interrupts comprehension and discourages trust in media-backed notes.

Data integrity. The element record remains, so metadata is not deleted. However, the source content may be unavailable without any visible diagnosis.

Analysis-only recommendation. Persist or derive a runtime load state and render a quiet, bounded error affordance inside the element with Retry and Locate/Replace Source. Never automatically remove the element on load failure.

Evidence
  • lib/canvas/canvas_controller.dart:4262–4317 returns silently when image decoding fails and explicitly leaves the placeholder.
  • lib/canvas/canvas_controller.dart:4320–4341 silently returns for PDF service errors or null results.

F12 · Settings writes mostly fail silently

LowHigh confidence

Root cause. Settings controls call repository futures directly from synchronous callbacks without awaiting or handling failure. The tool-wheel position is a notable exception: it catches errors and shows retry guidance.

Flow impact. A control can snap back only when the reactive database stream fails to change, with no explanation. This is especially confusing for stylus behavior and Focus defaults because the failure may only be noticed in a later workflow.

Data integrity. Failed preferences are not mis-stored, but user intent can be lost silently.

Analysis-only recommendation. Apply the existing tool-wheel error pattern through one small settings action helper: await, show neutral failure copy, and retain/revert visible state consistently. Avoid exposing raw database errors.

Evidence
  • lib/features/settings/presentation/pages/settings_page.dart:112–113, 128–182, 200–240, 271–272 invokes write futures without handling them.
  • lib/features/settings/data/settings_repository.dart:200–290 confirms these methods return Future<void>.
  • lib/canvas/widgets/canvas_toolbar.dart:222–245 shows the stronger caught-error pattern for wheel position.

F13 · Folder visibility state resets with the page

LowHigh confidence

Root cause. Collapsed folder identifiers live only in the Library page state. Search intentionally expands every matching group, but there is no persisted or restorable collapse preference.

Flow impact. A carefully reduced Library expands again after page recreation, so visual clutter returns and spatial scanning must be repeated.

Data integrity. None.

Analysis-only recommendation. First decide whether collapse state is a durable preference or session state. Persist only if real use shows repeated re-collapsing; otherwise keep the implementation simple.

Evidence
  • lib/features/library/presentation/pages/library_page.dart:44–73 keeps collapsed IDs in widget state.

F14 · Web Library cards lose visual recognition

LowHigh confidence

Root cause. The card thumbnail widget always renders its generic placeholder on web, even when a thumbnail path exists.

Flow impact. Visual thinkers cannot use sketch shape/color as a recognition cue in the web version and must rely on titles and folders—the same metadata already limiting search.

Data integrity. None; this is representation only.

Analysis-only recommendation. If web is a supported daily surface, produce browser-readable thumbnails (blob/IndexedDB bytes or generated data) and retain the placeholder only for absent/failed previews. If web is only a development target, document that constraint and keep this low priority.

F15 · Painted canvas knowledge is absent from the semantic and keyboard navigation model

MediumHigh confidence

Root cause. Canvas content is rendered as stacked CustomPaint layers inside a raw pointer listener. The toolbar has semantics, and the page has command shortcuts, but text notes, link chips, images and PDFs do not become focusable semantic children. Keyboard commands can act on an existing selection but cannot traverse painted elements to create that selection.

Flow impact. Screen-reader and keyboard-only retrieval stops at the toolbar. Even non-assistive desktop use remains pointer-dependent for finding and opening a link or text note. The knowledge is visually present but structurally invisible.

Data integrity. None; access to stored information is constrained.

Analysis-only recommendation. Add a viewport-aware semantic overlay for meaningful object elements first: text-note label/body, link label and open action, image/PDF label, selection state, and ordered keyboard traversal. Do not attempt to narrate every ink point; offer a concise canvas summary and object list for freehand-heavy canvases.

Evidence
  • lib/canvas/render/canvas_view.dart:1455–1552 renders grid, committed elements, live ink and overlays entirely through CustomPaint under Listener.
  • Repository-wide canvas source search finds semantics on toolbar controls but none representing rendered CanvasElement objects.
  • lib/canvas/canvas_editor_page.dart:550–623 defines undo, selection transforms and tool shortcuts, but no next/previous element traversal or open-selected-link action.

F16 · Partial element corruption is silent, and later retry can erase its remaining recovery evidence

HighHigh confidence

Root cause. Each canvas element has a generic envelope row plus a kind-specific detail row. Loading silently skips an envelope when its detail row is absent. The controller therefore believes the skipped element does not exist. If any later asynchronous canvas write fails and the user invokes retry, full-state synchronization treats every stored envelope absent from controller memory as stale and deletes it.

Flow impact. A partially damaged note can open with unexplained missing content. The user receives no warning to stop editing or make a backup; an otherwise sensible Retry can remove the surviving envelope that could help diagnose or recover the item.

Data integrity. High impact, but likely low frequency. Normal element writes are transactional, and this analysis found no evidence that partial corruption is currently occurring. The finding is about fail-safe behavior once an inconsistent database exists.

Analysis-only recommendation. Do not silently discard. Return load diagnostics alongside reconstructed elements, block destructive full-state reconciliation for unknown rows, and show a quiet “some content could not be loaded” state with export/backup guidance. Preserve raw rows for recovery; never auto-delete them as stale unless their absence was an intentional user edit.

Evidence
  • lib/canvas/persistence/canvas_repository.dart:77–82 explicitly says a missing detail row is skipped rather than failing load.
  • lib/canvas/persistence/canvas_repository.dart:177–191 omits every reconstruction that returns null.
  • lib/canvas/persistence/canvas_repository.dart:195–300 returns null for missing stroke, image, PDF, link, text or shape detail.
  • lib/canvas/canvas_controller.dart:1059–1090 retries failures by synchronizing the controller’s complete current snapshot.
  • lib/canvas/persistence/canvas_repository.dart:554–591 deletes stored element IDs not present in that snapshot.

F17 · Focus review offers a “Discard” contract that does not cover ritual edits made on the same screen

MediumHigh confidence

Root cause. The review page is treated as one unsaved form on every back attempt, even when untouched. Its energy and note are held until “Save & finish,” but ritual rename/add/retire actions write immediately to the repository. Back then shows the shared promise “You have unsaved changes. If you leave now, they will be lost.” Choosing Discard completes the session without review fields; it does not undo ritual changes.

Flow impact. The end-of-session screen mixes reflection with maintenance and gives two different persistence models one visual boundary. A user can reasonably believe a renamed or retired ritual item will be reverted, then meet the changed ritual next session. Back also demands a destructive-sounding confirmation when no review field was changed.

Data integrity. Historical ritual snapshots are preserved, so this does not corrupt past sessions. It violates current user intent through misleading persistence feedback.

Analysis-only recommendation. Move ritual maintenance out of the review transaction or label it as saved immediately. Track actual review dirtiness; when untouched, offer “Skip review” without claiming changes will be lost. If ritual maintenance remains inline, use a confirmation that explicitly lists what will be discarded and what was already saved.

Evidence
  • lib/features/focus/presentation/pages/focus_review_page.dart:52–56 blocks every back attempt regardless of actual dirty state.
  • lib/features/focus/presentation/pages/focus_review_page.dart:99–159 writes ritual edit/retire/add actions through RitualRepository while still inside review.
  • lib/core/widgets/app_dialog.dart:26–61 promises that unsaved changes will be lost on Discard.
  • lib/features/focus/presentation/pages/focus_review_page.dart:258–282 Discard only calls the session controller.
  • lib/features/focus/data/focus_repository.dart:268–275 completes the pending session without review fields; it does not revert ritual records.

F18 · Connections have neither a destination-side backlink surface nor visible health

MediumHigh confidence

Root cause. Link rows are deliberately queryable by target and documented as enabling backlinks/graphs, but active source only loads links as elements of their source canvas. The destination has no incoming-link list. Link rendering always uses the same gold chip and chain glyph; target existence is queried only after a Pan-tool tap.

Flow impact. A connection is recoverable only from the canvas where it was authored. On arrival, the reader cannot see “what led here” or discover related source contexts. If a target was deleted, the source still looks healthy until the user switches tool and activates it.

Data integrity. The soft reference intentionally preserves dangling links rather than cascading deletion, which is the safer storage choice. The missing piece is honest representation and reverse navigation.

Analysis-only recommendation. Start with a quiet per-canvas “Linked from” panel rather than a global graph. Query source title, link label and optional source viewport; make each backlink navigable. Resolve target health on load or in the background and render a subtle broken state without deleting the link.

Evidence
  • lib/core/database/tables/canvas_tables.dart:236–252 describes backlink/graph queries and stores a soft target reference.
  • Repository-wide active source search found no query or UI for incoming CanvasLinks.targetCanvasId.
  • lib/canvas/render/elements_painter.dart:754–836 paints a uniform gold chain chip from label data only.
  • lib/canvas/canvas_editor_page.dart:403–419 checks target existence only during follow and then shows a snackbar.

F19 · Zenno can export a picture of thought, but not a complete editable backup of it

HighHigh confidence

Root cause. The user-facing export path produces PNG, JPG or SVG for one canvas. No Library or Settings flow exports/restores the database, goals, reflections, revision cards, focus history, settings, bookmarks, attachments and owned media as a coherent bundle. A versioned ZennoDocumentCodec exists, but active application code does not call it; it omits bookmarks and serializes image/PDF source paths rather than packaging their bytes.

Flow impact. Export supports presentation, not continuity. The sole user cannot confidently migrate devices, make a portable backup, restore after storage failure, or move an editable canvas elsewhere. A visual file preserves appearance while discarding layers, object behavior, connections and study-system context.

Data integrity. No current record is damaged, but there is no in-app recovery boundary around the local database and app-owned files. That makes device/app storage the practical single point of failure.

Analysis-only recommendation. Define and test a versioned backup bundle that contains the database plus every referenced app-owned media file and a manifest/checksum. Restore into a validation/staging transaction before replacing current state; never partially import over live notes. Keep visual export as a separate “Share image” job. Decide whether a single-canvas editable package is also useful, but do not mistake it for whole-library backup.

Evidence
  • lib/canvas/io/canvas_export.dart:63–95 limits user-facing export to content/viewport/selection and PNG/JPG/SVG.
  • lib/canvas/widgets/canvas_toolbar.dart:1960–2025 writes a rendered file and reports its path; it does not create or restore an editable package.
  • lib/canvas/io/zenno_document.dart:13–83 defines a versioned editable canvas codec.
  • Active lib/ call-site search finds no use of ZennoDocumentCodec outside its definition; usage is test-only.
  • lib/canvas/io/zenno_document.dart:191–225 stores image/PDF paths, link/text data and object geometry but no media bytes or bookmarks.
  • Repository-wide application source search finds no whole-database backup/restore flow.

F20 · Focus history eagerly loads rich evidence, then shows only its count

MediumHigh confidence

Root cause. Every history emission resolves distractions and ritual-check snapshots for every session through two sequential child queries per session. The History card then uses only distraction count and ignores ritual snapshots entirely. Individual notes, kinds and elapsed times are visible during the one-time Review screen but have no later detail surface.

Flow impact. Zenno asks the user to capture why and when focus broke, then removes that context from retrospective learning. “When do I drift?” cannot be answered from History even though the rows are already loaded. As sessions accumulate, the page also pays a 1 + 2N query pattern and eagerly builds all session cards without exposing the data that caused the work.

Data integrity. The evidence remains stored; the failure is retrieval and eventual history performance, not loss.

Analysis-only recommendation. Keep the default card quiet, but let a session expand into distraction note/kind/timing and ritual completion. Fetch or batch child data when expanded rather than sequentially loading every child list for every card. Add one modest pattern view only after F7’s elapsed-time semantics are corrected.

Evidence
  • lib/features/focus/data/focus_repository.dart:7–25 defines History detail with full distractions and ritual snapshots.
  • lib/features/focus/data/focus_repository.dart:374–399 issues child reads inside a loop for every session.
  • lib/features/focus/presentation/pages/focus_history_page.dart:186–284 displays session summary, notes, linked canvas and distraction count only.
  • History source contains no use of detail.ritualChecks and no rendering of distraction note, kind or elapsed time.
  • lib/features/focus/presentation/pages/focus_review_page.dart:349–417 proves those distraction details exist only in immediate review UI.

F21 · Reusing a bookmark name silently replaces the saved place

LowHigh confidence

Root cause. The bookmark dialog accepts any non-empty name and hands it directly to the controller. Exact-name matches are deliberately implemented as upserts: the old viewport is replaced in memory and persistence. The UI neither indicates that the name already exists nor confirms whether a new place was added or an old one was moved.

Flow impact. A repeated generic name such as “Overview” can quietly destroy the only navigation cue back to an earlier region. The learner notices only later, when choosing the bookmark lands somewhere unexpected.

Data integrity. Canvas content is untouched, but a persisted user-authored orientation aid is irreversibly overwritten without an explicit replacement decision.

Analysis-only recommendation. Detect an existing name in the dialog and present “Replace saved view?” before commit, or expose explicit update/rename actions beside each bookmark. A lightweight “Bookmark saved” / “Bookmark updated” confirmation would make the state transition visible.

Evidence
  • lib/canvas/widgets/canvas_bookmarks_menu.dart:89–98 forwards the entered name without collision handling or feedback.
  • lib/canvas/widgets/canvas_bookmarks_menu.dart:109–159 validates only non-empty text; it has no access to or warning about existing names.
  • lib/canvas/canvas_controller.dart:3817–3844 replaces an exact-name bookmark and persists it via upsert.

F22 · A failed Focus restore becomes an apparent empty state with no retry path

MediumHigh confidence

Root cause. The active-session state models restoring, active and none, but not restore failure. Startup assigns one restoration future; _restoreAtStartup has a finally that changes restoring to none but no catch/retry. startFrom later awaits that same future before it can create a session.

Flow impact. If the restore read throws, Home replaces “Restoring…” with the ordinary “Start a focus session” card even if an in-progress row remains. Entering Setup and pressing Start then repeatedly produces a generic start failure because the cached restore future is still failed. The user cannot resume, retry, or understand that stored session state is blocking the path.

Data integrity. The session row is not deleted by this path, which is good. The risk is temporary inaccessibility and misleading empty state; repeated restarts are the only implicit retry visible in source.

Analysis-only recommendation. Add an explicit restoration-error state that keeps Start blocked and offers Retry plus a non-destructive diagnostic message. On retry, create a fresh restore future. Never offer “discard stored session” until its row can be read and the consequence is explicit.

Evidence
  • lib/features/focus/application/active_session_controller.dart:29–78 defines no error variant or error payload in ActiveSessionState.
  • lib/features/focus/application/active_session_controller.dart:106–117 starts one restoration future during provider build.
  • lib/features/focus/application/active_session_controller.dart:134–137 awaits that same future before every start.
  • lib/features/focus/application/active_session_controller.dart:406–454 lets restore errors escape while finally converts restoring to none.
  • lib/features/focus/presentation/pages/focus_home_page.dart:45–62 interprets that none state as the normal Start card.
  • lib/features/focus/presentation/pages/focus_setup_page.dart:166–204 catches the later failed await only as generic “Could not start.”

F23 · “Last edited” also means panned, zoomed, or changed tools

LowHigh confidence

Root cause. Library’s Recent sort and card subtitle both use canvases.updatedAt. Content writes bump that field, but so do saving the viewport, rotation-lock state and active pen/tool settings. A separate lastOpenedAt is recorded when a Library card opens, yet it is not used by the visible sort/subtitle.

Flow impact. Browsing a canvas, panning to inspect it, or changing a tool can move it to the top as “Edited” even when no note content changed. This weakens the list as an answer to “what did I actually revise?” and makes recency order less predictable.

Data integrity. No data is lost; the timestamp’s meaning is overloaded and the user-facing label is more specific than the stored event semantics.

Analysis-only recommendation. Decide which job the default sort serves. If it is resumption, sort/label by “Recently used” and intentionally combine open/interaction time. If it is content change, add a content-modified timestamp that excludes viewport and preference writes. Avoid presenting one overloaded timestamp as “Edited.”

Evidence
  • lib/features/library/data/library_repository.dart:38–63 defines Recent as descending updatedAt.
  • lib/features/library/presentation/widgets/canvas_card.dart:235–250 labels the same field “Edited.”
  • lib/canvas/persistence/canvas_repository.dart:915–949 bumps updatedAt for tool settings, viewport and rotation-lock state.
  • lib/features/library/data/library_repository.dart:255–260 maintains a distinct lastOpenedAt that the visible Recent sort does not use.

Flow strengths worth preserving

  • Fast blank-canvas entry: library_page.dart:82–103 creates and immediately opens a canvas without a naming gate.
  • Quiet full-screen editor: the canvas route sits outside the shell and gets the entire viewport.
  • Navigation continuity: canvas links push a chain and reuse an existing live editor where possible, preserving the return path.
  • Finger/stylus separation: fingers default to viewport movement while stylus/mouse follow the active tool, reducing accidental ink during navigation.
  • Write transparency: the toolbar exposes unsaved state; close handling does not pretend failed writes succeeded.
  • Focused distraction capture: the sheet is intentionally short and supports a one-tap kind capture.
  • Dirty-form guards: Revision and Goal editors protect in-progress changes on destructive or competing actions.
  • Accessible Kanban fallback: card move menus allow cross-lane movement even when drag targets are offscreen.
  • Folder deletion safety: deleting a folder unfiles canvases transactionally rather than deleting their content.

Product decisions to make before implementation

  1. Is Zenno’s primary retrieval unit a canvas, an idea inside a canvas, or any learning artifact? Search architecture depends on this answer.
  2. Should canvas removal default to Archive, and what retention/recovery window should apply to permanent deletion and owned media?
  3. Should a stationary single-finger tap open a link while finger drag remains pan, or should links expose a separate open handle?
  4. Should “Mark revised” schedule the next encounter automatically, prompt for a lane, or remain retrospective only?
  5. Is web a production note-taking surface? If not, web-only visual limitations should be documented rather than prioritized over tablet flow.
  6. Should Focus optimize for immediate entry with defaults, or is the pre-study ritual itself a required part of the intended practice?
