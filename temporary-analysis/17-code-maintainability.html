Executive summary

Zenno has strong feature coverage and many thoughtful local safeguards, but those safeguards increasingly compensate for boundaries that no longer match the product. The largest maintainability risk is not file length alone: note safety and interaction correctness depend on callers coordinating several oversized, duplicated representations by hand.

Findings

01. Database foreign keys encode destructive ownership that repositories must manually undo

CriticalHigh confidence

Evidence. lib/core/database/tables/canvas_tables.dart:29-33 declares nullable Canvases.folderId with onDelete: cascade, while lib/features/library/data/library_repository.dart:158-170 explicitly nulls every canvas folder reference before deleting a folder so canvases survive. Likewise, lib/core/database/tables/focus_tables.dart:74-78 makes FocusSessions.linkedCanvasId cascade, while library_repository.dart:187-199 explicitly detaches focus history before deleting a canvas. This is emitted into the current generated schema as ON DELETE CASCADE for both nullable columns (test/generated_migrations/schema_v13.dart:133-138,1721-1726). Preservation tests call only the compensating repository APIs (library_repository_test.dart:89-126); there is no direct-parent-delete assertion for these two optional relations.

Root cause. The schema says “owned child,” but product behavior says “optional association.” Safety is therefore an orchestration convention instead of a database invariant.

Flow/data impact. Any future delete path, maintenance script, direct DAO, migration, or test helper that bypasses these exact repository methods can delete canvases (notes) with a folder or delete focus history with a canvas. This conflicts directly with the project’s absolute data-integrity rule.

Analysis-only recommendation. Plan a schema migration to SET NULL for both optional relationships, preserve the repository detachment as defense in depth, and add migration/foreign-key tests that delete the parent directly and prove notes/history survive.

02. CanvasController is a 4,528-line orchestration monolith

HighHigh confidence

Evidence. lib/canvas/canvas_controller.dart:179-4519 combines element storage/spatial indexing, layers, persistence retries and batching, undo/redo, stroke capture, viewport, tool presets, erasing, hit testing, selection, transforms, shape creation, links/text/bookmarks, file import, raster scheduling, memory budgeting, and disposal. Static outlining found approximately 100 state fields and 150 methods. It imports 19 internal modules, the highest fan-out in the repository.

Root cause. The original controller grew by absorbing each new canvas capability while retaining direct knowledge of persistence, input-adjacent policy, geometry, and runtime media caches.

Flow/data impact. A local edit can disturb save ordering, undo semantics, selection, or raster lifecycle. The project lesson in AGENTS.md:40 already records a layer-stamping state split—exactly the kind of cross-responsibility failure this shape amplifies.

Analysis-only recommendation. Split along boundaries already present in the code: durable document store/persistence coordinator, command history, selection/transform session, tool state, and raster/import manager. Keep one small façade for the UI so interaction call sites remain simple. Extract one responsibility at a time behind characterization tests; do not rewrite the canvas wholesale in one step.

03. Durable meanings are stored as enum ordinals and magic integers

HighHigh confidence

Evidence. Drift tables use intEnum for element, stroke, link, layer, background, board, mastery, focus status/kind, distraction, theme, and sort values (lib/core/database/tables/canvas_tables.dart:47-63,90-91,146,182,246; board_tables.dart:13,70; focus_tables.dart:51,62,112; settings_tables.dart:16-17,44-45). Timer runtime state is stored explicitly as enum.index in focus_repository.dart:101-102,209-210. Canvas persistence does the same for arrow body/head styles and pen width mode (canvas_repository.dart:480-482,1161-1177). ShapeElement.shapeKind is only an int “Index of ShapeKind” (canvas_element.dart:106-107); render and export switch on 0..3 (shape_painter.dart:21-31, canvas_export.dart:759-780).

Root cause. In-memory declaration order doubles as a storage protocol, and one domain enum lives in the controller rather than the model. There is no stable persisted code separate from source order.

Flow/data impact. Reordering or inserting an enum value can silently reinterpret saved notes, shapes, focus sessions, or settings. Compiler exhaustiveness cannot detect that old integer 1 changed meaning. The central ShapeKind comment is also stale: canvas_controller.dart:73-77 claims shapes become InkElements, but current code creates ShapeElements.

Analysis-only recommendation. Define stable serialized codes/converters in domain types, put ShapeKind beside ShapeElement, and migrate incrementally. At minimum, document append-only ordinal contracts and add explicit tests pinning every persisted numeric value before further enum growth.

19. Focus runtime checkpoints can overlap because the periodic callback is reentrant

MediumMedium confidence

Evidence. Timer.periodic invokes the asynchronous _onTick() without awaiting or retaining its future (active_session_controller.dart:344-347). Once the counter reaches 15, it is reset only after _persistRuntime() completes (:357-370,391-404), so a write taking longer than one second allows every subsequent tick to enter another checkpoint. stop() cancels future ticks but does not track or await already-started checkpoints before its final finishSession write (:275-303). The safety test suite can gate a runtime write but exercises that mechanism for an explicit Pause operation, not a background tick racing a lifecycle transition (test/focus_flow_safety_test.dart:70-109,370-415).

Root cause. A UI repaint timer also owns durable checkpoint scheduling, but there is no single-flight future, lifecycle generation token, or repository-side status guard.

Flow/data impact. Reentrancy and redundant writes are certain under a sufficiently slow checkpoint. Whether a stale checkpoint can finish after the closing write depends on executor scheduling, so static analysis does not prove corruption in the current Drift implementation; if ordering changes or the repository is wrapped, an older tally could overwrite the final focus totals. Even without reordering, repeated writes create avoidable I/O during focused work.

Analysis-only recommendation. Separate repaint ticks from a serialized checkpoint loop. Keep at most one checkpoint in flight, coalesce pending demand, and make stop/discard coordinate with it. Add a controllable-repository test that blocks a background checkpoint, finishes the session, then releases the write and proves the final status/tallies remain authoritative.

22. The seed routine’s recovery path is not actually idempotent over existing user state

MediumHigh confidence

Evidence. seedDatabase returns only when the singleton row exists with dbSchemaSeeded == true; otherwise it starts a broad transaction (seed_data.dart:24-38). It then insertOrReplaces a default AppSettingsCompanion (:39-45), which replaces all editable values stored in that row, and replaces all fixed-id builtin templates (:80-145). It creates new random ids for both boards and every starter column on each run (:148-179), even though Boards has no uniqueness constraint on boardType (board_tables.dart:10-18). The settings feature writes user preferences into the same singleton (settings_repository.dart:176-197,286-290). Tests cover a clean seed and normal version migrations but do not cover an existing database whose marker is false while settings, boards/cards, or reflection entries already exist (database_test.dart:85-99,551-569).

Root cause. One global completion flag gates several independently seeded aggregates, while “recovery” mixes replacement, fixed-id replacement, and random-id insertion rather than converging each aggregate safely.

Flow/data impact. If the marker is ever false on a non-empty database, reopening can reset theme, palette, focus defaults, library sort, and wheel position; add duplicate boards/columns; or fail when replacing a builtin template that an ON DELETE RESTRICT reflection row references. The initial all-in-one transaction reduces normal crash exposure, but the code explicitly claims to handle partial prior seeds, making this edge path part of its contract.

Analysis-only recommendation. Make each seed operation convergent: insert the settings row only if absent and never replace user columns; give builtin boards/columns stable identities or enforce/type-upsert uniqueness; update builtin template content without delete-and-reinsert semantics; and set independent seed/version markers only after success. Add recovery tests with customized settings, populated cards, and saved reflections while the seed marker is false.

Root cause. A planned portable/native canvas format was implemented at the codec/test layer before its product lifecycle and media ownership semantics were defined.

Flow/data impact. Every new element or layer capability now has another serialization switch to maintain even though users cannot exercise it. If later wired directly, it preserves source canvasId/layerId values and absolute image/PDF paths rather than defining destination remapping or bundling media (zenno_document.dart:128-157,191-216,274-330), so “document import” could be mistaken for a portable backup when it is not.

Analysis-only recommendation. Make an explicit product decision. If native backup/import is intended, first define a package manifest, media bundling, id/layer remapping, conflict policy, and version migrations, then wire and test the full workflow. If it is not intended, remove the dormant codec in a dedicated authorized task so it stops expanding the element dispatch matrix.

24. Shell destinations and router branches are coupled by an undocumented list index

LowHigh confidence

Evidence. The five StatefulShellBranchs are declared in Library/Focus/Revision/Goals/Settings order in app_router.dart:29-73. A separate private _items list repeats labels/icons in the same order (app_scaffold.dart:16-42), and selection passes the item index directly to navigationShell.goBranch (:44-48). The responsive shell test constructs a third ordered path list (quiet_desk_design_test.dart:180-203) but asserts only rail/bar layout (:52-79), not label-to-route behavior.

Root cause. Destination identity is positional rather than a shared named value; routing and presentation cannot reference the same source of truth.

Flow/data impact. Inserting or reordering a branch or visual item independently still compiles and renders, but a user tapping “Focus” can land on another retained branch. The bug is easy to introduce during navigation work and hard to spot in a layout-only test.

Analysis-only recommendation. Introduce a small AppDestination definition/enum owning route identity, label, and icons, or at minimum named indices plus a parity assertion. Add one interaction test that taps every rail/bar destination and verifies the corresponding route/page.

25. Destructive orphan-file cleanup is tied to an auto-disposed provider lifecycle

HighMedium confidence

Evidence. LibraryRepository.cleanupOrphanedFiles explicitly says it is safe “at startup, when in-memory undo history is empty,” then builds its live-path set solely from current database image, PDF, and thumbnail rows (library_repository.dart:28-45). libraryRepository launches that cleanup unawaited every time the provider is constructed (library_providers.dart:15-24), while generated code marks the provider isAutoDispose: true (library_providers.g.dart:18-36). Cleanup walks the app-owned media/thumbnail directories and deletes every file missing from that database snapshot (library_file_cleanup_io.dart:29-59). Meanwhile, erasing an image/PDF hard-deletes its database element/detail rows (canvas_repository.dart:494-527) but deliberately keeps the full element—including its source path—in an undo command (canvas_commands.dart:85-120), so Undo can reinsert it.

Root cause. A one-time application lifecycle operation is hidden inside construction of a reusable data provider. The file collector knows only durable rows, while undo/import ownership also lives in active controller memory.

Flow/data impact. Normal initial construction is likely early enough to be safe, which is why confidence in a current user-visible trigger is medium. But any disposal/recreation or explicit invalidation while editing can delete the only app-owned image/PDF file after an erase and before Undo, or after a copied import and before its row commits. Undo would restore a broken media element rather than the note content. Future provider-lifetime refactors can activate this loss path without touching cleanup code.

Analysis-only recommendation. Move orphan cleanup to an explicit, awaitable startup coordinator that runs once before any editor/controller can own transient media; keep repository provider construction side-effect free. If cleanup must run later, include active undo/import leases in the ownership set. Add a filesystem-backed lifecycle test: erase media, force the repository provider to recreate, undo, and prove the backing file and rendered element survive.

26. Library streams add a second initial read on top of Drift’s native watch contract

LowHigh confidence

Evidence. Both watchCanvases and watchFolders route through _watchWithInitialRead (library_repository.dart:51-70,104-108). That helper first executes query.get() and then subscribes to query.watch() (:272-275). Drift’s watched select already fetches and emits a snapshot when its first listener subscribes (drift-2.31.0/lib/src/runtime/query_builder/statements/select/select.dart:68-76; src/runtime/executor/stream_queries.dart:260-284,328-359). Zenno’s other repositories use watch() directly, including Goal and Revision boards (goal_repository.dart:100; revision_repository.dart:90).

Root cause. The wrapper defensively reimplements an initialization guarantee already owned by the database library, creating a unique local stream contract without documenting why.

Flow/data impact. A normal subscription performs two initial queries and emits two list objects, triggering redundant provider/UI work even when the rows are identical. If data changes between calls, the watched snapshot still catches the latest state, so this is not being reported as a lost-update bug.

Analysis-only recommendation. Use query.watch() directly and keep initial-emission behavior at the Drift boundary. Add a narrow stream test only if the UI depends on first-emission timing; avoid a custom helper whose name implies functionality Drift already supplies.
