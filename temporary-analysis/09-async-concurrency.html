Executive summary

Highest-risk result: startup-style orphan cleanup is not actually isolated to startup and can delete a freshly imported image or PDF in the interval between filesystem copy and the database element write. This can leave a durable canvas element pointing at a deleted asset.

The focus subsystem has a separate durability problem: timer mutations are applied to the live engine before their database writes succeed. Failed pause, phase-change, finish, or abandon writes therefore leave the UI and restart state describing different sessions. The timer math itself is wall-clock based and robust; the weakness is commit ordering.

Rapid interaction also exposes stale-snapshot updates in composite settings, fractional Kanban positions, template/folder/attachment/ritual append positions, and the revision counter. These are mostly flow/ordering defects rather than note-text loss, but the cleanup race directly threatens imported note assets.

A09-001 — Orphan cleanup races media import and can break durable canvas assets

CriticalDefect confidence: HighNatural reachability: MediumData integrity

Evidence. The repository provider starts cleanup without awaiting it when constructed (lib/features/library/application/library_providers.dart:16-24); generated metadata confirms that the provider itself is auto-dispose (lib/features/library/application/library_providers.g.dart:27-36). Cleanup reads images, PDFs, and thumbnails in three sequential queries and passes that snapshot to filesystem deletion (lib/features/library/data/library_repository.dart:28-45). The deleter enumerates both owned roots and deletes every file absent from that earlier snapshot (lib/features/library/data/library_file_cleanup_io.dart:29-47,54-59).

Iteration 2 reachability correction. Production starts on the Library branch and retains it in a StatefulShellRoute.indexedStack (lib/config/router/app_router.dart:19-39), so the repository is normally kept watched and cleanup normally runs once per app/provider-container lifetime—not repeatedly on routine tab navigation. The race still exists while that fire-and-forget startup cleanup is enumerating files: Library list queries can finish and let the user open a canvas while deletion is still running. Natural occurrence therefore requires a sufficiently long cleanup plus a quick open/import, which is why reachability is marked Medium.

Import copies the selected asset into canvas_media first (lib/canvas/io/canvas_import.dart:87-107,115-132,151-164). Only after picker/decode/probe completion does the controller add elements and launch asynchronous persistence (lib/canvas/canvas_controller.dart:3891-3948,3961-4027); persistence itself is independently tracked rather than committed with the file move (lib/canvas/canvas_controller.dart:950-962,1099-1117).

  1. Cleanup snapshots DB paths; the new asset does not exist yet.
  2. Import copies a UUID-named image/PDF into the owned media root.
  3. Cleanup enumerates the root and deletes that path because its snapshot is stale.
  4. Import may fail while decoding, or the element write may still commit with the now-deleted path.
  5. After reopen, the note retains element geometry but displays a missing image/PDF placeholder.

Impact on note-taking. Imported source material can disappear or become permanently unavailable from a canvas. That is direct note asset loss, not cosmetic staleness. The “safe to call at startup” comment (library_repository.dart:28-30) is not backed by a barrier that waits for cleanup before enabling media mutations.

Root cause. Filesystem ownership and DB references are committed by separate actors with no shared lifecycle protocol, lock, transaction boundary, staging directory, or candidate-by-candidate liveness recheck.

Analysis-only recommendation. Treat media import as a two-phase commit: copy to a staging directory excluded from cleanup, commit the DB element, then atomically rename to its final path (or use a media registry row with lifecycle state). Run cleanup once through a keep-alive startup coordinator before user mutations, and serialize it with imports/deletes. Before deleting each candidate, re-query the authoritative DB path while holding that protocol lock. Add a deterministic test with gates around snapshot, file copy, deletion, and element commit.

A09-002 — Focus mutations become visible before persistence, so write failure changes restart semantics

HighConfidence: HighFocus history integrity

Evidence. Pause, resume, end-stretch, and skip-break mutate TimerEngine, emit UI state, and only then await runtime persistence (lib/features/focus/application/active_session_controller.dart:192-220). Stop similarly finishes/abandons the engine and stops the ticker before awaiting the closing row write (active_session_controller.dart:264-303). The repository persists runtime and final status in separate updates (lib/features/focus/data/focus_repository.dart:197-217,225-246).

The page catches the rejected future and says the requested action could not be completed (lib/features/focus/presentation/pages/focus_active_page.dart:119-137,139-167,169-220), but no engine rollback occurs. The existing failed-pause test asserts the SnackBar, not restoration of pre-action state (test/focus_flow_safety_test.dart:70-109).

Concrete effects. A failed pause leaves the live UI paused while the durable row may still say running; a kill/restart can count the paused wall time. A failed resume can restore paused and omit subsequent focus. Failed finish/abandon stops the local ticker while the row remains in-progress, so a restart reconstructs a session the user already attempted to end. The user can retry, but the window before retry is an integrity gap.

Root cause. The controller treats an in-memory state transition and a DB write as one operation without commit/rollback semantics. Error handling exists at the presentation boundary but cannot restore the prior engine snapshot.

Analysis-only recommendation. Serialize all session transitions. Capture a pre-transition runtime snapshot, compute the intended next snapshot, persist it, and publish it only after success; or publish an explicit “locally changed, save pending” state with durable retry and prevent teardown until resolved. For stop, retain/restart the prior engine on failed close or make a single repository transition the authoritative state-machine commit. Extend tests to assert UI state, ticker state, and restored DB state after each failed operation.

A09-003 — Settings controls can lose rapid updates and silently ignore repeated steps

MediumConfidence: HighRapid interaction

Evidence. Each stylus control reconstructs the entire mapping JSON from the current streamed model (lib/features/settings/presentation/pages/settings_page.dart:125-179); pen controls similarly call profile.copyWith on a captured profile (settings_page.dart:364-420). Repositories replace the whole JSON column (lib/features/settings/data/settings_repository.dart:223-235). Futures are returned from callbacks but not awaited or serialized, and write failures have no local feedback (settings_page.dart:111-114,193-240).

If the user changes “hold” and then “tap” before Drift’s stream rebuilds the widget, both writes derive from the same old mapping. The second full-JSON write restores the old hold value while applying tap. The stepper has the same stale-view issue: repeated taps calculate shown + step from one build (settings_page.dart:563-620), so two fast taps can persist the same one-step value twice.

Impact. Preferences appear to accept input, then snap back or preserve only the last sibling change. Incorrect stylus mappings disrupt ink flow and can select the wrong temporary tool, though note content is not directly deleted.

Analysis-only recommendation. Maintain an optimistic local draft/reducer with a monotonic revision and serialize persistence of the latest draft. For composite JSON settings, expose field-specific repository updates implemented as a fresh read-modify-write in one transaction, or store independent fields. Debounce/commit sliders intentionally and surface save failure without reverting unrelated pending input.

A09-004 — Kanban moves and adds compute positions from stale snapshots; renormalization can overwrite newer moves

MediumConfidence: HighGoal/revision ordering

Evidence. Column reorder computes neighbor positions from widget.board (lib/shared/kanban/kanban_board_view.dart:61-107) and card creation computes the tail from column.cards after an async dialog (lib/shared/kanban/kanban_column_view.dart:460-488). DragTarget callbacks return but do not await the action future (kanban_board_view.dart:208-222; kanban_column_view.dart:633-657), and the shared action wrappers only catch errors (kanban_board_view.dart:387-399; kanban_column_view.dart:914-927).

Both Goal and Revision repositories write the supplied position, then query an ordered list outside a transaction; if gaps are dense, a later transaction rewrites positions from that earlier list (lib/features/goal_cycle/data/goal_repository.dart:198-212,399-449; lib/features/revision/data/revision_repository.dart:168-182,351-401). Schema ordering columns are indexed but not unique (lib/core/database/tables/board_tables.dart:21-62).

Interleavings. Two adds launched before the board stream emits can choose the same tail position. More seriously, a renormalizer can read cards, a second move can land, and the first renormalizer can then overwrite that card’s newer position using its stale list. The card remains, but its intended organization can revert.

Impact. Goal/revision ordering becomes ambiguous or visibly jumps after rapid drag/drop. This interrupts spatial memory and planning flow; it does not erase card text.

Analysis-only recommendation. Serialize mutations per board/column and resolve neighbors from fresh DB rows inside the same transaction that writes the move and any renormalization. Add deterministic tie-breaking (position then stable ID) even if duplicate positions are prevented. UI should suppress a second drop/add until the first revision is confirmed, with optimistic state keyed by operation generation.

A09-005 — Withdrawn: pinned PDF backend serializes native render and close

Withdrawn in iteration 4Correction confidence: HighDependency-verified

The original pass treated the absence of a Zenno-owned render drain as evidence that PdfDocument.dispose could close a native handle during rendering (lib/canvas/pdf/pdf_raster_service.dart:159-208,228-248). Inspection of the pinned pdfrx 2.4.1/pdfrx_engine 0.4.2 implementation changes that conclusion: native render and close calls are submitted to the same single background worker, whose receive loop executes messages in send order (pubspec.lock:723-737; ~/.pub-cache/hosted/pub.dev/pdfrx_engine-0.4.2/lib/src/native/worker.dart:14-39,57-89,121-150). The document marks itself disposed before queueing close, and page render checks that state before queueing native work (~/.pub-cache/hosted/pub.dev/pdfrx_engine-0.4.2/lib/src/native/pdfrx_pdfium.dart:1315-1331,1555-1592).

Zenno additionally rejects a rendered buffer once the service is disposed and releases it (lib/canvas/pdf/pdf_raster_service.dart:187-208); the controller epoch guard rejects late decoded images. The WASM worker can overlap asynchronous commands, but PDF import is hidden on web (lib/canvas/widgets/canvas_toolbar.dart:696-720) and no concrete current-code path establishes an unsafe progressive render/close interleaving. The active Medium finding is therefore removed rather than retained as a package-dependent warning.

Analysis-only hardening option, not a defect recommendation. A service-level operation drain would reduce coupling to dependency internals if backend/version behavior changes, but it is not currently justified as a correctness fix.

A09-006 — Detached thumbnail capture can overwrite a newer preview

LowConfidence: MediumOrdering

Evidence. Link-driven close deliberately launches thumbnail capture without awaiting it (lib/canvas/canvas_editor_page.dart:251-258,291-297). Capture renders, encodes, writes the fixed path thumbnails/<canvasId>.png, then updates the DB without any generation/revision or existence condition (canvas_editor_page.dart:217-240).

A slow capture from editor instance A can continue after route pop. If the same canvas is reopened and instance B captures a newer state first, A can finish last and overwrite the preview with older pixels. Concurrent delete can also leave a best-effort orphan file, although the DB update affects zero rows.

Impact. Library preview can regress and misrepresent the note; canvas content remains intact. The race needs overlapping close/reopen/capture timing, hence medium confidence.

Analysis-only recommendation. Write to a unique temp file, attach a canvas content revision/capture generation, and conditionally promote it with atomic rename only if it is still the latest capture and the canvas exists. Serialize captures per canvas. Detached work should own no widget/ref state after pop.

A09-007 — Periodic Focus callbacks can overlap and amplify slow/failing runtime writes

LowConfidence: High for overlapTimer reentrancy

Evidence. Timer.periodic invokes the async _onTick callback without observing its future (lib/features/focus/application/active_session_controller.dart:344-371). Once the 15-second counter reaches threshold, every later tick can enter _persistRuntime until one write completes and resets the shared counter (active_session_controller.dart:391-404).

Impact. If a runtime write takes longer than one second or repeatedly fails, several DB updates can be in flight, causing write amplification and noisy failure/retry behavior during focus. Drift’s single connection preserves production statement sequencing, and _persistRuntime invokes the update before its first await, so this report does not claim a stale final row or a checkpoint writing after a later finish. Iteration 2 therefore downgrades this to Low.

Analysis-only recommendation. Add a single-flight checkpoint future/flag and record a pending-latest snapshot. On completion, persist at most the newest queued generation. Bind writes to the active session ID/generation, and prevent completion from resetting counters for a newer session.

A09-008 — Several append-position allocators are read-then-write races

LowConfidence: HighDeduplicated pattern

The same root pattern appears in three places:

  • Library folder MAX(position) + 1, outside a transaction: lib/features/library/data/library_repository.dart:111-132.
  • Reflection template “last + 1”, with the await embedded before insert: lib/features/goal_cycle/data/reflection_repository.dart:146-169,345-352. Template duplicate has no per-item in-flight guard and pushes after the write (lib/features/goal_cycle/presentation/pages/templates_page.dart:90-133).
  • Canvas attachment “last + 1000” before insert: lib/shared/canvas_attachments/card_canvas_attachment_repository.dart:115-146.
  • Focus ritual item “maximum + 1” before insert, with no unique ordering constraint: lib/features/focus/data/ritual_repository.dart:74-98; lib/core/database/tables/focus_tables.dart:23-37. The review page re-enables its Add action as soon as the dialog closes, before the first insert finishes (lib/features/focus/presentation/pages/focus_review_page.dart:152-159,197-230).

Concurrent callers can observe the same maximum and assign equal positions. Normal UI guards reduce likelihood for folders/attachments, but repository APIs do not guarantee ordering. Duplicate template taps are a direct rapid-interaction path. Query order uses position alone, so ties are not deterministic.

Analysis-only recommendation. Allocate and insert under one serialized transaction per list, or use a durable ordering service. Always add a stable secondary sort. Guard duplicate/create actions across their full async lifecycle, including navigation.

A09-009 — Revision count increment is non-atomic

LowConfidence: MediumConsistency

markRevised reads the current count, computes +1, then writes it in a separate statement (lib/features/revision/data/revision_repository.dart:258-276). The detail sheet blocks reentry within one mounted sheet (lib/features/revision/presentation/widgets/revision_card_detail_sheet.dart:53-64,113-115,173-197), which lowers likelihood, but two controllers/sheets or direct callers can both write the same next count.

Impact. A revision event can be undercounted; note/card text is unaffected. Recommendation: issue one atomic SQL increment plus timestamp update, and check the affected-row count.

A09-010 — Intermediate failures do not consistently release codecs/buffers or copied import files

LowConfidence: HighDisposal

Image decode allocates an immutable buffer, descriptor, and codec, but disposes them only after all awaits succeed; any intermediate throw returns null without finally cleanup (lib/canvas/canvas_controller.dart:4299-4317). Export decode has the same shape (lib/canvas/io/canvas_export.dart:393-410). Import copies the file before decode/probe and has no rollback for decode/probe failure (lib/canvas/io/canvas_import.dart:87-107,115-132); image codec disposal also occurs only after frame success.

PdfRasterService._ensureInitialized clears _initializing only on success, so one initialization failure leaves a completed-error future cached for that service’s lifetime (lib/canvas/pdf/pdf_raster_service.dart:91-106).

Impact. Repeated corrupt/unreadable assets can leak native memory and accumulate orphan files; a transient PDF init failure becomes sticky until the controller/service is recreated. Recommendation: use staged ownership and nested try/finally; remove copied files on failed import; clear initialization future in finally while setting initialized only after success.

A09-011 — Canvas load is a sequence of independent reads, not one snapshot

LowConfidence: MediumHydration consistency

Controller load sequentially awaits layers, elements, bookmarks, viewport, rotation, paper, and tools before applying them (lib/canvas/canvas_controller.dart:862-924). These repository calls are not wrapped in a single read transaction. A same-canvas mutation or delete from another editor/process during those awaits can produce a mixed-version state.

Current navigation is designed to avoid two mounted editors for the same canvas (lib/canvas/canvas_editor_navigation.dart:7-13,26-55), so ordinary UI strongly mitigates this. Cross-process/web mutation, deletion, or an uncoordinated caller remains possible.

Analysis-only recommendation. Add one repository loadCanvasSnapshot read transaction returning all durable components and a revision. Apply only if the canvas still exists and the controller’s load generation remains current.

A09-012 — Link navigation coalesces duplicate targets, not competing different targets

LowConfidence: MediumReentrancy

Follow-link checks existence, then launches navigation unawaited (lib/canvas/canvas_editor_page.dart:398-420). The coordinator uses a set keyed by destination ID, so rapid opens to the same canvas coalesce, but A→B and A→C can both push concurrently (lib/canvas/canvas_editor_navigation.dart:58-103). The existing test verifies same-target coalescing (test/canvas_editor_navigation_test.dart:20-128).

Impact. Fast taps on different links can create an unexpected route stack and trigger multiple editor loads/thumbnail closes. Recommendation: serialize route mutations globally (or per source route), retain only the latest requested target, and test competing target IDs.

A09-013 — Wakelock operations have no desired-state generation during restore/stop overlap

LowConfidence: MediumResource state

Restore publishes an active session and starts its ticker before awaiting the settings read and wakelock enable (lib/features/focus/application/active_session_controller.dart:406-445). Stop later awaits a separate disable (active_session_controller.dart:289-303,477-492), and provider disposal launches disable unawaited (active_session_controller.dart:103-115). The service is a direct asynchronous platform toggle with no generation or final-state reconciliation (lib/features/focus/application/focus_wakelock_service.dart:6-18).

If a restored session is ended while its enable request remains unresolved, correctness depends on platform-channel completion/processing order. A late effective enable could leave the screen awake after the session ends. This does not affect notes or focus history, and platform FIFO behavior may prevent it; hence Low severity and Medium confidence.

Analysis-only recommendation. Centralize a desired wakelock boolean with a monotonically increasing generation or serialized operation chain. After every async toggle, reconcile against the latest desired state; on shutdown, make the final disable part of an owned drain where the platform permits.

A09-014 — Export borrows controller-owned rasters across awaits without pinning them

LowDefect confidence: HighTiming likelihood: MediumResource ownership

Export snapshots element objects, but when an image/PDF already has a sufficient raster, _prepareElements reuses that ui.Image and records no ownership/pin (lib/canvas/io/canvas_export.dart:183-190,315-390). Only rasters decoded by export itself enter the owned list (canvas_export.dart:50-60). Rendering and encoding then cross more async boundaries (canvas_export.dart:191-247,1012-1057).

Meanwhile, a controller PDF job can replace a lower-resolution raster and immediately dispose the old image (lib/canvas/canvas_controller.dart:4327-4377), and completion of any raster job can enforce the budget and dispose off-screen rasters (canvas_controller.dart:4437-4488). The modal blocks new pointer input but does not cancel jobs already running. A content export is particularly exposed because it includes off-screen elements (canvas_export.dart:278-290).

Impact. A PDF-heavy or memory-constrained export can paint/encode a disposed image, aborting export and potentially surfacing a non-CanvasExportException. Durable canvas data is unaffected, so severity remains Low.

Analysis-only recommendation. Give export stable raster ownership: either render/decode independent export images for every media element, or add controller raster leases/refcounts that block replacement/eviction disposal until export releases them. Test with a gated higher-bucket PDF completion and budget eviction between preparation and paint.

Verified safeguards and non-findings

  • Canvas writes are visible and drainable. _track invokes each repository write immediately, pending writes are retained until completion, and failed writes are replaced by a full snapshot of the current controller state on retry (lib/canvas/canvas_controller.dart:926-943,1059-1117). Editor close awaits flush before warning about unsaved state, and widget disposal lets that drain finish before disposing the controller (lib/canvas/canvas_editor_page.dart:207-215,258-290). This audit found no command/persistence completion path that reverses newer in-memory state. Tests cover failure visibility and retrying newest state (test/canvas_repository_test.dart:870-927).
  • Raster result races are guarded. Controller epochs, visibility checks, resolution comparison, in-flight sets, and concurrency caps stop stale image/PDF results from mutating the element store (lib/canvas/canvas_controller.dart:4170-4244,4320-4350,4507-4526). A remaining finding concerns native handle lifetime, not result acceptance.
  • Import reentry is blocked. _isImporting prevents stacked file pickers and is reset in finally (lib/canvas/canvas_controller.dart:3870-3948,3961-4027). Tests cover completion after controller disposal (test/canvas_commands_test.dart:669-729).
  • Input timers are disposed. Canvas long-press/stylus timers are cancelled on movement/end and widget disposal (lib/canvas/render/canvas_view.dart:246-263,516-537,742-824,866-903).
  • Focus time math is wall-clock based. A throttled 1 Hz ticker does not itself lose elapsed time (lib/features/focus/application/active_session_controller.dart:80-93; lib/features/focus/domain/timer_engine.dart:142-160). Startup awaits restoration before allowing a new session (active_session_controller.dart:131-138), with explicit coverage (test/active_session_controller_test.dart:140-190).
  • Editor saves generally guard reentry. Canvas title, Goal detail, Revision detail, reflection/template editors, Focus setup/active/review, and attachment add flows contain mounted checks and busy/single-flight flags. These reduce but do not replace repository-level atomicity.
  • Web database ownership is explicit. One exclusive browser lock is intentionally held for tab lifetime (lib/core/database/web_database_lock.dart:8-41) and the DB provider is keep-alive (lib/core/providers/database_provider.dart:6-14). No multi-tab write race was claimed.

Recommended remediation order

  1. Protect media integrity first: redesign import/cleanup ownership and add a deterministic interleaving test for A09-001.
  2. Make Focus transitions transactional: define commit/rollback/pending semantics for all engine changes, especially stop/abandon.
  3. Introduce small serialization primitives: a per-board mutation queue, a focus checkpoint single-flight, and a settings draft writer. Keep each domain-specific and observable.
  4. Stabilize resource ownership: pin export rasters and make thumbnails generation-aware.
  5. Close low-risk atomicity gaps: position allocation, revision increment, decode cleanup, and competing navigation.

Limits and confidence notes

  • This is static analysis. Per task constraints, no app, build, test, install, profiler, database, or filesystem race harness was executed.
  • A09-005 was withdrawn after checking the locally pinned dependency implementation. That conclusion is version-specific; a future backend/version change should be re-audited rather than assumed equivalent.
  • Drift’s production executor is expected to serialize statements. A09-007 therefore reports overlapping controller operations/write amplification, not a proven out-of-order final commit.
  • Low findings that require alternate entry points or multiple mounted controllers are intentionally not promoted based only on theoretical reachability.
  • Line numbers refer to the repository state inspected on 2026-07-18; generated files were read only where they establish runtime lifecycle.
