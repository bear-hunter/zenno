Zenno cross-platform behavior

Scope and constraints

This report follows the assigned lens: Flutter behavior across Android and web, conditional imports, Drift web runtime, workers/WASM, browser storage and locking, and observable platform divergence. The repository was inspected read-only, including relevant hidden/untracked planning material. No credentials or secret values are reproduced.

Per delegation, I did not run Flutter/Dart builds, tests, analysis, installs, the app, or Git commands. Conclusions distinguish static proof from runtime risk. The sole written artifact is this report.

Executive summary

Bottom line: the database boundary reflects the repository's latest lesson—web uses a direct WasmDatabase with an IndexedDB filesystem and an exclusive Web Lock, avoiding the previously hanging shared-worker probe. The application entry graph does reach four unconditional dart:io imports, but an adversarial read of the installed Dart SDK corrected the first-pass conclusion: current JS/Wasm targets provide web stubs for dart:io, and Zenno's normal UI guards appear to avoid invoking unsupported file operations. This is architectural fragility, not a statically proven compile blocker.

The highest supported priorities are failure-safe lock lifetime, typed/recoverable initialization handling, and a real web compile/browser-database verification lane. Android remains the only complete note-taking target: web deliberately disables media import, export, and thumbnails, and its direct main-isolate database executor should be profiled before web is trusted for writing flow. Completed web writes are flushed to IndexedDB, but the newest in-flight write has no browser-unload guarantee.

Boundary debt
Web safety depends on runtime guards around unsupported dart:io operations.
Data access risk
A failed web initialization can retain the exclusive database lock until the tab closes/reloads.
Flow risk
Direct WASM SQLite and immediate per-gesture writes share the browser UI isolate; impact is unmeasured.
Good foundation
Connection conditional import, direct IndexedDB VFS, foreign keys, and fail-closed second-tab behavior are structurally sound choices.

Findings

MEDIUM

F01 — Web file safety relies on scattered runtime guards instead of compile-time boundaries

Confidence: high on structure; no current compile failure proven
Evidence
  • lib/config/router/app_router.dart:4-10 eagerly imports the canvas editor and library page from the root app graph.
  • lib/canvas/canvas_editor_page.dart:2, lib/features/library/presentation/widgets/canvas_card.dart:2, lib/canvas/io/canvas_import.dart:1, and lib/canvas/io/canvas_export.dart:2 directly import dart:io.
  • The editor imports CanvasController (canvas_editor_page.dart:14), which imports the native importer (canvas_controller.dart:14); the toolbar also imports the native exporter (canvas_toolbar.dart:7-8).
  • kIsWeb guards exist inside methods at canvas_editor_page.dart:217-239, canvas_card.dart:359-381, and canvas_toolbar.dart:695-724. Normal web UI paths appear to return before unsupported file operations.
  • Adversarial pass 2 inspected the installed Dart SDK platform map: JS and Wasm targets include dart:io web patches, and file/directory operations throw UnsupportedError. This disproves the first-pass assertion that direct import alone necessarily blocks compilation in the current toolchain.
Root cause
Platform-specific file APIs are protected by feature disabling at call sites instead of compile-time conditional imports/interfaces. The codebase already demonstrates the cleaner shape in lib/features/library/data/library_file_cleanup.dart:1-13.
Impact
The current guarded UI may work, but any new call path to thumbnail, importer, exporter, Platform.pathSeparator, or File can become a web-only UnsupportedError. The safety invariant is distributed across widgets rather than enforced by the type/import boundary. This is regression risk and feature divergence, not proven current unavailability.
Analysis-only recommendation
Create narrow platform boundaries for thumbnail storage/display, media import/source loading, and export destination. Keep shared models/rendering platform-neutral. Use native implementations under dart.library.io and web-safe implementations/stubs under dart.library.js_interop; then remove reliance on every caller remembering a kIsWeb guard.
HIGH

F02 — Failed web database initialization can strand the exclusive lock

Confidence: high
Evidence
connection_web.dart:9 acquires the lock before loading sqlite3.wasm and opening IndexedDB at lines 10-18. The lock callback returns _databaseLifetime.future (web_database_lock.dart:8,31-33), and that completer is never completed anywhere in the codebase.
Root cause
Lock lifetime is tied to the JavaScript module/tab rather than successful database lifetime. Initialization failure has no release path.
Impact
If WASM fetching, WASM instantiation, IndexedDB opening, schema migration, or first connection setup fails, that tab can continue owning the lock. A second tab then reports “Zenno is open in another tab,” obscuring the original fault and denying recovery until reload/close. This is availability/flow harm, not proven corruption; the fail-closed behavior does protect against concurrent writers.
Analysis-only recommendation
Make acquisition return a lease/release handle, and release it when connection initialization fails or when the database closes. Keep the lifetime hold only after a usable connection exists. Add a browser test that forces an initialization failure and proves another connection can subsequently acquire the lock.
MEDIUM

F03 — Web Locks is a hard, unprobed prerequisite for all persisted web screens

Confidence: high on code path; low incidence in documented Chrome preview
Evidence
web_database_lock.dart:22-34 directly calls navigator.locks.request. There is no capability/secure-context check, alternate path, or specific unsupported-browser exception. Every feature repository shares the database created by database_provider.dart:10-14.
Root cause
A data-integrity safeguard was implemented as a mandatory browser API without an explicit compatibility gate.
Impact
In a browser or hosting context where Web Locks is absent/unavailable, the app cannot access any canvases, focus sessions, goals, revision cards, or settings. The documented flutter run -d chrome localhost preview should provide the API, which lowers current incidence; broader browser/embedded-web support would expose the hard failure.
Analysis-only recommendation
Fail closed, but detect support before database creation and show a precise “this browser/context is unsupported” message. If broader web support becomes a goal, select a proven single-writer coordination design; do not silently open the same IndexedDB SQLite file from multiple direct connections.
MEDIUM

F04 — Direct WASM SQLite shares the browser UI isolate with note interaction

Confidence: medium; performance impact unmeasured
Evidence
connection_web.dart:6-20 constructs WasmDatabase directly and has no worker transport. Controller documentation says each committed element write fires immediately as its own small transaction (canvas_controller.dart:165-175); addElementToStore calls persistence at canvas_controller.dart:820-822; the repository transaction writes the generic row, detail row, and canvas timestamp (canvas_repository.dart:334-376).
Root cause
The direct connection intentionally avoids the known shared-worker hang, trading worker isolation for reliability.
Impact
Large encoded ink strokes or bursts of edits may cause browser-main-isolate work between marks, potentially disturbing writing flow. Static inspection cannot establish whether the cost is noticeable; viewport writes are correctly debounced to 400 ms.
Analysis-only recommendation
Preserve the no-hang direct path until measurement says otherwise. Profile frame timing and transaction duration in the supported browser with long strokes and rapid mark/erase cycles. Only consider a dedicated-worker design after it passes the in-app browser that motivated the direct connection; batching at gesture boundaries may be the simpler first lever.
HIGH IF WEB STORES REAL NOTES

F05 — Web persistence has no durability/backup contract while export is disabled

Confidence: medium-high
Evidence
Web stores the whole database in IndexedDbFileSystem(dbName: 'zenno') (connection_web.dart:10-18). The repository contains no browser-storage persistence request, usage/quota estimate, or status surface. Web export is rejected as Android-only (canvas_toolbar.dart:719-724). README calls web a development preview and Android the reliable persistence target (README.md:3-5,57-66).
Root cause
The preview acquired a persistent database sufficient for development but not a user-facing data retention and recovery design.
Impact
If web is used beyond preview, browser data clearing, private sessions, storage policy, quota exhaustion, origin changes, or a broken migration can leave notes unavailable/unrecoverable, with no in-app export escape hatch. Canvas write failures are visibly retained for retry, but retry cannot create more quota or recover a cleared origin. This is the largest data-integrity concern if web becomes authoritative.
Analysis-only recommendation
Keep web explicitly non-authoritative until it has a storage-durability status, backup/export path, migration browser tests, and recovery guidance. If preview-only remains the decision, put an unmissable non-production warning near the run instructions and in the web UI.
MEDIUM

F06 — Media-backed canvases are an Android-only data model in practice

Confidence: high
Evidence
The importer copies picker paths into native app documents and returns absolute paths (canvas_import.dart:61-68,87-164); image/PDF paths are persisted in Drift (canvas_repository.dart:401-435). Runtime reloading uses ui.ImmutableBuffer.fromFilePath (canvas_controller.dart:4299-4317) and PdfDocument.openFile (pdf_raster_service.dart:108-113). Web import/export are blocked (canvas_toolbar.dart:695-724), thumbnails are omitted (canvas_editor_page.dart:217-239; canvas_card.dart:359-381), and web file cleanup is a no-op (library_file_cleanup_stub.dart:1-5).
Root cause
The persisted media reference is a native filesystem path rather than a cross-platform asset identifier/blob abstraction.
Impact
Web can edit vector/text content only after compilation is fixed; it cannot create or faithfully rehydrate path-backed images/PDFs. Library recognition is also reduced because every web canvas card uses a placeholder.
Analysis-only recommendation
Either document the feature matrix as intentional, or introduce a media-store interface with native files and browser blob/IndexedDB implementations. Do not attempt to make native absolute paths portable; migration must preserve existing Android files and references.
MEDIUM

F07 — Installed web orientation contradicts the landscape-first app

Confidence: high on mismatch; medium on browser behavior
Evidence
Dart locks landscape before runApp (lib/main.dart:7-15), Android declares userLandscape (AndroidManifest.xml:7-16), while the web manifest requests portrait-primary (web/manifest.json:4-10).
Root cause
The web manifest retains scaffold defaults while Android/tablet orientation was customized.
Impact
An installed PWA may launch or advertise itself in the opposite orientation from the canvas layout, causing rotation/resizing friction at the start of a thinking session.
Analysis-only recommendation
Choose one web policy explicitly. For parity, set the PWA orientation to landscape; for responsive preview, remove a restrictive orientation rather than asking for portrait while the app requests landscape.

F08 — Worker guidance contradicts the implemented and learned-safe runtime

Confidence: high
Evidence
AGENTS.md:41 says to bundle a compiled Drift worker, while the immediately following lesson at AGENTS.md:42 says the default shared-worker probe can hang and directs a conditional direct WasmDatabase. .claude/CLAUDE.md:14,26 still says the web runtime needs a worker. Root cause
Historical guidance was appended rather than superseded, leaving mutually incompatible instructions active.
Impact
A future maintainer may “fix” the intentionally absent worker and reintroduce the in-app-browser hang already recorded as a failure.
Analysis-only recommendation
Retire/supersede the worker-required statements and document the current invariant: direct IndexedDB-backed WASM plus exclusive lock, with the exact browser environment that rejected shared workers.
HIGH

F09 — No verification lane executes the actual web boundary

Confidence: high
Evidence
No browser-targeted test annotation or web database test exists under test/. test/library_page_test.dart:15-46 injects a synthetic StateError; it does not load WASM, acquire a Web Lock, open IndexedDB, or compile the real web app. Database and migration tests use NativeDatabase.memory() and native SchemaVerifier connections (test/database_test.dart:15,101-160 and subsequent version cases), so they prove shared SQL/model behavior only on the native executor. The repository has no visible CI workflow. README validation lists generic analysis/tests and Android build smoke tests, but no web build check (README.md:68-92).
Root cause
Web is treated as a convenience preview, so VM widget tests substitute for platform integration evidence.
Impact
New unguarded calls into web-stubbed dart:io, missing/mismatched WASM, lock incompatibility, migration failures, and PWA asset-path failures can all land without a failing routine check.
Analysis-only recommendation
Add the smallest useful lane after the boundary fix: compile the app for web, then a browser integration test that opens the real database, writes/reads a sentinel, verifies a second tab fails closed, and verifies lock recovery after controlled initialization failure.
MEDIUM

F10 — The manually bundled SQLite WASM has no repository-visible provenance check

Confidence: high on missing provenance; no mismatch proven
Evidence
web/sqlite3.wasm exists (706,316 bytes during this pass), and pubspec.lock pins sqlite3 2.9.4 at lines 944-951. No script, manifest, comment, or test ties the binary's build/version/hash to the locked Dart package. The runtime loads the stable bare name at connection_web.dart:10; there is no content hash/version in the request URL.
Root cause
A required generated/vendor binary is checked in manually without an auditable refresh/verification procedure.
Impact
A future dependency upgrade can leave an old binary behind, replace it incorrectly, or serve a cached old response beside new Dart code when host cache headers are aggressive. Failures would occur at runtime before any notes load; because of F02, a failed tab may also retain the database lock.
Analysis-only recommendation
Record the binary source/tool version and deterministic refresh command, plus a lightweight version/hash assertion in maintenance checks. Use an intentional cache-invalidation policy for deployment. Treat the current binary as unverified provenance, not as known-bad.
HIGH

F11 — Web initialization failures collapse into a generic, non-recovering retry

Confidence: high
Evidence
Only the Library recognizes exact StateError(databaseAlreadyOpenMessage) (database_exceptions.dart:1-5; library_page.dart:302-323). Web deep links are preserved by go_router, so another tab can start directly on any branch. Canvas shows a generic Retry (canvas_editor_page.dart:132-150,502-530); Settings shows a generic provider invalidation (settings_page.dart:50-57); Focus and board pages render raw $error text (focus_home_page.dart:144-150; goal_board_page.dart:84-117; revision_board_page.dart:95-128). Every path still holds the same app-wide database.
Root cause
Infrastructure errors cross feature boundaries as raw objects, with one string-matched exception recognized in one feature. The locked Drift implementation's delayed executor memoizes its one open future, including failure; feature/query-provider invalidation does not replace the keep-alive ZennoDatabase at lib/core/providers/database_provider.dart:8-14.
Impact
The result depends on the starting route: the same second-tab or open-time failure is actionable in Library, generic in Canvas/Settings, and technical/raw in Focus/boards. For missing WASM, denied IndexedDB, or migration failure, “Try again” repeats work against the same failed delayed executor and cannot recover; a full page reload is required but not requested.
Analysis-only recommendation
Map database-open failures into stable typed categories at the connection/provider boundary and expose one app-level readiness/error surface before feature routes build. Define which categories are retryable and make retry recreate the executor/database only when safe; keep raw details in logs, not user-facing text.
MEDIUM

F12 — Web performs native-file cleanup scans even though cleanup is a no-op

Confidence: high
Evidence
library_providers.dart:15-24 launches cleanupOrphanedFiles() whenever the library repository is created. That method reads every image path, PDF path, and canvas thumbnail path before calling the platform cleanup function (library_repository.dart:28-45). On web, the selected implementation does nothing (library_file_cleanup_stub.dart:1-5).
Root cause
The conditional boundary wraps only file deletion, not the expensive prerequisite database scan or the platform capability itself.
Impact
Web startup adds three full-table reads and allocations that cannot produce any cleanup. Because the direct WASM executor shares the browser UI isolate, the waste grows with a mature note library and competes with first library paint. It also complicates database-open errors by adding another concurrent query source.
Analysis-only recommendation
Make cleanup capability explicit and skip the entire orchestration on platforms without owned files. Preserve native cleanup exactly; do not merely move the no-op later in the same query chain.
MEDIUM, DEPLOYMENT-CONDITIONAL

F13 — Fixed browser namespace can mix path-based deployments on one origin

Confidence: high on namespace; deployment incidence unknown
Evidence
Web always opens IndexedDbFileSystem(dbName: 'zenno') with file path /database (connection_web.dart:10-18) and always acquires zenno-drift-database (web_database_lock.dart:23-25). Neither name includes base path, environment, app version, or deployment identity.
Root cause
Browser storage is scoped by origin, while the application treats it like a native app sandbox. URL paths do not create separate IndexedDB namespaces.
Impact
If preview, staging, or production builds are ever hosted under different paths on the same origin, they sequentially open and migrate the same note database. The lock prevents simultaneous access but does not prevent an older/newer build from mutating a shared schema in turn. This can become a data-integrity risk; separate ports or hostnames are separate origins and avoid it.
Analysis-only recommendation
Document the one-origin/one-Zenno-database invariant now. If co-hosting is needed, derive a stable deployment namespace and design an explicit migration from the existing zenno store—changing the name without migration would appear to lose all existing web notes.
MEDIUM

F14 — Trackpad pan/pinch events are not handled by the canvas

Confidence: high on missing handlers; medium on device/browser manifestation
Evidence
pointer_classifier.dart:26-46 classifies PointerDeviceKind.trackpad as mouse. The canvas Listener registers down/move/up/cancel/hover/signal only (canvas_view.dart:1455-1469); there are no onPointerPanZoomStart, onPointerPanZoomUpdate, or onPointerPanZoomEnd handlers anywhere in lib/. _onPointerSignal treats every vertical scroll as fixed-step zoom and ignores horizontal delta (canvas_view.dart:1302-1314). Tests exercise touch and mouse buttons but contain no trackpad/pan-zoom case.
Root cause
Tablet touch gestures and mouse wheel zoom were implemented, but Flutter's distinct trackpad pan/zoom event family was omitted.
Impact
On web/desktop hardware that emits PointerPanZoom, two-finger trackpad navigation can be ignored or reduced to coarse scroll zoom, making the infinite canvas feel materially less direct than on the Android tablet.
Analysis-only recommendation
Add a dedicated trackpad gesture state that maps pan delta, scale, and rotation through the same viewport transform math as touch pinch, respecting rotation lock. Cover raw PointerPanZoom sequences in widget tests and manually verify browser behavior before changing scroll-wheel semantics.
MEDIUM

F15 — Browser tab close/reload can outrun the newest queued note write

Confidence: high on missing coordination; medium on browser timing incidence
Evidence
  • Canvas mutations start asynchronous repository work and retain its future in _pendingWrites (canvas_controller.dart:945-979,1099-1117).
  • flush() forces the debounced viewport write and awaits every tracked wave (canvas_controller.dart:926-943). The normal guarded editor close correctly awaits it before popping (canvas_editor_page.dart:258-305).
  • Unexpected widget disposal cannot await: it launches controller.flush() with unawaited and immediately returns (canvas_editor_page.dart:207-214). The app-wide provider similarly registers async db.close in a synchronous disposal callback (lib/core/providers/database_provider.dart:8-14).
  • No pagehide, beforeunload, visibility-change, or general app-lifecycle persistence coordinator exists in lib/ or web/.
  • Locked Drift 2.31.0 documents/implements the IndexedDB guarantee when the request completes. This finding therefore concerns only in-flight work, not previously completed writes.
  • The installed Flutter service-worker cleanup template navigates all open clients during activation. A deployment upgrading from a legacy registered Flutter worker can therefore initiate an external page reload; the pre-existing ignored bundle contains this generated behavior at build/web/flutter_service_worker.js:7-30.
Root cause
Persistence safety is attached to Flutter's guarded route-close path, while browser tab lifecycle is external to that path and cannot await arbitrary asynchronous cleanup during teardown.
Impact
An immediate reload, tab close, crash, browser process termination, or one-time legacy service-worker cleanup just after a stroke/transform can interrupt the latest transaction or a final debounced viewport save. The likely loss window is the newest unsatisfied future, not the existing library. Abrupt Android process death has an analogous asynchronous window, but reload/close is a routine web action and no web-specific state communicates whether the queue is drained.
Analysis-only recommendation
Make pending/saved status observable and add a web page-lifecycle adapter that proactively drains on visibility loss/page hide and warns on an intentional unload while work remains. Do not claim that an async beforeunload callback can guarantee completion; minimize the pending window and prove behavior with a browser test that reloads immediately after a mutation.
MEDIUM, DEPLOYMENT-CONDITIONAL

F16 — Direct WASM startup depends on an undocumented HTTP/MIME contract

Confidence: high on loader behavior; incidence unknown
Evidence
connection_web.dart:10 loads the bare relative sqlite3.wasm. The locked sqlite3 2.9.4 implementation resolves it against Uri.base, fetches the response, and passes it directly to WebAssembly.instantiateStreaming; that path does not check HTTP status or fall back to reading an array buffer. The repository has no production hosting/header configuration and README documents only flutter run -d chrome (README.md:57-66).
Root cause
The required native runtime binary is present, but delivery behavior is delegated entirely to whichever server hosts the generated web bundle.
Impact
A host that returns a 404/HTML response or does not serve .wasm as application/wasm prevents every database-backed screen from opening. F02 can then retain the acquired tab lock, and F11 presents a non-recovering generic retry. Flutter's development server is expected to meet the contract; no present failure is asserted.
Analysis-only recommendation
Document the base-path and application/wasm requirements, verify the actual deployment response in a browser smoke lane, and classify fetch/status/MIME/instantiation failures before lock retention. Prefer correcting server headers; only add a slower byte-buffer fallback if supported deployment environments require it.
LOW

F17 — Canvas keyboard shortcuts assume Ctrl/Delete conventions on every web host

Confidence: high
Evidence
The editor binds undo, redo, nudge, rotate, and scale only with SingleActivator(..., control: true), and selection deletion only to LogicalKeyboardKey.delete (canvas_editor_page.dart:550-608). There are no meta: true or Backspace alternatives. Flutter's SingleActivator treats Control and Meta as distinct exact modifiers. The editor tests verify title-mode disabling and Escape, but do not exercise platform modifier variants (test/canvas_editor_page_test.dart:53-72,147-188).
Root cause
Shortcuts follow the Android/Windows hardware-keyboard convention even though the same editor is exposed to browsers on macOS and compact keyboards.
Impact
Mac web users' expected Command-Z/Command-Shift-Z do not reach undo/redo, and a keyboard whose labeled Delete maps to logical Backspace cannot delete a selection. Toolbar/touch/stylus alternatives remain, so this is a flow inconsistency rather than data loss.
Analysis-only recommendation
Add Meta equivalents for command shortcuts on Apple hosts and a carefully scoped Backspace selection action while text editing is inactive. Test real key events with both modifier families; preserve the existing guard that empties canvas shortcuts while the title field is active.
MEDIUM IF WEB IS INSTALLED/OFFLINE

F18 — The standalone web shell has no offline cold-start contract

Confidence: high for the observed toolchain/artifact; future build flags can change it
Evidence
web/manifest.json:4-10 advertises a standalone install and web/index.html:23-44 uses the stock Flutter bootstrap. The checked-in .metadata:6-20 identifies the Flutter toolchain lineage. In the existing ignored bundle inspected read-only, build/web/flutter_bootstrap.js:36-41 has no local-CanvasKit flag, so its loader chooses the external gstatic.com/flutter-canvaskit base; build/web/flutter_service_worker.js:3-30 unregisters itself and clears the old worker lifecycle. The bundle is pre-existing generated evidence, not a source-of-truth guarantee for future build flags.
Root cause
Installable PWA metadata is present, but web remains a development preview and therefore has no intentional offline app-shell/cache design. The current Flutter service-worker path is also deprecated.
Impact
A cold-started installed web app can require network access before it can reach locally stored IndexedDB notes. Offline users may see an unavailable app even though their data still exists; this is availability/flow harm, not data deletion. Android release has no main-manifest Internet permission and its runtime/database/media are local, so the behavior diverges sharply.
Analysis-only recommendation
If web remains preview-only, state that installation/offline use is unsupported and consider removing signals that imply a finished PWA. If web becomes a real local-first target, bundle/select CanvasKit locally, choose an explicit post-deprecation app-shell caching strategy, include sqlite3.wasm, and verify a clean-profile offline cold start plus upgrade behavior.

Protective decisions worth preserving

GOOD

Correct database conditional import. connection.dart:3-5 keeps dart:js_interop/package:web out of native builds and selects a distinct web executor.

GOOD

Fail-closed multi-tab policy. ifAvailable: true refuses a second direct connection instead of risking concurrent mutation of the IndexedDB-backed SQLite file.

GOOD

Direct connection matches the latest failure lesson. The source avoids the default shared-worker probe that previously hung in the in-app browser.

GOOD

Shared schema protections. All platforms use schema version 13, text DateTimes, migrations, foreign keys, and seeding through the same ZennoDatabase (database.dart:48-159).

GOOD

Completed web writes flush to IndexedDB. The locked Drift 2.31.0 WasmDatabase implementation awaits the supplied IndexedDB filesystem after statements/transactions. F05 is about browser retention and recovery, not a claim that normal completed writes stay only in memory.

GOOD

Shared values avoid obvious JS precision divergence. DateTimes are stored as ISO-8601 text (database.dart:58-62), while sqlite3's WASM bindings use JavaScript BigInt for SQLite 64-bit integers. No cross-platform numeric corruption is supported by the schema pass.

GOOD

First-open seed is atomic. seed_data.dart:30-77 gates and writes settings/templates/boards/ritual data inside one Drift transaction, limiting partial-seed divergence across executors.

GOOD

Correct cleanup boundary pattern. library_file_cleanup.dart:1-13 is a small, readable conditional-import example to reuse.

GOOD

Focus timer degrades safely. Wakelock errors are caught (active_session_controller.dart:175-185,437-446) and wall-clock timer state does not rely on a continuously firing browser timer (active_session_controller.dart:82-93).

GOOD

Normal browser Back uses the guarded save path. canvas_editor_page.dart:481-485 intercepts route pops, and :258-305 saves the title, drains controller writes, and warns on failures before navigation. F15 is limited to external tab/page teardown and unexpected disposal.

GOOD

Android persistence stays app-owned. connection_native.dart:1-4 and canvas_import.dart:61-68,146-164 use the application documents directory for SQLite and copied media. library_file_cleanup_io.dart:5-59 resolves paths and deletes only inside Zenno's canvas_media/thumbnails roots.

GOOD

Native database work is isolated from UI. Locked drift_flutter 0.2.8 creates a background native connection for driftDatabase; the main-isolate concern is specific to the direct web executor in F04.

Recommended order of work (analysis only)

  1. Make lock lifetime failure-safe (F02), with typed initialization errors and real recovery behavior (F11).
  2. Add a web compile and real browser-database smoke lane (F09), including an immediate-reload durability case (F15), so every later change has evidence.
  3. Consolidate native file operations behind compile-time platform boundaries (F01). Do not change database architecture at the same time.
  4. Decide web's product contract: preview only, or real note storage. If real, solve durability/backup, media-store divergence, and offline shell availability before encouraging use (F05/F06/F18).
  5. Profile direct-WASM write latency before changing worker strategy (F04). Preserve the known no-hang behavior.
  6. Remove platform-specific startup waste and complete web lifecycle/input handling (F12/F14/F15/F17).
  7. Align capability/configuration, namespace policy, WASM delivery, and maintenance documentation (F03/F07/F08/F10/F13/F16).

Coverage and limits

Inspected areas include app/bootstrap/router, all repository dart:io/dart:js_interop/kIsWeb references, database connection/provider/schema setup, Web Lock implementation, canvas import/export/PDF/image reload, library thumbnails/cleanup, controller persistence cadence and teardown, focus wakelock behavior, Android manifests/Gradle settings, web manifest/index/WASM presence, dependency lock entries and relevant dependency runtime source, tests, README, AGENTS lessons, and relevant hidden project guidance.

Not verified at runtime: whether the current checkout compiles for web; browser API availability in the intended in-app browser; actual IndexedDB migration behavior; WASM binary/package compatibility; frame timing; Android device behavior; PWA launch orientation; storage eviction.
