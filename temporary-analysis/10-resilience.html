Executive summary

Zenno has several thoughtful local recovery controls: Drift transactions protect multi-row writes, the canvas editor records failed writes and offers a full-state retry, normal canvas exit is guarded, focus runtime is checkpointed, web tabs are locked to one database client, and most direct user actions show failure feedback. The core offline posture is also favorable: runtime data is local SQLite/IndexedDB and this pass found no network-backed note persistence path.

The highest residual risks occur at boundaries those controls do not cover. Canvas recovery state exists only inside the live controller, so a process kill or forced teardown can lose changes that were visible but not durable. Structurally incomplete canvas elements are intentionally omitted without warning and can then be deleted by full-state reconciliation. Focus restoration turns a database exception into an apparently empty state and retains a failed future with no retry path. Structurally wrong reflection JSON is likewise treated as empty and can be overwritten as empty. Deleting a Goal column also cascades all saved reflections while its confirmation names only the cards. A database open/migration/seed failure is retained by both Drift and the keep-alive provider, yet visible Retry buttons only re-query that poisoned instance. Several lower-level failures are mislabeled as normal empty states or escape their UI callback entirely. Finally, there is no app-wide crash/recovery or durable diagnostic boundary around startup and uncaught asynchronous failures.

Findings

R01 · Canvas recovery queue is volatile across abrupt lifecycle loss

HighConfidence: highData integrityRecovery

The editor applies mutations to memory immediately and starts asynchronous write-through. Failed closures are retained only in CanvasController._failedWrites. Normal back calls flush(), detects the queue, and asks before leaving, but controller disposal performs an unawaited flush and then destroys the only queue. There is no app-lifecycle checkpoint, durable journal, or startup recovery record for failed canvas mutations.

Evidencelib/canvas/canvas_controller.dart:232-252, :931-943, :1059-1117, :4514-4526; lib/canvas/canvas_editor_page.dart:207-214, :258-305, :481-485.
Root causeRecovery ownership is coupled to a route-scoped in-memory controller. The navigation guard is strong for cooperative exits but cannot cover OS process death, app crash, forced route teardown, or a storage outage that outlives the page.
ImpactFresh ink/text may remain visible during the session yet be absent after restart if its write failed and the process ended before full-state retry succeeded. This is the most direct threat to note-taking trust found in pass 1.
Analysis-only recommendationDesign a durable, idempotent mutation journal or draft snapshot owned above the route, with lifecycle-triggered flush, startup replay, and an explicit recovered/unsaved state. Preserve the existing normal-exit guard as a second layer.

R02 · Structurally incomplete canvas elements disappear silently

HighConfidence: highSilent failureData visibility

loadElements reconstructs each generic element from a kind-specific detail table. If that detail row is absent, _reconstruct returns null and the caller simply omits the element. There is no placeholder, warning, quarantine record, count mismatch, or diagnostic event. Transactions make this unlikely during healthy writes, but the behavior specifically handles corruption by hiding content.

Evidencelib/canvas/persistence/canvas_repository.dart:77-83, :177-192, and each silent return null at :213-300. Full-state sync computes every stored-but-not-loaded ID as stale and deletes it at :575-591.
Root causeThe read path treats “cannot reconstruct” as “element absent,” conflating corruption with a legitimate empty result.
ImpactA note stroke, text block, image, PDF page, link, or shape can vanish from the editor even though its generic row still exists. A later full-state retry could then synchronize the reduced in-memory set and make the omission harder to recover.
Analysis-only recommendationReturn a structured load result containing valid elements plus per-row recovery faults. Render a non-destructive placeholder, block destructive full-state sync while unresolved corruption exists, and provide export/diagnostic recovery before any cleanup.

R03 · Focus restoration failure collapses into “no session” and has no retry

HighConfidence: highRecoverySilent failure

The keep-alive controller starts restoration in an unawaited microtask. _restoreAtStartup has a finally but no catch: any database/decode failure sets state from “restoring” to “none” while the stored future remains failed. Focus Home consequently shows “Start session,” not a retry/error state. Later startFrom awaits the same failed future and fails before starting, so the feature can remain poisoned for the app lifetime.

Evidencelib/features/focus/application/active_session_controller.dart:103-117, :131-138, :406-455; lib/features/focus/presentation/pages/focus_home_page.dart:49-59.
Root causeThe state model represents “restoring” and “none,” but not “restore failed,” and the restoration future is immutable after failure.
ImpactAn in-progress or review-pending study session is hidden from the user, and new sessions may fail generically until restart. The database row is not proven lost, but recovery is inaccessible.
Analysis-only recommendationAdd an explicit restoration error state with safe retry that replaces the failed future. Keep persisted sessions authoritative; never offer a fresh start until restoration either succeeds or the user explicitly resolves the stale session.

R04 · Startup and uncaught async failures lack an app-wide recovery boundary

HighConfidence: highCrash surfaceObservability

main awaits immersive-mode and orientation platform calls before runApp, without fallback. No runZonedGuarded, FlutterError.onError, PlatformDispatcher.onError, or ErrorWidget.builder is configured anywhere in runtime source. Feature-local catches are useful, but errors from discarded futures and startup/plugin boundaries can still produce a blank launch, framework error screen, or console-only failure.

Evidencelib/main.dart:7-15. Repository-wide searches found no global Flutter/Dart error boundary; runtime diagnostics are isolated debugPrint calls.
Root causeFailure handling is implemented feature-by-feature, with no last-resort presentation, correlation, or recovery layer.
ImpactA platform-channel failure before first frame can make all notes inaccessible for that launch. Later uncaught errors are not converted into a stable, actionable “reload/retry/export diagnostics” experience.
Analysis-only recommendationLet the app render even if non-essential system UI calls fail. Add a privacy-conscious global boundary that records bounded local diagnostics and shows a recoverable shell without ever logging note contents or file paths unnecessarily.

R05 · Settings writes are discarded without failure feedback or retry ownership

MediumConfidence: highAsync failureFlow

Every settings control passes repository futures into callbacks typed as void. The futures are neither awaited nor caught. On storage failure, the control may snap back only when the unchanged stream re-emits—or appear accepted until restart—and the async error has no feature-local owner. The same pattern is used for canvas palette persistence; tool-wheel position is a notable exception because it catches and informs the user.

Evidencelib/features/settings/presentation/pages/settings_page.dart:112-113, :128-182, :200-240, :271-272; lib/canvas/canvas_editor_page.dart:664-671. Contrast lib/canvas/widgets/canvas_toolbar.dart:229-244.
Root causeUI callback signatures erase the returned Future<void>, and there is no shared settings write state/error presenter.
ImpactTheme, stylus mapping, pen response, focus defaults, keep-awake, palette, and sort preferences can silently fail. Unhandled future errors also feed the global crash/observability gap.
Analysis-only recommendationRoute all preference writes through one async command helper or controller that serializes rapid changes, exposes saving/failure state, restores confirmed values on failure, and offers unobtrusive retry.

R06 · Focus actions mutate the timer before persistence, then report the whole action as failed

MediumConfidence: highPartial failureState coherence

pause, resume, endStretch, and skipBreak mutate and emit the in-memory engine before awaiting the database checkpoint. If persistence fails, the UI says the action “could not” happen even though the visible timer has already transitioned. stop similarly finishes/abandons the engine and stops its ticker before the closing row is durable, though its UI permits retry.

Evidencelib/features/focus/application/active_session_controller.dart:192-220, :264-303; user-facing catch paths in lib/features/focus/presentation/pages/focus_active_page.dart:119-166, :199-213.
Root causeThe operation has two commits—memory first, database second—but exposes one undifferentiated success/failure result.
ImpactThe user may repeat an action unnecessarily or misunderstand whether the timer is paused, on break, finished, or still recoverable. A crash between the two commits restores older runtime.
Analysis-only recommendationModel “transition applied, persistence pending/failed” explicitly. Keep the wall-clock engine responsive, but make checkpoint status visible and retryable; use idempotent transition identifiers if exact phase history matters.

R07 · Periodic focus checkpoints can overlap during slow or failing storage

MediumConfidence: medium-highBackpressureRecovery

A one-second Timer.periodic invokes an async _onTick without awaiting it. Once the 15-second threshold is reached, the counter resets only after a successful write. If a checkpoint takes longer than a tick, subsequent ticks can start additional writes; during sustained failure, each tick retries. There is no in-flight/coalescing flag.

Evidencelib/features/focus/application/active_session_controller.dart:344-370, :391-404.
Root causeRetry cadence is driven by a counter but not serialized around the async persistence operation.
ImpactStorage degradation can cause a retry storm, extra database pressure, noisy console errors, and potentially stale snapshots competing with newer ones. Drift may serialize execution, but the controller does not establish that guarantee.
Analysis-only recommendationAllow at most one checkpoint in flight, coalesce to the newest runtime snapshot, and retry with bounded backoff while retaining an immediate retry for lifecycle/phase transitions.

R08 · Missing/corrupt media renders as a permanent placeholder with no diagnosis or recovery

MediumConfidence: highSilent failureAttachments

Image decode catches every object and returns null; PDF rasterization catches every object and returns. The element remains present, but the UI has no terminal error state distinct from “not rendered yet,” no retry control, and no path validation during load. Failures are not even sent to debugPrint. The PDF service also memoizes initialization and document-open futures; a rejected future is never evicted, so a transient failure is permanent for that controller lifetime.

Evidencelib/canvas/canvas_controller.dart:4069-4141, :4269-4317, :4327-4338; failed-future caches at lib/canvas/pdf/pdf_raster_service.dart:97-113. Source paths are loaded from lib/canvas/persistence/canvas_repository.dart:232-263.
Root causeRaster failure is treated as an acceptable cache miss even when permanent. Failure state is not represented, and memoized futures are retained on rejection.
ImpactImported learning material silently becomes inaccessible while its placeholder can be mistaken for transient loading. Image decode exceptions before the explicit dispose calls can also retain native buffer/descriptor/codec resources, and later viewport scheduling can retry a still-null element.
Analysis-only recommendationTrack per-element raster status and reason category; show a quiet broken-media indicator with bounded retry, relink, and metadata-only removal. Evict rejected initialization/document futures and dispose partially created image resources in finally. Never auto-delete the DB row or source merely because decode fails.

R09 · Startup orphan cleanup can race a concurrent media import

Medium severityHigh impact / low likelihoodConfidence: mediumFile integrityRace

Library provider creation starts orphan cleanup in the background and does not await it. Cleanup first snapshots all database-referenced media, then later scans and deletes every file absent from that snapshot. Import independently copies a new file before its element row is durably written. With no lock or age threshold, a long-running cleanup can observe the newly copied file as unreferenced and delete it during that window.

Evidencelib/features/library/application/library_providers.dart:15-24; lib/features/library/data/library_repository.dart:28-45; lib/features/library/data/library_file_cleanup_io.dart:29-50; copy-before-write at lib/canvas/io/canvas_import.dart:87-107, :115-132, :151-164.
Root causeReference snapshot, file staging, element commit, and deletion do not share synchronization or a generation/age rule.
ImpactAn imported image/PDF may be committed with a path whose file has just been removed, leading directly to R08. Ordinary startup timing makes the race unlikely, but large media directories or slow storage widen it.
Analysis-only recommendationUse a staging directory/manifest and atomic promote-after-DB-commit, or serialize cleanup with imports. Cleanup should ignore young files and recheck live DB references immediately before each deletion.

R10 · Web database initialization can remain in an indefinite loading state

MediumConfidence: mediumOfflineAvailability

The web connection is a delayed future that sequentially acquires a browser lock, fetches/initializes SQLite WASM, and opens IndexedDB. It has no timeout, cancellation, or root-level retry owner. A rejected open normally reaches provider error UIs, and the second-tab case is handled specifically, but a promise that stalls leaves feature providers loading indefinitely.

Evidencelib/core/database/connection_web.dart:6-21; lib/core/database/web_database_lock.dart:16-41; library loading fallback lib/features/library/presentation/pages/library_page.dart:282-325.
Root causeInitialization is lazy and distributed across feature provider subscriptions; no database-bootstrap state machine owns timeouts and retry.
ImpactThe library can show a spinner forever with no explanation. Web offline startup additionally depends on WASM/app assets being locally available; the runtime source does not establish an explicit offline readiness state.
Analysis-only recommendationAdd a bootstrap coordinator with bounded phase timeouts, named failure phases, explicit retry/reload guidance, and a locally testable “offline assets unavailable” state. Keep the existing exclusive-tab message.

R11 · File cleanup suppresses all exceptions and can stop halfway without evidence

LowConfidence: highObservabilityStorage

Both owned-file deletion functions wrap the entire operation in one broad catch. A single path-resolution, permission, or deletion error ends the remaining loop and is suppressed. The repository then reports successful canvas deletion because DB deletion is intentionally authoritative. Media preparation also copies into the final owned directory before image decode/PDF probe; if a later preparation step fails or placement is no longer possible, that copy is not removed and relies on a later opportunistic orphan scan.

Evidencelib/features/library/data/library_file_cleanup_io.dart:5-26, :29-51; caller at lib/features/library/data/library_repository.dart:187-205. Copy-before-decode/probe has no rollback at lib/canvas/io/canvas_import.dart:87-107, :115-132; controller early returns do not unlink the copy at lib/canvas/canvas_controller.dart:3897-3948, :3967-4026.
Root cause“Best effort” is implemented as operation-wide exception suppression instead of per-file isolation plus bounded outcome reporting.
ImpactOrphan files can accumulate after either deletion or failed import, and failures cannot be distinguished from successful cleanup. Direct note loss is not established because DB content is either already intentionally deleted or was never committed.
Analysis-only recommendationContinue per file, count skipped/deleted/failed paths, and record only non-sensitive reason categories. Surface storage cleanup health in diagnostics, not as disruptive modal UI.

R12 · Corrupt preference/tool JSON silently falls back with no repair signal

LowConfidence: highSilent fallbackObservability

Palette, tool-wheel position, tool-wheel presets, arrow control points, stylus mapping, and pen profile decoders intentionally fall back on malformed JSON. This keeps the app usable, but the user receives no indication that persisted settings were ignored, and diagnostics cannot distinguish corruption from intentional defaults.

Evidencelib/features/settings/data/settings_repository.dart:293-364; lib/canvas/persistence/canvas_repository.dart:1105-1155, :1186-1199; lib/canvas/input/stylus_button_mapping.dart:38-57; lib/canvas/input/pen_profile.dart:45-66.

ImpactUnexpected tool behavior can interrupt drawing flow and persist unnoticed. This does not directly corrupt note content in the reviewed paths.

R13 · Structurally invalid reflection JSON becomes empty content and can be saved destructively

HighConfidence: highData integritySilent failure

Reflection parsers throw for invalid JSON syntax, but syntactically valid values with the wrong shape are deliberately accepted as empty. A non-array schema, non-object prompt entries, missing/wrong-typed prompt fields, a non-object answers payload, or non-string answer values can therefore remove prompts or answers from the in-memory entry with no error. Existing-entry Save remains enabled even for an empty schema and empty answers; saving writes the derived empty map back as {}, irreversibly replacing the original answers_json value.

Evidencelib/features/goal_cycle/domain/reflection_template_schema.dart:27-37, :89-105, :125-140; mapping at lib/features/goal_cycle/data/reflection_repository.dart:254-266; unconditional existing-entry save at lib/features/goal_cycle/presentation/pages/reflection_editor_page.dart:92-109, :125-133; overwrite at lib/features/goal_cycle/data/reflection_repository.dart:306-317.
Root causeDeserialization uses one plain domain value for both “legitimately empty” and “persisted value failed structural validation.” The editor has no access to the original raw JSON or a validation fault.
ImpactSaved reflective learning content can appear blank. Merely opening the entry is non-destructive, but pressing Save can convert a potentially recoverable raw payload into an empty object. Duplicate/blank prompt keys can also collapse answers into the wrong field.
Analysis-only recommendationReturn a validated parse result that preserves the raw payload and reports structural faults. Make corrupt entries read-only by default, offer raw export/recovery, reject blank or duplicate prompt keys, and never rewrite a failed parse until the user has explicitly repaired it.

R14 · Link-target query failure is presented as “No other canvases”

MediumConfidence: highSilent failureFlow

The canvas link dialog awaits a future from canvasListProvider, but once that future completes it never checks snapshot.hasError. A failed database/provider query produces no data, is converted to an empty list, and displays the legitimate empty-state copy “No other canvases to link to.” There is no retry in the dialog.

EvidenceChooser query at lib/canvas/canvas_editor_page.dart:326-346; ignored error and null-to-empty conversion at lib/canvas/widgets/link_target_dialog.dart:157-170.
Root causeThe FutureBuilder branches only on completion, then conflates absent data from failure with a successful empty result.
ImpactCross-canvas linking becomes unavailable precisely during a storage/provider fault, while the user is told their library contains no targets. This prevents informed retry and can make existing notes seem missing.
Analysis-only recommendationHandle loading, error, and successful-empty as distinct states. Preserve the typed error privately, show calm retry copy, and recreate the options future on retry.

R15 · A missing seeded board becomes a normal empty board whose Add action is a no-op

MediumHigh impact / low likelihoodConfidence: highSilent failureRecovery

Both board repositories convert zero joined rows into a synthetic board with an empty ID and no columns. The shared UI treats that as a legitimate new board and invites the user to add a column. The repository then looks up the real seeded board and, if it is absent, returns normally without inserting anything. The UI receives apparent success but remains empty.

Evidencelib/features/revision/data/revision_repository.dart:55-105, :302-320; parallel goal behavior at lib/features/goal_cycle/data/goal_repository.dart:55-112, :350-368; empty-state action at lib/shared/kanban/kanban_board_view.dart:325-378.
Root cause“Seeded board missing” is encoded as ordinary domain data, and the write API treats a missing invariant as a successful no-op.
ImpactRevision or goal organization can look freshly empty and cannot be repaired in-app. Normal seeding is transactionally protected, so this primarily matters after corruption, external DB damage, or a bad legacy state.
Analysis-only recommendationRepresent missing required boards as an invariant/recovery error, not an empty board. Make writes throw on missing ownership and offer a non-destructive repair that recreates only missing scaffolding without replacing user boards or cards.

R16 · Canvas export catches domain errors but lets storage/rendering exceptions escape

MediumConfidence: highRecovery outputUnhandled async

Export gives helpful feedback for CanvasExportException, including missing media and size limits. However, the service also awaits application-directory lookup, directory creation, raster/codec operations, worker encoding, and a flushed file write, any of which can throw a different exception. The toolbar starts the export future from a void method and catches only the domain type. Its finally closes the progress dialog, but the original error then escapes without user feedback.

EvidenceUnowned call at lib/canvas/widgets/canvas_toolbar.dart:711-724; narrow catch at :1999-2025; raw I/O awaits at lib/canvas/io/canvas_export.dart:130-163.
Root causeThe export boundary translates expected content faults but not infrastructure faults, and its caller does not own the returned future.
ImpactLow storage, permission/path-provider failure, codec failure, or an isolate/worker error ends export with no explanation or retry. Export is an important recovery route when note durability is in doubt.
Analysis-only recommendationCatch all export-boundary failures, map them to safe reason categories, retain the underlying exception for bounded diagnostics, and keep retry available. Avoid claiming a destination until the flushed write succeeds.

R17 · Creating a focus-session canvas has no busy or failure owner

MediumConfidence: highUnhandled asyncFlow interruption

From Focus Setup, choosing “Create new canvas” closes the picker and awaits LibraryRepository.createCanvas inside an async callback with no catch, busy guard, or feedback. A database failure therefore becomes an uncaught asynchronous error and leaves the focus draft unchanged without explanation.

R18 · Board moves can commit, then report failure during post-commit renormalization

MediumConfidence: highPartial successOrdering

Goal and revision card moves first commit the moved row, then query and optionally renormalize the destination column. Column reorders use the same two-stage pattern. Renormalization itself is transactional, but the initial move/reorder is outside that transaction. If the later read or transaction fails, the returned future fails even though the move already became durable; the shared UI reports “Could not move/reorder.”

Evidencelib/features/revision/data/revision_repository.dart:168-182, :283-290, :356-401; mirrored at lib/features/goal_cycle/data/goal_repository.dart:198-212, :331-338, :404-449; UI error wrapper at lib/shared/kanban/kanban_column_view.dart:914-927.
Root causeOne user action spans two database commits but exposes a single all-or-nothing result.
ImpactThe card/column may visibly move while a snackbar says it failed. When positions are already dense, failed normalization can leave ambiguous ordering and encourage a duplicate user action.
Analysis-only recommendationRun move plus density check/renormalization in one transaction, or treat normalization as idempotent maintenance whose failure is surfaced separately without denying the committed move.

In contrast, both boards, Focus Setup and History, recent history, reflection lists/template pickers, attachment lists, and canvas pickers interpolate $error directly into the UI and generally have no invalidation/retry action. Raw Drift/platform exceptions may contain SQL, local paths, or implementation details while still not telling the user what action is safe.

Evidencelib/features/revision/presentation/pages/revision_board_page.dart:95-128; lib/features/goal_cycle/presentation/pages/goal_board_page.dart:84-117; lib/features/focus/presentation/pages/focus_history_page.dart:30-37; lib/features/focus/presentation/pages/focus_setup_page.dart:37-45, :79-85; lib/shared/canvas_attachments/canvas_picker_dialog.dart:97-104; lib/features/goal_cycle/presentation/widgets/goal_card_detail_sheet.dart:350-369.

Analysis-only recommendationBefore deletion, query and display the exact number of cards and saved reflections affected. Prefer soft deletion/trash with restore for learning content; at minimum require a stronger confirmation whenever reflections exist and verify the cascade in a dedicated test.

R23 · Soft/optional relationships use destructive foreign-key cascades and rely on every caller to compensate

MediumHigh impact / low likelihoodConfidence: highSchema invariantHistory preservation

Several nullable relationships represent categorization or historical context, but their schema action is ON DELETE CASCADE. Deleting a folder at the schema level can delete its canvases; deleting a linked canvas can delete focus sessions; deleting a ritual item can delete historical check snapshots. Current repositories carefully avoid the first two outcomes by nulling the link before delete, and ritual UI retires rather than deletes, but the database itself enforces the opposite of those preservation semantics.

EvidenceFolder → canvas cascade at lib/core/database/tables/canvas_tables.dart:18-33; canvas → focus-session and ritual-item → historical-check cascades at lib/core/database/tables/focus_tables.dart:74-98. Manual compensation is at lib/features/library/data/library_repository.dart:158-170 and :187-199; ritual items are retired at lib/features/focus/data/ritual_repository.dart:111-114.
Root causeReferential cleanup was encoded as ownership even where the domain treats the reference as optional metadata. Preservation therefore depends on repository choreography instead of a matching schema invariant.
ImpactA future maintenance path, migration, raw repair, or partial refactor that deletes the parent directly can erase entire canvases or study history. Normal current UI paths mitigate this, so likelihood is low and formal severity remains Medium.
Analysis-only recommendationModel these links as SET NULL (and preserve ritual snapshots independently) so the database’s default failure behavior protects content. Add direct-parent-delete tests proving canvases, focus sessions, and historical labels survive without repository pre-cleanup.

R24 · One out-of-range persisted enum can fail an entire query or stream

MediumHigh impact / low likelihoodConfidence: highCorruption isolationCrash surface

Thirteen persisted enum fields use Drift’s index converter. Generated row mapping calls EnumIndexConverter.fromSql, whose implementation directly evaluates values[fromDb]. The table definitions do not add a range constraint, fallback, quarantine, or row-local recovery. Consequently a single out-of-range value from corruption, a faulty migration, or external database modification throws during row mapping and rejects the whole query/stream instead of isolating the affected row.

EvidenceExamples include canvas element mapping at lib/core/database/database.g.dart:3192-3258, focus-session mapping at :8264-8370, and board mapping at :10022-10052. Enum columns originate at lib/core/database/tables/canvas_tables.dart:47-63, :140-182; lib/core/database/tables/focus_tables.dart:51-62; and lib/core/database/tables/board_tables.dart:11-15. Drift 2.31’s checked-in dependency implementation indexes without bounds handling at /Users/karlromero/.pub-cache/hosted/pub.dev/drift-2.31.0/lib/src/runtime/types/converters.dart:242-260.
Root causeStorage validity is assumed at decode time, and read APIs return all-or-error collections rather than a result that can carry quarantined rows.
ImpactOne damaged element can prevent a canvas from loading; one damaged session or board enum can take its whole history/board read offline. R19 then often presents a raw exception without a repair/retry path. No existing note is necessarily deleted, but access and recovery are feature-wide.
Analysis-only recommendationAdd database range constraints and migration validation for every enum. R25 · Feature Retry buttons cannot recover the keep-alive database after open/migration/seed failure

HighConfidence: highAvailabilityRecovery trapDatabase bootstrap

The app creates one synchronous, keep-alive ZennoDatabase around a delayed native/web connection. Both the delayed opener and Drift’s migration engine retain their first failure: LazyDatabase keeps a completed-error completer, and Drift explicitly stores a migration/before-open error and rethrows it on every later operation. Library, Settings, and canvas show Retry controls, but those controls only invalidate their feature stream or call load again; none closes/replaces databaseProvider. A transient acquisition failure or any migration/seed error is therefore unrecoverable inside the running app.

EvidenceThe database is keep-alive at lib/core/providers/database_provider.dart:6-14 and opened through one delayed connection at lib/core/database/connection_native.dart:1-4 / connection_web.dart:6-21. Feature retries only invalidate list streams at lib/features/library/presentation/pages/library_page.dart:302-323, invalidate settings at lib/features/settings/presentation/pages/settings_page.dart:49-58, or rerun controller load at lib/canvas/canvas_editor_page.dart:132-150. No runtime call invalidates databaseProvider.
Root causeDatabase bootstrap is hidden behind feature queries, while retry ownership stops one layer above the failed, permanently memoized resource.
ImpactAll notes, boards, reflections, and focus history can remain inaccessible for the process lifetime while Retry appears available but deterministically repeats the same failure. A restart may recover a transient error, but the app does not say so and offers no safe read-only/export/repair mode.
Analysis-only recommendationOwn database bootstrap as an app-level state machine. A retry must dispose the failed instance, create a fresh connection, rerun integrity/migration checks, and atomically rebind dependent providers. Separate retryable acquisition failures from migration/corruption failures; for the latter, preserve the file and offer backup/export diagnostics before repair.

R26 · Persisted viewport values bypass the invariant that canvas transforms are invertible

MediumHigh impact / low likelihoodConfidence: highCrash surfaceCorrupt-state recovery

The gesture code assumes every viewport scale has been clamped strictly positive, because screen-to-world mapping inverts its matrix. Interactive zoom does clamp new values, but canvas, bookmark, and link loaders construct ViewportState directly from persisted doubles without finiteness/range validation, and the schema has no positive-scale constraint. A stored zero makes the matrix singular; pointer conversion then throws. Negative or non-finite values can make content unreachable or propagate invalid geometry.

EvidenceRaw loads at lib/canvas/persistence/canvas_repository.dart:755-773, :825-840, and :1202-1218; the controller adopts the saved viewport unchanged at lib/canvas/canvas_controller.dart:876-905. CanvasTransform.toWorld states the positive-scale assumption and calls Matrix4.inverted at lib/canvas/engine/canvas_transform.dart:80-91. The table declares vpScale as an unconstrained real at lib/core/database/tables/canvas_tables.dart:39-43.
Root causeValidation exists at gesture mutation boundaries but not at persistence/import boundaries, so an engine invariant is documented rather than enforced.
ImpactA single corrupted camera record can let a canvas render into a broken state and then throw on touch/stylus input, blocking recovery from inside that canvas. Saved bookmarks/region links can reintroduce the same invalid state.
Analysis-only recommendationValidate finite translation/rotation and clamp finite positive scale at every decode boundary. Preserve the invalid raw values in diagnostics, fall back to identity/last-known-good viewport, and add schema checks plus fixtures for zero, negative, NaN-like, and extreme values.

Existing resilience controls worth preserving

  • Atomic multi-row writes: canvas element/detail writes, full-state canvas sync, focus session creation, goal saves, and revision creation use Drift transactions.
  • Canvas cooperative-exit guard: normal back flushes in-flight writes and warns before leaving with unsaved mutations.
  • Canvas full-state retry: retry does not replay possibly stale individual closures; it synchronizes current elements, layers, bookmarks, viewport, paper, and tool state.
  • Deleted-canvas protection: editor load checks existence and refuses to resurrect a stale route as a misleading blank note.
  • Focus persistence: opening session and ritual snapshot are atomic, runtime is checkpointed, wall-clock time survives throttled ticks, and pending reviews restore.

  • Owned-path deletion boundary: file cleanup resolves paths and only deletes beneath app-owned media/thumbnail roots.
  • Offline-first data plane: note/session repositories use local SQLite/IndexedDB; no runtime network persistence dependency was found in pass 1.
