Zenno performance, scalability, and resource analysis

Analyzer 08 examined rendering, rebuild breadth, allocation pressure, database/query cost, startup, large-note behavior, and resource lifetime. The dominant risk is not one slow API: several “viewport bounded” paths still perform work proportional to the entire note, while global controller notifications amplify that work during pen and pointer input.

Highest-value sequence: introduce one stable id/rank map and atomic bulk element-store path; use them to make hydration, commands, spatial-hit recovery, painting, and raster scheduling linear or viewport-bounded; split controller notifications by concern; then make tile invalidation and raster decoding incremental. These changes protect handwriting flow without changing durable note semantics.

Detailed findings

F01 · Large-canvas hydration becomes quadratic after full payload materialization

HighConfidence: high

Root cause. The repository correctly batches detail-table reads by element kind, but reconstructs every element and decodes every ink point before first display. The repository order is only zIndex; the controller then replays that list one element at a time through an insertion API that rescans the growing list for duplicate detection and for the layer-position-plus-z insertion point. Its comparator also linearly searches layers.

  • lib/canvas/persistence/canvas_repository.dart:83-193 reads every base row, issues up to six kind-detail reads, and reconstructs the full list; ink decoding occurs at :213-230.
  • lib/canvas/persistence/ink_codec.dart:76-123 creates one Dart StrokePoint per persisted point.
  • lib/canvas/canvas_controller.dart:862-923 awaits all document parts, then loops through loaded elements at :897-899.
  • addElementToStore scans for duplicate id and insertion point at canvas_controller.dart:791-807; _compareElements calls the linear _layerById at :635-642, 762-770.

Impact. Opening a handwritten note grows with total element and point count, not the viewport. The controller replay is O(n²); synchronous object construction increases the pre-first-frame heap. The likely result is a visibly stuck loader or process pressure on the target tablet. Durable rows are not directly corrupted, but an app kill breaks thinking flow.

Analysis-only recommendation. Introduce a bulk hydration path: build a layer-rank map, sort once by layer position and z, assign the list once, then build an id map and spatial index and derive the next z-index in one pass. For genuinely large notes, separate light element metadata from ink payload and decode visible/near-visible ink lazily or on an isolate, while preserving deterministic durable ordering.

F02 · One controller notification rebuilds the page, canvas view, toolbar, and bookmark listener

HighConfidence: high

Root cause. CanvasController is a single broad ChangeNotifier. The editor page listens around its entire loaded body; the nested view listens again around its four paint layers; the 4,841-line toolbar and bookmark menu each listen again. Notifications include high-rate hover and gesture state, not only document mutations.

  • lib/canvas/canvas_editor_page.dart:476-679 wraps all shortcuts, canvas, toolbar, title, and menu construction in a page-wide ListenableBuilder.
  • lib/canvas/render/canvas_view.dart:1455-1547 adds another controller listener around layout and all paint delegates.
  • lib/canvas/widgets/canvas_toolbar.dart:322-385 listens around the toolbar layout; canvas_bookmarks_menu.dart:23-76 listens independently.
  • Hover always notifies without an equality guard at canvas_controller.dart:1973-1977. Eraser and lasso append notify on every accepted raw move at :2031-2038, 2594-2600. Live ink is frame-coalesced, but still reaches every listener at :721-738.

Impact. Handwriting, hover, panning, erasing, and lassoing repeatedly reconstruct large widget subtrees and short-lived collections. RepaintBoundary protects raster repaint isolation, not Dart widget build cost. On a dense editor this competes directly with input latency.

Analysis-only recommendation. Expose small listenables or selectors for load/error, viewport, committed elements, live stroke, overlay, selection, rasters, and tool UI. Keep the page listener limited to load/save-error state; drive painters through targeted repaint/revision signals; keep static toolbar children outside builders. Add hover equality/screen-distance gating and frame-coalesce gesture overlays.

F03 · “Viewport-bounded” committed painting still scans or maps the whole note

HighConfidence: high

Root cause. The quadtree identifies visible ids, but the non-tile path recovers z-order by walking the entire element list. The tile path rebuilds two full-note maps on each paint before querying only visible tiles. Thus spatial culling reduces expensive draw calls, but not CPU/allocation cost to O(visible).

  • lib/canvas/render/elements_painter.dart:383-415 queries the spatial index, then calls _paintVisibleElements.
  • _paintVisibleElements loops every element and tests set membership at :429-456.
  • _paintCachedTiles creates elementsById and paintOrderById across every element at :491-499, even when pictures are already cached.
  • Viewport changes make the delegate repaint-eligible at :982-1003; CanvasView passes the entire visible-layer list at canvas_view.dart:1492-1508.

Impact. Pan and zoom frame cost and garbage scale with total note size even when only a few strokes are on screen. This contradicts the painter’s O(visible) contract and makes large, spatially sparse notes degrade.

Analysis-only recommendation. Maintain a stable controller-side id → element map plus paint-rank map. Convert quadtree hits directly to candidate references and sort only those candidates by stable rank. Pass these stable structures into the cache instead of allocating full maps in paint.

F04 · Each committed stroke globally clears tile pictures and committed stroke paths

HighConfidence: high

Root cause. Any structural element mutation increments one global revision. On the next paint, the tile cache treats that as a full-document invalidation, disposes every retained picture, and also clears the committed stroke-path cache. Recording then resumes for every visible tile.

  • lib/canvas/render/elements_painter.dart:62-85 has clear() dispose all pictures and clear strokePathCache; _syncRevision calls it for any revision change.
  • The painter calls _syncRevision before cached painting at :398-408; uncached tiles are re-recorded at :87-120.
  • lib/canvas/canvas_controller.dart:669-673 increments the shared element revision; add/remove call it at :807-834. Ending a stroke commits via AddElementCommand at :1307-1328.

Impact. The cost of pen-up is proportional to all visible committed content, not the new stroke. On a dense handwritten page, the pause can land exactly between strokes and interrupt the natural writing cadence. The same invalidation discards reusable high-zoom geometry for unaffected strokes.

Analysis-only recommendation. Invalidate only tiles overlapped by the old/new bounds of changed elements. Keep the stroke path cache independent from tile pictures and remove entries only for changed/deleted stroke ids. A command can expose its dirty world regions without altering durable data or undo semantics.

F05 · Images decode at native resolution and visible rasters can exceed the nominal 96 MB budget

HighConfidence: high

Root cause. Both initial import and later hydration decode the complete image without target dimensions. The cache budget evicts only off-screen elements; a single visible high-resolution photo can exceed it by itself. Unlike PDFs, images have no scale bucket or longest-edge cap.

  • lib/canvas/io/canvas_import.dart:87-107 reads the entire file into a Uint8List, then calls instantiateImageCodec(bytes) without target size.
  • lib/canvas/canvas_controller.dart:4299-4317 calls ImageDescriptor.instantiateCodec() without targetWidth/targetHeight.
  • The budget is 96 MB at canvas_controller.dart:446-461, while enforcement skips every visible id at :4447-4487.
  • lib/canvas/pdf/pdf_raster_service.dart:64-76, 174-184 caps PDF raster dimensions, demonstrating the missing analogous image policy.

Impact. A 12,000 × 9,000 decoded RGBA image is roughly 412 MiB before ancillary buffers. Importing or revealing such an image can cause a large frame stall or Android process kill. This is not direct database corruption, but it risks losing the newest in-flight interaction and makes image-heavy notes unreliable.

Analysis-only recommendation. Decode into resolution buckets derived from placement size × zoom × device pixel ratio, with a hard per-raster dimension/byte cap. Re-decode upward only after zoom settles; degrade visible resolution when needed instead of exempting visible items from a hard total. Avoid the import-time whole-file byte copy where the descriptor/file path API suffices.

F06 · Undo/redo history is unbounded and retains full geometry generations

HighConfidence: high

Root cause. Every command is retained until the controller closes. Commands preserve full before/after element snapshots; moving, scaling, rotating, partial-erasing, or clearing ink can retain additional point-list generations. Raster fields are correctly stripped, but vector geometry remains unbudgeted.

  • lib/canvas/canvas_controller.dart:283-287 defines the stacks; _runCommand appends without a cap at :1128-1134.
  • lib/canvas/engine/canvas_commands.dart:90-289 retains removed/added and original/moved or original/transformed lists. Clear snapshots all elements at :292-319.
  • lib/canvas/model/canvas_element.dart:285-303 translates an ink element by allocating a new StrokePoint for every point.
  • _commandSnapshot at canvas_commands.dart:5-10 explicitly removes image/PDF rasters, a verified strength that does not bound vector memory.

Impact. A long thinking session with repeated transforms or partial erases can keep large, unreachable-from-current-state ink arrays alive, increasing GC frequency and eventual OOM risk. Data remains correct while resident, but resource exhaustion threatens continuity.

Analysis-only recommendation. Define an undo memory budget, not merely a command count. Estimate retained point bytes per command, coalesce adjacent nudges/transforms, and drop the oldest commands only after their resulting state is durable. Preserve a clear, user-consistent undo horizon; never discard current note state.

F07 · Long stroke/eraser/lasso work is superlinear both during input and at commit

HighConfidence: high

Root cause. The mutable live-stroke builder is an improvement over per-sample list spread, but each frame’s snapshot still copies the entire accumulated point list and invalidates the full perfect-freehand outline. Eraser and lasso getters copy their paths on every broad rebuild and notify for each move. At gesture completion, narrow-phase eraser proximity/splitting and lasso coverage compare path segments or points against complete stroke geometry, producing O(path-points × stroke-points) work for each candidate.

  • lib/canvas/canvas_controller.dart:100-130 invalidates the cached snapshot per append and rebuilds it with List.unmodifiable; frame-coalesced notification is at :721-738.
  • lib/canvas/render/live_stroke_painter.dart:24-55, 108-152 rebuilds a complete outline whenever the stroke revision changes.
  • lib/canvas/engine/stroke_builder.dart:70-109 creates a PointVector list and perfect-freehand outline across all render points.
  • Eraser/lasso getters copy their current paths at canvas_controller.dart:543-551; appends notify unthrottled at :2031-2038, 2594-2600.
  • lib/canvas/tools/canvas_geometry.dart:62-107 nests polyline segment/vertex comparisons; lasso coverage repeatedly scans the polygon at :116-153; partial erase scans the eraser path for each stroke point/segment at :195-337.
  • Eraser and lasso broad phases query the spatial index but recover candidates by walking all elements at canvas_controller.dart:2147-2170, 2622-2635. Ink centerline lists are then reallocated at :2202-2209, 2679-2685.

Impact. Per-frame work rises with gesture duration, creating the familiar “the longer I draw, the slower it gets” curve; pen-up for a broad erase or large lasso can then synchronously multiply gesture length by candidate geometry. Dense handwriting is the worst case and the pause lands directly in the thinking loop.

Analysis-only recommendation. Keep a stable read-only view/version for active points, finalize immutable stroke chunks, and rebuild only a small mutable tail. Decimate gesture paths by minimum screen-space distance before exact work, notify overlays at most once per frame, map spatial hits directly, and use segment-level spatial acceleration/early coverage termination for exact commit geometry.

F08 · Export can retain every source raster plus 32 MP output and encoding buffers

MediumConfidence: high

Root cause. Export prepares every scoped raster before rendering and retains owned images until completion. The 32-megapixel output cap still permits a ~128 MiB RGBA surface. JPG export obtains another raw RGBA buffer, copies it, and creates a worker-side image representation. Source image decode is native resolution.

  • lib/canvas/io/canvas_export.dart:127-180 caps only output pixels at 32 Mi pixels.
  • _prepareElements accumulates decoded images/PDF pages in owned until the final finally at :315-390.
  • Image export decode has no target size at :393-409.
  • JPG takes raw RGBA then Uint8List.fromList before compute at :425-444. The isolate is a verified CPU-responsiveness improvement, but peak memory remains high.

Impact. A deliberate large export can stall or kill a memory-constrained tablet, especially for image/PDF-heavy content. Export failure does not delete the note, but a process kill can interrupt concurrent persistence and flow.

Analysis-only recommendation. Decode source rasters to export-required dimensions, tile the output or lower the default tablet pixel cap, release per-tile resources promptly, and avoid the extra JPG copy with transferable/worker-friendly buffers where supported. Surface the operation as explicitly heavy with progress.

F09 · Canvas open serializes independent reads and rereads the same canvas metadata row

MediumConfidence: high

Root cause. The controller awaits existence, layers, elements, bookmarks, viewport, rotation lock, paper, and tool settings one by one. Viewport/rotation/paper/tool methods each independently select the same canvases row.

  • lib/canvas/canvas_controller.dart:872-882 contains the sequential await chain.
  • lib/canvas/persistence/canvas_repository.dart:829-908 implements four separate canvas-row metadata reads; existence is another query at :959-965.

Impact. Fixed DB latency is added directly to every canvas open. It matters more on the synchronous WASM/IndexedDB web path and compounds F01 before the first useful frame.

Analysis-only recommendation. Read the canvas row once into a document-metadata value and use it for existence and all metadata fields. Run truly independent layers/elements/bookmarks reads concurrently only if the Drift connection’s transaction/ordering behavior remains explicit and safe.

F10 · Active Focus checkpoints can retrigger a full 2N+1 history load every 15 seconds

HighConfidence: high

Root cause. Every session-table stream emission sequentially fetches distractions and ritual checks for every session. The active timer writes runtime fields back to that same table every 15 seconds, so its own checkpoint can invalidate the full-history stream. The ritual foreign key lacks a session-id index. History UI and statistics also eagerly materialize/refold the complete history.

  • lib/features/focus/data/focus_repository.dart:367-399 watches all sessions without limit and performs two awaited child queries inside the loop.
  • lib/features/focus/application/active_session_controller.dart:357-403 emits each second and updates the session row after 15 seconds or a phase change.
  • lib/core/database/tables/focus_tables.dart:85-103 defines ritual checks without an index on sessionId; distractions do have one at :105-119.
  • lib/features/focus/presentation/pages/focus_history_page.dart:47-59 uses ListView(children: [...for every session]).
  • lib/features/focus/application/focus_stats_provider.dart:18-30 filters, copies, and folds the full history on each emission.
  • lib/features/focus/presentation/pages/focus_home_page.dart:31-35, 122-155 watches full history and stats but renders only sessions.take(5); pushed Active/Review routes normally leave Home mounted underneath.

Impact. During an active focus session, years of study history can turn a routine checkpoint into hundreds or thousands of sequential reads and allocations while the timer UI remains live. Route retention means this is likely even when the pushed Active page covers Home. The exact watcher-retention behavior is an architectural inference; the invalidation/query chain itself is direct.

Analysis-only recommendation. Give Home a limited recent-session query, paginate History, fetch children in joined/grouped batches for only the current page, and compute aggregates in SQL or incrementally. Add the ritual-check session index. Keep runtime-only checkpoints from invalidating full detail feeds, either through narrower reactive queries or a separately watched summary.

F11 · Goal board query multiplies card rows by every historical reflection

MediumConfidence: high

Root cause. The live board query joins reflection entries directly only to count their ids in Dart. Each reflection duplicates its card, detail, column, and board fields in the result. Any reflection-table change invalidates and remaps the entire board stream.

  • lib/features/goal_cycle/data/goal_repository.dart:60-100 documents and executes the card × reflection fan-out.
  • _rowsToBoard allocates per-card sets and walks every joined row at :103-169 solely to derive reflectionCount.

Impact. As reflection practice succeeds, opening or refreshing the goal board transports and maps more duplicated data even when the visible card information is unchanged except for a count. This is a slower-burn learning-history scalability issue, not an immediate data-integrity defect.

Analysis-only recommendation. Replace raw reflection rows with a grouped COUNT(*) GROUP BY card_id subquery/join, or keep card rows and counts in two batched reactive queries combined by id. Preserve the current set-based correctness for duplicate prevention.

F12 · Library initialization duplicates initial watch reads and launches a full DB/filesystem cleanup

MediumConfidence: high

Root cause. Canvas/folder watchers explicitly call get() before subscribing to Drift watch(), whose first listener performs an initial fetch in the project’s pinned Drift 2.31.0. Constructing the auto-dispose repository also launches orphan cleanup: three full table reads, path canonicalization for every reference, and directory scans. Recreating the provider can rerun this work.

  • lib/features/library/data/library_repository.dart:51-70, 104-108, 272-275 routes lists through _watchWithInitialRead.
  • pubspec.lock:284-291 pins Drift 2.31.0; its installed watch() implementation registers a query fetcher whose first listener fetches and emits data, confirming the second read rather than relying on generic API recollection.
  • lib/features/library/application/library_providers.dart:15-24 starts cleanup from provider construction; generated metadata marks it auto-dispose at library_providers.g.dart:27-36.
  • cleanupOrphanedFiles reads all images, PDFs, and canvases at library_repository.dart:28-45.
  • lib/features/library/data/library_file_cleanup_io.dart:29-59 resolves every referenced file and scans both owned directories.

Impact. Initial library presentation competes with maintenance I/O and may receive duplicate full-list emissions. The effect scales with media and canvas count. The current indexed shell likely keeps the active library subscription alive, so repeated cleanup frequency is a risk condition rather than proven constant churn.

Analysis-only recommendation. Use Drift’s watch stream directly unless a measured platform-specific reason requires a manual initial read. Make cleanup an explicit once-per-app-start maintenance service after the first useful frame, keep its singleton lifetime explicit, and batch/canonicalize only app-owned paths.

F13 · Raster scheduling scans the entire note on camera changes, even when there are no rasters

HighConfidence: high

Root cause. Viewport and size changes correctly coalesce scheduling to a post-frame callback, but the scheduler’s “viewport-bounded” implementation converts spatial hits to ids and then walks every element to find visible image/PDF jobs. Every ink, text, link, and shape is visited only to be skipped. Queue draining then resolves each job through another linear id scan.

  • lib/canvas/render/canvas_view.dart:1417-1453 schedules raster work whenever viewport or size changes, with one post-frame coalescing guard.
  • lib/canvas/canvas_controller.dart:4078-4141 queries visible ids, loops all _elements, sorts jobs, clears the queue, and repopulates it.
  • Queue draining calls _elementById at canvas_controller.dart:4152-4173; that helper is a full linear scan at :4247-4253.

Impact. Panning or zooming a large handwritten note adds O(total elements) controller work per changed frame even when the note contains zero images or PDFs. This stacks with F03’s rendering scan and broad F02 rebuilds, making sparse-view navigation scale with hidden content.

Analysis-only recommendation. Maintain the same stable id map proposed for F01/F03 and separately index only raster-bearing element ids. Query spatial candidates directly to elements, filter that much smaller set, and update a stable priority queue at viewport boundaries instead of clearing/rebuilding it on every camera delta.

F14 · The PDF document pool is described as capped but grows until the canvas closes

MediumConfidence: high

Root cause. PdfRasterService memoizes every opened document future by absolute path. There is no count, byte, LRU, or visibility limit; “capped” in the class comment means only that controller disposal eventually tears down the entire map. The service lives for the canvas-controller route lifetime.

  • lib/canvas/pdf/pdf_raster_service.dart:57-60, 84-113 claims a capped pool, declares an unconstrained map, and inserts one future per file path.
  • The only removal is whole-pool disposal at pdf_raster_service.dart:228-247.
  • lib/canvas/canvas_controller.dart:421-428, 4519-4526 owns the service for the controller lifetime and disposes it when the note closes.

Impact. Scrolling across many distinct PDFs within one large canvas retains native document handles, page collections, and library-side state after their pages leave view. The growth is bounded by distinct PDF files in that currently open note, so this is medium rather than high severity; the decoded-page image budget does not cover these handles.

Analysis-only recommendation. Use a small LRU or reference-counted document pool and close inactive documents only after their render/probe jobs settle. Keep one handle shared across pages of the same active PDF, and make lifecycle state explicit so eviction never closes a document still in use.

F15 · Broad settings subscriptions propagate unrelated changes into the app root and open editor

LowConfidence: high

Root cause. The app root watches the complete settings record to select one theme field; the editor also watches the complete record. Settings sliders invoke repository writes on every onChanged sample, and each row update can emit a new full model. The editor itself persists tool-wheel position through the same global row on drag end, causing the root and editor subscriptions to receive an otherwise local chrome change.

  • lib/app.dart:28-42 watches appSettingsProvider around MaterialApp.router but consumes only themeMode.
  • lib/canvas/canvas_editor_page.dart:476-480 watches the same full model in the editor build.
  • lib/features/settings/presentation/pages/settings_page.dart:625-687 wires slider onChanged directly to write callbacks; examples are supplied at :213-239, 402-419.
  • lib/features/settings/data/settings_repository.dart:230-290 persists individual settings with database updates.
  • lib/canvas/widgets/canvas_toolbar.dart:208-259 correctly defers tool-wheel persistence until drag end; canvas_editor_page.dart:645-671 then writes it through the global settings repository.

Impact. Dragging a settings slider creates avoidable database traffic and root rebuilds. Moving the tool wheel produces only one write, but that write can rebuild MaterialApp.router and the open editor despite not changing theme or canvas content. Frequency and exposure are limited, so this remains low severity rather than a core note-data risk.

Analysis-only recommendation. Select only the theme field at the app root and only editor-relevant settings in the canvas. Hold slider state locally during drag and persist on onChangeEnd or with a short trailing debounce, while keeping immediate visual feedback local.

F16 · Bulk commands are atomic in persistence but mutate the in-memory store element by element

HighConfidence: high

Root cause. The command abstraction exposes only single-element add/remove methods. Multi-element delete, replace, move, and transform commands loop through those methods. Each remove runs indexWhere and shifts the list; each add scans for duplicate id, scans for an ordered insertion point, shifts the list, updates the quadtree, and increments the global element revision. Persistence mutations are responsibly coalesced into one transaction, but that does not coalesce the synchronous controller work.

  • lib/canvas/engine/canvas_commands.dart:13-33 exposes only scalar store mutation; command apply/revert loops are at :90-289 and ClearCommand repeats the same pattern at :292-321.
  • lib/canvas/canvas_controller.dart:791-834 performs the duplicate scan, insertion scan, list insertion/removal, spatial mutation, raster bookkeeping, and revision bump for every item.
  • _applyCommandMutation batches only durable writes at canvas_controller.dart:945-1017, 1169-1175; moved selection reconciliation adds another element-list search per moved item at :1185-1203.
  • Full editable clear uses RemoveElementsCommand at canvas_controller.dart:2001-2012; selection move/transform commits at :3055-3072, 3127-3170; multi-page PDF import adds every page through ReplaceElementsCommand at :3952-4013.

Impact. Editing k elements in an n-element note is O(k × n) list work, with additional shifts; clearing or replaying most of a note approaches O(n²). Large lasso moves, transforms, deletes, partial erases, multi-page imports, and their undo/redo can synchronously freeze the editor. Repeated revision bumps also discard caches once the command notifies, compounding F04.

Analysis-only recommendation. Add a bulk store mutation surface that accepts removals/replacements atomically: construct the next ordered list and id map once, update or rebuild the spatial index once, reconcile selection once, track/dispose rasters once, and advance one revision with explicit dirty bounds. Keep the existing single persistence transaction and command-level undo semantics so the optimization cannot expose a partially applied durable edit.

F17 · Point transforms allocate a complete Matrix4 per point in grids and gesture overlays

MediumConfidence: high

Root cause. CanvasTransform.toScreen constructs and composes a new Matrix4 for every point; toWorld constructs that matrix and an inverse. Grid painting calls this helper for every dot or line endpoint, while eraser/lasso overlays call it for every accumulated path sample. Input mapping and visible-rect calculation repeatedly use the inverse helper as well.

  • lib/canvas/engine/canvas_transform.dart:68-86 allocates/composes the matrix inside each scalar transform call.
  • lib/canvas/render/grid_painter.dart:38-163, 183-223 invokes the scalar helper per line endpoint or generated dot. Dots are batched into one drawPoints call, but the preceding transforms still allocate individually.
  • lib/canvas/render/canvas_overlay_painter.dart:105-139, 156-183 transforms the full accumulated eraser/lasso path on every overlay paint.
  • lib/canvas/render/canvas_view.dart:272-274, 563-669, 697-723, 938-968 calls the inverse helper in high-rate selection and tool move paths.

Impact. Non-blank paper styles repaint during camera motion and can create hundreds to thousands of short-lived matrix objects per frame; long eraser/lasso gestures add a growing overlay cost. The issue is conditional on paper/gesture choice, so it is medium severity, but it competes directly with the canvas frame budget.

Analysis-only recommendation. Compute the world→screen matrix and inverse once per viewport revision and reuse them. For hot scalar loops, use the already-documented direct rotate/scale/translate arithmetic or transform a point buffer with one matrix. Pass the cached transform into painters/input mapping rather than hiding allocation inside each point helper.

F18 · The quadtree retains empty historical structure and rebuilds all live entries when its root expands

MediumConfidence: high

Root cause. Removing an id deletes its entry but deliberately never collapses empty nodes or shrinks the root. Thus node memory follows the spatial footprint historically populated during the open session, not only current content. Inserting outside the root repeatedly doubles it; every doubling flattens and reinserts all existing entries. A rebuild API exists, but production code never invokes it.

  • lib/canvas/engine/spatial_index.dart:54-86 expands in a loop and explicitly leaves tree structure in place on removal.
  • Nodes split and retain children at spatial_index.dart:183-221, 246-271; no upward empty-child collapse exists.
  • Root growth collects and reinserts every entry at spatial_index.dart:289-355.
  • SpatialIndex.rebuild is defined at :113-122; repository search found use only in test/spatial_index_test.dart:118, not the controller.

Impact. Drawing, moving, then deleting content across a wide infinite canvas can leave an increasingly sparse tree until the note closes. Memory and query traversal can degrade with session history, while far-away bulk moves can trigger O(n) rebuilds several times in one synchronous insert. This is a session resource leak, not durable note corruption.

Analysis-only recommendation. Collapse empty child quartets on removal, track live-entry-to-node occupancy, and periodically rebuild when deleted/history node count materially exceeds live entries. For bulk commands, compute required root bounds once and rebuild once; consider activating a safe coordinate-rebasing policy only as a separate, carefully migrated data-integrity project.

F19 · Canvas writes wake the full hidden Library query and grid beneath the editor

HighConfidence: high

Root cause. The full-screen editor is pushed on the root navigator above a state-retaining indexed shell; the initial Library branch remains mounted underneath. Library watches every non-archived canvas row. Each command transaction touches the current canvas’s updated_at, and viewport/tool/paper saves update the same table, so Drift invalidates the all-canvas query even though the Library is invisible. The resulting provider emission rebuilds Library grouping and its retained sliver tree.

  • lib/config/router/app_router.dart:21-31, 75-80 uses StatefulShellRoute.indexedStack and pushes Canvas on the root navigator above it.
  • lib/features/library/presentation/pages/library_page.dart:239-276 watches canvas/folder/settings providers; the canvas emission feeds full filtering/grouping and sliver reconstruction at :282-365, 519-600.
  • lib/features/library/data/library_repository.dart:47-70 watches all non-archived canvas rows and usually sorts by updatedAt.
  • lib/canvas/persistence/canvas_repository.dart:338-376, 530-551, 1004-1008 touches the canvas row for element commands; viewport, paper, and tool settings also write updatedAt at :868-950.
  • lib/canvas/canvas_controller.dart:1036-1057 debounces viewport persistence to 400 ms, which limits but does not remove hidden Library invalidation after camera gestures.

Impact. Every pen-up can add a metadata write, all-canvas select/sort, model allocation, and hidden widget rebuild on the same isolate/connection serving the active note. Cost grows with Library size and directly competes with the next stroke. It also weakens the benefit of F12’s lazy visible card building because the offstage page still processes provider state and rebuilds structure.

Analysis-only recommendation. Keep element durability per command, but coalesce noncritical recency metadata to an idle/exit checkpoint. Pause or avoid the Library subscription while its shell branch is covered/inactive, then refresh on return. Longer term, separate volatile viewport/tool fields from the row watched by Library and expose a purpose-built lightweight library summary stream; do not sacrifice content saves merely to suppress invalidation.

F20 · Persistence has no backlog bound, and failed-write closures accumulate full captured edits

MediumConfidence: high

Root cause. Every tracked write starts immediately and remains in an unbounded set until the database future completes. Rapid commands are batched only within each command, not across commands, so slow storage can accumulate queued transactions and their captured element batches. On error, the original closure is appended to _failedWrites for every failure. Retry never replays those closures—it clears the list and writes one full current-state sync—so retaining every captured closure provides only a boolean signal while holding potentially large geometry unnecessarily.

  • lib/canvas/canvas_controller.dart:222-252 declares unbounded pending futures and failed write closures.
  • _track invokes the closure immediately, adds every future, and retains every failed closure at canvas_controller.dart:1099-1117.
  • Each command ends in a new tracked applyElementBatch closure carrying delete/upsert lists at canvas_controller.dart:991-1017, 1128-1166.
  • retryFailedWrites discards all captured closures and instead snapshots/synchronizes the entire current canvas at canvas_controller.dart:1059-1090, proving individual failed closures are not required for recovery.
  • Exit blocks on every pending write in waves at canvas_controller.dart:926-943 and canvas_editor_page.dart:258-299.

Impact. A burst of long strokes or transforms on a slow device can create database backpressure, memory retention, and a long pause when leaving. Under a persistent storage error, continuing to work accumulates failed closures and their ink snapshots; resulting memory pressure increases the chance of process death before recovery, which can lose edits that exist only in memory.

Analysis-only recommendation. Serialize writes through a bounded/coalescing queue keyed by canvas/element while preserving command order and flush guarantees. Replace the failed-closure list with a failure generation/boolean plus the already-used full-state recovery snapshot. Apply backpressure or coalesce superseded metadata and same-element writes, but keep completed-stroke durability prompt and never drop the latest state.

F21 · Unbounded element-id IN clauses eventually hit SQLite variable/query limits

HighConfidence: high

Root cause. Large-note loading collects every element id per kind, then passes each complete list into one Drift isIn predicate. Bulk delete/sync and canvas-file cleanup do the same. In pinned Drift 2.31.0, isIn(values) creates one bound Variable per value. SQLite executors have finite host-parameter and statement-size limits, but the application does not chunk or join these lists.

  • lib/canvas/persistence/canvas_repository.dart:83-175 collects all ids and issues one IN detail query per kind; a handwriting-heavy note concentrates nearly all ids in the stroke query.
  • Bulk delete and recovery use whole delete-id lists at canvas_repository.dart:494-551, 554-591.
  • lib/features/library/data/library_repository.dart:207-230 repeats the all-element-id pattern before deleting a canvas to find its media.
  • pubspec.lock:284-291 pins Drift 2.31.0; inspection of that installed version’s Expression.isIn confirms a list comprehension producing one variable expression per input value.

Impact. Below the hard executor limit, SQL construction, binding, parsing, and large id lists still add startup memory and CPU. At the limit, a very large handwritten note can fail to open; a clear/large delete can mutate the in-memory view but fail persistence and enter recovery; deleting the note itself can also fail before the cascade. Rows are not inherently corrupted, but note accessibility and reliable save flow are compromised.

Analysis-only recommendation. Replace id fan-out with joins from each detail table to canvas_elements filtered by indexed canvas_id and kind, or chunk ids beneath a conservative cross-platform bind limit inside one read/transaction. Delete by canvas predicate or chunked ids where semantics permit. Add a static large-cardinality repository test later, but do not depend on any one platform’s current compile-time SQLite limit.
