Zenno touch, stylus, palm, and gesture safety audit

Analyzer 07 · analysis-only · current worktree · continuously revised

Safety boundary. This report is the only file written. No source, configuration, dependency, test, Git, branch, remote, PR, or external-service state was changed. No build, test, install, app run, or destructive command was performed.

Executive summary

1critical
6high
12medium
2low

Primary conclusion: Zenno rejects touch-driven viewport changes only after a tool pointer is active inside CanvasView. That protection is too local and starts too late. Touch contacts recorded before the pen can still invoke history shortcuts, a palm on selected content can capture the sole tool-pointer slot and commit a move, and the separate toolbar subtree can accept palm taps while the stylus is drawing.

The worst sequence is recoverability-destroying: an unintended undo occurs while a stroke is live, then the pen-up commit clears the redo stack. The previously undone note mutation is no longer recoverable through Zenno's history. The relevant chain is directly supported by canvas_view.dart:980-997, canvas_controller.dart:1140-1166, and canvas_controller.dart:1123-1134.

A repository-wide gesture scan also found organizational-integrity risks outside the editor: Library canvases and Kanban cards make their entire visual card a generic long-press drag source. A held stylus or palm-origin contact can therefore arm a persistent move without an explicit handle. These are rated medium because they reorder or refile content rather than deleting note content.

Input ownership map

The core architectural issue is not one bad threshold; it is that six interaction trackers and a sibling toolbar can be active without one authoritative arbiter.

Design direction. A single editor-level modality coordinator should decide which pointer set owns the interaction before any controller mutation. Controller previews already make most content gestures cancelable; the missing layer is intent/arbitration before those previews and history commands begin.

Findings

F-01 · A stationary palm chord can permanently strand an undone note change

CriticalConfidence: highData integrityPalm rejection

Root cause. The two-/three-touch shortcut is a maximum concurrent-contact counter, not a bounded tap recognizer. It has no elapsed-time, common-down-window, common-up-window, stylus proximity, or active-stroke check. Movement beyond 8 px and cancellation disqualify it, but a long stationary two-contact palm still calls undo(); three contacts call redo().

Evidence
  • lib/canvas/render/canvas_view.dart:317-327 records touch contacts and only tracks the maximum count.
  • lib/canvas/render/canvas_view.dart:511-517 disqualifies only movement beyond tapSlop; there is no duration criterion.
  • lib/canvas/render/canvas_view.dart:780-797, 980-997 resolves the chord after the final tracked touch lifts and invokes history with no _toolPointerId guard.
  • lib/canvas/canvas_controller.dart:1140-1166 applies undo/redo to the persisted element store.
  • lib/canvas/canvas_controller.dart:1123-1134 clears redo whenever a new command is committed.
  • test/canvas_view_input_test.dart:86-174 covers immediate chords, movement, and cancellation, but not duration, palm-shaped contacts, pre-pen contacts, or a chord released during a live stroke.

Failure sequence. Two palm contacts land first and remain within 8 px; the stylus starts a stroke; the palm lifts while the stylus is still down, causing undo; pen-up commits the new stroke and clears redo. The prior command is now absent from both the visible canvas and redo history.

Impact. Existing note content can be removed from application history by accidental input during handwriting. This violates the project's absolute data-integrity priority and interrupts thinking with an action that may not be noticed immediately.

Analysis-only recommendation. Replace contact counting with an explicit, short two-/three-finger tap recognizer. Disqualify on stylus down/hover, any live tool gesture, excessive down/up spread, duration, or palm-like contact metadata when available. Add a test for the exact pre-touch → stylus-down → touch-up → stylus-up sequence and assert both element state and redo history. Consider making multi-touch history shortcuts opt-in on the S Pen-first surface.

F-02 · A palm inside the selected frame captures input, blocks the pen, and commits a move

HighConfidence: highData integrityGesture arbitration

Root cause. Any touch beginning inside the selected frame—including blank space between sparsely selected items—becomes the global _toolPointerId immediately and calls beginSelectionDrag(). Unlike the deferred stylus/mouse selection session, the touch path does not wait for tap slop before applying deltas. A later stylus down is ignored because the one tool-pointer slot is occupied.

Evidence
  • lib/canvas/render/canvas_view.dart:303-316, 400-412 gives a selected-content touch ownership of _toolPointerId and starts drag immediately.
  • lib/canvas/canvas_controller.dart:2954-2970 defines selection hit testing over the whole visible selection box, explicitly including blank group interior.
  • lib/canvas/render/canvas_view.dart:337-341 ignores the stylus when any tool pointer already exists.
  • lib/canvas/render/canvas_view.dart:529-547, 719-722 routes every matching touch move into selection translation.
  • lib/canvas/canvas_controller.dart:3055-3072 commits any non-zero accumulated delta as an undoable, persisted command.
  • test/canvas_view_input_test.dart:392-465 proves direct touch move/scale is intended, but there is no concurrent palm-first/stylus-second arbitration test.

Impact. A resting palm can move handwritten notes, images, PDFs, links, shapes, or text; the intended pen stroke is silently absent. The mutation is undoable in isolation, but F-01 and F-03 show that history itself can be perturbed concurrently.

Analysis-only recommendation. Do not grant selection ownership on touch-down. Defer until movement and intent are established; cancel the candidate if stylus proximity/down arrives. For an S Pen-first mode, require two fingers or an explicit manipulation mode for touch transforms of selected content. Keep preview-before-commit semantics already present in the controller.

F-12 · Sub-slop two-touch jitter can both transform the viewport and invoke undo

HighConfidence: highGesture arbitrationHistory + viewport

Root cause. The shortcut and pinch paths do not compete for ownership. Movement up to and including 8 logical px remains shortcut-eligible, while any two-touch move—without its own slop or minimum meaningful span—immediately applies pan/zoom/rotation. The same touch chord can therefore complete both interpretations.

Evidence
  • lib/canvas/render/canvas_view.dart:511-517 disqualifies the shortcut only when movement is strictly greater than CanvasController.tapSlop (8 px at canvas_controller.dart:478-479).
  • lib/canvas/render/canvas_view.dart:550-558 applies pinch on every move whenever at least two touches exist, independently of shortcut eligibility.
  • lib/canvas/render/canvas_view.dart:1382-1410 accepts any non-zero starting distance and applies pan, scale, and rotation immediately.
  • lib/canvas/engine/canvas_transform.dart:18-22, 138-155 permits an exceptionally wide scale range from 1/65536× to 65536×.
  • test/canvas_view_input_test.dart:143-174 disqualifies the test chord with a 40 px move; no sub-slop movement case asserts that history and viewport are mutually exclusive.

Impact. Normal finger jitter or a multi-contact palm can shift/rotate/zoom the spatial workspace and then undo note content on lift. Close initial contacts amplify scale sensitivity. Both outcomes persist through independent controller write paths.

Analysis-only recommendation. Resolve one recognizer outcome per pointer set. Keep the viewport frozen while a multi-finger tap remains possible; once movement/scale/rotation crosses a deliberate threshold, permanently disqualify the shortcut and start a re-baselined transform. Require a sensible minimum pinch span and bound the tap duration.

F-03 · The persistent tool wheel bypasses CanvasView's stylus/touch arbitration

HighConfidence: high for code path; medium for OS palm deliveryTool wheelAccidental destructive action

Root cause. CanvasView and CanvasToolbar are sibling, full-screen layers sharing one controller. Each new pointer is hit-tested independently. The _toolPointerId guard exists only inside CanvasView, so it cannot suppress a touch delivered to wheel wedges, property controls, the 34 px undo/redo buttons, palette, or selection actions.

Evidence
  • lib/canvas/canvas_editor_page.dart:624-674 stacks a full-screen toolbar above the full-screen canvas.
  • lib/canvas/widgets/canvas_toolbar.dart:534-643 keeps the wheel, undo/redo, more button, and palette persistently interactive.
  • lib/canvas/widgets/canvas_toolbar.dart:2733-2786 gives every wheel wedge tap, long-press, and pan handlers.
  • lib/canvas/widgets/canvas_toolbar.dart:905-943 lets 34 px property targets change size, opacity, and smoothing by drag.
  • lib/canvas/widgets/canvas_toolbar.dart:1051-1095 exposes one-tap delete, rotate, and scale operations when the wheel is on its selection page.
  • lib/canvas/widgets/canvas_toolbar.dart:3089-3125 implements side actions as 34 px circular controls; no pointer-kind or stylus-active filter is present.
  • android/app/src/main/kotlin/com/bearhunter/zenno/MainActivity.kt:1-5 is an unmodified FlutterActivity; no app-level Android touch/stylus mediator exists outside the Flutter widgets.
  • test/canvas_toolbar_test.dart:279-327 verifies drawing through wheel gaps, but no test combines a live stylus pointer with a second touch on toolbar controls.

Impact. A palm can switch the next tool to eraser, alter brush opacity/size, move the wheel, invoke undo/redo, or—on the selection page—delete or transform selected notes. An undo during a live stroke has the same redo-clearing sequence as F-01 after pen-up.

Analysis-only recommendation. Centralize input modality state above both siblings. While stylus hover/down is active (plus a short release grace period), reject touch activation on destructive/history/tool controls or require deliberate confirmation for delete. Preserve mouse and accessibility semantics. Add cross-layer tests that hold a stylus on the canvas while touching each mutating toolbar category.

F-04 · A single pre-pen palm pans immediately, even below tap slop

MediumConfidence: highFlow interruptionViewport persistence

Root cause. One touch directly calls panBy() for every move. Tap slop is used only to disqualify shortcuts/long-press; it does not defer panning. Touch is ignored once the stylus owns the tool slot, but a palm that arrives first can already move and persist the viewport.

Evidence
  • lib/canvas/render/canvas_view.dart:504-517, 550-558 records slop state but still pans the one-touch viewport on the same move path.
  • lib/canvas/render/canvas_view.dart:306-312 only ignores touch after _toolPointerId is set.
  • lib/canvas/canvas_controller.dart:1358-1366 persists every non-zero pan through the debounced viewport save.
  • reviews/02-canvas.md:147-149 previously identified this race; current source still supports it.

Impact. The paper shifts under the intended stroke origin, making writing jump and storing the accidental camera position. Note elements are not directly changed, but thinking flow and spatial recall are disturbed.

Analysis-only recommendation. Defer one-finger pan until touch intent crosses a platform-appropriate threshold, and cancel the candidate if stylus hover/down arrives. A stricter, simpler S Pen-first policy is two-finger viewport transform plus explicit pan tool for one-pointer pan.

F-05 · Pre-existing two-touch state can apply a stale pinch after the stylus lifts

MediumConfidence: highGesture state machine

Root cause. Pinch baselines are captured when touch counts change. Touch positions continue updating while a stylus is active, but pinch application is skipped. Ending the stylus does not re-baseline the still-down touches. Their next move compares current palm positions with the old pre-stylus midpoint/distance/angle and can apply the whole suppressed delta at once.

Evidence
  • lib/canvas/render/canvas_view.dart:504-510 updates every active pointer position before arbitration.
  • lib/canvas/render/canvas_view.dart:550-553 skips touch transforms while a tool pointer is active.
  • lib/canvas/render/canvas_view.dart:771-779 clears tool state without calling _syncTouchGesture().
  • lib/canvas/render/canvas_view.dart:1361-1410 computes live pinch from the captured baseline.

Impact. The first post-pen palm/finger move can jump pan, zoom, and rotation and then persist that viewport. This is especially disruptive when the paper is spatially organized.

Analysis-only recommendation. On tool-gesture start, quarantine/cancel active touch gestures; on tool-gesture end, re-baseline any touches still down before accepting further transforms. Track pinch pointer IDs explicitly to make ownership auditable.

F-06 · The default pen long-press cancels a legitimate dot and changes modality

MediumConfidence: highStylus flowDefault mapping

Root cause. The default no-button pen long-press is temporary lasso. Pen-down starts a real live stroke immediately; remaining within 8 px for 520 ms cancels that stroke and starts the mapped action. A deliberately held period, dot, diagram node, or brief pause on the glass is therefore interpreted as mode input rather than ink.

Evidence
  • lib/canvas/input/stylus_button_mapping.dart:18-29 defaults penLongPress to temporaryLasso.
  • lib/canvas/render/canvas_view.dart:364-367 starts the active tool gesture and schedules long-press concurrently.
  • lib/canvas/render/canvas_view.dart:818-858 cancels the pending tool gesture at 520 ms and begins the mapped action.
  • test/canvas_view_input_test.dart:825-876, 1520-1546 validates mode takeover, but not legitimate long-duration dot retention.

Impact. Intended ink disappears and the next movement lassos instead of writes. No committed prior data is lost, but the core handwriting bridge becomes surprising.

Analysis-only recommendation. Make no-button pen long-press disabled by default, or require hover/button/chord intent for modality changes. If retained, use pressure/lift behavior and a visible pre-activation cue, and verify dots and pauses on the target S Pen hardware.

F-09 · A third touch can transform the viewport during a two-touch selection transform

HighConfidence: highGesture arbitrationSelection integrity

Root cause. Selection-transform pointers are tracked in a dedicated set, but a third touch is admitted to the separate global touch pipeline. Its move is not recognized as a selection-transform move, sees at least two total touches, and calls _applyPinch() using the first two touch positions—the same two contacts currently transforming the selection. A third- touch move immediately after landing is a no-op because that pair also established the baseline; the failure appears when a selection-owned finger moves and the next third-touch event applies the stale global baseline. The two state machines are active at once rather than mutually exclusive.

Evidence
  • lib/canvas/render/canvas_view.dart:306-328 admits a new touch to global shortcut/pinch state when _selectionTransformTouchPointers is active and _toolPointerId has been cleared.
  • lib/canvas/render/canvas_view.dart:519-558 routes the first two pointers to selection updates but routes the third pointer to global pinch.
  • lib/canvas/render/canvas_view.dart:906-935 clears _toolPointerId when promoting the first two touches to a selection transform.
  • lib/canvas/render/canvas_view.dart:938-968 calculates selection translation using _toWorld(), so a simultaneous camera change also changes the coordinate mapping used by the content transform.
  • test/canvas_view_input_test.dart:426-465 covers exactly two selection touches only; no third-contact/palm case is present.

Impact. A third finger or palm contact can pan/zoom/rotate the paper while the selected notes are also being scaled/rotated. Because selection transforms commit as commands and the viewport persists separately, one accidental contact can leave both content geometry and spatial framing changed.

Analysis-only recommendation. Make selection transform exclusive: while its fixed pointer pair is active, ignore or explicitly cancel all extra touches and suspend global pan/pinch/shortcut recognition. Decide and document whether a third contact cancels or is ignored, then test both the live preview and final persisted command.

F-13 · The visually solid property ring can pass stylus input through and draw underneath

MediumConfidence: highTool-wheel hit testingAccidental ink

Root cause. When an ink preset is active, the wheel painter fills the complete inner property ring. That paint layer is wrapped in IgnorePointer. Only three 34×34 property controls and the center disk are hittable; the visibly filled areas between them have no hit-test target, so the sibling stack can route a fresh pen-down to the canvas below.

Evidence
  • lib/canvas/widgets/canvas_toolbar.dart:2719-2731 wraps all wheel background paint in IgnorePointer.
  • lib/canvas/widgets/canvas_toolbar.dart:2857-2909 provides only 34×34 hit targets for the sparse property controls.
  • lib/canvas/widgets/canvas_toolbar.dart:2910-2957 separately covers only the center disk.
  • lib/canvas/widgets/canvas_toolbar.dart:2983-3003 paints the entire inner radius as an opaque-looking surface when properties exist.
  • test/canvas_toolbar_test.dart:279-327 deliberately covers transparent outer-wheel gaps, but no test probes the visually filled property-ring gaps.

Impact. A user aiming at the visible wheel can leave an ink dot or stroke on the note beneath it. This is especially likely with a stylus near the small property targets, and the mark may remain hidden by the persistent wheel until it is moved.

Analysis-only recommendation. Make visual and hit-test geometry agree. Either make the noninteractive ring areas visibly transparent, or add an annular hit surface that consumes input and deliberately chooses between property adjustment and wheel movement. Add hit-map tests for center, each property, filled gaps, outer wedge, and transparent wedge gap.

F-07 · Stylus-button state is sampled only on pointer-down

MediumConfidence: mediumHardware-dependentStylus button

Root cause. The mapping decision is made from event.buttons on down. Move events never compare current button bits with prior bits. A button pressed after contact is ignored; a button released during a mapped drag does not end the temporary action before pen-up.

Evidence
  • lib/canvas/input/pointer_classifier.dart:3, 64-65 exposes a bitmask check, not a transition state machine.
  • lib/canvas/render/canvas_view.dart:344-367 resolves side-button mappings only during pointer-down.
  • lib/canvas/render/canvas_view.dart:504-560 routes move events without re-reading button transitions.
  • .plans/plan-canvas-evolution.html:982, 996-1011 explicitly warns that Android reporting varies and recommends hardware diagnostics; no diagnostic/transition layer was found in current source.

Impact. Depending on Galaxy Tab event delivery, temporary erase/lasso/pan can fail to engage or remain active longer than the physical hold, creating unexpected edits.

Analysis-only recommendation. Record prior button bits and resolve down/up transitions during the pointer stream, with cancel-safe restoration. First capture actual S Pen event traces on the target device; do not guess hardware semantics.

F-10 · “Temporary eraser/lasso/pan” becomes persistent when assigned to tap

MediumConfidence: highStylus mapping semanticsAccidental next action

Root cause. Settings reuse one action list and one label set for side-button hold, tap, and drag. The UI calls three actions “Temporary,” but the tap dispatcher handles them by calling setTool(), permanently changing the active tool rather than pushing and restoring a temporary tool.

Evidence
  • lib/features/settings/presentation/pages/settings_page.dart:12-24, 125-160 offers the same action list for hold, tap, and drag.
  • lib/features/settings/presentation/pages/settings_page.dart:481-495 labels the actions “Temporary eraser,” “Temporary lasso,” and “Temporary pan.”
  • lib/canvas/render/canvas_view.dart:1194-1226 handles those tap actions with persistent setTool() calls.

Impact. A user who chooses the literally described tap mapping can believe the tool was momentary, then erase or select on the next pen contact instead of drawing. The wheel updates, but the mapping contract itself is misleading.

Analysis-only recommendation. Use trigger-specific choices and language. Either remove temporary actions from tap, label them “Switch to eraser/lasso/pan,” or define a clear tap lifetime such as “until next stroke.” Do not silently conflate temporary and persistent modes.

F-14 · The default side-button tap can activate eraser while the wheel still says Pen

HighConfidence: highTool-state desynchronizationAccidental erasure

Root cause. The default side-button tap calls togglePreviousTool(). Unlike every explicit wheel/tool selection path, that method swaps only activeTool; it does not synchronize activeToolWheelIndex, apply the corresponding preset, or save tool settings. The wheel renders its selected wedge, center icon, label, and settings from the stale preset index.

Evidence
  • lib/canvas/input/stylus_button_mapping.dart:18-29 makes togglePreviousTool the default tap mapping.
  • lib/canvas/render/canvas_view.dart:1194-1226 dispatches the tap directly to controller.togglePreviousTool().
  • lib/canvas/canvas_controller.dart:1520-1551 synchronizes the wheel index for setTool()/selectToolWheelPreset().
  • lib/canvas/canvas_controller.dart:1596-1603 toggles only activeTool and previous tool.
  • lib/canvas/widgets/canvas_toolbar.dart:833-900 derives visible wheel identity and selection exclusively from activeToolWheelPreset/activeToolWheelIndex.
  • test/canvas_view_input_test.dart:1041-1070, 1340-1356 asserts the toggled active tool but never asserts wheel index or visible label; test/tool_wheel_preset_test.dart has no toggle case.

Impact. After Pen was selected from Eraser, the default button tap can make the next stroke erase while the persistent wheel continues to highlight and label Pen. This is the precise kind of invisible-mode failure that can remove notes before the user realizes the tool changed.

Analysis-only recommendation. Establish one atomic tool-selection method that owns activeTool, previous tool, active preset index, preset values, persistence, and notification. Route toggle through it. Add a regression test covering eraser → pen → default side-button tap and assert controller tool, wheel selection, center label/tooltip, hover mode, and next gesture behavior.

F-11 · A touch long-press lasso can remain active when a stylus gesture begins

MediumConfidence: highPalm-first raceConcurrent gesture state

Root cause. A one-touch long press starts lasso via _longPressLassoPointerId without taking _toolPointerId. If the 520 ms timer fires before stylus-down, the later stylus is allowed to begin its own tool gesture. Touch lasso updates are prioritized separately on move, so both streams can mutate controller interaction state.

Evidence
  • lib/canvas/render/canvas_view.dart:800-815 starts the touch lasso but never assigns tool-pointer ownership.
  • lib/canvas/render/canvas_view.dart:337-367 allows a later stylus because _toolPointerId is still null.
  • lib/canvas/render/canvas_view.dart:524-547 routes the touch lasso and stylus tool through independent early-return branches.
  • test/canvas_view_input_test.dart:1507-1517 verifies touch long-press lasso cleanup only; it does not introduce a stylus after activation.

Impact. With pen active, palm lasso selection can change while handwriting is in progress. With lasso active, both pointers append/finish the same controller lasso lifecycle, so one pointer can end the path while the other still believes it owns it. This creates surprising selection state and can prime destructive selection-wheel actions.

Analysis-only recommendation. Represent touch long-press lasso in the same exclusive gesture owner state as every other tool gesture. Stylus-down should cancel a palm-origin candidate or already-active touch lasso before starting ink.

F-08 · Trackpad and unknown-pointer routing is incomplete

LowConfidence: highNon-primary device

Root cause. Trackpad maps to mouse, unknown pointers become a silent no-op, and CanvasView does not register PointerPanZoom* handlers. Scroll zoom uses a fixed 1.15 factor based only on vertical direction, ignoring magnitude; a zero vertical delta takes the zoom-out branch.

Evidence
  • lib/canvas/input/pointer_classifier.dart:34-46 maps trackpad to CanvasInputKind.mouse and preserves unknown as unknown.
  • lib/canvas/render/canvas_view.dart:337-341 follows tools only for stylus/mouse, leaving unknown input inert.
  • lib/canvas/render/canvas_view.dart:1302-1314 reduces every scroll event to fixed-step zoom.
  • lib/canvas/render/canvas_view.dart:1455-1467 registers pointer and signal handlers but no pan/zoom handlers.

Impact. Trackpad gestures can feel jumpy, do nothing, or follow the active drawing tool instead of the expected navigation model; an unrecognized digitizer is silently dead. This is lower severity because the documented target is a Galaxy Tab with S Pen.

Analysis-only recommendation. Define a trackpad-specific navigation contract and route PointerPanZoom deltas continuously; scale scroll zoom by magnitude; choose a safe, visible fallback policy for unknown devices.

F-15 · Hold/drag radial-menu triggers cannot select a wedge with the triggering contact

LowConfidence: highTool-wheel flowFramework-confirmed

Root cause. Hold, drag, and pen-long-press callbacks insert the modal wheel after the pen is already down. Flutter caches the hit-test path on pointer-down and routes subsequent move/up events to that original path. The new overlay therefore cannot receive the triggering pen stream; its wedges expose tap handlers only, requiring lift and a second tap.

Evidence
  • lib/canvas/render/canvas_view.dart:818-903, 1229-1248 can open quick tools from timers or an in-progress drag.
  • lib/canvas/canvas_editor_page.dart:445-473 inserts the quick-menu dialog asynchronously.
  • lib/canvas/widgets/canvas_toolbar.dart:2056-2144 gives modal wedges onTap actions; it has no marking-menu hover/drag selection API.
  • /opt/homebrew/share/flutter/packages/flutter/lib/src/gestures/binding.dart:359-370, 397-429 documents and implements cached hit tests from down through up/cancel.
  • test/canvas_view_input_test.dart:1009-1103, 1520-1546 checks only that the open callback fires, not end-to-end wedge selection from the triggering gesture.

Impact. A side-button hold/drag that visually suggests a radial shortcut becomes a two-step modal interaction, breaking handwriting flow and increasing the chance that the next tap dismisses the transparent barrier instead of selecting a tool.

Analysis-only recommendation. Either describe and design it explicitly as “open menu, then tap,” or implement a true marking menu that receives pointer-router/global position updates from the original stream and commits the highlighted wedge on release.

F-16 · Releasing an activated temporary-pan hold over a link follows the link

MediumConfidence: highStylus mapping compositionUnexpected navigation

Root cause. Temporary pan is available for both side-button hold and pen long-press. After the 520 ms activation, the state marks the action as long-press-active, resets _toolPointerMoved, and begins an ordinary pan tool gesture. Releasing without subsequent movement bypasses the provisional side-button tap branch and reaches the normal rule that an unmoved pan gesture follows a link.

Evidence
  • lib/features/settings/presentation/pages/settings_page.dart:12-24, 161-170 offers temporary pan for side-button triggers and pen long press.
  • lib/canvas/render/canvas_view.dart:818-903 activates the temporary tool, marks long-press state, resets movement, and begins the new gesture.
  • lib/canvas/render/canvas_view.dart:1006-1013 suppresses release-tap dispatch only for a side-button drag that has not become long-press-active.
  • lib/canvas/render/canvas_view.dart:1075-1080, 1271-1282 follows a link for any uncancelled, unmoved pan gesture.
  • test/canvas_view_input_test.dart:304-331, 1256-1296 tests normal pan link-follow and temporary-pan jitter separately, but never composes hold activation with release over a link.

Impact. Holding for a temporary viewport tool over a link chip can navigate to a different canvas on release even though no link-follow tap was intended. The editor flushes through its guarded navigation path, so this is primarily a severe flow interruption rather than direct data loss.

Analysis-only recommendation. Track the gesture's activation origin. A hold-derived temporary pan should never inherit ordinary tap-to-follow behavior; require post-activation movement for pan, and reserve link following for an explicit non-temporary pan tap.

F-17 · Every Library canvas card is a stylus-capable long-press drag source

MediumConfidence: high for routing; medium for accidental-drop likelihoodOrganizational integrityWhole-card gesture

Root cause. The Library wraps the complete CanvasCard in LongPressDraggable, while the same card is also the tap target for opening a canvas. The draggable supplies neither a device-kind restriction nor a dedicated handle. Flutter's delayed multi-drag defaults to primary-button input and preserves the event's pointer kind, so stylus input is not excluded. Lifting the armed drag over any broad folder header immediately persists a folder move.

Evidence

  • lib/features/library/presentation/widgets/canvas_card.dart:226-273, 322-351 makes the card body an open-on-tap ink response, so open and move intent share the same surface.

  • test/library_page_test.dart:88-180, 208-227 validates deliberate touch drops and failure handling, but has no slow stylus tap, palm contact, drag-cancel, or accidental-header-drop case.

Impact. Resting the pen or palm long enough, then shifting toward a folder header, can refile a canvas without confirmation or an in-app undo. The notes remain intact and the move emits a snackbar, so this is organizational corruption and flow disruption rather than note deletion.

Analysis-only recommendation. Restrict refile drag initiation to a visible, touch-sized handle and define which pointer kinds may start it; keep the rest of the card exclusively for opening. F-18 · Kanban cards arm persistent moves from a long press anywhere on the card

MediumConfidence: high for routing; medium for accidental-drop likelihoodOrganizational integrityGesture arbitration

Root cause. Each Kanban card is also a whole-surface, unfiltered LongPressDraggable wrapped around an InkWell tap target. Unlike column reorder, which correctly confines the gesture to a 44 px handle, card move has no separate owner. Once armed, a drop into an empty column, the 160 px trailing area, or an inter-card zone writes the card's column and fractional position. The controller contract exposes no move undo.

Evidence
  • lib/shared/kanban/kanban_column_view.dart:492-535 wraps the entire card surface in LongPressDraggable<KanbanCardData>; lines 539-600 put the open action inside that same surface.
  • lib/shared/kanban/kanban_column_view.dart:279-299 demonstrates the safer contrasting pattern: column reorder has an explicit 44 px handle.
  • lib/shared/kanban/kanban_column_view.dart:177-247, 633-679 defines full empty-column, 160 px trailing, and inter-card drop targets.
  • lib/shared/kanban/kanban_column_view.dart:68-110 translates an accepted drop into controller.moveCard(); lib/shared/kanban/kanban_controller.dart:19-24 defines the persisted move contract with no inverse/undo API.
  • test/kanban_board_view_test.dart:110-161 covers tap and menu-driven move, but does not exercise long-press card dragging, pointer kinds, drag cancellation, or accidental drop acceptance.

Impact. A slow stylus tap intended to open a learning/revision card can become a drag, and a small subsequent motion plus release over a valid zone can silently reorder it or move it to another learning stage. Content is preserved, but workflow state and study order can change.

Analysis-only recommendation. Apply the already-used column pattern to cards: make the visible drag indicator the only long-press/drag source and keep the body a tap-only open target. F-19 · A selection gesture changes owner mid-contact, splitting undo and then panning the viewport

MediumConfidence: highGesture atomicitySelection + viewport

Root cause. Touch selection manipulation is not one gesture transaction. If the first finger has already moved the selection, landing a second finger calls endSelectionDrag() immediately, committing that translation as a command, and then starts a new selection-transform snapshot. Lifting either transform finger commits the second command and clears both transform owners even though the other finger remains down; that surviving contact is instantly reinterpreted as ordinary one-finger viewport pan.

Evidence
  • lib/canvas/render/canvas_view.dart:303-315, 400-411 gives the first selected-content touch the move-selection owner; lines 306-312 promote a second touch.
  • lib/canvas/render/canvas_view.dart:906-935 calls endSelectionDrag() before beginSelectionTransform(), dividing one continuous contact sequence into two controller transactions.
  • lib/canvas/canvas_controller.dart:3049-3072, 3081-3100, 3127-3175 shows that promotion persists the move command, the transform snapshots the already-moved elements, and cancellation can discard only the second preview—not the first committed move.
  • lib/canvas/render/canvas_view.dart:758-769, 971-977 ends the transform when either owned finger lifts and clears both owner IDs; lines 550-558 then route a move of the still-down contact to viewport pan.
  • test/canvas_view_input_test.dart:426-465 starts with both fingers down before movement and lifts them without an intervening one-finger move; it does not assert undo depth, promotion cancellation, or post-transform owner switching.

Impact. A natural “move, add finger to scale, lift one finger” sequence produces two history entries, so one undo leaves the initial translation behind. If the transform is cancelled, the pre-promotion move still persists. Continuing to move the remaining finger shifts and persists the viewport instead of continuing—or cleanly ending—the selection interaction.

Analysis-only recommendation. Treat promotion and demotion as one gesture session. Snapshot original element geometry on the first touch, preview move/scale/rotation against that single snapshot, and commit one command only after all owning contacts lift. A cancellation should restore the pre-first-touch state. Do not rearm viewport gestures until every contact from the selection session is up; add assertions for command count, two-step undo, cancel after promotion, and remaining-finger motion.

F-20 · Library and Kanban drags cannot reach off-screen destinations

HighConfidence: highGesture completenessOrganization flow

Root cause. Zenno implements Library, Kanban-card, and Kanban-column movement with generic LongPressDraggable widgets, but none reports onDragUpdate into an edge scroller. Kanban has an explicit horizontal ScrollController and each populated lane has a vertical ListView, while Library uses a vertical CustomScrollView; holding a drag near any edge does not advance those scroll positions.

Evidence
  • lib/shared/kanban/kanban_board_view.dart:128-184 places all columns in a horizontally scrolling view with _horizontalController, but the controller is used only by the scroll view/scrollbar.
  • lib/shared/kanban/kanban_column_view.dart:212-249 puts populated cards in a vertical ListView.builder.
  • lib/shared/kanban/kanban_column_view.dart:279-299, 512-535 creates the column/card draggables with no onDragUpdate, pointer-global position callback, or edge-scroll coordinator.
  • lib/features/library/presentation/pages/library_page.dart:566-600, 770-790 likewise combines a vertical CustomScrollView with a draggable that exposes no drag-update route.
  • A repository-wide search finds no EdgeDraggingAutoScroller, autoscroll helper, or drag-update callback outside wheel repositioning. test/library_page_test.dart:88-180 keeps both folders visible, and test/kanban_board_view_test.dart has no draggable widget path.
  • reviews/06-kanban-and-attachments.md:15-17 previously identified Kanban edge reachability; current source still has the same missing path.

Impact. On a non-trivial knowledge base, the core organization gesture becomes impossible or forces risky intermediate drops and manual scrolling.

Analysis-only recommendation. F-21 · Column reorder depends on a 4 px drop slot that grows only after acquisition

MediumConfidence: highTarget acquisitionStylus drag

Root cause. Each inter-column DragTarget renders at AppSpacing.xs—4 logical px—before hover and widens to only 8 px after the pointer has already hit it. The visual indicator and the acquisition region are the same narrow object. The source handle is a much healthier 44 px square, so the gesture begins reliably but is exceptionally difficult to finish at the intended insertion point.

Evidence
  • lib/shared/kanban/kanban_board_view.dart:208-237 sets the target width to xs normally and sm only while hovering.
  • lib/config/theme/app_spacing.dart:8-12 defines those tokens as 4 and 8 logical px.
  • lib/shared/kanban/kanban_column_view.dart:279-299 provides a 44 px drag handle, showing the mismatch between source acquisition and destination acquisition.
  • test/kanban_board_view_test.dart:1-180 checks position arithmetic and non-drag UI flows, but never acquires a column slot through a real pointer drag.
  • reviews/06-kanban-and-attachments.md:23-25 reported the same usability defect before the current branch; current dimensions remain unchanged.

Impact. Stylus users can miss the intended slot, release with no reorder, or land in an adjacent target. Repeated precise attempts break flow; combined with F-20, off-screen reorder is not merely difficult but unreachable.

Analysis-only recommendation. Separate hit geometry from paint geometry. Keep a thin insertion line, but give each slot a 24–48 px transparent acquisition band or divide neighboring column bodies into before/after halves. Add pointer-driven tests for each slot and near-boundary drops.

Challenged and corrected prior claims

Not carried forward: the prior review claim that adding a third touch can reorder the first two pinch points “between moves without a touch-count change” (reviews/02-canvas.md:143-145) is weak against the current implementation. Dart's normal map iteration preserves insertion order; adding a third entry does not itself reorder the existing first two, and touch-up calls _syncTouchGesture() to re-baseline. Explicit pointer IDs would still make the state machine clearer, but the specific third-finger reorder failure is not reported as a supported finding here.

Narrowed: “touch is ignored while stylus drawing” is true only for canvas touches arriving after tool ownership is established. It does not cover pre-existing touches, selection ownership, toolbar touches, or touch-shortcut resolution.

Refined: F-09 does not claim that the third contact changes the viewport merely by moving immediately after landing. That event uses an unchanged first-two- pointer baseline. The supported failure requires an interleaving selection-pointer move followed by a third-pointer event, which applies the global baseline against the now-changed first two positions.

Stale invariant: pointer_classifier.dart:15-16 says a palm “can only ever pan,” but current routing also lets touch move/transform selections, start lasso, and invoke undo/redo. The comment should not be relied on as evidence of safety.
