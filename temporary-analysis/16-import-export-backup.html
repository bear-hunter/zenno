Executive summary

Bottom line: Zenno currently has durable in-place persistence, but not a recovery system. All primary data lives in one Drift/SQLite store while imported media lives beside it as absolute-path files. There is no user-controlled full backup, restore, or portable native document workflow. The visible “Export” command produces presentation images only and saves them to app-local storage.

Largest data-integrity exposure

Device loss, uninstall, app-data reset, database corruption, or a failed migration has no in-app recovery path. Android’s ambient platform backup behavior is not an explicit, verified Zenno contract.

Largest portability trap

The unused native document codec serializes absolute image/PDF paths, not the files. Moving the JSON to another installation would preserve references to locations that do not exist there.

Largest flow break

PNG/JPG/SVG export succeeds into getApplicationDocumentsDirectory()/canvas_exports, then reports an internal path. There is no Save As, share sheet, or file-picker destination.

Strongest existing controls

Element writes and multi-step deletes are transaction-backed; canvas deletion confirms permanence and detaches focus history; schema snapshots and migration fixtures exist through v13.

Scope and method

Analyzer 16 read the repository inventory (including relevant untracked planning/review material), then traced storage from UI actions through controllers, repositories, Drift tables, platform database connections, file-system helpers, and codec tests. The core inspected surfaces include:

  • lib/canvas/io/, lib/canvas/persistence/, lib/canvas/pdf/, canvas controller/editor/toolbar call sites.
  • lib/core/database/, every handwritten table definition, schema snapshots v1–v13, and migration tests.
  • Library cleanup/deletion, settings, reflection JSON models, Android/web platform configuration, and related tests.

Constraint: this task expressly forbids builds, tests, installs, app launches, Git mutations, and external-service changes. Therefore runtime/platform conclusions are labelled as static inferences where appropriate. No credentials or secret values were inspected or reproduced.

Findings

Critical

F01 — There is no complete, user-controlled backup or restore path

Zenno’s primary records are all held by one ZennoDatabase; image/PDF payloads and thumbnails are separate files. The Settings UI covers appearance, stylus, focus, library sort, and About, but exposes no backup, restore, verification, or recovery action. The only export UI offers PNG/JPG/SVG rendering of one canvas.

Confidence
High — exhaustive symbol search found no full-data backup/restore implementation or call site.
Impact
Catastrophic worst case: all canvases, text, ink, boards, reflections, focus history, settings, and imported media can become unrecoverable after device/app-data loss or database damage.
Flow effect
Recovery depends on outside platform behavior rather than a visible Zenno promise; the user cannot verify that a restorable copy exists.
Root cause
Durable local persistence was implemented, but recoverability was not designed as a first-class product boundary.
Recommendation
Design one versioned, self-contained backup package containing a consistent SQLite snapshot/relational export, every referenced media file, a manifest with hashes and app/schema versions, and an atomic validated restore flow. Quiesce/flush writers or use a database-native snapshot, capture the exact referenced-file generation, offer authenticated encryption for the sensitive note archive, and keep source data untouched until full validation succeeds.

Confidence
High.

The export service writes to getApplicationDocumentsDirectory()/canvas_exports using an internal generated filename. The toolbar shows that path in a SnackBar. Root cause
Rendering and persistence were implemented, but the product-level destination/handoff boundary was omitted.
Recommendation
Render to bytes/temp, then use a platform Save As/share flow; only claim success after the destination confirms. Provide an explicit filename and preserve failure/cancel semantics.

The project deliberately supports a web database via WASM + IndexedDB, yet canvas import/export directly imports dart:io, uses File/Directory, requires PlatformFile.path, and calls a documents-directory provider. F05 — One malformed ink blob can make an entire canvas fail to open; missing details disappear silently

loadElements reconstructs every element in one operation. An ink detail is decoded without per-element containment, and InkCodec intentionally throws on short, misaligned, or unsupported payloads. That exception aborts controller hydration and sends the entire editor to its generic load-error state. Conversely, a generic element missing its detail row is simply skipped, making saved content vanish from view without any integrity warning. Malformed shape control-point JSON is caught but replaced with an empty list, so one bad point can silently alter the rendered shape.

Confidence
High.
Impact
A local defect affecting one stroke can block access to otherwise healthy notes. Partial relational corruption can look like legitimate deletion, which is dangerous during later backup or cleanup.
Root cause
The repository has no quarantine/reporting layer between row decoding and canvas hydration.
Recommendation
Load elements independently, collect integrity diagnostics, quarantine undecodable rows without deleting them, and open the rest of the canvas read-only with an explicit recovery banner. Back up raw rows before any repair.

F08 — Import has no preflight size/resource limits or content deduplication

Image import copies the full source, reads all bytes into memory, and instantiates the image codec at native dimensions. There is no source-size, pixel-count, dimension, or available-storage check. PDF page rasterization is bounded later, but the source PDF itself is copied and probed without a file-size policy. Every import receives a fresh UUID copy even when bytes are identical; the PDF table’s long-standing nullable import_hash is never populated or queried.

Confidence
High static evidence.
Impact
A very large or adversarial image can cause long stalls or memory pressure; repeated use of the same large PDF multiplies storage until future media or note writes fail.
Root cause
Export has an explicit pixel budget, but import lacks the corresponding admission boundary and media is addressed by copy path rather than content identity.
Recommendation
Inspect metadata/size before copying or decoding, reject unsafe limits clearly, decode a bounded preview first, check free space, and address/deduplicate app-owned media by a verified content hash with reference counting.

F13 — Startup orphan cleanup can race live imports and undo-restorable media

The library provider launches orphan cleanup with unawaited, so the Library UI becomes interactive while cleanup is still querying a snapshot of referenced paths and scanning the media directory. No lock or generation check coordinates that snapshot with canvas writes. A file copied by an import after the reference snapshot but before/during the directory scan can be deleted as “orphaned,” even if its database row is committed moments later. Similarly, an undoable image/PDF deletion can remove its row while its command still retains the path; cleanup can then delete the only payload before Undo re-adds the element.

Confidence
High for the unsynchronized interleaving; probability depends on media-directory size and user timing.
Impact
A newly imported or undo-restored element can persist with a missing source file, leaving a permanent blank/error placeholder and blocking complete export.
Root cause
Garbage collection decides liveness from one database snapshot, while temporary/import/undo ownership exists outside that snapshot and user actions are not gated on cleanup completion.
Recommendation
Use a media ownership ledger with staged/live/trash states, or coordinate cleanup under the same repository-level lock/epoch as imports and command history. Recheck liveness immediately before each delete and never collect files still reachable from an active editor’s undo stack.

F17 — Normal navigation is durable, but process-lifecycle exits have no save checkpoint

Most canvas mutations are written through asynchronously and normal Back navigation explicitly flushes them. However, Zenno registers no app-lifecycle observer for inactive/paused/detached states. If the route is disposed outside the guarded close path, its final flush is deliberately fire-and-forget. A process kill can therefore end the only in-memory owner of pending writes, the debounced viewport update, or failed-write retry closures before their durable outcome is known.

Confidence
High for the missing lifecycle coordination; the exposure window depends on OS timing and whether a write has already reached SQLite.
Impact
The latest gesture, transform, viewport, or recoverable failed write can be absent after reopening even though older note content remains intact. This is a narrow but high-friction form of silent rollback.
Root cause
Durability is coupled to route navigation and controller lifetime, not to application lifecycle transitions or an app-level write coordinator.
Recommendation
Add an app-level persistence checkpoint for lifecycle transitions, make pending/failed state observable outside the route, and persist debounced state before suspension where the platform gives time. Continue write-through rather than relying on lifecycle callbacks as the sole save mechanism.

F21 — Opening a newer database with an older build silently stamps the schema version backward

Zenno’s migration callback only contains ascending guards such as if (from < 13). The locked Drift version invokes the same onUpgrade callback whenever stored and current versions differ, including downgrades. If a future v14 store is opened by this v13 code, every migration guard is false, the callback succeeds without changing the v14 schema, and Drift records version 13. Reinstalling v14 can then try its 13→14 migration against columns/tables that already exist. There is no explicit “data is from a newer app” refusal or read-only recovery path.

Confidence
