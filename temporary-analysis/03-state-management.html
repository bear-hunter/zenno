Executive summary

The strongest integrity risk is a time-of-check/time-of-use race between startup orphan-file cleanup and canvas media import. A copied image or PDF can be classified using an older database snapshot and deleted before its element reference becomes durable. The remaining confirmed risks mainly concern lifecycle recovery, overlapping asynchronous writes, and UI callbacks that replace compound persisted objects using stale snapshots.

The canvas persistence core is substantially more defensive than the settings and focus-session edges: command mutations are batched, failed writes are retained for full-state retry, and ordinary editor exit awaits a flush. The risk profile is therefore concentrated at cross-controller boundaries and around side effects launched outside an explicit coordinator.

Method and scope

This pass traced Riverpod provider ownership, Drift write paths, timers, stream-backed UI, canvas command persistence, focus-session restoration, shell navigation, teardown, and application-level settings. It covered tracked source and tests plus repository-level instructions and the visible relevant untracked inventory. Evidence is based on static source reading; runtime behavior is not claimed as dynamically reproduced.

  • Primary lens: state ownership, initialization and disposal, asynchronous sequencing, stale snapshots, persistence invariants, and controller/provider interaction.
  • Severity: user impact and likelihood combined, weighted heavily toward loss or corruption of learning material.
  • Confidence: strength of the static execution path, not a claim that the issue was observed on-device.
  • Excluded actions: builds, tests, app launches, installs, migrations, writes outside this file, and all network/Git mutations.

Detailed findings

F1 · Orphan cleanup can delete a newly imported image or PDF before its database reference is durable

High severity High confidence Data integrity TOCTOU

Invariant: once canvas import accepts a file, the owned file and the durable element reference must enter the system as one coordinated operation.

  • lib/features/library/application/library_providers.dart:16-24 launches cleanupOrphanedFiles() without awaiting it whenever the repository provider is constructed.
  • lib/features/library/application/library_providers.g.dart:27-39 marks that generated provider auto-dispose even though the source comment describes a singleton. Active consumers may keep it alive for long periods, but provider reconstruction is still an implicit trigger rather than an explicit once-only lifecycle phase.
  • lib/features/library/data/library_repository.dart:28-45 snapshots image, PDF, and thumbnail references, then separately invokes file-system cleanup.
  • lib/features/library/data/library_file_cleanup_io.dart:29-47 later scans owned roots and deletes every file absent from that earlier snapshot.
  • lib/canvas/io/canvas_import.dart:87-107 and :115-132 copy images/PDFs into the owned media directory before returning the imported value.
  • lib/canvas/canvas_controller.dart:3891-3949 and :3961-4027 only create canvas elements after those copy/probe awaits; lib/canvas/canvas_controller.dart:1103-1117 tracks the resulting persistence asynchronously.
  • The same stale-snapshot class also applies to a first thumbnail write: lib/canvas/canvas_editor_page.dart:217-236 writes the owned file before persisting its path.

Failure sequence: cleanup captures DB references; import copies a file; cleanup scans and deletes that not-yet-referenced path; the controller then persists an element containing the now-missing path. An equally dangerous interleaving exists if cleanup scans while the element write is only in flight. A newly imported element that is removed from the DB but remains reachable from in-memory undo history is another unrepresented lease: cleanup can delete the file that Undo expects to restore.

Root cause: “orphan” is decided from a stale reference snapshot, while file creation, reference insertion, and in-memory undo ownership have no shared lock, lease, staging state, or final recheck. Auto-dispose construction makes the side effect less predictable than a single explicit startup phase.

Impact on thinking flow/data: an image or PDF can appear immediately from memory and later reopen as a placeholder or missing asset. This is persistent loss of imported learning material, not merely a visual refresh issue.

Analysis-only recommendation: move cleanup to a single explicit coordinator after database initialization, serialize it against imports, and make deletion conditional on a fresh per-file database recheck. A stronger design imports into a staging directory, writes/registers the reference transactionally, then atomically promotes the file. Making the provider keep-alive only reduces repetitions; it does not by itself close the race.

Verification needed: a deterministic concurrency test that pauses cleanup after its snapshot, imports a file or writes a first thumbnail, resumes scanning, and asserts the file/reference pair survives. Existing coverage at test/library_repository_test.dart:128-176 verifies deletion-time shared-path handling, but does not invoke startup cleanup.

F2 · One restoration exception permanently poisons focus-session start for the provider lifetime

Medium severity High confidence Lifecycle recovery
  • lib/features/focus/application/active_session_controller.dart:103-118 assigns one microtask to _restoreFuture and exposes restoring state.
  • lib/features/focus/application/active_session_controller.dart:131-138 begins every startFrom by awaiting that same future.
  • lib/features/focus/application/active_session_controller.dart:449-455 resets visible restoring state in finally, but does not catch or replace a restoration failure.
  • The provider is explicitly keep-alive at lib/features/focus/application/active_session_controller.dart:94-95.

Root cause: visible state recovery and asynchronous gate recovery are separate. The finally makes the UI look idle, while _restoreFuture remains completed with the original error. Every later start rethrows before reaching the normal guard or repository create call.

Impact: after a transient read/decoding failure, the user sees a startable focus screen but cannot start a session until the provider container/app restarts. If an in-progress row exists, the UI also lacks an explicit reconciliation state.

Analysis-only recommendation: catch the restoration error, expose a distinct retryable error state, and ensure the gate completes normally after state has been reconciled. A start attempt can retry restoration once or require an explicit retry, but must never repeatedly await an already-failed future.

Verification needed: inject a repository whose first restore read throws and second succeeds; assert that retry/start is possible without reconstructing the provider container. test/active_session_controller_test.dart:14-293 covers successful restore, concurrent start, wakelock failure, and pending-review restore, but no repository restoration exception.

F3 · The periodic focus callback permits overlapping runtime checkpoints

Medium severity High confidence for overlap Medium confidence for stale completion Synchronization
  • lib/features/focus/application/active_session_controller.dart:344-347 uses Timer.periodic(..., (_) => _onTick()); the timer does not await the returned future.
  • lib/features/focus/application/active_session_controller.dart:357-371 increments the counter and awaits a checkpoint after a phase transition or every 15 ticks, with no single-flight guard.
  • lib/features/focus/application/active_session_controller.dart:391-404 resets the counter only after the repository write completes.

Root cause: periodic scheduling and asynchronous persistence have independent clocks. If one write lasts longer than the tick interval once the threshold is reached, subsequent ticks continue satisfying the threshold and launch more writes.

Impact: a slow or locked database can turn one checkpoint into a write burst exactly when the persistence layer is under pressure. Overlap is certain under delayed writes; an older runtime overwriting a newer one is possible if completion order is not guaranteed by the executor, so that narrower consequence remains medium-confidence rather than asserted.

Terminal interleaving: a tick checkpoint already in flight is not joined or cancelled before stop(). The closing write clears runtime fields, while an older checkpoint writes them and the focus tally. Drift normally serializes work on one connection, which may preserve invocation order, but the controller itself does not encode or test the required “terminal write wins” invariant.

Analysis-only recommendation: make checkpointing single-flight. While a write is active, mark a dirty/phase-transition flag; after completion, write the newest engine snapshot once if needed. Keep wall-clock timer computation independent from persistence latency.

Verification needed: a fake repository with controllable delayed completions should assert maximum concurrency of one and monotonic persisted runtime. test/focus_flow_safety_test.dart:70-109 delays a user-triggered pause write, but it completes before a periodic threshold and therefore does not exercise overlapping _onTick calls.

F4 · Rapid compound settings edits can overwrite each other with stale widget snapshots

Medium severity High confidence Lost update
  • lib/features/settings/presentation/pages/settings_page.dart:125-178 reconstructs the entire StylusButtonMapping for each individual selector, copying unaffected fields from the last streamed model.
  • lib/features/settings/presentation/pages/settings_page.dart:180-183 forwards pen-profile changes directly to the repository.
  • lib/features/settings/presentation/pages/settings_page.dart:364-420 constructs each new full PenProfile from the widget’s current profile property.
  • lib/features/settings/data/settings_repository.dart:223-234 persists the whole mapping/profile representation rather than a subfield patch.

Failure sequence: change “hold”; before the settings stream emits and rebuilds, change “tap”; the second callback copies the old “hold” from its stale model and writes a whole mapping, reverting the first choice. Slider interactions create the same class of risk for stabilizer/smoothing.

Root cause: functional update semantics are implemented in a stream-backed view snapshot, outside a serialized state owner. Whole-object last-write-wins persistence amplifies the stale field.

Impact: stylus tuning can feel unreliable and interrupt setup flow. This does not threaten note contents directly, but it violates predictable input behavior for the primary writing tool.

Analysis-only recommendation: route compound setting edits through a notifier/repository API that serializes functional mutations against the latest authoritative value. Maintain optimistic local command state if immediate UI response is desired; persist ordered snapshots and reconcile failures explicitly.

F5 · Focus draft and active controllers keep stale linked-canvas IDs after Library deletes that canvas

Medium severity High confidence Cross-controller stale state
  • lib/config/router/app_router.dart:21-79 uses an indexed stateful shell, retaining branch state while the user moves between Focus and Library.
  • lib/features/focus/application/focus_setup_controller.dart:122-145 owns a screen-lifetime setup draft, and :195-203 only changes the linked ID through explicit user actions.
  • lib/features/focus/presentation/pages/focus_setup_page.dart:224-289 notices that a deleted ID has no matching list row, but leaves the ID in the draft and passes it to session creation; lib/core/database/tables/focus_tables.dart:74-78 enforces a canvas foreign key.
  • lib/features/focus/application/active_session_controller.dart:169-174 stores the start-time config, and :378-388 keeps copying that same config on each tick.
  • lib/features/library/data/library_repository.dart:187-205 correctly nulls database focusSessions.linkedCanvasId before deleting the canvas.
  • lib/features/focus/presentation/pages/focus_active_page.dart:311-324 and focus_review_page.dart:85-97 offer “Open canvas” from the controller’s cached config.

Root cause: the database repairs persisted referential state, but neither screen-lifetime draft nor long-lived active controller watches canvas existence or receives a deletion event. Both treat the selected ID as locally authoritative after selection/start.

Impact: in Setup, the row renders a generic “Linked canvas” label and Start reaches a foreign-key failure until the user explicitly clears/changes the selection. During an active session, deletion leaves a dead “Open canvas” action until the controller is reconstructed. Existing focus history is protected by the Library transaction, so this is a workflow failure rather than deletion of the session record.

Analysis-only recommendation: reconcile linked-canvas existence reactively or validate it before both session creation and navigation. When deletion is observed, update draft/active config to null and keep the already-correct database detachment.

F6 · Settings mutations are fire-and-forget, so write failures are invisible and non-retryable

Medium severity High confidence Error-state ownership
  • The callbacks at lib/features/settings/presentation/pages/settings_page.dart:125-183 invoke repository futures through void callbacks without awaiting or attaching error handling.
  • The pen controls at lib/features/settings/presentation/pages/settings_page.dart:397-419 have the same void callback boundary.
  • Canvas toolbar global palette/wheel settings use the same pattern at lib/canvas/canvas_editor_page.dart:665-671.
  • Unlike these settings paths, canvas content writes are explicitly tracked, surfaced, retained, and retried at lib/canvas/canvas_controller.dart:1059-1117.

Root cause: persistence futures cross a synchronous UI callback with no controller that owns pending/error state. The stream is expected to become the only feedback path, but cannot explain why a write failed.

Impact: a control can snap back or fail to persist after restart with no visible reason. Unhandled asynchronous errors may also reach the framework error zone, depending on the caller.

Analysis-only recommendation: centralize settings commands in a notifier with serialized pending writes and a small error/retry state. Keep feedback unobtrusive, but do not silently claim persistence.

F7 · Ordinary editor exit is guarded, but forced route disposal and app lifecycle changes retain an asynchronous flush window

Low–medium severity Conditional Lifecycle
  • lib/canvas/canvas_editor_page.dart:258-309 safely awaits flush() in the normal close flow and prompts when unsaved writes remain.
  • lib/canvas/canvas_editor_page.dart:207-214 can only launch flush().whenComplete(dispose) without awaiting when the widget is disposed through another route/lifecycle path.
  • lib/canvas/canvas_controller.dart:4507-4526 cancels the viewport timer and relies on the caller to flush tracked persistence before disposal.
  • lib/canvas/canvas_controller.dart:876-882 hydrates layers, elements, bookmarks, viewport, rotation, paper, and tools through separate reads rather than one snapshot transaction, making a forced-dispose/immediate-reopen overlap capable of observing a mixed old/new state.
  • A repository-wide source search found no AppLifecycleListener, WidgetsBindingObserver, or didChangeAppLifecycleState implementation under lib/.

Root cause: durable shutdown depends on one navigation helper, while widget disposal itself cannot await and there is no application-lifecycle checkpoint owner.

Impact: normal back/close is protected. The remaining window is forced route replacement, OS background/termination, or another bypass: an immediate reopen can race the old flush, and abrupt termination can lose writes that existed only in memory or were still pending. Process death can never be fully eliminated, so this finding is deliberately conditional.

Analysis-only recommendation: checkpoint on inactive/paused lifecycle transitions, keep per-canvas persistence ordered independently of widget lifetime, and ensure every route removal uses the guarded coordinator. Preserve the current save-error prompt for ordinary navigation.

F8 · Duplicate canvas attachment is reported as success with a newly generated ID that has no row

Low severity High confidence API invariant
  • lib/core/database/tables/board_tables.dart:98-116 makes (cardId, canvasId) unique.
  • lib/shared/canvas_attachments/card_canvas_attachment_repository.dart:115-135 generates a fresh ID, performs InsertMode.insertOrIgnore, never checks the insert result, and returns the fresh ID unconditionally.
  • lib/shared/canvas_attachments/canvas_picker_dialog.dart:64-156 lists every library canvas and has no attached-ID exclusion, so the UI can select an existing pair.
  • lib/shared/canvas_attachments/card_canvas_attachments_section.dart:70-98 treats the completed future as success and shows no “already attached” result.
  • test/card_canvas_attachment_repository_test.dart:24-93 covers create, failure rollback, attach/rename/detach, and cascades, but not duplicate attach or returned-ID existence.

Root cause: “ignore” conflict semantics are incompatible with a method that promises the identity of a newly inserted row. The command neither returns the existing row nor signals that no insert happened.

Impact: selecting the same canvas again closes the picker and appears to work, but the attachment list does not change. Current callers ignore the returned attachment ID, limiting damage; a future caller could retain a permanently invalid ID.

Analysis-only recommendation: filter already-attached canvases in the picker and make the repository contract explicit: return the existing row ID, throw a typed duplicate error, or use a conflict update that returns the authoritative ID. Add a duplicate-attach invariant test.

F9 · Failed focus transitions leave optimistic engine state divergent from durable runtime

Medium severity High confidence State-machine durability
  • lib/features/focus/application/active_session_controller.dart:192-220 mutates and emits pause, resume, end-stretch, or skip-break state before awaiting _persistRuntime().
  • lib/features/focus/application/active_session_controller.dart:264-303 finishes/abandons the engine and stops its ticker before awaiting the closing database write.
  • lib/features/focus/presentation/pages/focus_active_page.dart:119-137 catches operation failures and clears only the page-local busy flag; it does not restore the prior engine snapshot or expose a durable “transition pending” state.
  • lib/features/focus/presentation/pages/focus_active_page.dart:350-410 renders controls from the already-mutated snapshot, so a failed pause shows Paused and a failed stop shows Finished/Ended even though the row still contains the old lifecycle.
  • test/focus_flow_safety_test.dart:70-109 deliberately fails a pause write and asserts the error message, but does not assert engine rollback, durable runtime equivalence, or restart behavior.

Failure consequences: a failed pause leaves the database running, so a restart before a later checkpoint can count wall time that the local UI considered paused. A failed resume leaves the database paused, so locally focused time can be omitted after restart. Failed phase changes restore the wrong phase/tally. A failed stop leaves a durable in-progress row while the local ticker is stopped; if the user exits/restarts instead of retrying Finish, restoration can resume and add time after the intended end.

Root cause: the controller has an optimistic in-memory transition but no commit/rollback protocol and no durable dirty-transition state. A SnackBar communicates the exception but does not repair either side of the invariant.

Analysis-only recommendation: treat each lifecycle change as a serialized state-machine command. Either persist a candidate snapshot before publishing it, or retain the prior engine/runtime snapshot and roll back on failure. For terminal transitions, expose an explicit “ending, retry required” state that cannot be mistaken for a committed Review/abandon. Reuse the single-flight checkpoint queue recommended in F3.

F10 · “Keep screen on” is sampled only at session start/restore, so changing it during a live session has no effect

Low–medium severity High confidence in implementation Live policy stale state
  • lib/features/settings/presentation/pages/settings_page.dart:233-241 describes the setting as stopping display sleep “while a Focus timer runs” and persists changes from a live switch.
  • lib/features/focus/application/active_session_controller.dart:176-184 samples the setting after start, and :437-446 samples it after restore.
  • lib/features/focus/application/active_session_controller.dart:477-483 performs a one-shot repository read; the keep-alive active controller has no listener to appSettingsProvider or the settings stream.
  • test/active_session_controller_test.dart:202-234 covers a wakelock-service failure at start, while no test changes the persisted setting during an active session.

Impact: turning the switch on during a live focus timer still permits sleep; turning it off can leave the screen held awake until finish/abandon. The behavior repairs itself on the next session. Severity is conditional because the intended product semantics could be “next session only,” but the current copy presents it as a live-session policy.

Analysis-only recommendation: have the active controller listen to just the keep-awake field while a session exists and reconcile changes through a serialized best-effort wakelock command. If changes are intentionally next-session-only, make that contract explicit in copy and tests.

F11 · The “partial seed recovery” path replaces user state and does not preserve logical singletons

Medium severity Recovery-only trigger High confidence Initialization invariant
  • lib/core/database/seed/seed_data.dart:24-33 uses only app_settings.db_schema_seeded as the global proof that all settings, templates, boards, columns, and ritual data are complete.
  • If that marker is false or the row is missing, lib/core/database/seed/seed_data.dart:38-45 uses insertOrReplace with an empty settings companion, resetting every setting to its schema default rather than preserving an existing row.
  • lib/core/database/seed/seed_data.dart:80-145 replaces builtin template rows. Because saved entries use a restricting template foreign key at lib/core/database/tables/reflection_tables.dart:31-36, recovery can fail and roll back instead of opening.
  • lib/core/database/seed/seed_data.dart:148-209 always generates fresh board/checklist IDs and inserts all starter columns/items.
  • lib/core/database/tables/board_tables.dart:10-19 has no uniqueness constraint on boardType, so a partial database can receive duplicate revision/goal boards even though repositories assume one logical board.
  • test/database_test.dart:85-99 verifies an empty database seed, but no test seeds a partially populated database with user settings, existing boards, or reflection references.

Trigger boundary: normal first open is transactional and normal subsequent opens return early, so this is not claimed as an every-start reset. It applies when the marker is false/missing while any user or partially seeded state already exists—the exact recovery state the comments say this routine handles.

Root cause: one boolean is used as a cross-table completeness certificate, while recovery operations are replacement/insertion commands rather than idempotent “ensure missing row” operations. The schema does not enforce several “one per type/default” assumptions.

Impact: recovery may silently reset theme, stylus, timer, and library preferences; add unreachable duplicate boards/rituals; or fail database open when replacement conflicts with saved reflections. The surrounding transaction prevents a partially applied new seed, but it cannot make replacement semantics non-destructive.

Analysis-only recommendation: preserve an existing settings row and update only the marker; use insert-if-missing/update-in-place for fixed builtin templates; enforce one board per type and one default ritual (or discover/repair existing rows); and use per-entity migration/seed checks rather than one global sentinel. Test representative partial states and referenced builtin templates.

F12 · The database schema says a canvas owns focus history, while the repository says history must survive

Medium severity Latent path High confidence Referential integrity
  • lib/core/database/tables/focus_tables.dart:74-78 defines nullable linkedCanvasId with onDelete: KeyAction.cascade.
  • lib/features/library/data/library_repository.dart:187-199 explicitly nulls every linked focus session before deleting a canvas “so the canvas foreign key cannot cascade-delete past study records.”
  • lib/core/database/database.dart:153-157 enables foreign keys on every open, so the cascade is operational rather than documentary.
  • test/library_repository_test.dart:107-126 proves the repository workaround preserves history, while test/database_test.dart:60-82 tests direct canvas cascades only for owned canvas elements and does not assert focus-history survival.

Root cause: ownership semantics are encoded at the wrong layer. A historical session merely references a working canvas; it is not child content of that canvas. Application code compensates, leaving the destructive schema action available to migrations, future repositories, maintenance code, or any direct delete.

Impact: the current UI deletion route is protected. Any path that bypasses that exact repository transaction can delete focus sessions, their ritual snapshots, and distractions through downstream cascades. This is latent rather than a demonstrated current-UI loss, but the failure mode destroys learning history.

Analysis-only recommendation: migrate the nullable foreign key to ON DELETE SET NULL so the database enforces the intended invariant. Keep the explicit repository detachment as defense in depth, and add a direct-database deletion test proving focus history survives.

Protective invariants already present

These patterns materially reduce state risk and should be preserved during any remediation:

  • Database ownership: lib/core/providers/database_provider.dart:6-14 creates one keep-alive database per provider container and closes it on container disposal.
  • Atomic canvas command persistence: lib/canvas/canvas_controller.dart:982-1017 coalesces structural command effects, while lib/features/canvas/data/canvas_repository.dart:530-552 applies delete/upsert groups transactionally.
  • Canvas write recovery: lib/canvas/canvas_controller.dart:1059-1117 records failures without discarding current state, and retries by syncing the latest complete canvas snapshot.
  • Guarded editor exit: lib/canvas/canvas_editor_page.dart:258-309 awaits tracked persistence and exposes a stay/leave choice when writes remain unsaved.
  • Focus creation invariant: lib/features/focus/data/focus_repository.dart:53-111 creates a session and ritual snapshot in a transaction while preventing a second unfinished session; :138-177 repairs older duplicate in-progress rows.
  • Wall-clock timer semantics: lib/features/focus/domain/timer_engine.dart:136-163 derives time from timestamps rather than trusting periodic tick count, limiting UI drift when the event loop stalls.
