Scope and method

Executive summary

Zenno has a clear product decomposition and a strong local-first persistence core, but its implemented dependency graph does not consistently match the documented “feature-first” architecture. The main structural fault line is the canvas: roughly 21,816 handwritten lines across 37 files, including two files over 4,500 lines. Its controller owns document state, command history, tool behavior, persistence write-through, import, raster scheduling, and resource lifetime. This makes the app’s most flow-sensitive subsystem the highest-blast-radius place to change.

The next fault line is ownership. Domain-facing models and rendering code import enums from Drift table definitions; “shared” attachment code imports the concrete library feature; settings owns global pen preferences but imports their types from canvas input; and the canvas editor directly consumes library and settings providers. These edges form cycles and place schema/application details upstream of models that should be stable.

The highest-confidence data-integrity design defect is at the canvas load/recovery seam: missing element-detail rows are intentionally omitted from memory, but later full-state retry reconciliation interprets every durable row absent from memory as stale and deletes it. That turns a lossy read into authoritative destructive repair. Additional exposures deserve hardening: board-card ownership is duplicated without a database invariant tying a card’s board to its column’s board; historical associations rely on repository conventions to override destructive cascades; and abnormal bootstrap recovery can reset preferences, duplicate seeded aggregates, or fail against referenced builtin templates.

Findings

High A01 — Canvas responsibilities are concentrated into change-amplifying monoliths

Confidence
High
Status
Observed structural condition; not itself a proven runtime defect
Flow impact
High: input latency, undo, persistence, imports, and tool UI share change surfaces
Data integrity
Medium exposure: durable writes and document mutation are controlled by the same very large mutable object

Evidence. lib/canvas/canvas_controller.dart is 4,528 lines. Its imports span commands, transforms, spatial indexing, stroke construction, input processing/profile, import, models, PDF rasterization, persistence, geometry, and IDs (:8–26). Its own contract says it holds viewport, elements, live gestures, tool state, undo/redo, spatial index and persistence (:149–178). The same class hydrates seven categories of durable state through sequential repository reads (:862–923), launches and retries asynchronous writes (:926–1117), owns command application (:1123–1135), and disposes raster/PDF resources (:4490–4526). Separately, lib/canvas/widgets/canvas_toolbar.dart is 4,841 lines and lib/canvas/render/canvas_view.dart is 1,553 lines.

Root cause. Canvas features were added around a single mutable controller and a single comprehensive toolbar because those were convenient, already-connected integration points. The architectural seam is class-level rather than capability-level. Historical planning made this direction explicit: .plans/plan-canvas-evolution.html:638–724 said to extend rather than tear down the architecture and assigned viewport, tools, selection, undo/redo, and persistence write-through to CanvasController; its later roadmap then added arrows, export, stylus mapping, smarter pen, and deep zoom around that pipeline (:1432–1501). That plan is context, not proof of a present defect, but it explains the accumulation pattern.

Counterevidence / mitigation. The controller is unusually well covered by focused tests: command, view-input, repository, export, toolbar, fill, geometry, raster and document suites instantiate it directly. Persistence batching is transactional and tested for rollback and newest-state retry (test/canvas_repository_test.dart:804–837,839–927). This reduces regression probability but does not reduce the ownership or change-blast radius.

Recommendation (analysis only). Treat this as a staged subsystem decomposition, not a cosmetic file split. Keep existing data formats and behavior stable while extracting capability owners behind narrow interfaces: document/command state, persistence coordinator, raster/import service, viewport state, and tool configuration. Use the existing direct-controller tests as characterization coverage, then move one owner at a time. Splitting methods into extensions without changing ownership would not reduce the risk.

Medium A02 — Persistence definitions sit upstream of domain models, rendering, and document interchange

Confidence
High
Flow impact
Medium: schema evolution can force unrelated editor/render/export changes
Data integrity
Medium: import/export semantics can drift with database representation

Evidence. CanvasLayer imports core/database/tables/canvas_tables.dart and uses CanvasLayerKind directly (lib/canvas/model/canvas_layer.dart:3,16,27). CanvasPaperStyle imports the same table file (lib/canvas/model/canvas_style.dart:4); the renderer then imports the table file to compare BackgroundKind (lib/canvas/render/grid_painter.dart:8,64,83). The standalone document codec also imports table enums (lib/canvas/io/zenno_document.dart:11,97–103). Board, mastery, focus, and settings enums similarly live in table-definition files and are consumed above the data layer.

Root cause. Drift table files became the canonical home for concepts because intEnum needs enums, so database representation and domain vocabulary were collapsed into one module.

Recommendation (analysis only). Move stable product concepts to domain/model modules and make Drift tables/repositories map to them. The desired direction is database adapter → domain, not renderer/model/export codec → database schema. Preserve stored enum ordinals explicitly during any move and verify migrations/document compatibility.

Medium A03 — “Shared” and feature boundaries form dependency cycles and obscure ownership

Confidence
High
Flow impact
Medium: changes to library/settings/canvas integration spread across modules
Data integrity
Low direct risk; medium coordination risk around cross-feature operations

Evidence. Canvas editor UI imports library and settings application providers (lib/canvas/canvas_editor_page.dart:27–28), while library presentation imports canvas code and settings providers, and settings data imports canvas input types (lib/features/settings/data/settings_repository.dart:6–7). The supposedly lower-level attachment repository imports the concrete LibraryRepository (lib/shared/canvas_attachments/card_canvas_attachment_repository.dart:5,30–35) and calls it inside a shared transaction to create a canvas (:76–93); attachment providers and picker also import library application providers.

Root cause. Cross-feature user journeys were placed under shared, but shared mixes reusable UI/contracts with orchestration that necessarily knows concrete features. Settings also became the persistence owner for types physically owned by canvas.

Recommendation (analysis only). Separate truly reusable primitives (shared/kanban) from integration/application services. Compose canvas↔library↔settings and card↔canvas workflows at an app/integration layer using small ports defined by the consumer. Give global pen/stylus preference types a neutral domain owner. Do not create a generic service locator; make the few cross-feature dependencies explicit.

Medium A04 — Board-card ownership is duplicated without an enforced consistency invariant

Confidence
High for schema exposure; medium for practical likelihood
Status
Latent invariant risk; current board-local UI appears mitigating
Flow impact
Potential cards disappearing, appearing in the wrong workflow, or failing later operations
Data integrity
Medium: stored ownership can become internally contradictory

Evidence. BoardCards stores both columnId and denormalized boardId, each with an independent foreign key (lib/core/database/tables/board_tables.dart:40–61). Nothing ensures the referenced column belongs to the referenced board. Both RevisionRepository.moveCard and GoalRepository.moveCard update only columnId and position (lib/features/revision/data/revision_repository.dart:168–181; lib/features/goal_cycle/data/goal_repository.dart:198–211). Their public add/move/reorder/rename/remove methods accept arbitrary column IDs; helpers derive whatever board owns the supplied column but do not verify that it has the feature’s expected BoardType (revision_repository.dart:304–348; goal_repository.dart:350–396).

Root cause. boardId was denormalized for query speed, but the write model has no single owner responsible for keeping the duplicate relationship coherent.

Counterevidence / mitigation. Shared Kanban widgets receive columns from one board snapshot, so normal drag/drop supplies same-board IDs. Card creation derives boardId from the selected column. Existing repository tests cover position normalization and transactional goal saves, but no inspected test deliberately passes a cross-board column to a feature repository.

Recommendation (analysis only). Encode the invariant at the most durable feasible layer: either remove redundant ownership and query through the column, or introduce a composite relationship/validated transaction that derives boardId from toColumnId. Also scope every feature mutation to its expected board type and ensure feature subtype details match it. Add cross-board/corruption-oriented repository tests before altering the schema.

Medium A05 — Non-owning relationships use destructive cascades that repositories must manually override

Confidence
High
Status
Current repository paths preserve the records; schema semantics remain unsafe if bypassed
Flow impact
Low under current paths; potentially high after an alternate deletion path or migration
Data integrity
High impact to canvases or historical records if repository guards are bypassed

Evidence. Three nullable/reference relationships behave as associations in product code but as ownership in the schema. (1) Canvases.folderId cascades on folder deletion (lib/core/database/tables/canvas_tables.dart:28–33), while LibraryRepository.deleteFolder first moves canvases to unfiled (lib/features/library/data/library_repository.dart:158–170). (2) FocusSessions.linkedCanvasId cascades on canvas deletion (lib/core/database/tables/focus_tables.dart:74–78), while LibraryRepository.deleteCanvas first nulls matching links (library_repository.dart:187–199). (3) FocusSessionRitualChecks.itemId is nullable and its label is snapshotted, yet source-item deletion cascades the historical check row (focus_tables.dart:85–102); RitualRepository avoids deletion by retiring items (lib/features/focus/data/ritual_repository.dart:107–114).

Counterevidence / mitigation. Inspected production paths use the preserving repository methods. test/library_repository_test.dart:89–126 verifies folder deletion keeps its canvas and canvas deletion keeps linked focus history. No production checklist deletion API was found.

Root cause. Foreign-key actions were chosen as broad cleanup defaults rather than from relationship semantics. Safety therefore lives as procedural knowledge in repositories rather than in durable constraints.

Recommendation (analysis only). Classify every FK as ownership, association, or snapshot provenance. Use SET NULL for nullable associations/provenance and cascade only true owned aggregates. Keep preserving repository actions, but no longer make them the sole barrier. Verify generated migrations plus folder, session, and ritual-history tests. This is hardening, not evidence that current UI paths lose these records.

Medium A06 — Filesystem garbage collection is tied to an auto-disposed repository lifecycle rather than a controlled maintenance boundary

Confidence
Medium-high
Flow impact
Potential background I/O during navigation/provider recreation
Data integrity
Medium exposure for app-owned imported media if a valid transient file is not yet referenced

Evidence. The generated libraryRepositoryProvider is explicitly isAutoDispose: true (lib/features/library/application/library_providers.g.dart:18–36) and starts cleanupOrphanedFiles() unawaited every time it is created (lib/features/library/application/library_providers.dart:15–24). The auto-disposed attachment repository watches the library repository (lib/shared/canvas_attachments/card_canvas_attachment_providers.dart:10–27), so opening card attachment surfaces is another construction path. The repository itself says cleanup is safe “at startup, when in-memory undo history is empty” (lib/features/library/data/library_repository.dart:28–44). Native cleanup enumerates all files directly under the app’s media and thumbnail roots and deletes any absent from a previously collected database-reference set (lib/features/library/data/library_file_cleanup_io.dart:29–47,54–59). Image/PDF import copies a file before the controller creates the persisted element reference (lib/canvas/io/canvas_import.dart:96–107,125–132,151–164), and thumbnail capture writes before updating its DB path (lib/canvas/canvas_editor_page.dart:217–239), creating narrow concurrency windows if cleanup is still running.

Root cause. Maintenance startup behavior is attached to dependency construction, which Riverpod may repeat based on listeners, instead of an app-lifecycle owner with a single-run/serialized contract.

Counterevidence / mitigation. While an editor is mounted, its title/provider dependency normally keeps the library repository alive, so repeated cleanup during one editing session is not expected. The risk is startup/provider recreation overlapping file staging, not routine deletion of referenced files. Existing path-root and symlink checks constrain deletion to app-owned directories.

Recommendation (analysis only). Give cleanup a deliberate app-start maintenance coordinator, run it once after persistence initialization, and serialize it against import/thumbnail finalization. Re-check references immediately before deletion or use an age/quarantine policy. Existing path-root and symlink checks are valuable and should be preserved.

Medium A08 — Database bootstrap recovery is neither independently idempotent nor safe for referenced builtin rows

Confidence
High for structure and SQL conflict semantics; low likelihood in a healthy database
Status
Latent abnormal-state recovery failure
Flow impact
Potential database-open failure, duplicate boards/checklists, or reset preferences after bootstrap-state damage
Data integrity
Medium exposure for preferences and seeded workflow identity; no established canvas-note loss

Evidence. Every database open calls seedDatabase from beforeOpen after enabling foreign keys (lib/core/database/database.dart:153–158). Seeding decides global completion solely from app_settings.db_schema_seeded (lib/core/database/seed/seed_data.dart:24–33). When false or missing, it replaces the singleton with defaults, replaces all fixed-ID builtin templates, then creates fresh UUID boards, columns, checklist, and items (:38–76,80–145,148–209). Boards has no uniqueness constraint on boardType (lib/core/database/tables/board_tables.dart:10–19). More seriously, reflection entries reference templates with ON DELETE RESTRICT (lib/core/database/tables/reflection_tables.dart:23–36); SQLite replacement deletes the conflicting template row before inserting the replacement, so a rerun after reflections exist can be rejected by that relationship and roll back the entire open-time seed transaction.

Root cause. Schema/bootstrap metadata shares ownership with editable user preferences, and every seeded aggregate delegates idempotence to one mutable sentinel. Conflict behavior is selected per insert without an aggregate-level recovery contract.

Counterevidence / mitigation. Migration ownership is otherwise unusually explicit. test/database_test.dart:551–570 validates every schema version 1–12 against the exact v13 schema, while targeted cases assert preservation/default contracts for focus runtime, canvases, arrows, layers, bookmarks, and tool-wheel settings (:101–549). This makes ordinary upgrade drift much less likely; A08 concerns abnormal bootstrap-state recovery, which those tests do not cover.

Recommendation (analysis only). Keep bootstrap metadata separate from user settings. Make each seed independently idempotent with stable identifiers or uniqueness constraints. Update builtin templates in place only where explicitly intended; do not use delete-and-reinsert replacement against referenced rows, and never replace user settings merely to recover seed state. Add recovery tests for “settings exists but sentinel false,” “settings missing while reflections reference builtins,” and “boards/checklist exist but sentinel is false” before changing bootstrap behavior.

High A09 — Lossy canvas loading becomes destructive when retry reconciliation treats memory as complete authority

Confidence
High
Status
Demonstrated code-path composition; requires pre-existing incomplete/corrupt data plus a later retry
Flow impact
A damaged element can silently disappear, or a malformed stroke can prevent the whole canvas from opening
Data integrity
High: recoverable durable rows can be permanently deleted by unrelated save recovery

Evidence. CanvasRepository.loadElements deliberately skips any generic element whose per-kind detail row is missing (lib/canvas/persistence/canvas_repository.dart:77–82,177–192,195–300). The controller therefore has no identifier or diagnostic for the omitted durable row. When any asynchronous save later fails, retryFailedWrites sends the controller’s in-memory snapshot to syncCanvasState (lib/canvas/canvas_controller.dart:1059–1091). That reconciliation selects every stored element ID and deletes every ID absent from memory (lib/canvas/persistence/canvas_repository.dart:554–591), including skipped incomplete rows and soft-deleted rows not loaded into memory. In the opposite corruption mode, malformed stroke bytes throw FormatException from InkCodec.decodePoints (lib/canvas/persistence/ink_codec.dart:71–123) and abort aggregate loading rather than isolating one element.

Root cause. The persistence boundary returns only List<CanvasElement>, collapsing “validly loaded,” “filtered,” “quarantined,” and “failed to reconstruct” into presence/absence. Recovery then assumes absence means intentional deletion.

Counterevidence / mitigation. Current generic/detail writes are transactional and a failed replace batch is regression-tested to restore the original element (lib/canvas/persistence/canvas_repository.dart:326–376,530–551; test/canvas_repository_test.dart:804–837), so normal writes should not manufacture a missing-detail row. The retry test proves newest-state recovery for healthy rows (test/canvas_repository_test.dart:896–927), but no inspected test composes retry with skipped or soft-deleted durable rows. The defect is therefore a recovery-of-damaged-state hazard, not a routine-save failure.

Recommendation (analysis only). Return a typed load report containing loaded elements, explicitly filtered IDs, quarantined/corrupt IDs, and diagnostics. Reconciliation may delete only IDs the controller explicitly removed during its session, never IDs absent because they could not be loaded. Preserve corrupt rows for export/repair, surface a non-destructive warning, and contain per-element decode failures where safe. Add a test composing a missing detail row, unrelated write failure, retry, and verification that the original row remains recoverable.

Low A11 — The focus-history “aggregate stream” watches only the root table

Confidence
High
Flow impact
Low-to-medium: history detail refresh depends on an unrelated session-row emission
Data integrity
None directly; this is stale projection risk

Evidence. watchHistoryDetails subscribes to watchHistory(), which watches only focus_sessions, then performs one-shot child reads for distractions and ritual checks on each root emission (lib/features/focus/data/focus_repository.dart:367–399). Inserts into distractions or changes to snapshot rows do not themselves trigger this stream. Medium A14 — Recovery state exists in the schema but has no end-to-end owner

Confidence
High
Flow impact
High after an accidental confirmed deletion; no in-app recovery path
Data integrity
High consequence, user-mediated likelihood

Evidence. Canvases have isArchived and elements have isDeleted columns (lib/core/database/tables/canvas_tables.dart:18–33,131–161). LibraryRepository.archiveCanvas exists (lib/features/library/data/library_repository.dart:180–185) but repository-wide search found no caller. The library card instead confirms and calls permanent deleteCanvas (lib/features/library/presentation/widgets/canvas_card.dart:171–212). Element deletion hard-deletes generic/detail rows (lib/canvas/persistence/canvas_repository.dart:494–528); isDeleted is only a load filter and test fixture. Kanban column/card and reflection-entry deletion similarly commit cascades/hard deletes with no durable trash aggregate.

Root cause. Recovery concepts were added at storage level, but application workflows and retention/purge policy were never assigned to a module. As a result, safe lifecycle fields are dormant while destructive services own the real behavior.

Recommendation (analysis only). Make archive/trash the primary application operation for canvases and other high-value writing; assign restore, retention, and final purge to the library/data-maintenance boundary. Decide whether element soft deletion is part of undo/recovery or remove the misleading field after migration. Do not implement UI-only undo over already-purged rows.

Medium A15 — One malformed reflection JSON row can poison an entire aggregate stream

Confidence
High
Status
Damaged/legacy-state resilience gap; normal writers emit valid JSON
Flow impact
Templates or a card’s saved reflections can become collectively inaccessible because one row cannot decode
Data integrity
Stored answers remain in SQLite, but the application has no row-isolated recovery path

Evidence. The reflection codec’s documentation says non-array or malformed/older schema should be treated as empty, yet ReflectionTemplateSchema.fromJsonString calls jsonDecode without catching FormatException (lib/features/goal_cycle/domain/reflection_template_schema.dart:89–106). The answers decoder has the same uncaught parse step (:125–141). ReflectionRepository.watchTemplates maps every result row in one stream transformation (lib/features/goal_cycle/data/reflection_repository.dart:109–140), and watchEntriesForCard likewise maps every entry through both codecs (:244–266). Consequently one syntactically invalid schema_json, snapshot, or answers_json throws the whole emission rather than isolating the affected row. Settings and canvas tool-wheel/control-point codecs provide useful counterexamples: they catch parse failures and select bounded defaults (lib/features/settings/data/settings_repository.dart:314–364; lib/canvas/persistence/canvas_repository.dart:1105–1155,1186–1199).

Root cause. Raw serialized storage is decoded inside aggregate projection with no explicit error-result type, so row-level corruption is promoted to feature-level stream failure. The codec contract and implementation disagree about tolerance.

Counterevidence / mitigation. Repository and UI write paths construct JSON via the paired encoders, so ordinary saves should be valid. No inspected test injects syntactically malformed reflection JSON. This is a recovery and forward/backward-compatibility risk, not evidence that normal reflection editing corrupts data.

Recommendation (analysis only). Give reflection codecs a deliberate result contract: either return a validated value plus diagnostics or throw a typed row-local decode error that the repository can quarantine. Preserve raw snapshot/answer text, render unaffected rows, and surface which reflection needs repair. Add malformed-template and malformed-single-entry tests that prove sibling history remains available; do not silently overwrite damaged JSON with an empty value.

Medium A16 — Persistence has no single policy distinguishing UTC instants from local calendar dates

Confidence
High for inconsistency; medium for user-visible likelihood
Status
Systemic ordering/semantic exposure, most visible after timezone or daylight-offset changes
Flow impact
“Recent” canvases can be misordered after travel/offset changes; date-only goals risk accidental instant-based handling
Data integrity
Low-to-medium: timestamp meaning can drift even though note content remains intact

Evidence. The database deliberately stores every DateTime as ISO-8601 text and calls that representation sortable (lib/core/database/database.dart:55–62). Canvas persistence writes local DateTime.now() throughout (lib/canvas/persistence/canvas_repository.dart:61–69,347–375,510–570,678–730,781–810,879–949,988–1007), and library creation/rename/move/open paths do the same (lib/features/library/data/library_repository.dart:79–100,111–130,142–176,253–267). By contrast, focus, revision, goal, reflection, attachment, and seed writes generally call toUtc() (for example lib/features/focus/application/active_session_controller.dart:19–21; lib/features/revision/data/revision_repository.dart:168–225; lib/features/goal_cycle/data/goal_repository.dart:198–278). Drift’s text mapping preserves a local value with its UTC offset while UTC values end in Z; lexical ordering is only chronological when comparable instants use one normalized representation. Library “recent” and “created” sorts order the stored text columns directly (library_repository.dart:47–68). Separately, goal targetDate is a calendar-day concept but shares the same generic DateTime storage/API as instants (goal_repository.dart:232–250,294–309).

Root cause. Repositories choose clocks and timezone conversion independently, and the schema uses one type for two meanings: timeline instants and user-local calendar dates.

Counterevidence / mitigation. Canvas and library currently use local time consistently with each other, so ordering is normally correct while the device remains on one offset. Other feature aggregates are internally mostly UTC. The risk emerges across travel/DST, old/new code paths, imports, or future cross-feature queries—not on every save.

Recommendation (analysis only). Define one persistence time policy: store all true instants in UTC and inject a clock where ordering/recovery tests need control. Represent a goal target day as a date-only value/encoding rather than silently converting it as an instant. Before normalizing existing rows, write migration tests using mixed offsets and preserve the intended local day for targets. Avoid a broad mechanical toUtc() replacement because calendar dates have different semantics.

Structural strengths worth preserving

  • Single explicit database composition: ZennoDatabase lists all tables and migrations centrally (lib/core/database/database.dart:12–65), which makes durability review feasible.
  • Historical migration verification: generated schemas cover versions 1–13, every older version is validated against current v13, and targeted tests assert important data-preservation/default contracts (test/generated_migrations/schema.dart:7–56; test/database_test.dart:101–570).
  • Transactional aggregate writes: canvas generic/detail rows are written together (lib/canvas/persistence/canvas_repository.dart:326–376), and card plus subtype details are created transactionally in feature repositories.
  • Safe current canvas deletion orchestration: focus links are detached before canvas deletion and media files are deleted only after remaining references are checked (lib/features/library/data/library_repository.dart:187–251).
  • Useful canvas seam already exists: CanvasRepository explicitly maps engine objects to Drift rows, and retry uses a full current-state reconciliation rather than replaying stale failed closures (lib/canvas/canvas_controller.dart:1059–1091).
  • Shared Kanban contract is directionally sound: KanbanController keeps the generic widget database-free (lib/shared/kanban/kanban_controller.dart:5–52).
  • Focus domain is comparatively clean: FocusSessionConfig and TimerEngine are plain Dart and explicitly separate from Flutter/Drift (lib/features/focus/domain/focus_session_config.dart:1–10).

Recommended architectural sequence

  1. Close the lossy reconciliation path: make canvas load completeness explicit and prevent retry from deleting rows that were not successfully materialized. Treat malformed rows as recoverable evidence, not authoritative absence.
  2. Protect durable invariants: codify folder/focus/ritual relationship semantics, board/column ownership, cleanup lifecycle, archive/restore policy, and instant-vs-calendar time semantics with focused corruption and migration tests.
  3. Move product enums out of Drift tables: establish stable domain types and explicit database mapping while preserving stored ordinals.
  4. Clarify integration ownership: relocate card↔canvas and canvas↔settings/library composition out of lower-level shared/feature internals.
  5. Extract canvas capability owners incrementally: persistence coordinator and raster/import lifecycle first, then document/command state and tool configuration. Keep the existing controller as a façade during migration.
  6. Shrink presentation/data coupling where it pays: remove Drift types from application APIs and route complex mutations through feature controllers, without inventing abstraction for simple reads.

This order minimizes data risk: it closes the one demonstrated destructive composition first, then makes implicit invariants executable before moving the high-blast-radius canvas code.
