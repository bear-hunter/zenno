Executive summary

The most consequential issues are the Android release identity and absence of a proven recovery channel. The release variant is deliberately signed with the debug key, while the repository exposes no complete database-plus-media backup/restore flow. Moving later to a proper signing key may therefore force a choice between keeping an insecure development identity and reinstalling a data-bearing local app without a verified recovery artifact. Base versionCode also remains 1 and there is no checked-in version/release procedure.

Reproduction is partially pinned: pubspec.lock, the Gradle distribution, Android Gradle Plugin, Kotlin plugin, and the project’s Flutter creation revision are recorded. However, the actual Flutter/JDK/Android SDK/NDK toolchain is not enforced, CI is absent, and the Gradle launchers/JAR are injected from whatever Flutter SDK happens to run the build. Native PDF rendering also downloads a PDFium archive during the build without verifying a checksum. For a single-user local app this may work day to day, but it does not establish that a clean or offline machine can reproduce the same artifact.

Database code-generation hygiene is currently strong: schema version 13, the generated Drift database, the latest JSON snapshot, and the generated verifier were last changed together. The weak point is procedural: schema-helper regeneration has a known manual repair step, and there is no automated drift gate. That is the main build-system risk to note integrity.

Evidence-backed findings

F1. Release builds use the debug signing key High Confidence: High

Evidence. android/app/build.gradle.kts:33-38 assigns signingConfigs.getByName("debug") to the release build and explicitly says proper release signing is still a TODO. pubspec.yaml:19 supplies the application version consumed at android/app/build.gradle.kts:29-30. Read-only certificate inspection of the ignored local ARM64 release APK confirmed CN=Android Debug; this validates the configuration’s real output without asserting that the old APK represents current source.

Root cause. The release configuration is optimized for convenient local flutter run --release, so installation identity is inherited from the local development environment instead of being a durable property of the note database’s lifecycle.

Impact. Android only accepts an in-place update when the new APK is signed compatibly with the installed one. Switching from this debug-signed release to a proper key can require uninstalling. In addition, default debug keystores are workstation-local: a “release” built on another clean machine can carry a different certificate and fail to update the tablet even without an intentional signing change. Zenno is local-first, so any uninstall workaround is a direct note-loss hazard unless export/backup and restore are proven first.

Analysis-only recommendation. Define one durable private release keystore and a non-secret checked-in signing contract; load secret material only from ignored/local or secure CI inputs. Before changing the key on the real tablet, identify the signing certificate of the currently installed APK and prove a data-preserving migration/export path. Do not “fix” this by simply changing the Gradle line on an existing data-bearing installation.

F2. Static base versioning creates cross-artifact downgrade traps High Confidence: High

Evidence. pubspec.yaml:19 remains 1.0.0+1; Android maps the build number to base versionCode at android/app/build.gradle.kts:29-30. Ignored output metadata for generic debug/profile/release artifacts records code 1 and name 1.0.0. Read-only APK inspection shows Flutter’s old split-per-ABI output derives codes 1001 (ARMv7), 2001 (ARM64), and 4001 (x86_64), while keeping version name 1.0.0. Those ABI offsets do not represent source revisions and repeat on the next build unless the base build number changes. README.md:87-92 lists build commands but no version increment, artifact naming, signature inspection, install-as-upgrade check, or data backup/restore checkpoint.

Root cause. The repository models “build an APK” but not “produce the next installable revision of the same local data-bearing app,” and it mixes universal/AAB and split-ABI channels without a shared monotonic code strategy.

Impact. The observed ARM64 APK has code 2001, while a later universal APK with different/newer compiled Dart code has code 1. If the tablet carries the ARM64 build, Android can correctly reject the later universal artifact as a downgrade. Rebuilding either channel without increasing the base code also repeats its prior code. The tempting workaround—uninstalling—is unacceptable without F15’s missing recovery path.

Analysis-only recommendation. First read the installed tablet’s package version code and signing certificate without changing it. Choose one canonical delivery channel. Make its next code strictly higher than every code already installed (including ABI-derived offsets), then keep it monotonic. Treat signing identity, upgrade installation, database migration validation, and explicit backup confirmation as one release gate.

F3. The toolchain is recorded but not enforced Medium Confidence: High

Evidence. .metadata:6-20 records one Flutter stable revision, and the current workstation’s read-only SDK/cache stamps exactly match it (Flutter 3.41.6, Dart 3.11.4); there is no observed local Flutter drift. Setup, however, only says flutter pub get (README.md:31-41). pubspec.yaml:21-22 gives a Dart lower-bound range, and pubspec.lock:1240-1242 gives lower bounds of Dart 3.11.4 and Flutter 3.41.0, not an enforced toolchain. AGP 8.11.1 and Kotlin 2.2.20 are pinned at android/settings.gradle.kts:20-24, Gradle 8.14 at android/gradle/wrapper/gradle-wrapper.properties:1-5, and Java language level 17 at android/app/build.gradle.kts:13-20; no JDK vendor/version, Android SDK packages, NDK revision, or Flutter version manager configuration is checked in. The Gradle distribution has no distributionSha256Sum, and no Gradle dependency-verification metadata exists.

Root cause. Template metadata and dependency constraints are being used as if they were an environment lock.

Impact. Two clean machines can resolve the same Dart packages but use different Flutter engines, build tools, JDK patch levels, compile/target SDKs, and NDKs. Native PDF/SQLite/plugin packaging is especially sensitive. A failure may interrupt delivery of note fixes, while silent artifact differences make debugging tablet-only failures harder.

Analysis-only recommendation. Add one authoritative toolchain declaration and bootstrap document: exact Flutter revision, supported JDK, required Android SDK/NDK packages, and a verification command that only reports versions. Preserve .metadata as migration metadata, not the sole pin.

F4. The required ARM64 artifact is policy text, not a reproducible build target Medium Confidence: High

Evidence. AGENTS.md:35 requires feature work to be built into arm-v8a. README.md:87-92 instead documents generic flutter build apk --debug and flutter build appbundle --release. Relevant untracked plans likewise name generic debug APK/app-bundle smoke builds rather than an ARM64 release/handoff command. android/app/build.gradle.kts:22-31 has no ABI filter or split configuration, and no checked-in build script names, hashes, or locates an arm64 artifact. The ignored build tree proves an ARM64-only APK has been produced before, but the command/provenance is absent from the repository.

Root cause. The desired delivery artifact is expressed as a human/agent instruction but is absent from build configuration and documentation.

Impact. “Finished” can yield different artifact forms (universal APK, AAB, or ABI-specific APK) depending on who runs the command. Those forms also carry incompatible version-code ranges in the observed outputs, so choosing the wrong binary can be rejected before a fix reaches the tablet and can encourage an unsafe uninstall.

Analysis-only recommendation. Choose one canonical Galaxy Tab delivery command and artifact path, with arm64-v8a inspection and checksum as non-destructive post-build evidence. Keep universal/AAB builds separate from the personal tablet handoff.

F5. Web SQLite materialization is reproducible in principle but undocumented Low Confidence: High

Evidence. lib/core/database/connection_web.dart:6-19 directly loads the 706,316-byte web/sqlite3.wasm into an IndexedDB filesystem. Adversarial re-check found that its SHA-256 (3981a484…a197d6) is byte-for-byte identical to extension/devtools/build/sqlite3.wasm inside the locked Drift 2.31.0 package, whose package archive is itself authenticated by pubspec.lock. Drift 2.31.0 and sqlite3 2.9.4 were already locked when Zenno added the file. However, no repository instruction or script identifies that source, performs the copy, or checks the digest.

Root cause. A reproducible dependency-owned asset was manually materialized into the web root without recording the relationship.

Impact. The present bytes have a credible locked source, so the initial “unauditable binary” concern was too strong. The remaining risk is future drift: updating Drift/sqlite3 or replacing the file can break web startup without a visible dependency/config change. Web is a preview target, so direct Android note risk is low.

Analysis-only recommendation. Document/codify the exact source path and expected SHA-256, then verify the copied asset whenever Drift/sqlite3 changes. Add a web startup/read-write smoke check; do not fetch an arbitrary latest binary.

F6. Drift schema regeneration has a known manual repair step Medium Confidence: High

Evidence. AGENTS.md:43 states that drift_dev schema generate can overwrite test/generated_migrations/schema.dart away from the project’s required GeneratedHelper, and instructs a manual restore/update. The helper identifies itself as generated/do-not-modify at test/generated_migrations/schema.dart:1-3 yet contains the project-specific 1–13 switch at lines 21–56. The public setup section only documents build_runner (README.md:37-47), not the schema dump/generate/helper repair sequence.

Root cause. A generated file is also a manually curated integration point, so rerunning the official generator is not idempotent for this repository.

Impact. A future database change can appear fully generated while silently dropping the helper used by migration verification. That weakens the main guard protecting old notes during schema upgrades.

Analysis-only recommendation. Make schema export plus helper reconstruction one checked-in deterministic command, or move the hand-written stable helper outside generator ownership. Fail automation when schemaVersion, the latest JSON snapshot, generated database, verifier class, and helper version list diverge.

F7. Reproducibility and drift checks are entirely manual Medium Confidence: High

Evidence. No tracked GitHub Actions, other CI configuration, Makefile, shell build script, or release automation exists. README.md:68-92 lists analyzer, tests, and two Android build commands, but nothing verifies a clean generated-code diff, WASM presence/hash, release signing certificate, version monotonicity, ABI contents, or web package metadata.

Root cause. Validation is documented as individual commands rather than encoded as a reproducible acceptance contract.

Impact. Important checks can pass on one already-prepared workstation and still fail on a clean clone, and generated/configuration drift is only found when it blocks work. This raises interruption risk and delays data-safety fixes.

Analysis-only recommendation. Start with a minimal read-only verification lane: dependency resolution from lockfile, generated-output cleanliness, analyzer/tests, Android arm64 compile, web compile plus SQLite asset smoke, and artifact metadata inspection. Do not add deployment or signing secrets until the local contract is stable.

F8. Six declared packages form two unused dependency families Low Confidence: High

Evidence. Repository-wide package-import search found no use of collection, cupertino_icons, freezed_annotation, or json_annotation. No freezed/JsonSerializable annotations or *.freezed.dart parts exist, so the direct dev dependencies freezed and json_serializable have no current generator target. They remain declared at pubspec.yaml:34-35,40,43,67-68. Dependency-graph reconciliation shows collection and the annotation packages would still be transitively required by active Flutter/analyzer/build packages; the likely package-count reduction is therefore limited to the unused icon and generator packages.

Root cause. Template/planned architecture dependencies outlived the implementation that uses hand-written models and serializers.

Impact. Manifest intent is misleading and two inactive generators add upgrade/codegen compatibility surface. The initial implication of a large resolution-graph reduction was too strong because most libraries remain transitive. Runtime size impact is tiny but measurable: the observed web build includes the unused 1,472-byte Cupertino Icons font.

Analysis-only recommendation. Confirm no near-term model conversion is intended, then remove the unused families together. Keep build_runner, drift_dev, and Riverpod generator/lint packages; they have active outputs.

F9. Web package metadata contradicts the tablet-first product Low Confidence: High

Evidence. Android forces userLandscape at android/app/src/main/AndroidManifest.xml:7-16, while the PWA manifest requests portrait-primary at web/manifest.json:9. web/index.html:21,26,32 and web/manifest.json:2-8 retain template names/descriptions (“zenno” and “A new Flutter project”). Visual inspection confirms both web and Android launcher assets are still the stock Flutter logo; Android also lacks an adaptive-icon resource set.

Root cause. Android product configuration evolved while the generated web shell remained mostly untouched.

Impact. Installed web previews can open in the wrong orientation and generic labels make preview artifacts harder to identify. This is a flow/cosmetic issue, not evidence of note corruption.

Analysis-only recommendation. Align web title, description, color, and orientation with Zenno’s canvas/tablet behavior, or explicitly document web as non-installable development preview and remove PWA expectations.

F10. Schema version 11 is an inert duplicate of version 10 Low Confidence: High

Evidence. drift_schemas/drift_schema_v10.json and drift_schemas/drift_schema_v11.json are byte-for-byte identical (same SHA-256 1006a881…9d635). lib/core/database/database.dart:142-150 has migrations for versions 10, 12, and 13 but no version-11 operation.

Root cause. The schema counter advanced for a change that did not alter the database structure.

Impact. No current data-integrity defect is shown; Drift can traverse the no-op version. It does add one more snapshot/helper case and makes migration history slightly harder to reason about.

Analysis-only recommendation. Preserve it—renumbering shipped schemas is riskier than the duplication. Document v11 explicitly as intentional/no-op so future reviewers do not search for a missing migration.

F11. Android exists outside Flutter’s platform migration metadata Medium Confidence: High

Evidence. Android and web were both present in the initial Git commit, but .metadata:12-20 lists only root and web under migration platforms. Flutter’s local tool source describes this map as tracking the creation and last successful migration revisions separately for every supported platform and adds Android when Android is generated. The Android entry has never existed in repository history.

Root cause. The Android host project appears to have been introduced outside the same Flutter-create metadata transaction (for example, generated/copied separately), leaving the primary runtime unregistered for template migration bookkeeping.

Impact. A future Flutter platform migration cannot use a recorded Android create/base revision to reason about template changes. That increases manual upgrade work and the chance that Gradle/manifest changes required by a new Flutter release are missed—especially problematic because Android is the real note-taking runtime.

Analysis-only recommendation. Before the next Flutter upgrade, compare Android against the template for the recorded creation revision, then use Flutter’s supported metadata/migration flow to establish an Android baseline. Do not regenerate the Android directory wholesale; preserve application ID, signing identity, manifest behavior, and stored-data compatibility.

F12. Native PDFium is downloaded at build time without integrity verification Medium Confidence: High

Evidence. pdfrx 2.4.1 resolves pdfium_flutter 0.2.1 and pdfium_dart 0.2.2 in pubspec.lock:707-738. The resolved pdfium_dart build hook pins release tag chromium/7811, downloads a target-architecture archive from a GitHub release, checks only HTTP 200 and the expected member path, then writes the shared library. It does not compare a digest or signature. The ignored local hook cache contains extracted ARMv7/ARM64/x64 libraries; the cached ARM64 library and the APK entry match at SHA-256 ef8c440d…2eb14. This proves current local consistency but is not a Zenno-owned expected checksum or portable cache.

Root cause. The Pub lockfile authenticates the hook’s Dart source, not the executable native library fetched later by that source.

Impact. A first clean/offline build cannot package PDF support, and network or upstream-release failure blocks delivering Zenno. More importantly, the final executable includes a native library whose bytes are not covered by the repository or lockfile. Existing ignored native-asset caches can make one workstation succeed while a clean one fails or receives different bytes.

Analysis-only recommendation. Record expected SHA-256 values per supported PDFium target, verify the archive before extraction, and support a controlled local cache/mirror for repeat builds. Include the resolved PDFium release and digest in artifact provenance.

F13. The friendly local APK name currently points to older source state Medium Confidence: High for observed workspace

Evidence. In the ignored build tree, app-arm64-v8a-release.apk and zenno.apk are byte-identical (SHA-256 47619463…1d74a) and timestamped 2026-07-12 12:55 +08:00. Current HEAD is a later 2026-07-13 18:24 +08:00 commit, and a generic app-release.apk was produced after that commit. The ARM64 libapp.so inside that later APK has a different SHA-256 from the one in zenno.apk, proving the compiled Dart application payload differs. The friendly/ARM64 artifact reports derived version code 2001; the newer universal artifact reports base code 1. Neither code identifies the source revision. No repository file references, copies, validates, or cleans zenno.apk.

Root cause. A convenient handoff filename was manually copied into an ignored output directory with no source revision, build command, version, ABI, or signing metadata attached.

Impact. Selecting the intuitively named zenno.apk for Drive upload can deliver an older app even when a newer build exists nearby. All observed artifacts keep version name 1.0.0 and the same application ID; ABI-derived codes do not expose the source mismatch.

Analysis-only recommendation. Generate the handoff artifact from one canonical command and name it with app version, build number, commit, ABI, and signing channel; emit a SHA-256/provenance record and refuse to reuse an existing name. Treat all current ignored artifacts as untrusted until rebuilt from an identified revision.

F14. Android APKs carry both native PDFium and web PDFium assets Low Confidence: High for observed artifact

Evidence. pdfrx declares its entire assets/ directory for every Flutter target. The ignored ARM64 APK contains a 6,386,696-byte native libpdfium.so plus pdfium.wasm (5,231,809 bytes uncompressed), its worker, and client JavaScript. The WASM trio consumes about 2.41 MiB compressed in that APK despite Android using the native library.

Root cause. One dependency package serves native and web runtimes from a platform-agnostic Flutter asset declaration.

Impact. The personal tablet APK and Drive upload are larger than required. This is delivery/storage friction, not a functional or data-integrity defect.

Analysis-only recommendation. If artifact size matters, evaluate a deterministic platform-specific dependency asset step supported by pdfrx; ensure it is automatically reversed or isolated so web preview builds retain PDFium WASM. Avoid manual Pub-cache edits.

F15. No complete, proven backup/restore artifact protects the local-first data set High Confidence: High on repository evidence

Evidence. Native persistence splits the Drift database (lib/core/database/connection_native.dart:1-4) from imported media/thumbnails under the application documents directory (lib/canvas/io/canvas_import.dart:61-68,146-164; lib/features/library/data/library_file_cleanup_io.dart:57-58). Repository-wide search found no whole-database/media backup or restore workflow and no Android dataExtractionRules/fullBackupContent resource. The wired canvas export supports only PNG/JPG/SVG (lib/canvas/io/canvas_export.dart:63-73,127-163). ZennoDocumentCodec is used only by its test, covers one canvas rather than boards/focus/reflections/settings, and serializes image/PDF paths instead of their bytes (lib/canvas/io/zenno_document.dart:29-84,191-205), so it is not a self-contained recovery artifact.

Root cause. Export was designed for sharing/rendering and for an isolated canvas format, while installation identity and OS backup behavior were left implicit. No one component owns the complete durable data graph.

Impact. There is no repository-supported way to prove that all notes, canvas media, study boards, reflections, settings, and history can survive an uninstall, device replacement, signing-key change, or partial filesystem loss. This turns F1’s future signing transition from a packaging inconvenience into a credible data-loss boundary. OS-level backup may exist on a particular device, but its scope and restoration behavior are not specified or evidenced here.

Analysis-only recommendation. Before any signing/application-ID change, define a versioned, checksummed, atomic backup bundle containing the database plus every referenced media file; validate references before export, verify before import, never overwrite live data until validation succeeds, and exercise restore on a disposable install. Separately specify and test Android backup rules. Preserve the original installation until both paths are proven.

F16. The web shell advertises an installable PWA without an offline application cache Low Confidence: High

Evidence. web/manifest.json:4-10 uses display: standalone, suggesting installation. Zenno uses the default flutter_bootstrap.js path (web/index.html:35-44). Under the exact recorded Flutter 3.41.6 toolchain, the generated service worker contains no resource manifest: it calls skipWaiting(), unregisters itself on activation, and reloads clients. The current Flutter tool source confirms this is intentional deprecation behavior. The observed build’s service worker does not list main.dart.js, sqlite3.wasm, or PDF assets.

Root cause. The legacy template PWA manifest remains while Flutter has retired its generated offline cache and Zenno has not chosen a replacement web-offline strategy.

Impact. An installed web preview may retain IndexedDB notes but lacks a repository-defined way to guarantee the application shell and WASM engines are available offline. A network/cache failure can therefore strand browser-local notes temporarily. Android is the declared reliable target, so severity remains low.

Analysis-only recommendation. If web stays development-only, make that status explicit and avoid presenting it as a durable installable note client. If offline web becomes supported, own a tested service worker/update policy that versions the app shell, SQLite WASM, PDFium assets, and database migration behavior together.

F17. Clean clones receive stale instructions while corrective lessons are untracked Medium Confidence: High

Evidence. AGENTS.md is present but untracked and not ignored. It is the only current workspace document that requires ARM64 delivery (AGENTS.md:35), warns that schema generation can overwrite the required helper (AGENTS.md:43), and records the deliberate direct-WASM/no-shared-worker design (AGENTS.md:41-42). A clean clone instead receives tracked .claude/CLAUDE.md, whose stack still says models use Freezed/json-serializable (.claude/CLAUDE.md:6-9) and whose web guidance twice says DB flows still need drift_worker.js (.claude/CLAUDE.md:11-14,26). Current source directly opens WasmDatabase with IndexedDbFileSystem and no worker (lib/core/database/connection_web.dart:6-21), while no Freezed/JSON model codegen exists.

Root cause. Operational knowledge is split across a stale tracked assistant note, a newer untracked agent note, and README fragments; there is no single maintained build/runtime contract.

Impact. A fresh clone or another agent can follow the tracked worker instruction and reintroduce the browser-hang failure already captured in the untracked lessons. It can also miss the schema-helper repair and ARM64 handoff requirement, directly feeding F4/F6. Stale Freezed claims keep the unused dependencies looking intentional.

Analysis-only recommendation. Consolidate durable build, web-runtime, schema-generation, release, and recovery facts into tracked documentation with one owner. Update or retire contradictory assistant-specific notes. If AGENTS.md is intentionally local, move its repository-critical facts into tracked README/developer docs rather than relying on the local file.

Method, scope, and limitations

Inspected tracked inventory; relevant untracked plans/reviews by build-related terms; ignored build-file names and artifact metadata; Git status/history for build-generated surfaces; manifests; Gradle configuration; Flutter metadata/tool migration logic; lockfile/direct dependency use; resolved plugin constraints and build hooks; source imports; codegen parts/annotations; schema snapshots/helpers; web database loading; asset types/sizes/hashes; APK entries/certificate metadata; and local Flutter tool source governing wrapper injection. Planning material was used only to check for missing/contradictory procedures, never as proof that a build or behavior works.

Explicitly not performed: dependency resolution, flutter/dart/gradle commands, builds, tests, analyzer, installs, app launches, network vulnerability/freshness lookups, secret inspection, branch changes, commits, pushes, PRs, or edits outside this report. Consequently, runtime/build success and current advisory status remain unverified.

Severity reflects likely impact on note-taking flow/data integrity plus probability. Recommendations are analysis-only and intentionally avoid suggesting destructive migration shortcuts.
