Scope and current conclusion

The database implementation is materially stronger than a typical early-stage local app: every schema version from 1 through 13 has a committed snapshot, the migration suite validates every old version against the exact v13 shape, major aggregate writes use transactions, canvas writes are tracked, and ordinary editor exit waits for persistence. The largest remaining exposure is recoverability rather than routine transactional correctness. Zenno has no complete, user-operable backup/restore mechanism for the database plus imported media, and several intentional delete paths permanently cascade through note-bearing rows.

Detailed findings

DI-01 — Zenno lacks a complete backup, restore, and corruption-recovery path

High

Root cause. Durable state is split between a Drift/SQLite database and app-owned files under canvas_media / thumbnails, but the repository contains no workflow that snapshots both, verifies the snapshot, and restores it. The native connection simply opens the named database; the web connection opens one IndexedDB-backed WASM database. No integrity check, backup rotation, restore staging, or salvage path is present.

  • lib/core/database/connection_native.dart:1-4 opens driftDatabase(name: 'zenno') with no backup/recovery wrapper.
  • lib/core/database/connection_web.dart:6-20 stores /database in IndexedDB, protected against concurrent tabs but not backed up.
  • android/app/src/main/AndroidManifest.xml:1-32 contains no app-defined backup/data-extraction rules or fragile-user-data retention declaration. Platform defaults are not a verified, user-operable Zenno backup contract.
  • lib/canvas/io/zenno_document.dart:13-83 defines an in-memory JSON codec, but repository-wide references show it is used only by its unit test; there is no user-facing import/restore path. Its document shape also omits title, folder membership, bookmarks, rotation-lock/tool settings, card relationships, focus history, and reflections.
  • lib/canvas/io/zenno_document.dart:191-205 serializes image/PDF paths, not file bytes or hashes, so even that document cannot independently recover media.
  • lib/canvas/io/canvas_export.dart:65-70, 130-240 exposes PNG/JPG/SVG rendering only; those are useful presentation exports, not editable backups.
Flow / integrity impact
A lost tablet, app-data clear, uninstall, IndexedDB eviction, filesystem damage, or SQLite corruption can remove the entire thinking history with no supported recovery route.
Recommendation
Design a versioned, atomic Zenno backup package containing a consistent SQLite snapshot plus every referenced owned media file, a manifest with sizes/hashes/schema version, and a restore flow that extracts to staging, verifies everything, then swaps only after success. Add periodic local snapshots and a non-destructive salvage/export path before attempting repair.
Important caveat
Thumbnails are regenerable and need not block restore; imported images/PDFs and note rows are authoritative and must.

DI-02 — Folder foreign-key behavior contradicts the safe domain rule

High

Root cause. The schema declares canvases.folder_id → canvas_folders.id ON DELETE CASCADE. The repository and UI explicitly promise that deleting a folder moves its canvases to Unfiled, and the current repository carefully nulls those references in a transaction before deleting the folder. The safety property therefore lives only in one call path; the database invariant encodes the opposite behavior.

  • lib/core/database/tables/canvas_tables.dart:18-33 defines the destructive cascade.
  • lib/features/library/data/library_repository.dart:158-170 first sets folder_id = NULL, then deletes the folder transactionally.
  • lib/features/library/presentation/pages/library_page.dart:176-203 tells the user canvases will move to Unfiled.
  • test/library_repository_test.dart:89-105 verifies only the repository path, not direct FK behavior.
Failure mode
Any future repository, migration, maintenance operation, or direct Drift delete that removes a folder without the pre-update will cascade through canvases, elements, strokes, text, links, attachments, and owned-file cleanup candidates.
Recommendation
Make the schema express the domain: migrate folder_id to ON DELETE SET NULL (or restrict deletion and require explicit unfiling), then add a direct-DB test proving a folder delete preserves canvas rows. Keep the current transaction as defense in depth.

DI-03 — Destructive cascades have confirmation but no recovery window

High

Root cause. Destructive actions commit immediately. A canvas delete cascades through all canvas content; a board-column delete cascades through every card, its details and attachments, and—in Goal Cycle—saved reflection entries. There is no trash, tombstone retention, delayed commit, or restore snapshot. The existing is_archived column and archiveCanvas method are not wired into a visible archive/restore flow.

  • lib/features/library/data/library_repository.dart:180-205 contains both an archive method and permanent delete; repository-wide search found no call to archiveCanvas.
  • lib/features/library/presentation/widgets/canvas_card.dart:171-212 confirms then immediately calls permanent deletion.
  • lib/features/goal_cycle/data/goal_repository.dart:288-292, 370-375 deletes cards/columns, relying on cascades for reflections and detail rows.
  • lib/shared/kanban/kanban_column_view.dart:391-425 warns by card count but does not enumerate reflection-bearing cards or offer Undo.
  • lib/core/database/tables/reflection_tables.dart:23-50 makes reflection entries cascade with their goal card.
Flow / integrity impact
A single mistaken confirmation can permanently remove a dense collection of learning notes. The column dialog understates value at risk by counting cards while omitting saved reflections/status notes.
Recommendation
Use soft deletion/trash for canvases and note-bearing cards/columns, with an explicit retention window and restore. At minimum, delay destructive commit until an Undo window expires. For column deletion, show the number of cards and reflections and preserve an atomic restore snapshot. Do not implement “undo” by re-creating only parent rows; all child IDs, timestamps, ordering, attachments, and reflections must round-trip.

DI-04 — Corruption handling can turn one bad element into whole-canvas failure or silent loss

High

Root cause. Corruption is handled inconsistently and mostly outside aggregate boundaries. loadElements skips generic element rows whose detail row is missing, but decoding a malformed ink BLOB is not isolated per element: InkCodec.decodePoints throws, aborting the entire load. The stored point_count is not cross-checked, so a record-aligned truncation can silently decode fewer points. Reflection JSON readers likewise allow malformed JSON/type casts to escape and terminate whole template/entry streams. Later, “retry failed writes” uses the in-memory canvas list as authoritative and deletes stored element IDs not in that list, including rows skipped during load. Startup enables future FK enforcement but never runs integrity_check, quick_check, or foreign_key_check to detect pre-existing damage.

  • lib/canvas/persistence/canvas_repository.dart:77-91, 177-192 describes and implements silent omission of rows with missing detail records.
  • lib/canvas/persistence/canvas_repository.dart:213-231 decodes ink without a per-row recovery boundary.
  • lib/canvas/persistence/ink_codec.dart:71-123 correctly rejects malformed lengths/versions, but the caller does not isolate the exception and never compares decoded length with point_count.
  • lib/core/database/database.g.dart:3257-3258, 3888-3889 maps persisted element/stroke enum integers through ordinal converters; the table SQL has no enum-range CHECK, so a bad ordinal can fail generated row conversion before repository-level recovery runs.
  • lib/features/goal_cycle/domain/reflection_template_schema.dart:27-37, 89-106, 125-140 claims malformed data is tolerated, but jsonDecode and wrong-typed as casts are not caught.
  • lib/features/goal_cycle/data/reflection_repository.dart:109-139, 244-266 maps every row through those parsers, so one bad row can fail the entire templates stream or all reflections for a card.
  • lib/canvas/persistence/canvas_repository.dart:575-591 deletes every stored element not represented in the current controller snapshot during recovery sync.
  • lib/canvas/canvas_controller.dart:1060-1090 invokes that destructive full-state sync after failed writes.
  • lib/core/database/database.dart:153-158 enables foreign keys and seeds, but repository-wide PRAGMA search found no startup integrity or foreign-key validation.
Failure modes
(1) One malformed stroke blocks opening the whole canvas. (2) Missing detail rows disappear with no warning. (3) A later retry can remove skipped generic rows, reducing salvage evidence. (4) Aligned truncation can silently shorten a stroke. (5) One malformed reflection can hide every entry on a card.
Recommendation
Load each note-bearing row behind a corruption boundary; return structured results containing valid objects plus quarantined row IDs/errors. Show a non-destructive “some content could not be read” state, prevent full-state sync from deleting quarantined IDs, validate point_count, run periodic/read-only integrity diagnostics, and provide raw-row export before repair. Never silently convert corruption into deletion or an empty schema.

DI-05 — Orphan-file cleanup can race valid imports and Undo recovery

High

Root cause. Constructing the auto-disposed library repository starts cleanup fire-and-forget. Cleanup is explicitly documented as safe “at startup, when in-memory undo history is empty,” but the provider is not a process-once startup coordinator. It builds a reference set using three independent queries, then deletes every file under the owned roots that is not in that set. There is no transactionally consistent snapshot, startup barrier, minimum file age, active-editor/Undo exclusion, “imports in flight” registry, or rename-from-staging protocol.

  • lib/features/library/application/library_providers.dart:15-24 starts cleanup with unawaited whenever the provider is constructed.
  • lib/features/library/application/library_providers.g.dart:18-36 confirms this purported “singleton” is actually generated with isAutoDispose: true, so construction and cleanup are not process-once guarantees.
  • lib/features/library/data/library_repository.dart:28-45 reads image, PDF, and thumbnail references separately.
  • lib/features/library/data/library_file_cleanup_io.dart:29-47 enumerates the roots and immediately deletes unreferenced files.
  • lib/canvas/io/canvas_import.dart:146-164 copies a picked file directly into the cleanup-managed canvas_media directory before any DB row exists.
  • lib/canvas/canvas_controller.dart:3897-3918, 3967-4013 creates the DB-backed element only after image decode / PDF probing and placement.
  • lib/canvas/engine/canvas_commands.dart:5-10, 85-121 deliberately retains only the media path (not raster bytes) in an undo snapshot, and restores the removed element from that snapshot.
  • lib/canvas/canvas_controller.dart:825-845, 945-979 deletes the element/detail DB row on erase and re-upserts it on Undo; file survival is therefore required for Undo to restore the note.
Concrete races
(1) Cleanup snapshots references → import copies a file into canvas_media → cleanup deletes the not-yet-referenced file → controller persists an element pointing at the missing path. (2) Cleanup begins while an editor is active → the user erases an image/PDF before its reference query → cleanup sees and deletes the now-unreferenced file → Undo re-inserts the element row, but its only retained source path is permanently broken.
Confidence note
Both timing windows may be small, but the provider is definitively auto-disposed; filesystem enumeration and PDF probing widen them, and no synchronization closes either. The code's own safety comment depends on a lifecycle guarantee the provider does not enforce.
Recommendation
Run cleanup once behind an awaited startup coordinator before any editor can mutate state, take reference reads in one database snapshot, ignore files newer than a conservative grace period, and never collect files still reachable from any active Undo stack. Copy imports into a staging directory outside cleanup scope; commit/register the DB reference, then atomically rename into the owned media directory before cleanup can see it.

DI-06 — “Save” on an emptied text-note dialog performs deletion

High

Root cause. The text editor returns the field value from a button labelled Save. For an existing note, the controller trims it and routes an empty value to removeElements. The deletion is technically undoable while the editor remains open, but the user is neither told that a delete occurred nor offered a focused Undo action.

  • lib/canvas/canvas_editor_page.dart:349-395 passes an existing note's result directly to updateTextElement; the dialog action remains “Save.”
  • lib/canvas/canvas_controller.dart:3733-3746 removes the element when the trimmed body is empty.
Flow / integrity impact
A user clearing text to rewrite later, or accidentally selecting/deleting all text, can destroy the note under a non-destructive label. If the editor is then closed, the command-stack undo opportunity disappears.
Recommendation
Persist an empty note box or require an explicit “Delete note?” confirmation. If delete-on-empty remains intentional, relabel the action and show an immediate Undo Snackbar tied to the command.

DI-07 — Imported media is path-addressed without durable verification

Medium

Root cause. Image/PDF rows store absolute file paths and geometry, but no enforced content hash, size, or availability state. pdf_documents.import_hash exists but is never populated by CanvasRepository; images have no equivalent. Load reconstructs elements even if their files are missing, and failure appears later during raster decode. Absolute device paths also make a future restore/package import dependent on rebasing paths correctly.

  • lib/core/database/tables/canvas_tables.dart:190-233 defines path-backed media; only PDF has an optional hash field.
  • lib/canvas/persistence/canvas_repository.dart:401-435 writes paths but not importHash.
  • lib/canvas/persistence/canvas_repository.dart:232-263 reconstructs media elements without checking file existence or integrity.
Impact
Filesystem loss or bit rot leaves durable DB rows that look valid but cannot render; there is no diagnostic inventory or way to reconnect a replacement file. Copying an otherwise healthy DB/media set to a location with a different documents root also breaks every absolute reference.
Recommendation
Store media by stable content ID or path relative to a resolved app-owned root; record a content hash and byte length for every object; verify on import and backup; surface missing/corrupt media distinctly from loading; and support non-destructive relinking. Hash once at import rather than on every canvas open.

DI-08 — Ordinary element updates rewrite creation timestamps

Medium

Root cause. upsertElements uses INSERT OR REPLACE and supplies createdAt: now for both new and existing IDs. Moving, editing, reordering, or undo/redo therefore silently resets the element's creation time. SQLite REPLACE also models the operation as delete + insert, though the transaction protects row/detail atomicity.

  • lib/canvas/persistence/canvas_repository.dart:338-376 supplies both timestamps and uses InsertMode.insertOrReplace.
  • lib/core/database/tables/canvas_tables.dart:131-165 defines created_at as durable metadata.
Impact
Today this is metadata loss rather than visible note loss, but it removes provenance that future history, auditing, sync, or recovery logic would reasonably trust.
Recommendation
Use a conflict update that preserves existing created_at and updates only mutable fields plus updated_at. Add a regression test that creates, edits, and reloads an element while asserting creation time stability.

DI-09 — Focus-session history safety is not enforced by the schema

Medium

Root cause. focus_sessions.linked_canvas_id uses ON DELETE CASCADE, so the database's default reaction to deleting a canvas is to delete complete study sessions and their review notes, distractions, and ritual snapshots. LibraryRepository.deleteCanvas correctly nulls the link first, but the safety property is again limited to one code path. The same mismatch exists for ritual snapshots: focus_session_ritual_checks.item_id is nullable and carries a label snapshot, yet deleting its source item cascades the historical check row instead of nulling the link.

  • lib/core/database/tables/focus_tables.dart:39-83 defines the linked-canvas cascade.
  • lib/core/database/tables/focus_tables.dart:85-103 describes snapshot preservation but configures item_id with cascade.
  • lib/features/library/data/library_repository.dart:187-199 explicitly detaches focus sessions before canvas deletion.
  • lib/features/focus/data/ritual_repository.dart:107-114 retires items instead of deleting them specifically to preserve history.
  • test/library_repository_test.dart:107-126 proves the current canvas-repository workaround preserves history, but there are no direct-FK tests for either relationship.
Impact
A future/direct canvas or ritual-item deletion path can erase historical learning records that are semantically independent of the source object and already contain their own snapshots.
Recommendation
Migrate both reference FKs to ON DELETE SET NULL and retain repository-level retirement/detach as defense in depth. Add direct-DB foreign-key tests that source deletion preserves the session and snapshot rows.

DI-10 — Seed recovery replaces existing singleton/builtin rows

Medium

Root cause. If db_schema_seeded is false, seeding starts by INSERT OR REPLACE on the settings singleton, resetting every unspecified preference to its schema default, then replaces builtin templates by ID. Despite the “idempotent” method comment, boards and the ritual checklist receive fresh UUIDs and use ordinary inserts, so re-running after a false flag duplicates them. Normally the whole seed is one transaction and the flag is immediately true, so this affects abnormal/repair states—not routine opens. But a false/corrupt flag on a mature database can trigger surprising replacement semantics; builtin templates referenced by ON DELETE RESTRICT reflections can also reject REPLACE's implicit delete.

  • lib/core/database/seed/seed_data.dart:24-77 claims idempotence, checks the flag, replaces settings, seeds other rows, then marks true in one transaction.
  • lib/core/database/seed/seed_data.dart:140-165, 181-207 replaces builtin templates but creates new random board/checklist IDs on each run.
  • lib/core/database/tables/board_tables.dart:10-19 has no unique constraint on board_type to reject duplicate seeded boards.
  • lib/core/database/tables/reflection_tables.dart:31-36 restricts deletion of referenced templates.
Impact
Preferences can revert, duplicate seeded boards/checklists can appear, or startup can fail repeatedly rather than repairing a database whose seed flag is false but whose reflections are mature.
Recommendation
Use stable IDs and insert-if-absent for every seed aggregate, enforce one board per board_type, update only explicitly versioned builtin fields when safe, and treat “flag false with user data present” as a repair case with diagnostics. Test the abnormal state with existing settings, boards, ritual data, and reflection entries.

DI-11 — Canvas write-through is not checkpointed on app lifecycle transitions

Medium

Root cause. A committed canvas command starts its Drift write asynchronously and records the future. Normal editor back/navigation awaits flush(), which is strong, but the repository contains no AppLifecycleListener, WidgetsBindingObserver, or equivalent canvas checkpoint when the app becomes inactive/paused. Widget dispose starts a flush without awaiting it, and provider-container disposal can concurrently close the database.

  • lib/canvas/canvas_controller.dart:926-943 implements an effective drain for callers that await it.
  • lib/canvas/canvas_editor_page.dart:207-214 invokes the dispose safety net with unawaited; explicit close does await at lines 258-290.
  • lib/core/providers/database_provider.dart:6-14 closes the shared DB when the provider container is disposed.
  • A repository-wide search found no canvas app-lifecycle observer; only Focus documents why its wall-clock timer needs no lifecycle reconciliation, which does not cover pending canvas futures.
Failure mode
User commits an edit, immediately backgrounds Zenno, and the OS terminates the process before the asynchronous transaction finishes. The in-memory command has no next-start replay log, and normal navigation's guard never ran.
Recommendation
Checkpoint the controller on inactive/paused/detached transitions, serialize database close behind pending controller flushes, and consider a minimal durable operation journal if zero-loss across sudden process death is required. Keep immediate write-through; lifecycle flushing is defense in depth, not a replacement.
Confidence note
Static evidence proves the missing checkpoint, while actual loss probability depends on platform scheduling and transaction duration; that is why severity/confidence are below DI-01–DI-06.

Verified protections worth preserving

  • Migration discipline: schemaVersion == 13; committed Drift snapshots exist for v1–v13; test/database_test.dart:551-569 statically shows every prior version is migrated and validated against exact v13 with dropped-entity validation enabled.
  • Additive migrations: the production migration strategy adds columns/tables/indexes and explicitly backfills default canvas layers; targeted fixtures cover important v1, v5, v6, v7, v8, v9, and v12 transitions.
  • Persisted enum evolution so far: Git history shows new stored enum members were appended (for example FocusSessionStatus.reviewPending and newer stroke tools) rather than reordered, preserving existing ordinal meaning. This discipline must remain explicit because the schema stores indices.
  • Localized preference-codec fallback: malformed palette, stylus mapping, pen profile, wheel position/preset, and shape-control-point JSON is caught and converted to usable defaults instead of blocking database open. Reflection JSON is the documented exception in DI-04.
  • Foreign keys enabled: PRAGMA foreign_keys = ON runs before seeding at lib/core/database/database.dart:153-158.
  • Atomic canvas writes: generic element + detail + canvas touch occur in a transaction; command batches and failed-replacement rollback are represented in CanvasRepository and its tests.
  • Save-failure visibility: controller writes are tracked, failures remain retryable even after banner dismissal, normal close awaits flush(), and PopScope funnels system back through the same guard.
  • Focus recovery: session creation and ritual snapshots share one transaction; runtime fields checkpoint every 15 seconds and on transitions; startup rebuilds the wall-clock timer; and older duplicate live sessions are closed as preserved “abandoned” history rather than deleted (lib/features/focus/data/focus_repository.dart:53-111, 138-177; lib/features/focus/application/active_session_controller.dart:354-447).
  • Reflection immutability: every saved reflection snapshots the template name and prompt schema, editing a template leaves prior entries unchanged, and templates referenced by history are protected by ON DELETE RESTRICT plus an application pre-check (lib/features/goal_cycle/data/reflection_repository.dart:172-220, 273-299).
  • Safe current folder delete: canvases are unfiled and the folder is deleted in one transaction.
  • Safe current canvas delete for history: focus sessions are detached in the same transaction before canvas cascade; file cleanup checks cross-canvas references before deletion.
  • Web concurrency guard: an exclusive browser-wide lock prevents two independent WASM connections from mutating the same IndexedDB file.
  • Duplicate-editor guard: current UI entry points use openCanvasEditor, whose route registry coalesces rapid duplicate opens and reuses an already-mounted editor for the same canvas (lib/canvas/canvas_editor_navigation.dart:7-13, 58-103). This materially narrows same-canvas lost-update and torn-read exposure.

Coverage, evidence, and limits

Iterations 1–5 read the only applicable AGENTS.md, repository/worktree status, tracked and relevant untracked inventory, Drift tables and generated schema helpers, migrations and migration tests, native/web connections, seed logic, canvas repository/controller/editor persistence paths, library cleanup/import handling, focus recovery, settings, revision/goal/reflection/attachment repositories, destructive UI confirmations, export/document codecs, provider generation/lifetimes, schema diffs, enum history, navigation/controller ownership, every declared foreign-key action, and relevant plans/reviews. Generated database.g.dart was searched but source table declarations and schema snapshots were treated as primary evidence. Existing untracked analysis material was used only to direct re-checks; findings above were independently confirmed against current source.

Adversarially reviewed but not promoted to findings: loadElements reads its base rows and six detail sets without one explicit read transaction, but normal UI navigation prevents two live editors for one canvas and element writes are transactional, so a credible user-reachable torn snapshot was not established. The denormalized board_cards.board_id is not constrained to match the board owning column_id, but current feature-specific repositories do not offer cross-board moves. Controller writes are launched as tracked futures rather than chained through an explicit controller-side serial queue; command mutations themselves collapse to atomic batches and the single Drift connection is expected to schedule operations, but ordering was not dynamically exercised under this task's constraints. These remain useful invariant-hardening candidates, not demonstrated note-loss paths in the current UI.

Not executed by instruction: tests, builds, analyzers, app runs, dependency commands, migration commands, SQLite opening, filesystem mutation outside this report, Git mutation, or network/external service access. Therefore dynamic timing for DI-05 and actual platform durability settings remain unmeasured; confidence is explicitly lower where that matters.
