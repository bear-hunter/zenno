Zenno implementation plan

Performance optimization + Adaptive pen

A staged, source-backed plan to make the infinite canvas scale with what is visible, reduce high-frequency rebuilds and persistence work, protect long drawing sessions, and expose the existing zoom-aware pen behavior as an intuitive on/off option.

01 · Intended outcome

Make frequent actions proportional to visible work

Zenno already has strong low-level primitives: a spatial index, separate repaint layers, tile and stroke caches, bounded raster concurrency, a decoded-raster budget, frame-coalesced live ink, and capped PDF rendering. The next gains come from stopping small events from triggering whole-editor, whole-canvas, or whole-history work.

A

Ink stays immediate

Pen samples update the live ink layer without rebuilding the toolbar, editor shell, or unrelated committed content.

B

Canvas cost follows visibility

Painting and raster scheduling operate on viewport hits, not every element stored in the document.

C

Large notes open predictably

Hydration is bulk and linear, caches are invalidated locally, and image memory is sized for the current view.

D

Pen behavior is obvious

“Adaptive pen” clearly communicates whether brush size remains stable under the hand while zooming.

Guiding constraint: optimize runtime representations and event delivery without changing durable note geometry, deleting source media, or rewriting previously committed strokes.

02 · Source evidence

Work is already culled at the bottom, but not at the top

The following findings define the implementation order. They are algorithmic observations from the source, not measured timing claims.

Priority 0

Controller notification fan-out

CanvasController is one broad ChangeNotifier. The editor page, canvas view, toolbar, bookmarks, and sheets listen to it, so ink, hover, viewport, tool, and raster events share one rebuild channel.

Sources: canvas_editor_page.dart, canvas_view.dart, canvas_toolbar.dart

Priority 0

Culling still scans all elements

ElementsPainter obtains visible IDs from the spatial index, then iterates the complete z-ordered list. Tile painting rebuilds full ID/order maps, and raster scheduling scans the full element list after its viewport query.

Sources: elements_painter.dart, canvas_controller.dart

Priority 0

Continuous settings cause write bursts

Brush size, opacity, smoothing, and eraser controls update on every drag delta. Their setters immediately notify the broad controller and persist tool settings.

Sources: canvas_toolbar.dart, canvas_repository.dart

Priority 1

Hydration and cache churn grow with document size

Already sorted elements are added one at a time through duplicate and insertion scans. A global element revision clears every tile picture and the stroke path cache.

Sources: canvas_controller.dart, elements_painter.dart

Priority 1

Live stroke work grows during the gesture

Each new sample invalidates a snapshot containing all prior points, and the preview outline is rebuilt from the full point set.

Sources: live_stroke_painter.dart, stroke_builder.dart

Priority 1

Background features repeat broad data work

Focus history resolves two child queries per session, live runtime checkpoints update the watched session table, goal reflections fan out joined rows, and library cleanup begins with provider creation.

Sources: focus_repository.dart, goal_repository.dart, library_providers.dart

03 · Adaptive pen decision

Expose the behavior that already exists

The staging source already supports both behaviors through PenWidthMode.screen and PenWidthMode.canvas. It persists the mode in the canvas row and in each ink tool-wheel preset, snapshots the resolved width at stroke start, and has baseline repository and controller tests. The implementation should improve the product language and control—not create another data field.

User control Existing model Drawing behavior Hover behavior Existing strokes
Adaptive pen · On PenWidthMode.screen The selected width is divided by zoom when the stroke begins, so it appears the same size under the hand at any zoom level. Indicator remains the selected diameter in screen pixels. Never changed.
Adaptive pen · Off PenWidthMode.canvas The selected width is stored directly in canvas units, so it visually grows and shrinks with the canvas. Indicator scales with the current viewport. Never changed.

Recommended UX contract

  • Label the control Adaptive pen.
  • Use an explicit switch rather than “Screen / Canvas” jargon.
  • Supporting text: “Keeps this brush the same visual size while zooming.”
  • Keep the default on, matching the current PenWidthMode.screen default.
  • Apply a mode change only to strokes created after the toggle.

Compatibility contract

  • No database migration and no new settings column.
  • Do not reorder or rename enum values in persistence.
  • Continue decoding older tool-wheel JSON exactly as today.
  • Keep hover radius and committed width derived from one mode.
  • Persist the final toggle immediately; it is not a drag stream.
Scope assumption: Adaptive pen remains per ink preset, because ToolWheelPreset.widthMode already stores it that way. Each brush can therefore remember its own preference. If the desired product behavior is one global switch for every brush, decide that before implementation; it changes preset-switching semantics even though it still does not require rewriting notes.
Adaptive pen implementation checklist
  • Replace or augment the current width-mode picker with an explicit Adaptive pen switch in the active brush property UI.
  • Rename the radial-wheel action label to “Adaptive pen” and make its selected state mean on.
  • Map switch on/off to screen/canvas through the existing setPenWidthMode method.
  • Ensure switching brush presets immediately restores that preset’s saved adaptive setting.
  • Verify zoom changes after stroke start do not mutate the live or committed stroke width.
  • Add accessible semantics, tooltip text, widget keys, and tests for both states.

04 · Recommended implementation sequence

Six gates, each independently reviewable

The phases deliberately establish measurement and event boundaries before changing cache or data-loading behavior. Each implementation PR targets staging, contains only its task-owned changes, and must leave the app usable before the next phase begins.

0

Baseline and regression harness

Build deterministic large-canvas fixtures and counters before changing architecture. Record build, paint, query, write, memory, and load behavior in profile mode on the target tablet.

Risk: Low Dependency: None Output: Reproducible evidence
1

Canvas event isolation + Adaptive pen UX

Split controller observation into narrow channels, remove the redundant whole-editor listener, prevent toolbar rebuilds during live ink, add equality guards, coalesce continuous tool-setting persistence, and expose the adaptive switch over the existing width mode.

Risk: Medium Dependency: Phase 0 Expected payoff: Highest
2

True visible-set processing + linear hydration

Add O(1) element lookup and stable paint order, use spatial hits directly for painting and raster scheduling, combine canvas metadata reads, and bulk-build the element store and spatial index during load.

Risk: Medium Dependency: Phase 1 event channels Expected payoff: Large canvases
3

Cache longevity + incremental live ink

Dirty only affected tiles, separate tile and stroke-path invalidation, cache the stable prefix of an active stroke, and preserve only a small recomputed tail for live feedback.

Risk: Medium–High Dependency: Phase 2 ID/bounds tracking Expected payoff: Long sessions
4

Zoom-aware image memory

Preserve original image files while decoding bounded, viewport-appropriate raster buckets. Track access recency for eviction and keep visible raster memory behavior explicit.

Risk: Medium Dependency: Phase 2 scheduler Expected payoff: Media-heavy canvases
5

Background data and retained-screen work

Batch focus-history children, add the missing ritual-check index, decouple live runtime writes from broad history work, narrow 1 Hz subscriptions, aggregate reflection counts, and schedule library cleanup once after startup settles.

Risk: Low–Medium Dependency: Independent after Phase 1 Expected payoff: Battery and data growth
Phase 0 · Baseline and performance fixtures

Implement

  • Add deterministic fixture builders for 100, 1,000, and 10,000 mixed canvas elements, including sparse off-screen content.
  • Add a long-stroke scenario with enough points to expose per-frame full-path rebuilding.
  • Add a media scenario with several large images and PDFs.
  • Add a focus-history fixture with hundreds of sessions, distractions, and ritual checks.
  • Record controller notifications, widget builds, element lookups, paint candidates, persistence calls, SQL statement counts, frame timings, and decoded raster bytes.

Gate

  • Fixtures are deterministic and never use production note data.
  • Baseline results identify revision, device, build mode, and scenario.
  • Performance instrumentation is excluded or inert in release builds.
Phase 1 · Event isolation, write coalescing, and Adaptive pen

Implement

  • Introduce narrow listenables/revision channels for load state, viewport, committed elements, live stroke, selection/overlay, and toolbar/tool state.
  • Keep mutation ownership in CanvasController; do not migrate the editor to a second state architecture.
  • Remove the full-controller ListenableBuilder around the loaded editor. Route import errors through a targeted event or error channel.
  • Give each painter only the revision values that can change its output. Ensure toolbar and radial-wheel painters do not observe live-stroke or hover revisions.
  • Add equality guards to continuous setters. Update UI state immediately, debounce intermediate repository writes, and force the exact final value on gesture end.
  • Implement the Adaptive pen UX contract using the existing PenWidthMode, persistence column, and preset JSON.

Gate

  • A pen-move frame does not rebuild the toolbar or editor shell.
  • A hover-only change does not rebuild committed elements.
  • A tool-only change does not repaint the grid or committed layer.
  • A slider drag updates immediately and produces a bounded write count.
  • Adaptive on/off survives canvas close, reopen, and preset switching.
  • Existing strokes retain identical point data and stored width.
Phase 2 · Visible-set processing and bulk load

Implement

  • Maintain an element ID map and a stable z/layer paint-order map alongside the ordered list.
  • Update list, maps, spatial index, revisions, and raster ownership through one invariant-preserving mutation boundary.
  • Resolve spatial-query IDs through the map and sort only visible hits. Add selected preview elements only when required.
  • Schedule image/PDF work from visible element hits rather than scanning the complete store.
  • Replace repeated canvas-row reads with one metadata snapshot.
  • Hydrate already sorted elements in bulk, rebuild the spatial index once, compute the next z-index once, and emit one final loaded notification.

Gate

  • A viewport containing K elements performs lookups and ordering for K hits, independent of total N except when intentionally rebuilding.
  • Add, remove, undo, redo, reorder, layer change, and raster swap keep all stores consistent.
  • Opening a canvas produces the same element order, bounds, layers, and viewport as before.
  • Malformed or missing detail rows retain current safe behavior.
Phase 3 · Local cache invalidation and incremental live stroke

Implement

  • Derive dirty tile keys from old and new world bounds for add, remove, edit, transform, layer, and raster changes.
  • Preserve unaffected tile pictures and per-element stroke paths.
  • Keep a global clear for schema-level, ordering-wide, or defensive recovery events only.
  • Split live ink into a cached stable prefix plus a small recomputed tail. Reconcile both into the complete stroke on commit.
  • Preserve the original point stream exactly; preview simplification must never become persisted data.

Gate

  • Editing one element retains cache entries outside its dirty bounds.
  • Moving an element invalidates both its old and new regions.
  • A long-stroke preview does not rebuild geometry from point zero every frame.
  • Committed stroke points, pressure, tilt, timestamps, and velocity are unchanged.
Phase 4 · View-sized image rasters and memory policy

Implement

  • Decode imports from ImmutableBuffer.fromFilePath rather than first copying the full encoded file into a Dart byte array.
  • Select target pixel dimensions from element bounds, viewport scale, device pixel ratio, and a capped image scale ladder.
  • Request a sharper raster only after crossing a bucket threshold; do not re-decode on every pinch frame.
  • Track raster access recency and evict least-recently-used off-screen rasters first.
  • Keep the original file path authoritative for export and future higher-resolution decoding.

Gate

  • No imported source file is resized, replaced, or deleted.
  • Decoded image dimensions obey the configured maximum side.
  • Zooming in eventually improves visible sharpness without per-frame decode churn.
  • Eviction never disposes a raster still used by a visible element.
  • Export continues to use durable media and preserves expected fidelity.
Phase 5 · Focus, goal, library, and retained branch work

Implement

  • Replace focus history’s per-session child reads with one session query plus batched distraction and ritual-check queries.
  • Add an index for focus_session_ritual_checks.session_id through the normal Drift migration and schema-snapshot workflow.
  • Prevent 15-second runtime checkpoint updates from reconstructing full history details unless displayed history data actually changed.
  • Use Riverpod selection so Focus Home observes only restoring, session-present, and review-pending flags. Isolate 1 Hz rebuilding to the timer display and phase-dependent controls.
  • Replace reflection row fan-out with an aggregate count per card.
  • Run orphan cleanup once per process after the first useful frame or during idle, while keeping its path ownership protections.
  • Confirm whether the library’s explicit initial read is necessary before removing it.

Gate

  • Focus history refresh uses a bounded query count independent of session count.
  • Migration tests prove the new index upgrades existing databases safely.
  • The focus engine remains wall-clock correct while its UI is hidden.
  • Reflection badges remain exact after create, edit, move, and delete.
  • Cleanup never removes a referenced media or thumbnail file.

06 · Risks, non-goals, and decisions

Protect flow by keeping each change narrow

Store divergence

Adding ID/order maps can create multiple sources of truth.

Mitigation: one mutation boundary, invariant tests, and defensive rebuild only as recovery—not normal flow.

Stale cache regions

Local invalidation can leave visual ghosts if old bounds are lost.

Mitigation: commands supply before/after bounds; transformations dirty both; global clear remains available.

Settings persistence gap

Debouncing continuous controls can lose the final value if only a timer is used.

Mitigation: persist exactly on gesture end and use debounce only for intermediate safety checkpoints.

Preview/data coupling

Optimizing live ink must not simplify the stored point stream.

Mitigation: separate preview geometry from the authoritative point buffer and assert byte-level round trips.

Image quality thrash

Too many raster buckets can trade memory savings for repeated decode.

Mitigation: a small scale ladder, hysteresis, capped concurrency, and visible-priority scheduling.

Hidden timer correctness

Pausing UI work must not pause the focus engine.

Mitigation: keep wall-clock transitions and durable checkpoints active; narrow only presentation emissions.

Explicit non-goals

  • No replacement of Drift, Riverpod, or GoRouter.
  • No rewrite of the canvas command architecture.
  • No lazy stroke persistence or destructive media compression.
  • No arbitrary SQLite pragma tuning before query work is fixed.
  • No speculative visual simplification or removal of useful UI.
  • No dependency-upgrade campaign inside performance PRs.

One product decision to confirm

Should Adaptive pen be remembered independently by each brush preset, or should one switch control every brush?

Recommended: per preset. It matches the current source model, preserves existing saved behavior, and lets a highlighter remain canvas-scaled while a pen remains screen-adaptive.

Definition of done for the full optimization program
  • Every high-frequency controller event has a documented narrow consumer set.
  • Visible paint and raster scheduling avoid full-element scans.
  • Canvas hydration is linear and emits one completed-load update.
  • Tile/path caches survive unrelated element changes.
  • Long live strokes reuse stable geometry without losing source points.
  • Large image rasters are view-sized while source media remains untouched.
  • Focus history has bounded query count and hidden branches avoid unnecessary rebuilds.
  • Adaptive pen is discoverable, persisted, preset-correct, and non-destructive.
  • Profile results are recorded against the original baseline on the target device.
  • The arm64-v8a release APK is built as zenno.apk and manually verified.
