Schedule Revision card layout, drag, and add-card options plan

Outcome

On the Schedule Revision page, each Kanban column stretches to the bottom of the available screen, cards can be moved across columns repeatedly with their persisted column/status updated each time, and newly added revision cards expose the same edit/options surface available when tapping an existing card.

Codebase Evidence

  • lib/features/revision/presentation/pages/revision_board_page.dart: Schedule Revision renders KanbanBoardView and opens showRevisionCardDetailSheet on card tap.
  • lib/shared/kanban/kanban_board_view.dart: board uses horizontal SingleChildScrollView with IntrinsicHeight, which can prevent columns from filling the viewport height.
  • lib/shared/kanban/kanban_column_view.dart: columns already use Column + Expanded card list + bottom add button; card drag/drop is implemented with LongPressDraggable<KanbanCardData> and DragTarget<KanbanCardData>.
  • lib/shared/kanban/kanban_controller.dart: moveCard contract already supports cross-column movement and fractional positions.
  • lib/features/revision/data/revision_repository.dart: moveCard persists board_cards.column_id, position, and updated_at; stream rebuilds card columnId from DB.
  • lib/features/revision/application/revision_providers.dart: RevisionBoardController delegates generic card moves and exposes revision-specific update/flag/mark methods.
  • lib/features/revision/presentation/widgets/revision_card_detail_sheet.dart: existing tap sheet contains title/notes editing, mastery selection, revision history, canvas attachments, mark revised, save, and delete.
  • test/kanban_board_view_test.dart, test/revision_card_detail_sheet_test.dart, and test/board_empty_state_test.dart: existing widget coverage for add-card dialog, card tap semantics, detail sheet writes, and empty boards.

Assumptions

  • “Status” means the card’s current revision column/bucket, represented by board_cards.column_id; no new explicit status field is needed.
  • “Options when adding a card” means after creating a card, the same revision-card detail sheet should be available immediately, or the creation UI should collect enough data to open that sheet for the new card.
  • Because KanbanBoardView is shared with Goal Cycle, shared layout/drag fixes should preserve goal-board behavior unless the implementation deliberately adds a revision-only wrapper.

Plan

  1. Fix full-height columns in the shared board layout: replace the IntrinsicHeight-based horizontal scroll content in KanbanBoardView with a height-constrained layout from LayoutBuilder (for example, wrap the horizontal scroll child in ConstrainedBox(minHeight: constraints.maxHeight) / SizedBox(height: constraints.maxHeight) when finite). Keep column width math intact and ensure the add-column affordance also stretches visually.
  2. Harden cross-column card dragging in KanbanColumnView: make each column body a broad drop target, not only the thin inter-card gaps. Add an “append to this column” target that covers remaining empty space below cards so users can drop anywhere in a column, including repeatedly after prior moves.
  3. Verify/preserve persistence semantics: keep routing all drops through controller.moveCard(cardId, toColumnId, newPosition). The existing revision repository already updates column_id, which is the persisted bucket/status. If a moved card leaves its old column with near-converged positions, consider renormalising both old and new columns only if tests/manual behavior reveal ordering drift; otherwise avoid expanding repository writes.
  4. Expose post-add card options for revision cards without coupling the shared Kanban widget to revision UI. Add an optional callback to the shared add-card path, such as onCardAdded receiving enough data to identify the created card, or change KanbanController.addCard to return the new card id. Since the repository already returns String and the controller currently discards it, the smallest coherent change is to update the controller interface to Future<String?> addCard(...) and have implementations return the new id when available.
  5. In RevisionBoardPage, pass a revision-specific post-add handler that waits for the created card to appear in revisionBoardProvider (or looks it up from the current/refreshed board snapshot) and opens showRevisionCardDetailSheet for that card. If lookup is not immediately available from the stream, show no blocking UI and rely on the card being tappable after creation.
  6. Update all affected implementations/tests of KanbanController.addCard, including Goal Cycle and test fakes, to match the return type while preserving existing behavior where no post-add sheet is required.
  7. Add widget tests: full-height board layout has columns matching the available body height; dropping a card into another column calls moveCard with that column id; adding a revision card can trigger/open the same detail/options sheet or at least invokes the new post-add hook with the created id.

Validation

  • Run targeted tests: flutter test test/kanban_board_view_test.dart test/revision_card_detail_sheet_test.dart test/board_empty_state_test.dart.
  • Run flutter analyze because shared interfaces and multiple controller implementations will change.
  • If behavior logic changes beyond widget wiring, run full flutter test.
  • Manual tablet check: open Schedule Revision, confirm columns fill from below the app bar to bottom, drag the same card between multiple columns repeatedly, kill/reopen app and confirm it remains in the last column, add a new card and confirm the same card options/details are available.

Risks And Guardrails

  • Changing KanbanController.addCard affects shared Goal Cycle code and test fakes; update all implementers in one pass.
  • Flutter drag/drop widget tests can be brittle with long-press draggables; keep tests focused on controller calls and use existing keys/visible text where possible.
  • Opening a bottom sheet immediately after adding depends on the reactive stream delivering the new card; guard against missing lookup and avoid crashing if the card is not found yet.
  • No DB migration should be needed because status is already represented by board_cards.column_id.
  • No Git writes, dependency changes, destructive data operations, or deployments are required.

Open Questions

  • Should the same post-add detail/options behavior apply only to Schedule Revision, or also to Goal Cycle cards?
  • Should the add flow open the detail sheet automatically after saving, or should the add dialog itself include the extra options before creating the card?
