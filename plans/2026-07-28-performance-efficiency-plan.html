Zenno · Performance & Efficiency · 2026-07-28

Making every frame and every joule count

A code-level audit of where Zenno actually spends CPU, memory and battery on the Tab S9 FE. The good news first: the rendering core is already well-built — tile pictures, a raster resolution ladder with a 96 MB budget, per-concern repaint channels, a spatial index, binary ink storage. What remains is a specific set of per-frame and startup costs, each traced to its line. At 90 Hz the frame budget is 11.1 ms; everything below is measured against that.

1P0 — Per-frame work during pan & zoom

These run on every one of the 90 frames of a pan gesture. Biggest wins per line changed.

1.1 · Raster scheduling walks every element on every viewport change P0

_scheduleVisibleRasters (canvas_controller.dart:4854) loops for (final element in _elements) — the entire store — on every viewport change, after already computing visibleIds from the spatial index. On a 5,000-element canvas that is 5,000 iterations plus a set build per pan frame, to conclude (almost always) that nothing needs decoding.

Fix, two independent halves:

  • Iterate visibleIds and look each id up in _elementsById — the work becomes proportional to what is on screen, not what exists.
  • Debounce: rasters only need scheduling when the camera settles. Run the sweep when the viewport has been stable for ~80 ms or the gesture ends, not per frame mid-fling. The ladder's "keep what you have until sharper lands" behaviour already hides the delay.
lib/canvas/canvas_controller.dart · lib/canvas/render/canvas_view.dart

1.2 · Paper texture recomputes up to ~20k hashed cells per frame P0

PaperTexturePainter repaints on every viewport change and, per cell, computes a hash, derives an anchor/angle/length, and projects through CanvasTransform.toScreen — per point, per frame. At ~14 px screen spacing on the Tab's 2560×1600 panel that is a five-figure op count every frame of every pan, for a background that never changes.

Fix: the texture is deterministic per (texture, step) — _paperHash guarantees cell (x,y) always draws the same marks. So:

  • Record one world-space texture tile (say 512×512 world units at the current step) into a ui.Picture once, then stamp it across the visible rect under the canvas's world transform — the per-point toScreen disappears along with the per-frame hashing. The picture invalidates only when step (zoom bucket) or the style changes.
  • Same treatment for GridPainter's dot lattice: it already batches into one drawPoints, but still regenerates the point list per frame. One recorded tile stamped N times beats regenerating thousands of offsets.

A pan then costs the GPU blitting a handful of cached pictures — effectively free — and the CPU nothing.

lib/canvas/render/grid_painter.dart

1.3 · viewportElements re-queries and re-sorts per pan frame P1

The getter's cache is invalidated on every viewport change, so each frame of a pan re-runs the spatial query and re-sorts the result — even though during a pure pan the visible set changes only at the edges. The tile path doesn't consume this list, but the build closure reads it every elements-listenable fire.

Fix: keep the invalidation, but short-circuit the rebuild: if the new query returns the same id set as the cached list (cheap set compare against a kept id set), reuse the previous sorted list. Sorting only happens when membership actually changed.

lib/canvas/canvas_controller.dart

1.4 · S Pen hover repaints the full overlay layer at report rate P1

An S Pen hovers continuously within ~1 cm of the glass. Every hover event moves hoverPointWorld, which fires _notifyOverlay, which repaints the whole full-screen overlay CustomPaint — selection box, bookmarks chrome, eraser trail logic — to move one small ring. That is a full-screen layer rasterisation per frame whenever the pen is merely near the tablet, which is most of a study session. Pure battery burn.

Fix: split the hover ring out of CanvasOverlayPainter into its own tiny positioned widget (a Transform.translate around a ~64 px RepaintBoundary). Moving a boundary is a compositor offset update — no rasterisation at all. The overlay painter keeps everything else and stops depending on the hover point.

2P1 — Opening a canvas

The costs between tapping a note and drawing on it.

2.1 · load() serialises seven independent queries P1

canvas_controller.dart:1279–1285: layers, elements, bookmarks, viewport, rotation lock, paper style, tool settings — awaited one after another. Each is a round-trip to drift's background isolate; the payloads are independent.

Fix: Future.wait over all seven (elements is the long pole; the six small reads ride along free). Trivial, safe, saves six round-trips of latency on every open.

lib/canvas/canvas_controller.dart

2.2 · Every ink BLOB decodes on the UI isolate at open P1

loadElements calls InkCodec.decodePoints per stroke on the calling (UI) isolate. v3 records are 48 bytes/point; a dense study canvas — thousands of strokes, hundreds of points each — is tens of MB of ByteData reads in one synchronous burst while the open animation is trying to run.

Fix: move the row→StrokePoint[] decode into a single compute() call: ship the raw BLOBs (they're Uint8Lists — transferable, near zero copy cost) to a worker isolate, get point lists back. One isolate spawn per open, not per stroke. Decode of images/PDFs already happens off-thread; ink is the last decoder on the UI isolate.

lib/canvas/persistence/canvas_repository.dart · lib/canvas/persistence/ink_codec.dart

2.3 · First paint tessellates every visible stroke at once P1

InkElement.outlinePath is built lazily on first read — which means the first frame after load runs perfect_freehand over every visible stroke simultaneously, then records tile pictures on top. One big jank spike exactly when the user is looking.

Fix: pre-warm in idle slices. After hydration, walk the visible-first element list and touch outlinePath a few strokes per SchedulerBinding.scheduleTask(Priority.animation - 1) slice, yielding every ~4 ms. The spike becomes a ramp the user never sees; anything not yet warmed still builds lazily as before, so nothing can render wrong — only later.

3P1 — Memory over a long session

Zenno is a study tool; sessions run hours. Growth that never stops eventually kills the app — and Android kills first, asks never.

3.1 · The undo history is unbounded P1

_undoStack has no cap. Every command holds full element snapshots — including complete stroke point lists. An afternoon of writing accumulates every stroke ever drawn twice: once in the store, once in history. Nothing is ever released until the canvas closes.

Fix: cap the stack (200 commands) and drop from the bottom. No data risk by construction: every command past the cap is already committed to SQLite — the cap only limits how far back undo reaches, which past 200 steps is a feature nobody has ever used. Constant chosen generously; make it a static const so it is one line to tune.

lib/canvas/canvas_controller.dart

3.2 · No response to system memory pressure P1

The raster budget (96 MB) is enforced only against itself. When Android signals memory pressure — the step before it starts killing processes — Zenno does nothing. The tile cache (up to 96 pictures), warm rasters, and the undo stack all sit untouched while the OS decides whether to keep us alive.

Fix: implement didHaveMemoryPressure in the editor's existing WidgetsBindingObserver: clear the tile cache (rebuilds lazily from intact state), evict all off-screen rasters immediately, and trim the undo stack to its most recent quarter. All three are pure caches or already-persisted history — nothing the user can lose. Being a good citizen here is also what keeps the lifecycle-flush guarantee meaningful: the process that isn't killed doesn't need its crash-recovery path.

lib/canvas/canvas_editor_page.dart · lib/canvas/canvas_controller.dart · lib/canvas/render/elements_painter.dart

3.3 · Verify: tile pictures must not outlive evicted rasters audit

A recorded tile picture that contains drawImageRect holds a reference to that ui.Image. Raster eviction calls image.dispose(). If eviction does not also invalidate the tiles covering that element, a cached tile either keeps the "freed" memory alive or replays a disposed image. Reading the code suggests the damage path covers it (the swap bumps the revision), but this is a correctness-adjacent memory question that deserves a test, not a belief: evict → assert the covering tile was dropped from the cache.

4P2 — Storage & smaller costs

Real, but behind everything above.

4.1 · Ink codec v4: cut the 48 bytes/point roughly in half P2 · measure first

v3 spends float64 on x, y, velocity and timestamp per point. Velocity is a render hint (float32 is plenty); timestamps fit in a uint32 delta from the stroke's start; tilt/azimuth fit in int16 fixed-point. That is ~22–24 bytes/point — half the disk, half the decode traffic — while x/y stay float64 for the deep-zoom guarantee. Gated on measurement: after 2.2 moves decode off-thread, remeasure; if open latency and DB size are fine, this stays deferred. Any v4 must follow the codec's standing rule — the decoder keeps v1/v2/v3 support forever, old notes are never rewritten in place.

lib/canvas/persistence/ink_codec.dart

4.2 · Micro-items P2

  • _TileKey allocates per tile per frame in _paintCachedTiles — hoist to an int key (x*const+y) if allocation shows in profile; likely noise, listed to be honest that it was seen and judged.
  • ElementsTileCache._evictIfNeeded is O(n) scan per eviction — fine at 96 entries, would matter if maxTiles grows; note in code, don't fix.
  • endLasso narrow phase runs full geometry per candidate; fine post-thinning, revisit only if a 10k-element lasso lags on device.
  • _track-wrapped saves fire one SQLite transaction per committed stroke — correct (durability per stroke is the point); do not batch.

5Measurement protocol

Before/after on the actual device, or the numbers are fiction.
  1. Baseline first: flutter run --profile on the Tab S9 FE. DevTools timeline over three scripted scenarios: (a) 30 s continuous pan over a dense canvas, (b) open a canvas with 2,000+ strokes and an image, (c) 60 s of S Pen hover without touching. Record: average/worst frame build+raster ms, UI-isolate jank count, dirty-layer area during hover.
  2. Per-fix verification: re-run only the affected scenario after each numbered item. A fix that does not move its scenario's number gets reverted, not kept as lore.
  3. Targets: pan p95 frame < 8 ms total (headroom under 11.1); open-to-interactive on the 2,000-stroke canvas < 600 ms after 2.1–2.3; hover dirty area ≤ the ring's own boundary after 1.4.
  4. Memory: DevTools memory view through a simulated 1-hour session (scripted stroke commits); heap must plateau after 3.1, not climb.

Data safety

Nothing in P0/P1 touches what is written to disk — every item is caching, scheduling, or decode location. The two items adjacent to persistence are explicitly guarded: the undo cap only discards history already committed to SQLite, and codec v4 (if it ever happens) is additive — v3 notes decode forever, unchanged. The memory-pressure handler drops only reconstructible caches.
