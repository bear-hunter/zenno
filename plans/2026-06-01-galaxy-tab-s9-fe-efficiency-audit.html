Zenno Efficiency Audit for Galaxy Tab S9 FE

A codebase-first performance review focused on making the Android tablet experience fast, calm, and reliable without compromising canvas features, note data, imports, exports, undo, or the current flow of the app.

Audit date: 2026-06-01 Repo: /Users/karlromero/personal/zenno Target: Samsung Galaxy Tab S9 FE base model Priority: S Pen latency, memory, and persistence safety

Executive Summary

Zenno already has the right architecture for a thinking-first tablet note app: a spatial index, visible culling, tile picture caching, RepaintBoundaries, cached committed ink paths, async raster loading, and Drift on a background connection. The app is not in bad shape. The big efficiency wins are mostly about reducing accidental work during pointer movement and separating expensive runtime caches from durable note state.

2 P0 fixes should be done first because they directly affect handwriting and panning smoothness.
5 P1 fixes protect memory, persistence, large canvases, PDF/image work, and selected-object transforms.
90 Hz The tablet display target leaves roughly 11.1 ms per frame, so pointer-time work must be extremely small.
0 Recommended changes require removing existing core features. This is an optimization pass, not a rebuild.
Main diagnosis: the canvas has strong low-level ingredients, but the current notification and painting pipeline can invalidate too much UI on every pointer event. Fixing that will make the app feel much faster without changing the user-facing workflow.

Priority Findings

P0 Stop repainting committed canvas content for unrelated controller updates

The committed elements layer receives fresh list, set, and map objects on every rebuild. ElementsPainter.shouldRepaint treats a new elements list identity as a repaint trigger, so hover, live stroke, lasso, selection overlay, and other controller notifications can make the expensive committed layer eligible to repaint.

Evidence

CanvasController.visibleElements creates a new list at lib/canvas/canvas_controller.dart:234. selectedIds creates a new set at :436. CanvasView passes these into ElementsPainter at lib/canvas/render/canvas_view.dart:1047. ElementsPainter.shouldRepaint compares list identity at lib/canvas/render/elements_painter.dart:916.

Solution

Introduce stable canvas-layer inputs. Keep cached unmodifiable views for visible elements and selection state, plus explicit revision integers such as elementsRevision, selectionRevision, and viewportRevision. Better still, split the controller notifications into small listenables: committed elements, live stroke, overlay, viewport, and raster state.

Expected impact: less UI-thread and raster-thread work while writing, hovering, panning, and selecting. This should be the first optimization because it protects the exact moments where the app needs to disappear.

P0 Replace live-stroke list cloning and full outline rebuilds during S Pen input

Live drawing currently grows the active stroke by cloning the entire point list for every accepted pointer sample, then the live painter rebuilds the freehand outline from all current points on repaint. For long strokes, this creates rising per-sample cost exactly while the user is writing.

Evidence

appendToActiveStroke creates <StrokePoint>[...stroke.points, newPoint] at lib/canvas/canvas_controller.dart:901. LiveStrokePainter calls buildStrokePath from all active points at lib/canvas/render/live_stroke_painter.dart:58. buildStrokePath invokes perfect_freehand.getStroke at lib/canvas/engine/stroke_builder.dart:83.

Solution

Use a mutable LiveStrokeBuilder only for the active stroke. Append points into a growable buffer, coalesce pointer notifications to at most one per frame, and cache the generated live path incrementally or rebuild only a tail segment. On pointer up, freeze the final immutable InkElement and persist exactly as today.

Expected impact: much lower latency for handwriting and long strokes, especially on the base tablet. This preserves the final stroke model and undo behavior while making the in-progress stroke cheaper.

P1 Separate raster cache memory from undo/redo element snapshots

Raster cache eviction currently avoids disposing some images because undo commands may still reference element objects that contain runtime raster fields. This protects correctness, but it weakens the memory budget on a RAM-constrained tablet.

Evidence

Raster budget is configured around _maxRasterCacheBytes at lib/canvas/canvas_controller.dart:336. Eviction logic notes that disposed ui.Image objects can still be referenced through undo snapshots at lib/canvas/canvas_controller.dart:3292.

Solution

Keep durable element snapshots free of decoded ui.Image instances. Store persistent image/PDF metadata in elements, and store decoded rasters in a dedicated runtime cache keyed by element id plus resolution bucket. Undo/redo commands should restore metadata and request raster hydration, not hold decoded image objects.

Expected impact: predictable memory release when moving around large canvases with images or PDFs. This also makes it safer to lower or adapt the cache budget for the base model.

P1 Batch canvas loading and persistence instead of many small queries

Canvas load and element reconstruction use several single-purpose queries. Each element detail is reconstructed through a separate detail-table read. For a large note, that becomes many async database round trips even though the database itself is on a background connection.

Evidence

CanvasRepository.loadElements reads base rows, then calls _reconstruct per row at lib/canvas/persistence/canvas_repository.dart:72. Per-type detail queries live around :103 through :199. CanvasController.load separately loads layers, elements, viewport, rotation lock, paper style, and tool settings at lib/canvas/canvas_controller.dart:637. upsertElement starts a transaction per element at lib/canvas/persistence/canvas_repository.dart:235.

Solution

Add a repository method that loads the full canvas state in one orchestration: canvas row, layers, base element rows, and all detail tables in batches grouped by element_id. Add upsertElementsBatch and deleteElementsBatch for multi-element commands. Ensure the default content layer once during canvas creation/load instead of inside every element upsert.

Expected impact: faster opening of large canvases, smoother undo/redo for multi-element edits, and fewer small writes during imports or bulk selection operations.

P1 Queue visible PDF/image raster work with priority and concurrency limits

Visible image and PDF rasters are scheduled asynchronously, which is good. The next step is to prevent too many heavy jobs from starting together when a viewport includes many pages or high-resolution images.

Evidence

_scheduleVisibleRasters walks all elements and starts loads for visible raster candidates at lib/canvas/canvas_controller.dart:3049. PDF rendering is bucketed and capped in lib/canvas/pdf/pdf_raster_service.dart, but scheduling still needs viewport-aware pressure control.

Solution

Add a small raster job queue. Prioritize elements closest to the viewport center, limit PDF work to one or two active jobs, deprioritize or cancel stale off-screen jobs, and keep decoded image targets close to displayed size during interaction. Consider a dynamic raster budget of 64 to 96 MB depending on memory pressure.

Expected impact: fewer frame stalls and fewer memory spikes when navigating PDF-heavy or image-heavy notes.

P1 Render selection transforms as a preview matrix, then bake geometry once

Selection transform preview currently creates transformed copies of selected elements on every transform update. For selected ink strokes, that means touching every selected point repeatedly while a pinch or drag gesture is still in progress.

Evidence

Selection transform updates are handled around lib/canvas/canvas_controller.dart:2080. Ink point transforms are copied in geometry helpers around :2332 and :2395. The preview map is exposed through copied state at :424.

Solution

During the gesture, store only the selected ids plus a transform matrix. Let the painter draw selected elements through that matrix. When the gesture ends, bake the transform into the actual element geometry once and push a single undoable command.

Expected impact: smoother transform gestures for groups of handwritten notes, links, pasted images, and imported PDFs.

P1 Save durable canvas data before best-effort thumbnail capture on editor dispose

When leaving a canvas, thumbnail capture runs before controller flush/dispose. Thumbnail work is useful, but durable note persistence should win the ordering decision.

Evidence

CanvasEditorPage.dispose calls _captureThumbnail().whenComplete(() { controller.flush()... }) at lib/canvas/canvas_editor_page.dart:145. Thumbnail capture uses toImage, PNG encoding, file writing, and a database update around :155.

Solution

Flush controller changes first, then run thumbnail capture as best-effort work. If thumbnail capture fails or times out, keep the note data safe and regenerate the thumbnail later.

Expected impact: better data-integrity posture and less risk that visual thumbnail work delays critical note writes.

P2 Make tile cache lookup and stroke revisions incremental

Tile caching is the right direction, but some internals still scan broad lists or hash point data during paint. These costs are usually hidden by the cache, then show up during invalidation, high zoom, or selected/dynamic states.

Evidence

Tile recording gets visible ids, then still iterates elements in _pictureFor at lib/canvas/render/elements_painter.dart:95. Normal visible painting also iterates the full element list at :409. High-zoom stroke path cache computes a revision by hashing every point at :550.

Solution

Maintain an id -> element map or have the spatial index return ordered element references. Store precomputed element and stroke revisions when elements are created or edited. Dirty only the tiles overlapped by changed elements instead of clearing broad cache state whenever the signature changes.

Expected impact: better large-canvas scaling, especially at high zoom and after small edits.

P2 Reduce library page repeated filtering and thumbnail decode size

The library page is not the hottest path, but it should stay light because it is the first thing the app shows. Current folder filtering repeatedly scans canvases, and thumbnail image widgets do not request a smaller decode size.

Evidence

Folder search checks canvases.any inside a folder filter at lib/features/library/presentation/pages/library_page.dart:291. Folder sections repeatedly build folderCanvases lists around :341. Canvas cards use Image.file without cacheWidth or cacheHeight around :664.

Solution

Group canvases by folder once per build and pass grouped lists down. Generate thumbnails at the intended card size or pass decode hints such as cacheWidth and cacheHeight. Keep existing visual design, just decode fewer pixels.

Expected impact: lower memory use and smoother library scrolling as the number of canvases grows.

P2 Move heavy export encoding off the UI isolate and lower tablet defaults

Export can allocate a large raw image and then encode PNG/JPG. That is acceptable for a deliberate export action, but the current maximum is high for a base tablet and JPG encoding happens synchronously.

Evidence

Export allows up to 64MP at lib/canvas/io/canvas_export.dart:84. JPG encoding converts raw RGBA and uses the image package synchronously around :265.

Solution

Use a lower Android tablet default export cap, move JPG encoding into an isolate, and consider tiled export for very large canvases. Keep high-quality export available through an explicit setting or warning.

Expected impact: fewer app stalls or memory pressure events during export while preserving high-quality output when intentionally requested.

P3 Flatten repeated shadows and expensive decoration on dense surfaces

The visual system is restrained overall, but repeated cards and columns still use shadows and blur. On mobile GPUs, shadows across many scrolling items are often more expensive than their visual value.

Evidence

AuroraPanel uses a blur shadow at lib/core/widgets/aurora.dart:127. Library cards and Kanban columns also include shadows in repeated surfaces.

Solution

Keep depth on sparse, important panels if it helps the mood. For repeated cards, columns, and dense lists, prefer flat fills, subtle borders, or one low-blur shadow. This can be gated by an Android tablet performance theme.

Expected impact: small but reliable GPU savings in library and planning screens.

P3 Narrow editor provider watches and post-frame scheduling

Some editor rebuild triggers are broader than needed. This is lower priority than painting and input, but it is a clean way to reduce background churn.

Evidence

CanvasEditorPage watches canvasListProvider to find one title at lib/canvas/canvas_editor_page.dart:325. CanvasView schedules a post-frame callback from build when syncing viewport/raster work at lib/canvas/render/canvas_view.dart:990.

Solution

Add a single-canvas summary/title provider for the editor chrome. Move viewport-size reporting to a size-change signal or otherwise coalesce the post-frame sync to viewport changes only.

Expected impact: smaller rebuild surfaces and less incidental work while the canvas is active.

Recommended Roadmap

Phase 1: Quick Wins

1 to 2 focused sessions

  • Stable painter inputs and revision tokens.
  • Split or narrow controller notifications.
  • Flush before thumbnail capture.
  • Library thumbnail decode hints.
  • Canvas title provider instead of full list watch.

Phase 2: Ink Latency

2 to 4 focused sessions

  • Mutable live stroke builder.
  • One notification per frame during drawing.
  • Incremental live path or tail rebuild.
  • Matrix-only selection transform preview.

Phase 3: Memory and IO

2 to 4 focused sessions

  • Raster cache detached from undo snapshots.
  • PDF/image raster job queue.
  • Batch canvas load and batch writes.
  • Export encoding isolate.

Phase 4: Profiling Lock

Ongoing baseline

  • Profile-mode runs on the real tablet.
  • Save frame chart screenshots.
  • Record memory during PDF/image stress tests.
  • Add durable Lessons Learned only after manual confirmation.

Performance Budget

Frame target At 90 Hz, aim under 11.1 ms per frame. For handwriting, keep UI isolate work comfortably below that because Flutter and the GPU still need room.
Pointer moves Pointer handlers should append data and schedule work, not rebuild full paths, clone long lists, or notify multiple heavy layers per sample.
Raster memory Keep decoded runtime rasters explicit and disposable. A practical tablet range is 64 to 96 MB, adjusted after real-device memory profiling.
Database writes Preserve every note change, but batch multi-element operations and avoid repeated setup reads inside hot persistence paths.
Exports Large export is allowed, but it should be an explicit heavy operation with progress, isolate work, and memory safeguards.

Validation Plan

The fastest way to avoid accidental regressions is to combine targeted automated tests with real Galaxy Tab S9 FE profile-mode checks. The app is for flow, so the final judge is how pen input feels on the actual tablet.

Check Scenario Pass Signal
Static validation Run flutter analyze and the existing targeted canvas tests after each implementation phase. No new analyzer errors and no failing canvas persistence/rendering tests.
Handwriting Profile mode on tablet, draw a 30-second continuous stroke and several quick short strokes. No visible stroke lag, no rising frame time as the stroke gets longer.
Large canvas Canvas with hundreds or thousands of strokes, pan and zoom with grid enabled. Frame chart stays mostly below budget and no long UI stalls occur during movement.

Do-Not-Compromise Guardrails

  • Data integrity stays first. Persistence order should favor saving note data before thumbnails, preview caches, or cosmetic updates.
  • Undo/redo must remain exact. Optimizations should move runtime caches out of command snapshots, not weaken command history.
  • No destructive migrations. Database changes should be additive and covered by migration tests.
  • Current tools stay intact. Pen, eraser, lasso, select, links, images, PDFs, layers, export, focus, and library workflows should survive each phase.
  • Optimize interaction, not just benchmarks. The winning metric is how little the app interrupts thinking while writing and navigating.

Suggested First Implementation Set

If only one pass is done first, implement these in order:

  1. Give ElementsPainter stable inputs and revision tokens so unrelated controller notifications stop repainting committed content.
  2. Change live stroke handling to a mutable in-progress buffer with one repaint notification per frame, freezing into the existing immutable model on commit.
  3. Change editor dispose ordering so controller.flush() happens before thumbnail capture.
  4. Add thumbnail decode hints and pre-group canvases by folder in the library page.
  5. Then tackle raster cache separation and PDF/image job queueing once the main drawing path is calmer.
Bottom line: the app does not need to lose features to become much faster. The main move is to stop making stable canvas content participate in every tiny live interaction, then make live ink and raster work behave like bounded, frame-aware systems.
