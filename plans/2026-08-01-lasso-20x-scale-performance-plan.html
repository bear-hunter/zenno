Lasso at 20x Scale — Round 2

Round 1 (branch fix/lasso-selection-performance, commit 0c2d8fe) simplified the committed loop, added an early-exit majority test, and capped coverage samples. That made a large mindmap fast — but a 20x-larger one still chokes the tablet. Round 1 shrank the constants; the algorithm is still linear-in-the-loop per element at commit, and after the commit the renderer silently falls back to full vector repaints every frame for as long as anything is selected. This plan fixes both, with no change to how lasso selection behaves.

Three deviations from the plan below, all deliberate:

  • No halo in the grid (Step 1). Inflating each element's query rectangle by its own reach is both simpler and tighter than baking one global worst-case halo into the cells, and it makes the rejection provable: a box inflated by r that misses the loop entirely cannot have geometry within r of it, because box inflation covers the Euclidean disc. A summed-area table over the boundary cells makes classifyRect four array reads regardless of element size.
  • The tile cache was left alone (Step 4). Reading it closely killed the original plan: _visibleTileCount > maxTiles already disables tiles at overview zoom, which is exactly where a 20x lasso happens — so excluding the selection from tiles would have bought nothing in the case being fixed.
  • The selection floats in its own layer instead. Root Cause B's real damage was per-frame repaints, and those are now gone at every zoom: a drag splits the canvas into an unselected layer that holds still and a selected layer moved by a widget transform, on its own notification channel so the committed layer is never even woken.

Two costs not in the original analysis turned up while implementing and were fixed as part of Step 3: viewportElements was rebuilt (spatial query + sort of everything on screen) once per pointer sample, and it deduplicated the selection with List.contains — selected x visible comparisons, tens of millions of them on a big selection.

1. Where the Time Goes at 20x

ROOT CAUSE A Commit: every candidate still pays O(loop) — and rejected candidates pay O(loop × stroke).
  • A loop drawn around a 20x mindmap has a bounding box that covers the whole canvas, so the spatial-index broad phase in endLasso (canvas_controller.dart:3371) returns every element as a candidate. The broad phase is dead weight at this scale.
  • After Round 1's RDP simplify, the loop still keeps S ≈ 150–500 vertices (a curvy hand-drawn loop at 2 px tolerance). Every polygonContainsPoint call walks all S vertices.
  • Elements inside the loop are cheap now: the majority test short-circuits after ~17 of 32 samples → ~17 × S ops each.
  • Elements inside the bbox but outside the loop are the killer. The majority test fails (~16 × S ops), then they fall into the boundary-touch fallback polylinesWithinDistance(boundary, centerline, slop) (canvas_geometry.dart:69) — a nested segment-pair loop: S × strokeSegments ≈ 400 × 200 = 80k+ ops per rejected stroke, times three passes (two vertex sweeps + the pair loop). Thousands of such elements → hundreds of millions of ops, synchronous at pen-up.
  • Fill strokes outside the loop are worse still: boundary.any(outlinePath.contains) = S native Path.contains calls each.
ROOT CAUSE B After commit: the tile raster cache turns off while anything is selected.

_canUseTileCache (elements_painter.dart:415) returns false whenever selectedIds.isNotEmpty. The moment a big lasso selection exists, every frame — pan, zoom, selection drag, even idle overlay repaints — re-paints every visible element as vectors. On a 20x canvas that alone is a frame-budget blowout, and it lasts the entire lifetime of the selection. This is why the tablet keeps struggling after the loop closes, not just at pen-up.

ROOT CAUSE C Per-frame O(N) selection-bounds scan.

The selectionBounds getter (canvas_controller.dart:851) is documented as "read on every overlay repaint" and scans all elements whenever a selection exists. With a selection active on a 20x canvas, every overlay frame (including every frame of a selection drag) walks tens of thousands of elements just to redraw the selection box.

2. Fix Steps

0PREREQ Merge Round 1 into staging

fix/lasso-selection-performance (commit 0c2d8fe: simplifyPolyline, polygonMajorityInside, 32-sample stride + its 152 lines of geometry tests) is not on staging — the tested APK came from the branch. Round 2 builds directly on those primitives, so merge first and confirm flutter analyze + flutter test stay green.

1FIX Build a one-shot lasso region grid at commit (kills Root Cause A)

Add LassoRegionGrid (new, in lib/canvas/tools/) — built once in endLasso from the simplified loop, then thrown away:

  • A uniform grid over the loop's bounding box (target ~128 cells on the long axis, hard cap ~32k cells — a few hundred KB of bytes, transient).
  • Boundary cells: walk each of the S loop segments (supercover / DDA), marking touched cells plus a halo of ceil((touchSlop + maxStrokeHalfWidth) / cellSize) cells. Each boundary cell keeps the indices of the segments crossing it.
  • Inside/outside cells: per grid row, compute the even-odd crossings of the polygon at the row's center-y (O(S) per row) and classify the non-boundary runs. Total build cost ≈ O(rows × S + cells) ≈ 100k ops — trivial, once.

Then reuse it everywhere in the narrow phase:

  • containsPoint(p): O(1) for points in decided cells; points in a boundary cell fall back to the exact polygonContainsPoint. Result is bit-identical to today's test.
  • segmentsNear(rect): union of segment indices from the boundary cells overlapping rect — the loop passes near any single element only once or twice, so this is ~5–20 segments instead of all S.
  • classifyRect(rect): inside / outside / boundary — inside/outside only when the rect overlaps zero boundary cells (then one corner's containsPoint decides), otherwise boundary.
2FIX Bbox fast paths in endLasso — most elements never reach geometry

For each candidate, classify its worldBounds inflated by touchSlop (+ stroke.width / 2 for ink) via classifyRect:

  • inside → select immediately. (Every coverage sample of an element whose inflated bbox is fully inside the polygon is inside → the majority rule is trivially true. Same answer, zero geometry.)
  • outside → reject immediately. (No sample can be inside, and no rendered geometry can reach within touchSlop of the boundary — the inflation guarantees it. The quadratic fallback and the Path.contains sweep for fills never run.)
  • boundary → run the existing narrow phase, but accelerated:
    • majority test uses grid.containsPoint per sample;
    • polylinesWithinDistance receives only grid.segmentsNear(inflatedBounds) as the lasso side instead of the full boundary (drop-in: build the local polyline list from those segments);
    • fill strokes test only the vertices of those local segments against outlinePath.contains.

Expected: at 20x, the overwhelming majority of candidates are cleanly inside or outside → O(bbox-cells) each. Only elements the loop actually grazes (typically dozens, not thousands) do narrow-phase work, and that work drops ~20–50x from the local-segment prefilter. Commit goes from seconds to a few milliseconds.

3FIX Cache selectionBounds (kills Root Cause C)

Store the computed base rect in a field; invalidate on selection-set change, element store mutation, layer-visibility change, and transform commit — all of which already funnel through a handful of methods (_applySelectionIds, store add/remove/replace, layer setters). The per-frame getter becomes cache-hit + shift(selectionDragDelta), which is O(1). The existing empty-selection early return stays.

4FIX Keep the tile cache alive while a selection exists (kills Root Cause B)

Tiles already bake elements with _paintUnselectedElement (no halo), so the cache content is selection-agnostic. Change the strategy from "any selection disables tiles" to "selected elements are excluded from tiles and painted on top":

  • Pass selectedIds into tile picture recording; a tile's picture skips selected elements. Key each tile's picture by whether it contained any selected element, and invalidate exactly those tiles when the selection set changes (bounds are known — reuse the damage path _invalidateBounds per selected element's worldBounds).
  • Per frame: draw tiles (unselected content, cached), then vector-paint only the selected elements on top with their halo — translated by selectionDragDelta or transformed by the preview when dragging.
  • _canUseTileCache drops the selectedIds.isNotEmpty, _dragging, and _transforming disqualifiers; the pending-erase disqualifier stays.
  • On selection clear / commit of a move, re-invalidate the affected tiles once so the elements bake back in.

Cost model: selection commit and drag-end each pay a one-time rebake of the tiles the selection touches; every frame in between pays tiles + Nselected vector paints instead of Nvisible. For "select a region of a 20x canvas and drag it", that is the difference between janking and 60/120 fps.

DESIGN NOTE Painting selected elements on top of the tiles hoists them above overlapping unselected content while selected — standard select-and-float behavior in canvas apps (they float during drag anyway), but it is a visible z-order nuance. If it feels wrong in practice, the fallback is per-tile two-layer pictures (below-selection / above-selection), at the cost of tile-cache complexity. Start with float-on-top.

5CONTINGENCY Chunked commit — only if measurement says so

Instrument endLasso with a Stopwatch (debug/profile log). If, after Steps 1–2, a worst-case 20x commit still exceeds ~2 frames (>16 ms), slice the candidate loop into batches processed across frames with the lasso overlay held on screen until the selection lands. Do not build this speculatively — the grid math says it should not be needed.

3. Verification

EQUIVALENCE
  • Grid vs exact: property-style unit test — random jagged polygons + random points; LassoRegionGrid.containsPoint must equal polygonContainsPoint for every point.
  • Selection result unchanged: randomized scenes (ink, fills, shapes, images with rotation) × random loops; the id-set from the new endLasso must equal the pre-change narrow phase run exhaustively. Existing lasso tests keep passing.
  • Classify-rect safety: unit tests that rects overlapping any boundary cell are never classified inside/outside (the correctness linchpin of Step 2).
PERFORMANCE
  • Synthetic 20x benchmark test: ~10k strokes × 200 points scattered over a huge extent; lasso around 60% of them; assert commit wall-time and log the number (test asserts a generous bound; the log is the real signal).
  • On-device (Tab S9 FE, profile mode): trace the full gesture — draw loop, pen up, pan with selection, drag selection. Pen-up under a frame; pan/drag with selection at steady frame rate (tiles active — verify via timeline that the elements painter is not re-recording everything).
  • flutter analyze clean, full flutter test green.
  • Build arm64-v8a release APK (zenno naming) for on-device confirmation.

4. Risks & Constraints

  • RISK Boundary-cell halo too small → an outside-rejected element the loop should have touched. Mitigated by deriving the halo from touchSlop + maxStrokeHalfWidth (computed from the actual candidates, not a constant) and by the classify-rect safety tests.
  • RISK Tile invalidation bugs (stale selected element baked in a tile → ghost duplicate while dragging). Mitigated by routing all selection-set changes through one invalidation helper and an on-device visual pass. Rendering-only change — zero risk to note data.
  • RISK Self-intersecting loops: even-odd scanline classification must match polygonContainsPoint exactly (both are even-odd — keep it that way; the property test covers self-intersecting inputs).
  • Constraint: no behavior change — selection results bit-identical, loop rendering while tracing untouched, no new UI. The only intentionally visible difference is the Step 4 z-order note.
