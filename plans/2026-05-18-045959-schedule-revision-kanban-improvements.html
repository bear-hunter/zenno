Schedule Revision Kanban Improvements Plan

Outcome

The Schedule Revision board columns fill the available screen height, cards can be repeatedly dragged between any columns with persisted column/status updates, and card creation exposes the same revision options available when opening an existing card.

Codebase Evidence

  • lib/features/revision/presentation/pages/revision_board_page.dart: Schedule Revision renders KanbanBoardView and opens showRevisionCardDetailSheet on card tap.
  • lib/shared/kanban/kanban_board_view.dart: board uses a horizontal SingleChildScrollView with IntrinsicHeight; this is likely why columns size to content instead of full body height.
  • lib/shared/kanban/kanban_column_view.dart: columns already contain Expanded card lists and LongPressDraggable/DragTarget card drop zones; add-card currently uses a simple title/notes dialog only.
  • lib/features/revision/data/revision_repository.dart: moveCard persists columnId and position; addCard creates revision details with default yellow mastery.
  • lib/features/revision/presentation/widgets/revision_card_detail_sheet.dart: existing card sheet supports title, notes, mastery, revision stats, canvas attachments, mark revised, save, and delete.
  • test/kanban_board_view_test.dart and test/revision_card_detail_sheet_test.dart: existing widget coverage for add-card dialog, tap semantics, and revision detail behavior.

Assumptions

  • “Status” means the card’s current Kanban column/bucket, represented by BoardCards.columnId, not a separate status field.
  • “When adding a card it should also give me options that is also when I am clicking the card” means after creating a revision card, immediately open the full revision detail sheet for that new card, or replace the add flow with a creation sheet that includes those same controls.

Plan

  1. Make KanbanBoardView height-aware: remove the content-sizing IntrinsicHeight path and constrain the horizontal scroll content to constraints.maxHeight (or wrap the row in a full-height SizedBox) so each KanbanColumnView stretches to the bottom of the Scaffold body.
  2. Harden card drag/drop for repeat cross-column moves in KanbanColumnView: keep the existing fractional position logic, but add widget tests that drag a card from column A to B and then from B to A using an updated board snapshot. If touch long-press is the usability blocker, make the drag handle or whole card support immediate mouse/stylus drag while preserving tap-to-open.
  3. Expose a post-create hook from the generic Kanban layer: change KanbanController.addCard to return the new card id, and add an optional onCardAdded/onAddCardComplete callback to KanbanBoardView/KanbanColumnView. Update revision and goal controllers/repositories to match the new return type.
  4. For Schedule Revision, after add-card succeeds, locate the newly emitted card from revisionBoardProvider or construct a minimal KanbanCardData with default RevisionCardExtra, then open showRevisionCardDetailSheet. This gives the same options as tapping a card without duplicating the whole detail UI.
  5. If Karl wants true “options before save” instead, create a revision-specific add-card sheet using the existing detail-sheet fields for title, notes, mastery, and attachments after save; keep generic add-card behavior for Goal Cycle unchanged except for the return-type plumbing.
  6. Update tests for full-height layout, repeated cross-column move callbacks, new addCard return type, and revision add-card opening the detail/options flow.

Validation

  • Run targeted widget tests: flutter test test/kanban_board_view_test.dart test/revision_card_detail_sheet_test.dart.
  • Run flutter analyze for Dart API changes across shared Kanban, revision, goal cycle, and test fakes.
  • Manual Android tablet smoke test: open Schedule Revision, confirm columns fill the visible body height, drag the same card between multiple columns repeatedly, kill/reopen app and confirm it remains in the last column, add a card and confirm full card options are available.

Risks And Guardrails

  • Changing KanbanController.addCard affects both Schedule Revision and Goal Cycle plus test fakes; keep the API change small and mechanical.
  • Opening a detail sheet immediately after insert depends on the board stream timing; prefer using the returned id plus the next provider emission, or a minimal newly-created card object with known defaults.
  • No database migration should be needed if “status” remains columnId.
  • No Git writes, dependency changes, or destructive operations are required.

Open Questions

  • Should add-card open the full options sheet after creating with title/notes, or should the initial add-card UI itself include mastery/mark-revised/canvas options before saving?
