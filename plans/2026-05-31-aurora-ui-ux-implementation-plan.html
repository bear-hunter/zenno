Zenno Aurora UI/UX Implementation Plan

This plan translates UIUXdesign/01-aurora/index.html into Zenno's Flutter app. Aurora's goal is a premium dark tablet experience with a warm gold accent, frosted HUD surfaces, richer study cards, and an immersive canvas editor while preserving Zenno's core priority: staying out of Karl's thinking flow.

Product stance: implement the Aurora design language, not the static prototype literally. The Flutter app must remain data-safe, S Pen-first, and fast on the Samsung Galaxy Tab target. Decorative blur, shadows, and motion are allowed only where they do not slow handwriting, hide content, or make controls harder to hit.

Design Source Inventory

Shell

Full-window dark aurora background, persistent left rail, gold active destination, compact labels, avatar footer, and stage content that feels layered over the background.

Library

Folder sections with counts, responsive canvas cards, real thumbnails, relative timestamps, search, sort segments, new folder, and new canvas actions.

Focus

Large start-session panel, Pomodoro and Flowmodoro mode cards, monthly stats, recent sessions, and a separate immersive active timer with a glowing progress ring.

Boards

Revision and Goal Cycle use the same glass kanban language: column tags, compact counts, calm cards, due chips, mastery dots, and explicit add buttons.

Settings

Grouped preference panels for appearance, canvas input, pen tuning, focus defaults, library defaults, and about. Controls are swatches, segments, sliders, steppers, and toggles.

Canvas Editor

Full-bleed paper, floating top bars, left tool HUD, bottom pen dock, paper picker, title affordance, zoom controls, import/export, layers, and subtle branding.

Implementation Principles

  • Data first: no schema or persistence change is required for the Aurora visual migration. Avoid touching repositories unless a UI action is currently missing.
  • Canvas performance first: avoid expensive blur over the drawing surface while ink is moving. Use translucent surfaces and one or two bounded BackdropFilter areas only if profiling stays smooth.
  • Do not bury tools: the design looks rich, but the active pen, width, color, eraser mode, undo/redo, import/export, paper, layers, and back safety must remain one tap away.
  • Responsive tablet layout: target landscape tablet first, then gracefully collapse to one-column layouts for web/mobile previews.
  • Keep Material semantics: use Flutter buttons, tooltips, focus traversal, dialogs, snackbars, and semantic labels instead of building purely decorative gesture surfaces.

Phased Plan

Phase 0Baseline And Guardrails

  1. Run current checks before visual work: flutter analyze, targeted widget tests for touched screens, and a web/Android smoke run if available.
  2. Capture current screenshots for Library, Focus home, active Focus, Revision, Goals, Settings, and Canvas Editor.
  3. Add golden-free widget tests or smoke tests only where existing tests are already close, such as toolbar and board empty states. Avoid brittle pixel goldens until the design stabilizes.

Phase 1Aurora Theme Foundation

  1. Extend AppColors with Aurora palette tokens: base surfaces, ink colors, gold ramp, cool accents, status colors, glass fill, and hairline values.
  2. Update AppTheme to use a closer Aurora dark surface ramp while preserving light theme validity.
  3. Add shared Aurora widgets for background, glass panels, icon buttons, action buttons, topbars, chips, and segmented controls.
  4. Keep default border radii close to current app rules: 8 to 16 for cards and controls, 18 to 24 only for large rails/HUD panels.

Phase 2Application Shell

  1. Refactor AppScaffold into a custom shell that wraps the current StatefulNavigationShell.
  2. Replace the plain NavigationRail look with the Aurora rail: brand mark, destination icons, compact labels, gold selected state, and footer avatar.
  3. Keep branch switching behavior exactly as-is, including resetting a branch when the selected destination is tapped again.
  4. Verify that canvas routes remain full-bleed enough and do not inherit unwanted page padding from the shell.

Phase 3Library Screen

  1. Move Library title, folder creation, sort, search, and new canvas into an Aurora topbar area.
  2. Add local search filtering against canvas titles and folder names. This should be UI-only and should not alter repository APIs unless needed later.
  3. Restyle CanvasCard with thumbnail-first layout, subtle hover/focus elevation for desktop/web, timestamp row, and overflow action preservation.
  4. Restyle folder headers with icon, count, divider line, and existing rename/delete menu.
  5. Keep permanent canvas deletion behind the existing confirmation dialog. Do not add swipe-delete or accidental destructive gestures.

Phase 4Focus Home And Timer

  1. Recompose FocusHomePage into a responsive layout: start/resume panel and recent sessions on the left, stats card on the right for wide screens.
  2. Surface Pomodoro and Flowmodoro choice in the setup path only if it can write through the existing session config cleanly; otherwise keep the prototype's mode cards as navigation into setup defaults.
  3. Restyle recent sessions with status dots, cycle count, completion status, and existing history navigation.
  4. Update TimerDisplay to match Aurora's large ring, tabular time, phase label, and cycle summary while keeping the existing controller and snapshot logic.
  5. Make the active timer immersive, but keep End early, pause/resume, distraction logging, linked canvas, and finish controls visible and reachable.

Phase 5Kanban Boards

  1. Restyle KanbanBoardView and KanbanColumnView once so Revision and Goal Cycle both inherit the Aurora board treatment.
  2. Add column header count pills, status color tags, quiet add buttons, and stronger drop-zone feedback.
  3. Update revision and goal card tiles to use Aurora chips, mastery dots, and due/reflection metadata while preserving drag/drop and detail-sheet interactions.
  4. Verify board scrolling on tablet landscape and narrower web widths; columns should not become too narrow for readable card titles.

Phase 6Settings

  1. Replace the list-style Settings body with grouped Aurora panels. Keep the current repository calls and SettingsModel.
  2. Convert color pickers into visible swatch rows plus the existing dialog for custom values.
  3. Restyle pen profile sliders, focus steppers, switches, and library sort segmented control with shared Aurora primitives.
  4. Make the About section match the prototype's brand mark, version, and concise product description.

Phase 7Canvas Editor HUD

  1. Split CanvasToolbar into smaller internal widgets: top-left document/back/undo-redo cluster, top-right import/layers/export/zoom cluster, left tool HUD, bottom pen dock, and paper picker.
  2. Keep all existing controller commands wired: back, zoom, fit, reset, paper settings, snap, layers, rotation lock, import image/PDF, export, undo/redo, clear/delete, bookmarks, tools, pen kinds, width, palette, eraser modes, shape modes, selection transforms, arrow settings.
  3. Place HUDs outside the user's most likely handwriting zone where possible. The bottom pen dock should collapse or scroll horizontally on narrow widths.
  4. Preserve CanvasEditorPage save-error banner, thumbnail capture, editable title, keyboard shortcuts, route extra viewport handling, and guarded back behavior.
  5. After layout is done, test with actual S Pen input. This is the phase most likely to affect flow, even if no engine code changes.

Phase 8Motion, Polish, And Accessibility

  1. Add subtle page fade/slide transitions only after static layout is stable.
  2. Respect reduced motion and keep timer/countdown updates stable with no layout shift.
  3. Check contrast for muted text on glass surfaces and status chips.
  4. Add tooltips to icon-only controls and semantics labels where custom widgets replace stock Material controls.
  5. Audit focus order for keyboard users and web preview.

Acceptance Criteria

  • Library, Focus, Revision, Goals, Settings, and Canvas Editor all visibly match the Aurora direction: dark mesh, gold accent, frosted panels, compact high-end tablet feel.
  • Existing data flows still work: creating/opening/renaming/moving/deleting canvases, folder CRUD, focus session lifecycle, distraction capture, revision board edits, goal board edits, settings persistence, and canvas save/load.
  • Canvas drawing latency and pointer behavior feel unchanged or better on the Android tablet target.
  • No destructive action becomes easier to trigger accidentally.
  • All custom visual controls have tooltips or labels and maintain usable hit targets.
  • Relevant validation passes: flutter analyze, targeted widget/unit tests for touched areas, and a manual smoke test on web plus Android when available.

Known Risks

  • Over-styling the thinking surface: the canvas editor is where decoration can become friction. Keep HUDs quiet, movable/collapsible if needed, and never cover save warnings or active input feedback.
  • Blur cost: Flutter BackdropFilter can be expensive, especially over live canvas content. Start with alpha panels and only add blur to bounded static surfaces after profiling.
  • Prototype-only affordances: Aurora's demo includes live accent swapping and mock stats. In the real app, everything should read/write through existing settings and repositories, or remain visual only until product behavior is defined.
  • Tablet vs web mismatch: web preview is useful, but the real target is Android tablet with S Pen. Final approval should include device testing.

Not In Scope For This Visual Migration

  • New persistence schema for nested folders, favorites, tags, or brush libraries.
  • New drawing engine behavior beyond already-present pen kinds, layers, paper styles, shapes, and selection transforms.
  • Changing focus timer math, spaced-revision scheduling, or goal-cycle workflow semantics.
  • Adding network sync, accounts, or cloud assets.

Recommended First PR Scope

Start with Phase 1 and Phase 2 only: Aurora tokens, shared primitives, background, and shell rail. That gives every later screen a stable visual foundation and keeps the first implementation low-risk. The second PR should handle Library because it exercises the shared components without touching the handwriting engine. Canvas HUD should be last because it has the highest flow and performance risk.
